# 知识谱系 TABLE 整表抽取改造

本次改造聚焦 `/llm/weaponry` 知识谱系解析接口中 `TABLE` 类型字段的抽取方式：原实现把表格字段中的每个子字段当作普通 `INPUT` 字段逐个查询，无法稳定生成“每个对象一行、各项指标为列”的表格结果。改造后，`TABLE.tableFieldList` 在请求阶段作为列模板，后端按整表检索和结构化行抽取生成多行二维结果。

## 1. 背景与需求

项目以 AnythingLLM 为核心构建 RAG 后端。`/llm/weaponry` 接口根据 `architectureId` 定位目标 Workspace，并对 `weaponryTemplateFieldList` 中的字段执行信息抽取。

此前 `INPUT` 字段与 `TABLE` 字段的处理方式基本一致：

- `INPUT` 字段：针对单个字段独立检索、提问、回填 `analyseData` 和 `analyseDataSource`。
- `TABLE` 字段：遍历请求中的 `tableFieldList`，对每个单元格定义调用一次 `_query_input_field()`。

这种处理方式适合标量字段，但不适合前端希望展示的真实表格。例如“某艘航母装载了哪些种类的雷达，每种雷达各作为一行，展示各项数据指标”这一场景中，后端必须先识别“雷达型号”这些行实体，再为每一行填充频段、探测距离、用途等列。逐单元格查询只能得到多个互不对齐的字段值，无法保证同一行内的多个指标属于同一个雷达。

本次需求要求：

- 请求协议保持不变，仍使用 `fieldType="TABLE"` 和二维 `tableFieldList`。
- 请求中的 `tableFieldList` 作为列模板，而不是固定数据行。
- 后端对 `TABLE` 执行整表抽取，回调时扩展为多行二维 `tableFieldList`。
- 每个单元格仍独立包含 `analyseData` 和 `analyseDataSource`。
- 继续沿用目标证据过滤、术语规则辅助、来源文件原名映射和临时 Thread 隔离机制。

## 2. 目标数据流

改造后的 `TABLE` 字段处理流程如下：

```text
/llm/weaponry
  -> 遍历 weaponryTemplateFieldList
    -> INPUT:
       -> 继续走原有 _query_input_field()
    -> TABLE:
       -> 从 tableFieldList 提取列模板
       -> 使用表名、表说明、全部列定义构造表级检索 query
       -> AnythingLLM vector-search 召回目标证据 Chunk
       -> 过滤 term_rule_*.md 等非目标来源
       -> 可选检索术语规则 workspace，作为字段口径辅助
       -> 按来源文件聚合多个 Chunk
       -> 对每个来源文件发起整表 JSON 抽取 Prompt
       -> 解析 JSON 数组为多行结构
       -> 按 __rowKey / 名称 / 型号等行标识合并重复行
       -> 组装为协议要求的二维 tableFieldList
```

其中，模型输出不直接作为最终协议返回，而是先进入服务端解析和合并层。这样可以在保留现有接口结构的同时，把“列模板”转换成“数据行”。

## 3. 核心实现内容

### 3.1 新增 TABLE 整表抽取 Prompt

**代码位置**：`app/services/core/prompts.py`

新增 `build_table_extraction_prompt()`，用于构建整表抽取 Prompt。

Prompt 约束重点：

1. 只能基于提供的 Chunk 文本抽取，不得使用外部知识。
2. 每一行必须表示一个独立对象、部件、型号或记录。
3. 不得把多个行实体合并到同一个单元格。
4. 只填写列定义中要求的字段，缺少明确依据的列填空字符串。
5. 每行必须提供 `__rowKey`，用于服务端合并同一行实体。
6. 只输出合法 JSON 数组；没有结果时输出 `[]`。

示例语义：

```json
[
  {
    "__rowKey": "AN/SPY-1D",
    "雷达名称": "AN/SPY-1D",
    "频段": "S波段",
    "探测距离": "约320公里"
  }
]
```

### 3.2 TABLE 字段不再逐单元格查询

**代码位置**：`app/services/llm_service/weaponry_service.py`

重写 `_query_table_field()`：

- 不再遍历 `tableFieldList` 的每个 cell 调用 `_query_input_field()`。
- 先调用 `_extract_table_column_defs()` 从请求表格中提取列模板。
- 调用 `_build_table_retrieval_query()` 构造表级检索 query。
- 使用 `TABLE_EVIDENCE_TOP_N=16` 获取更宽的表格候选证据。
- 沿用 `_is_target_source()` 过滤术语文档和非目标来源。
- 按 `_extract_chunk_source_name()` 提取来源文件名，并按文件聚合 Chunk。

这使表格抽取从“列值独立查询”变成“基于同一上下文生成多行记录”。

### 3.3 术语规则仍作为辅助上下文

TABLE 也复用现有术语规则分池机制：

```text
目标 workspace:
  只检索目标装备资料 Chunk

术语规则 workspace:
  单独检索 term_rule_*.md
  只作为 Prompt 中的字段口径、别名、单位参考
```

新增 `_build_table_terms_rule_query()`，把表名、表说明和列定义组合成术语规则检索 query。术语规则仍不进入正式 `analyseData` / `analyseDataSource`。

### 3.4 JSON 响应解析与降级

**代码位置**：`_parse_table_json_rows()`

新增一组 TABLE JSON 解析辅助函数：

- `_clean_table_json_response()`：去除 `<think>`、Markdown code fence 等包裹。
- `_load_table_json_response()`：尝试解析完整文本、数组片段或对象片段。
- `_parse_table_json_rows()`：兼容 JSON 数组、带 `rows/data/items/result/tableRows/tableFieldList` 包裹的对象，以及数组行。
- `_normalize_table_cell_value()`：把 `null`、`None`、`未找到` 等归一为空字符串，同时保留可能有业务含义的 `"无"`。

当模型返回无法解析的内容时，表格不会让整个任务失败；该文件的表格响应会被跳过，并记录 warning。若所有来源都无法得到有效行，则返回空 `tableFieldList`。

### 3.5 行实体合并与单元格来源

**代码位置**：`_merge_table_rows()`、`_assemble_table_rows()`

模型可能从多个来源文件中抽取到同一行实体。本次新增行合并逻辑：

1. 优先使用 `__rowKey` 作为行标识。
2. 没有 `__rowKey` 时，优先使用字段名包含 `名称`、`型号`、`编号`、`代号`、`标识`、`类型` 的列。
3. 仍无法确定时，使用第一个非空列值。
4. 同一行实体重复出现时，优先保留已有非空值，后续来源补充来源链。

每个单元格最终包含：

```json
{
  "fieldName": "频段",
  "fieldType": "INPUT",
  "analyseData": "S波段",
  "analyseDataSource": [
    {
      "content": "S波段",
      "source": "航母雷达资料.pdf",
      "time": "2026-06-22 12:00:00",
      "translate": ""
    }
  ]
}
```

TABLE 模式下，`analyseDataSource.source` 使用来源文件名，并优先通过既有 `_resolve_original_source_name()` 映射为 `documents.original_name`。

### 3.6 进度统计调整

**代码位置**：`_count_query_fields()`

原逻辑把 `TABLE` 按单元格数量计入总进度。整表抽取后，数据行数量在查询前不可知，因此改为：

- `INPUT` 算 1 个查询任务。
- `TABLE` 算 1 个表级查询任务。

`_query_table_field()` 完成后只触发一次进度回调，避免进度统计继续绑定旧的逐单元格行为。

## 4. 协议兼容性

本次不改变 `/llm/weaponry` 的请求和回调协议。

### 4.1 请求侧

请求仍使用：

```json
{
  "fieldName": "雷达配置",
  "fieldType": "TABLE",
  "tableFieldList": [
    [
      { "fieldName": "雷达名称", "fieldType": "INPUT" },
      { "fieldName": "频段", "fieldType": "INPUT" },
      { "fieldName": "探测距离", "fieldType": "INPUT" }
    ]
  ]
}
```

但语义从“已有一行待填单元格”明确为“列模板定义”。

### 4.2 回调侧

回调仍返回二维 `tableFieldList`：

```json
{
  "fieldName": "雷达配置",
  "fieldType": "TABLE",
  "tableFieldList": [
    [
      { "fieldName": "雷达名称", "analyseData": "AN/SPY-1D", "analyseDataSource": [] },
      { "fieldName": "频段", "analyseData": "S波段", "analyseDataSource": [] }
    ],
    [
      { "fieldName": "雷达名称", "analyseData": "AN/SPS-49", "analyseDataSource": [] },
      { "fieldName": "频段", "analyseData": "L波段", "analyseDataSource": [] }
    ]
  ]
}
```

前端和本地调试页原本已经按二维数组渲染 `TABLE`，因此无需同步改造展示结构。

- `_parse_table_json_rows()` 可以解析 Markdown code fence 包裹的 JSON 数组。
- `_query_table_field()` 在 mock 场景下只执行一次表级向量检索，生成两行雷达数据。
- TABLE 单元格 `analyseDataSource.source` 可以映射为原始文件名。
- TABLE 进度回调只触发一次。

## 6. 文档更新

同步更新：

- `README.md`
- `docs/接口文档/知识谱系解析.md`

文档中明确：

- `TABLE` 字段不再按单元格逐个查询。
- 请求中的 `tableFieldList` 是列模板。
- 回调中的 `tableFieldList` 是服务端根据文档内容扩展出的数据行。
- 典型场景是“每种雷达一行、各项指标为列”。

## 7. 变更影响总结

1. `INPUT` 字段抽取流程保持不变。
2. `TABLE` 字段从逐单元格查询改为整表 JSON 行抽取。
3. `TABLE` 的向量召回默认 `topN` 从普通字段的 8 扩展为 16，以提高多行表格的召回覆盖。
4. 术语规则仍只作为字段口径辅助，不作为装备事实来源。
5. `TABLE` 返回结构仍是协议定义的二维 `tableFieldList`，前端无需调整结构解析。
6. 若模型无法输出可解析 JSON，当前表格会返回空行结果，不影响其他字段继续抽取。

## 8. 风险与控制

### 8.1 模型 JSON 稳定性

风险：模型可能输出说明文字、Markdown 包裹、单对象或其他非标准结构。

控制：

- Prompt 明确要求只输出 JSON 数组。
- 服务端解析支持 code fence、数组片段和常见对象包裹字段。
- 无法解析时只跳过该来源，不中断整个任务。

### 8.2 行实体合并误差

风险：不同来源对同一实体的命名不一致，例如缩写、大小写、连字符差异。

控制：

- Prompt 要求输出 `__rowKey`。
- 服务端在没有 `__rowKey` 时用名称、型号、编号等字段兜底。
- 后续如需要更强的同义归并，可以加入别名规则或术语规则驱动的 row key 归一化。

### 8.3 表格召回不足

风险：表格行分散在多个 Chunk 中，普通 topN 可能召回不全。

控制：

- TABLE 使用独立的 `TABLE_EVIDENCE_TOP_N=16`。
- 按来源文件聚合多个 Chunk 后再提问，减少单 Chunk 信息不完整的问题。
