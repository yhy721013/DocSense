## 6. 阶段 2～6 输入清单

### 6.1 阶段 2：统一任务语义与进程内隔离

1. 以现有 `TaskId`、`TaskBusinessRef`、不可变 input snapshot 和 expected TaskId 条件写为
   输入，冻结通用 Task/Attempt/Step/Event/Artifact/Callback Delivery 关系。
2. 把 `accepted/running/terminal/stale` 兼容事实映射为正式状态机；终态不可逆，重试必须
   创建新 attempt，不得原地重置。
3. 为 `running` 增加 attempt lease、心跳、checkpoint 和 reaper；在这些事实完成前继续
   只观测、不自动重跑可能已经产生外部副作用的任务。
4. 抽取统一的本地执行许可和可取消调度边界，保持重型 AnythingLLM/模型任务按资源限流
   排队，不能恢复“每请求一线程”或无界 Python Queue。
5. 保留同业务键 latest-wins、Callback Guard fencing 和按业务键 Progress 发布隔离，将
   进程内锁明确视为兼容实现，而不是多实例承诺。

### 6.2 阶段 3：MySQL、SQLAlchemy 与 MinIO

1. 盘点并重新设计 `llm_tasks`、`llm_task_executions`、`callback_delivery_guards`、
   `callback_guard_release_audits`、`report_resource_records` 及 interaction/attempt/lifecycle
   表；SQLite DDL 不是生产迁移脚本。
2. 使用同步 SQLAlchemy Repository、Unit of Work 和 Alembic 建立唯一 MySQL 写路径；历史
   SQLite 仅为测试数据，不迁移。
3. `dispatch_sequence` 改用 MySQL 原生且并发安全的顺序事实；索引必须覆盖 ready scan、
   active uniqueness、latest owner、lease 和恢复扫描。
4. 将本地 ArtifactRef 映射到 MinIO 对象引用，保留 TaskId 命名空间、长度/SHA-256 完整性、
   retention class 和幂等删除语义；具体自动保留天数仍未确定，不得擅自启用 TTL。

### 6.3 阶段 4～6：Outbox、RabbitMQ 与生产切换

1. Task/input/Outbox 必须在同一个 MySQL 事务提交；Relay 使用 publisher confirm，只有可靠
   发布后更新 Outbox 事实。
2. RabbitMQ/Celery Worker 使用 late ACK、幂等 attempt、有限重试、DLQ 和可审计人工恢复；
   normal backlog 不设业务数量上限，但必须以资源/磁盘/告警门禁保护基础设施。
3. Callback 独立为可靠投递 Worker，继续使用 latest/lease/fencing；unknown 不自动重发，
   必须由显式、审计化恢复命令重新授权。
4. 阶段 6 用可靠队列 Adapter 替换本地 Dispatcher，同时保留 Report Application/Ports。
   **2026-07-17 后续决策修订**：甲方规定 `check-task` 永久保留请求内同步恢复；可靠队列
   仅增加后台兜底，两种触发源共用同一 Callback Guard，不建设无 Guard 的同步并行链。
5. 切换前停止新受理、盘点 accepted/running/Guard/资源事实、确认旧进程和旧 Worker 已停止
   或隔离；禁止双写、双执行、双 callback。

## 8. 回滚说明

本轮没有生产发布，无需执行生产回滚。新增内容主要是静态门禁和文档状态；若门禁本身需要
调整，应先证明新的生产依赖方向仍满足 Report Application/Ports 边界，不能简单删除断言。

未来生产切换或回滚仍须先停止报告新受理，关闭当前唯一 Dispatcher，盘点 accepted/running、
Callback Guard、资源恢复和最终 Artifact 事实，确认不会重复执行或重复回调后再切换绑定。
增量 SQLite 现场不得破坏性删除；已批准的 202 空体和 409 契约不因内部实现回滚而恢复为
旧成功 JSON。
