# 知识谱系解析来源文件原名支持

本次改造聚焦 `/llm/weaponry` 回调结果中来源文件名的展示问题：在 `WEAPONRY_ANALYSE_MODE=2` 按文件聚合抽取时，`analyseDataSource.source` 此前返回哈希后的内部文件名，需要改为返回 `documents.original_name` 中记录的文件原名。

## 1. 背景与需求

项目以 AnythingLLM 为核心构建 RAG 后端。文件解析接口 `/llm/analysis` 使用调用方传入的 `fileName` 作为业务文件标识，该值通常是哈希后的文件名；同时会把用户可读的原始文件名写入本地知识库 `documents.original_name`。

`/llm/weaponry` 在字段抽取时会从目标 Workspace 召回相关文档片段，并在 `WEAPONRY_ANALYSE_MODE=2` 下按来源文件聚合多个 Chunk 后提问。该模式下回调中的 `analyseDataSource.source` 直接使用聚合时提取到的来源文件名，因此会暴露哈希文件名，不便于业务系统和用户核验来源。

本次需求要求：

- 仅改造 `WEAPONRY_ANALYSE_MODE=2` 的回调来源文件名。
- `analyseDataSource.source` 优先返回 `documents.original_name`。
- 无法映射原名时回退现有内部文件名，保证任务不中断。
- `WEAPONRY_ANALYSE_MODE=1` 暂不改动，继续保持 `source` 返回 Chunk 原文的既有语义。
- 不改变 `/llm/weaponry` 请求协议、任务状态协议和字段抽取主流程。

## 2. 核心实现内容

### 2.1 检索上下文增加来源原名映射

**代码位置**：`app/services/llm_service/weaponry_service.py`

在 `WeaponryRetrievalContext` 中新增：

```python
source_original_names: Optional[Dict[str, str]] = None
single_target_original_name: str = ""
```

其中：

- `source_original_names`：保存内部来源标识到文件原名的映射。
- `single_target_original_name`：当任务只关联一份目标文档且检索来源名缺失时，作为保守回退。

### 2.2 构建多形态来源名映射

**代码位置**：`_prepare_retrieval_context()`

在准备 weaponry 检索上下文时，从 `documents` 表筛选当前 `architecture_id` 下的文档记录，并为同一份文档登记多种可能的来源 key：

- `file_name`
- `original_name`
- `doc_path`
- `Path(doc_path).name`
- `anything_doc_id`
- `{anything_doc_id}.json`
- `custom-documents/{anything_doc_id}.json`

这些 key 最终都映射到同一个 `original_name`。如果历史数据中 `original_name` 为空，则回退使用 `file_name`。

该设计是为了兼容 AnythingLLM 在不同接口和版本中可能返回的不同来源标识，例如 `metadata.title`、`metadata.sourceDocument`、`metadata.file_name` 或 `sourceDocument:` 文本。

### 2.3 Mode 2 回调 source 改为文件原名

**代码位置**：`_query_input_field()`

`WEAPONRY_ANALYSE_MODE=2` 的内部流程仍然按文件聚合 Chunk：

```text
vector-search
  -> 提取内部来源文件名
  -> 按内部来源文件名聚合 Chunk
  -> 对同一文件的多个 Chunk 合并提问
  -> 组装 analyseDataSource
```

本次只在最后组装 `analyseDataSource` 时做来源名转换：

```python
original_source_name = _resolve_original_source_name(file_name, retrieval_context)
mapped_source = {
    "content": text_response,
    "source": original_source_name,
    "time": datetime.now().strftime("%Y-%m-%d %H:%M:%S"),
    "translate": _translate_if_needed(text_response),
}
```

这样可以保持内部聚合和排序逻辑继续使用稳定的内部文件标识，避免原始文件名重复或特殊字符影响 RAG 处理；同时对外回调返回用户可读的文件原名。

### 2.4 Mode 1 保持不变

`WEAPONRY_ANALYSE_MODE=1` 当前以 Chunk 为单位提问，`analyseDataSource.source` 返回的是 Chunk 原文，用于直接展示证据片段。

本次没有改动 `_map_source_to_analyse_data_source()` 的 Mode 1 映射逻辑，避免把“原文证据片段”语义改成“来源文件名”而影响已有核验流程。

## 3. 数据库兼容处理

**代码位置**：`app/services/core/database.py`

`documents` 表建表语句已经包含 `original_name`，但 SQLite 的 `CREATE TABLE IF NOT EXISTS` 不会为旧表自动补列。为了避免旧 `.runtime/knowledge_base.sqlite3` 在读取 `original_name` 时失败，本次新增 `_ensure_documents_schema()`：

```python
cursor = conn.execute("PRAGMA table_info(documents)")
columns = {row[1] for row in cursor.fetchall()}

if "original_name" not in columns:
    conn.execute("ALTER TABLE documents ADD COLUMN original_name TEXT NOT NULL DEFAULT ''")

if "doc_path" not in columns:
    conn.execute("ALTER TABLE documents ADD COLUMN doc_path TEXT")
```

同时补充回填：

```sql
UPDATE documents
SET original_name = file_name
WHERE original_name IS NULL OR original_name = ''
```

因此旧库可以继续运行；对于没有历史原名的数据，回调会自然回退为原有哈希文件名。

## 4. 数据流总览

```text
文件解析：
  POST /llm/analysis
    -> params: { fileName: "hash.pdf", originalFileName: "装备资料.pdf", ... }
    -> analysis_service 解析完成后
    -> kb_service.save_document_record(..., original_name="装备资料.pdf")
    -> documents 表: { file_name: "hash.pdf", original_name: "装备资料.pdf", doc_path: ... }

知识谱系解析：
  POST /llm/weaponry
    -> _prepare_retrieval_context()
    -> 从 documents 表构建:
       hash.pdf / doc_path / anything_doc_id -> 装备资料.pdf
    -> WEAPONRY_ANALYSE_MODE=2 按内部文件名聚合 Chunk
    -> 组装回调前解析原名
    -> analyseDataSource.source = "装备资料.pdf"
```

## 5. 相关测试更新

**测试文件**：`tests/test_weaponry_service.py`

补充和调整的测试覆盖：

- `_resolve_original_source_name()` 能把哈希文件名映射为 `original_name`。
- `_resolve_original_source_name()` 能把 `custom-documents/...` 形式的 `doc_path` 映射为 `original_name`。
- 单目标文档且来源名缺失时，可以回退到 `single_target_original_name`。
- `term_rule_*.md` 术语规则文件不会被映射成业务来源文件。
- `WEAPONRY_ANALYSE_MODE=2` 在启用或关闭术语规则辅助上下文时，回调 `analyseDataSource.source` 均返回文件原名。

## 6. 文档更新

同步更新：

文档中明确：

- `WEAPONRY_ANALYSE_MODE=2` 按文件聚合抽取时，`analyseDataSource.source` 优先返回 `documents.original_name`。

- 术语规则仍只作为字段口径、别名和单位参考，不进入正式 `analyseDataSource`。

## 7. 变更影响总结

1. `/llm/weaponry` 请求参数不变，调用方无需调整请求报文。
2. `WEAPONRY_ANALYSE_MODE=2` 回调中的 `analyseDataSource.source` 从哈希文件名切换为文件原名。
3. `WEAPONRY_ANALYSE_MODE=1` 暂不改动，仍返回 Chunk 原文。
4. 内部 RAG 检索、Chunk 聚合、术语规则分池和任务状态流转均保持原有逻辑。
5. 旧版 `knowledge_base.sqlite3` 会在启动初始化时自动补齐 `original_name` 和 `doc_path` 列。
6. 历史记录没有原名时只能回退 `file_name`，无法凭空恢复真实原始文件名。
