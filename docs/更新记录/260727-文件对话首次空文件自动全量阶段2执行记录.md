## 2. 内部候选 DTO

新增 `ChatDocumentSelectionCandidates`，分别冻结：

1. `explicit_documents`：调用方非空 `fileNames` 对应的显式增量文档；
2. `new_session_default_documents`：只允许未来阶段 3 在受理事务实际创建 session 时采用的
   默认全量文档。

两组非空候选互斥，防止显式文件和默认全量被意外合并。DTO 自身以及嵌套的文档引用均不可变，
构造时复制外部序列，避免调用方列表在受理前被其他线程改写。

DTO 提供严格内部 Schema v1：

- 只包含字符串、整数、列表和对象等 JSON 基础类型；
- 未知顶层字段、未知 Schema 版本、缺失文档字段、空文本、非规范文本和错误类型均失败关闭；
- `to_payload()` 与 `from_payload()` 可严格往返，为未来持久化命令或可靠队列提供稳定输入；
- Schema 不属于 HTTP、SSE、历史响应或 AnythingLLM Port 契约。

## 3. 候选解析路径

`SynchronousChatRunExecutor.resolve_document_candidates()` 提供三条内部路径：

| 输入状态 | 处理 |
| --- | --- |
| `fileNames` 非空 | 只调用 `resolve_many()`，只产生 explicit 候选，不读取全量目录 |
| `fileNames=[]` 且本地 session 已存在 | 返回两组空候选，不扫描知识库 |
| `fileNames=[]` 且事务外未读到 session | 调用一次 `resolve_all_available()`，冻结 default 候选 |

session 当前只做状态迁移，不物理删除，因此“读到 session 后跳过全量目录”的优化不会把既有
会话误判为新会话。反向情况仍可能发生：事务外未读到 session 后，另一个并发请求先创建它。
这只会多准备一份候选，阶段 3 必须根据事务内真实 `session_created` 决定不采用该候选。

日志只记录内部 selection mode 和候选数量，不输出消息正文或完整文件清单。

## 4. 阶段门禁

本阶段刻意没有让公开 `prepare_chat_run()` 消费默认全量候选，也没有修改
`ChatCommandService`、`ChatRunCoordinator` 或 SQLite Lock Service：

1. 若现在读取默认候选后仍按旧命令持久化空文件，会形成“目录已校验、候选被静默丢弃”的半实现；
2. 若在事务外直接采用默认候选，两个并发首次请求可能同时认为自己是新会话；
3. 候选采用、有效数量上限、session 首次插入和 run/input/message 持久化必须在阶段 3 的
   同一 SQLite 受理事务中完成。

对应测试明确证明：即使 Resolver 能返回默认全量文档，阶段 2 的公开运行输入仍为空，且不会
调用全量目录解析。该门禁防止内部准备能力被误写成已交付行为。
