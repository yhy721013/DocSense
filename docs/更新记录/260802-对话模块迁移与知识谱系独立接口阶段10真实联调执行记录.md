## 5. 联调发现与修正

第一轮删除后检查发现，虽然消息和 Chunk 已清除，旧实现仍保留 `conversations`、成功 Run、关闭
租约、清理任务以及完整 Workspace/Thread 引用。这违反已批准的“只保留不含正文的最小审计事实”。

修正内容：

1. Schema v9 将 `conversation_deletion_audits` 改为不依赖在线 Conversation 聚合的独立审计表；
2. Weaponry 删除终态事务先写五字段最小审计，再删除 Identity 和整个 Conversation 聚合；其余
   Run、Input、Event、Scope、Binding、Message、Chunk、Lease、Cleanup Job 由外键级联删除；
3. File 身份继续保留不可复用的全世代墓碑，行为不变；
4. 删除后同一 Weaponry `userId + architectureId` 可以创建新的随机 Conversation。

真实复验确认 Weaponry 删除后，除 schema 元数据和
`conversation_deletion_audits(conversation_id, identity_kind, deletion_status, cleanup_result,
deleted_at)` 外，所有在线业务表均为 0；审计中不存在用户 ID、文件名、Chunk、消息或供应商引用。

## 8. 阶段 10 后全面审查与修正

真实验收完成后又对供应商协议、删除状态机、Schema、组合根、公开路由和永久门禁进行了逐层
复核，并修正以下不会改变公开接口合同的问题：

1. `finalize_completed_delete()` 不再返回已经被物理删除的旧 Identity Binding，Port 和 SQLite
   Adapter 统一返回 `None`，避免调用方误用失效对象；
2. 删除终态事务不再只相信 Application 的调用顺序，而是在同一个 `BEGIN IMMEDIATE` 事务中
   重新验证 Conversation 必须处于 `deleting`、存在 `delete_chat + succeeded` 清理事实且所有
   Resource Lease 均为 `closed`，任一条件缺失都回滚并保留在线聚合；
3. AnythingLLM Stream Client 在 Finalization 或 QueryRejection 后若继续收到任何 JSON 事件会
   失败关闭，避免把上游的终态后文本静默重排到终态之前；空心跳和 `[DONE]` 仍由解码器过滤；
4. Schema v9 临时表所有权矩阵和结构测试同步到当前版本，避免资产门禁仍只认可 v1～v8。

## 9. 后续阶段必须处理的恢复边界

当前同步删除仍包含两个不能组成单一原子事务的步骤：先完成 AnythingLLM 远端资源清理，再提交
本地最小审计和在线聚合删除。正常路径及故障返回路径已经通过；但如果进程在“清理任务已成功、
租约已关闭”之后、`finalize_completed_delete()` 提交之前被终止，Conversation 会保留在
`deleting`。现有公开合同规定 `deleting` 下再次删除返回 HTTP 409，因此当前实现没有通过公开
重试自动跨过这个窗口。

这不影响本次阶段 10 已实际完成的正常路径验收，也不会丢失消息、Chunk 或远端资源引用；但它
意味着当前版本不能宣称删除具备进程崩溃后的自动收敛能力。后续可靠任务基础设施阶段应增加持久化
Reconciler/Finalizer：只认定“删除清理任务成功 + 全部租约关闭 + Conversation 仍为 deleting”
的严格事实，并幂等提交本地终态。若改为让公开 delete 请求直接恢复该状态，会改变当前冻结的
`deleting → HTTP 409` 语义，必须先单独确认并修改接口文档。
