## 1. 已确认并落实的公开契约

### 1.1 reportId

- 入站继续接受 JSON 整数或十进制整数字符串，输出继续保持既有 JSON number。
- 十进制数字部分最多为 128 位；可选正负号不计入、前导零计入该上限。
- 同整数值规范化为同一业务键，例如 `132`、`"+132"` 和 `"00132"` 均对应 `"132"`。
- 超过上限返回既有 HTTP 400 单字段结构，错误文本为
  `reportId不能超过128位十进制数字`；WebSocket 只拒绝当前消息并保持连接。
- Web Adapter 和 Report Domain 使用同一上限。领域工厂在调用 `str()` 前先比较数值，
  因此极端 Python 大整数也只会形成稳定领域错误，不会泄漏解释器转换异常。

### 1.2 可选文本兼容

- `templateDesc`、`requirement` 的参数名、位置、必填性和输出行为均未改变。
- 字段缺失时冻结为空字符串；历史请求传入数字、布尔值、对象、数组或 `null` 时，沿用
  旧 f-string 执行链语义转换为字符串，再进入不可变领域命令。
- 转换只发生在请求副本中，不修改 Flask 原始对象，不把完整业务文本写入日志。

契约权威说明已同步至 `docs/接口文档/README.md` 和
`docs/接口文档/文件处理和报告生成.md`。

## 2. 内部契约和数据边界修复

### 2.1 RAG trace 与审计门禁

原有 Report RAG DTO 只能表达摘要，无法证明任务 trace、每次模型调用、来源校验和模型
调用前失败现场。本次补充：

- `trace_id`、Context/Conversation 引用、最终 `call_id` 和清洗后的摘要；
- 每次 attempt 的全局序号、操作内重试序号、`call_id`、Prompt 类型/摘要、原始响应、来源
  证据、来源验证计数和失败阶段；
- 完整 lifecycle events；模型调用前失败允许 attempts 为空，但必须保留失败现场；
- Application 冻结一次完整 Prompt，并校验请求/响应/失败 trace 的 task trace ID、Context
  名称及最终响应对应关系；
- 审计命令携带业务引用和完整 Prompt。1C-4 的生产 Audit Adapter 必须无损保存 trace ID
  与 call ID，不能退回只保存最终响应的旧摘要。

成功 trace 仍必须至少包含一次明确模型调用；已确认的空 RAG 结果继续按成功处理，但不能
绕过完整审计门禁。

### 2.2 Artifact 与清理所有权

- 最终 `report_html` Artifact 必须携带字节大小和校验值，避免终态引用无法验证。
- cleanup 结果拒绝重复引用，也拒绝同一 Artifact 同时出现在 cleaned/pending。
- 旧 execution 在终态条件写失败后不再 retain 未提交的最终报告，防止形成无人拥有的
  孤儿 Artifact；其余 scratch/RAG 资源仍按清理端口结果进入 cleaned 或 pending。

### 2.3 内部 execution 与公开回调投影分离

此前一个 result wrapper 同时服务内部恢复和旧 `llm_tasks` 投影，check-task 重放时可能把
内部 Schema、Artifact 结构或大型重复内容发送给外部。本次把 Codec 结果拆分为：

- execution 结果：只保存 Schema、报告标识、状态、空结果标记和最终 Artifact 元数据；
- projection 结果：只保存与既有甲方 callback 完全一致的公开字典。

两份 JSON 在进入 SQLite 写事务前完成序列化，并在同一事务分别写入 execution 与最新
投影。回调恢复读取旧投影时不会接触内部 wrapper。

### 2.4 stale execution 收敛

进度或终态条件写发现 latest owner 已变化时，除返回 `False` 并停止副作用外，还会在同一
短事务把仍处于 accepted/running 的旧 execution 标记为 stale 并写完成时间。这样旧任务
不会永久污染 running 数量、恢复扫描和容量指标；已经终态或身份不匹配的行不会被覆盖。

## 3. Callback Guard 并发补强

### 3.1 权威获取与 fencing

SQLite Guard 增加随机 `lease_token`、单调 `lease_version` 和恢复扫描索引：

1. acquire 在 `BEGIN IMMEDIATE` 内重新读取 execution、latest 投影和 Guard，事务外
   `is_latest` 只作为优化，不能授予发送权；
2. 同一业务键同一时刻只允许一个发送者，50 个并发 acquire 的结果固定为
   1 acquired/49 busy；
3. complete 同时匹配 owner execution、lease token 和 fencing token，迟到 Worker 的旧
   token 只能 CAS 失败，不能覆盖新租约；
4. 发送租约到期或时间字段损坏时，系统无法证明 HTTP 是否到达接收方，因此直接冻结为
   `delivery_outcome_unknown`，不得自动重抢；
5. 常规等待只使用读连接，只有可能过期时才进入短写事务复核，避免等待请求无意义争抢
   SQLite 写锁。

### 3.2 HTTP 结果分类和重放策略

- 2xx → `success`；非 2xx → `rejected`；
- 连接建立前的 ConnectTimeout/无效 URL → `definitely_not_sent`；
- 读取超时、连接中断等无法证明是否送达的 RequestException →
  `delivery_outcome_unknown`；
- 未配置 callback URL → `skipped`；
- callback 历史调试副本保存失败只记录日志，不改变真实 HTTP outcome。

`success`、`skipped`、`rejected` 和 `definitely_not_sent` 一旦完成即形成本次明确终局；普通
Worker 重放返回 `already_completed`，不隐式自动重试。未来可靠恢复必须使用单独、可审计
的 recovery command 重新授权。

Application 现在要求 Guard `complete()` 明确返回布尔 CAS 结果；返回 `False` 会记录为可
观察的 callback 端口错误，不能误报成功。

## 4. SQLite 与计划顺序补强

- SQLite 连接启用外键、`busy_timeout`、`synchronous=NORMAL`；初始化启用 WAL，减少短写
  事务排队时对 Progress/查询读连接的阻塞。它仍不是最终 50 并发生产数据库。
- 原计划在 1C-5 切路由、1C-6 才完成 Callback Guard，存在旧回调穿越切换窗口的风险。
  现调整为：1C-4 生产 I/O/Audit Adapter → 1C-5 Guard/Artifact/cleanup 闭环 → 1C-6
  Dispatcher/Container/旧在途排空/路由切换 → 1C-7 全量验收。
- 路由切换前必须停止新受理，盘点并排空或隔离旧 daemon 线程与新 execution；新旧路径
  不允许双写、双执行或双 callback。
