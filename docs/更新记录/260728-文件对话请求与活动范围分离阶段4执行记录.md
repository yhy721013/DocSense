# 文件对话请求与活动范围分离阶段 4 执行记录

## 1. 执行输入与恢复

`SynchronousChatRunExecutor` 现在只根据 `run_id` 从 SQLite 重建执行输入：

- `requested_files` 只用于待处理用户消息的附件身份和后续历史投影；
- `effective_scope_revision_id` 解析出的有序成员用于文档绑定和模型查询；
- 执行期不重新读取知识库目录；
- 执行期不使用 Workspace current bindings 推断模型范围。

离线重建测试在受理后重新装配 `ChatStore`、Coordinator 和 Executor，并故意提供内容不同的
新目录 Resolver。恢复执行未调用 Resolver，模型仍只收到受理时冻结的文档引用，空请求的用户
历史附件仍为空。

## 2. Workspace 累计绑定与活动范围

既有 resource lease、`attach_documents()`、binding revision 和
`stream_message(document_refs=...)` 链保持不变，但输入统一来自 Effective Scope。

专项测试验证：

- 首轮显式选择 A/B 后，Workspace 和本地 current bindings 累计包含 A/B；
- 后续显式选择 B 会整体替换 Active Scope，但不解绑 A；
- 本轮模型只查询 B；
- 再次空请求继续只查询 B；
- 已绑定的 B 不会重复 attach；
- 三轮历史分别只记录 `[A,B]`、`[B]`、`[]`。

因此 Workspace bindings 只是累计资源事实，不再兼任当前模型范围。

## 3. 失败与幂等边界

- 显式非空范围在受理事务提交时即成为新 Head；
- 即使该 run 随后执行失败，下一轮空请求仍复用这份最后 accepted 的显式范围；
- 受理后知识库目录变化不会改写运行快照；
- 断连、abort、错误、执行权重复领取和资源补偿继续沿用既有收敛路径；
- Scope 中的顺序原样传递给 `stream_message(document_refs=...)`。
