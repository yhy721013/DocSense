# 知识谱系本地来源规则重排序改造计划

> **状态：已于 2026-07-18 被阶段 1D-0R 取代，禁止按本文直接实施。** 本文允许来源权威度
> 压过字段相关性、缺失配置时退回原始向量分数，以及不设置独立最低相关门禁，这些口径不再
> 满足当前高精度 Evidence Selection 要求。现行依据为
> `260720-阶段1D武器谱整合执行记录.md` 和
> `../重构记录/260717-阶段1D武器谱文件级实施设计.md`。来源权威度未来只能在候选已经通过
> 字段相关性与 execution 来源身份门禁后参与排序，不能把无关 Chunk 提升为 Selected Evidence。

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 为 `/llm/weaponry` 的多个召回来源增加本地固定配置文件驱动的来源权威度重排序能力，使 `analyseDataSource` 按“专业规则集权重 + 检索相关性”从高到低展示。

**Architecture:** 保留 AnythingLLM 的 `vector-search` 作为召回入口，在 DocSense 后端增加一个纯本地、无云端依赖的 source reranker。reranker 从 chunk 的 `metadata` 和 `<document_metadata>` 中提取来源元数据，匹配本地组合规则集，计算最终排序分数，再把排序后的候选交给现有字段提取流程。

**Tech Stack:** Python 3.12、Flask、AnythingLLM vector-search、JSON 配置文件、unittest。第一版不引入 BGE、Cohere、Voyage 等语义 rerank 模型或外部 API。

---

## 1. 背景与当前状态

当前 `app/services/llm_service/weaponry_service.py` 中，`_query_input_field()` 已经通过 `AnythingLLMClient.vector_search()` 拿到多个候选 chunk。`vector_search()` 返回结构包含 `text`、`metadata`、`distance`、`score` 等字段。

现有排序逻辑：

- mode 1：按 chunk 的 `score` 降序处理。
- mode 2：先按文件聚合，再按该文件内最高 `score` 降序处理。
- `analyseDataSource` 最终按代码生成顺序返回，本地调试页按该数组顺序展示。

现有问题：

- `score` 只表达向量召回相关性，不表达来源权威度。
- 专业领域里，来源来自 Jane's、官方手册、舰艇年鉴、新闻稿、百科等时，可信度不应相同。
- 用户需要按本地固定规则集进行组合规则排序，例如“来源名包含 Jane's + 类型为 report/book + 出版方匹配 + 年份较新”时给予更高权重。

## 2. 目标与非目标

### 2.1 目标

1. 支持本地固定 JSON 规则文件维护来源权威度规则。
2. 支持组合规则条件，不只按单一书名匹配。
3. 对 mode 1 的 chunk 级候选和 mode 2 的文件聚合候选都生效。
4. 默认保持正式回调协议字段不变，只改变 `analyseDataSource` 的顺序。
5. 配置缺失或规则不匹配时可安全降级为现有向量分数排序。
6. 为规则解析、匹配、计分、排序和 weaponry 集成补充单元测试。

### 2.2 非目标

1. 第一版不引入本地语义 rerank 模型。
2. 第一版不改 AnythingLLM 服务端、向量库或文档入库流程。
3. 第一版不允许每次 `/llm/weaponry` 请求动态传入规则集。
4. 第一版不强制向正式 `analyseDataSource` 增加 `rankScore`、`rankReason` 等新字段，避免破坏甲方协议兼容性。
5. 第一版不做前端复杂排序交互；本地调试页继续按后端返回顺序展示。

## 3. 目标数据流

```text
/llm/weaponry
  -> _query_input_field()
    -> build_input_field_prompt()
    -> AnythingLLMClient.vector_search()
    -> weaponry_source_reranker.rerank_chunks()
      -> 提取 chunk 元数据
      -> 读取本地规则集
      -> 匹配组合条件
      -> 计算 authority_score
      -> 融合 vector_score 得到 final_score
      -> 降序返回候选
    -> mode 1: 按排序后 chunk 逐条提问
    -> mode 2: 按排序后 chunk 聚合到文件，再按文件级分数排序
    -> analyseDataSource 按最终排序顺序返回
```

## 5. 规则文件设计

### 5.1 推荐配置结构

```json
{
  "version": 1,
  "enabled": true,
  "defaultAuthorityWeight": 0.3,
  "vectorWeight": 0.3,
  "authorityWeight": 0.7,
  "rules": [
    {
      "id": "janes_recent_report",
      "enabled": true,
      "priority": 100,
      "conditions": {
        "sourceNameContains": ["Jane's", "Janes"],
        "sourceTypeIn": ["book", "report"],
        "publisherContains": ["Jane", "IHS Markit"],
        "yearGte": 2020
      },
      "weight": 0.98,
      "reason": "Jane's 近年装备资料，来源权威度最高"
    },
    {
      "id": "official_navy_source",
      "enabled": true,
      "priority": 90,
      "conditions": {
        "publisherContains": ["U.S. Navy", "Naval Sea Systems Command"],
        "sourceTypeIn": ["official", "manual", "report"]
      },
      "weight": 0.92,
      "reason": "官方海军来源"
    },
    {
      "id": "low_authority_wiki",
      "enabled": true,
      "priority": 10,
      "conditions": {
        "sourceNameContains": ["Wikipedia", "wiki"]
      },
      "weight": 0.25,
      "reason": "百科类来源仅作为低权重参考"
    }
  ]
}
```

### 5.2 支持的候选元数据字段

reranker 统一生成以下归一化字段：

- `source_name`：来源名称，优先取 `metadata.title`、`metadata.sourceName`、`sourceDocument`、文件名。
- `file_name`：文件名，优先取 `metadata.file_name`、`metadata.title`、`metadata.sourceDocument`。
- `source_document`：AnythingLLM 或 document metadata 中的 sourceDocument。
- `source_type`：来源类型，例如 `book`、`report`、`manual`、`official`、`news`、`wiki`。
- `publisher`：出版方或机构。
- `author`：作者或机构作者。
- `year`：年份，优先从 metadata 显式字段取；没有时从文件名或 metadata 文本中提取四位年份。
- `language`：语种。
- `raw_metadata`：原始 metadata 字典，仅内部调试使用。

### 5.3 支持的组合条件

每条 rule 的 `conditions` 内部是 AND 关系；同一个条件值数组内部是 OR 关系。

支持条件：

- `sourceNameContains`
- `sourceNameEquals`
- `fileNameContains`
- `sourceDocumentContains`
- `sourceTypeIn`
- `publisherContains`
- `authorContains`
- `languageIn`
- `yearGte`
- `yearLte`
- `yearBetween`

匹配示例：

```json
{
  "conditions": {
    "sourceNameContains": ["Jane's", "Janes"],
    "sourceTypeIn": ["book", "report"],
    "yearGte": 2020
  }
}
```

含义：

```text
(source_name 包含 Jane's 或 Janes)
AND (source_type 是 book 或 report)
AND (year >= 2020)
```

### 5.4 多规则命中策略

一个候选来源可能命中多条规则。第一版采用确定性策略：

1. 过滤 `enabled=false` 的规则。
2. 找出所有命中的规则。
3. 选 `weight` 最大的规则作为主规则。
4. 若 `weight` 相同，选 `priority` 最大的规则。
5. 若仍相同，按规则在文件中的顺序选择靠前者。
6. 无规则命中时使用 `defaultAuthorityWeight`。

## 6. 排序公式

### 6.1 chunk 级排序

第一版固定使用：

```text
final_score = normalized_vector_score * vectorWeight + authority_score * authorityWeight
```

默认：

```text
final_score = normalized_vector_score * 0.3 + authority_score * 0.7
```

说明：

- `normalized_vector_score` 来自 AnythingLLM 的 `score`，转换到 `0.0 ~ 1.0`。
- 若 `score` 缺失或无法解析，按 `0.0` 处理。
- `authority_score` 来自本地规则集，范围 `0.0 ~ 1.0`。
- 如果配置中 `vectorWeight + authorityWeight <= 0`，降级为 `0.3/0.7`。
- 如果权重和不等于 1，可以在加载时归一化。

### 6.2 文件聚合 mode 2 排序

mode 2 会把多个 chunk 聚合到同一文件后再提问。文件级排序分数建议为：

```text
file_final_score =
  max(chunk.final_score for chunk in file_chunks)
```

同时保存：

```text
file_authority_score = max(chunk.authority_score for chunk in file_chunks)
file_vector_score = max(chunk.vector_score for chunk in file_chunks)
```

选择 `max` 而不是平均值的原因：

- 一个文件中只要存在高度相关且高权威 chunk，就应优先进入该文件的综合提取。
- 平均值会被同文件内弱相关 chunk 拉低，和当前“按文件最高置信度”逻辑不一致。

### 6.3 稳定排序

排序键：

```text
(-final_score, -authority_score, -vector_score, original_index)
```

这样同分时保持可预测顺序，避免同一请求多次返回顺序漂移。

## 7. 错误处理与降级策略

### 7.1 配置文件缺失

行为：

- 记录 warning。
- 使用内置默认配置：`enabled=false` 或 `defaultAuthorityWeight=0.3`。
- 不让 weaponry 任务失败。

### 7.2 配置 JSON 非法

行为：

- 记录 warning，包含配置路径和解析错误。
- 降级为现有向量 `score` 排序。
- 不让 weaponry 任务失败。

### 7.3 规则字段非法

行为：

- 单条非法规则跳过。
- 其他规则继续生效。
- 若所有规则非法，使用默认权重。

### 7.4 来源元数据缺失

行为：

- 从 `<document_metadata>...</document_metadata>` 文本块中兜底解析。
- 再从文件名中尝试解析年份。
- 仍无法提取时使用空字段和默认权重。

### 7.5 严格模式

第一版不启用严格模式，避免因规则文件问题中断业务任务。后续如生产需要，可追加：

```text
WEAPONRY_RERANK_STRICT_CONFIG=true
```

严格模式下配置错误可让任务失败，但这不纳入第一版。

## 8. 环境变量设计

`.env.example` 增加：

```dotenv
# ============================================
# LLM 知识抽取来源重排序配置
# ============================================
# 是否启用本地来源规则重排序。启用后，/llm/weaponry 的多个召回来源会按规则权威度和向量相关性融合排序。
WEAPONRY_RERANK_ENABLED=true
# 本地固定规则文件路径。相对路径按仓库根目录解析。
WEAPONRY_SOURCE_RANK_RULES_PATH=config/weaponry_source_rank_rules.json
# 向量召回相关性权重。
WEAPONRY_RERANK_VECTOR_WEIGHT=0.3
# 来源权威度权重。
WEAPONRY_RERANK_AUTHORITY_WEIGHT=0.7
```

环境变量优先级：

1. `WEAPONRY_RERANK_ENABLED` 可总开关。
2. `WEAPONRY_SOURCE_RANK_RULES_PATH` 可覆盖默认规则文件位置。
3. `WEAPONRY_RERANK_VECTOR_WEIGHT` 和 `WEAPONRY_RERANK_AUTHORITY_WEIGHT` 覆盖规则文件中的默认融合权重。
4. 规则文件中的 `enabled` 可作为文件级开关。

| 条件匹配 | 多条件全部满足 | 命中规则 |
| 条件匹配 | 任一 AND 条件不满足 | 不命中规则 |
| 多规则命中 | 权重不同 | 选择权重最高 |
| 多规则命中 | 权重相同 priority 不同 | 选择 priority 最高 |
| 排序 | 低向量分 + 高权威来源 | 可排到高向量分 + 低权威来源之前 |
| mode 1 | chunk 重排序 | 第一个有效结果来自 final_score 最高 chunk |
| mode 2 | 文件聚合重排序 | 第一个有效结果来自 final_score 最高文件 |
| 关闭开关 | `WEAPONRY_RERANK_ENABLED=false` | 退回原向量 score 排序 |

## 11. 风险与控制

### 11.1 元数据质量风险

如果 AnythingLLM 返回的 `metadata` 不包含来源类型、出版方、年份等字段，组合规则只能基于文件名或 `sourceDocument` 匹配。

控制：

- 规则第一版应允许 `sourceNameContains`、`fileNameContains` 这类弱结构条件。
- 后续如需要强结构匹配，再改进文档入库 metadata。

### 11.2 权重压过相关性风险

高权威来源但不相关的 chunk 可能被推到前面。

控制：

- 保留 `vectorWeight=0.3`。
- 低相关 chunk 如果 vector score 接近 0，不应仅靠权威来源排到最前。
- 后续可增加最低向量分阈值，例如 `WEAPONRY_RERANK_MIN_VECTOR_SCORE=0.15`，但第一版不启用，避免召回为空。

### 11.3 正式协议兼容风险

新增 `rankScore` 字段可能影响甲方解析。

控制：

- 第一版只调整数组顺序，不新增正式回调字段。
- 若要展示排序原因，后续用 debug-only 或可配置字段扩展。

### 11.4 规则维护风险

规则文件会随专业判断变化而变化。

控制：

- 规则文件必须进 Git，变更可审查。
- 每条规则必须有 `id` 和 `reason`。
- 规则文件不放密钥、不放敏感原始资料。

## 12. 后续可选增强

1. 增加 `rankScore`、`rankReason`、`matchedRuleId` 到 debug 页展示，但不进入正式回调。
2. 增加 `WEAPONRY_RERANK_MIN_VECTOR_SCORE`，过滤明显不相关候选。
3. 引入本地 BGE reranker 作为第三个分数：`model_rerank_score`。
4. 在文档入库阶段补充结构化 metadata，使 `publisher`、`sourceType`、`year` 不依赖文件名解析。
5. 为不同 `architectureId` 支持不同规则集，但仍保持本地固定配置文件维护。

## 14. 完成标准

满足以下条件才算改造完成：

- 本地规则文件存在且可解析。
- `/llm/weaponry` mode 1 和 mode 2 都使用本地规则重排序。
- `analyseDataSource` 按最终分数降序返回。
- 未配置规则或关闭开关时，行为可降级到现有向量分排序。
- 不改变正式回调字段结构。
- 新增和既有单元测试通过。
- README 与接口文档说明同步更新。
