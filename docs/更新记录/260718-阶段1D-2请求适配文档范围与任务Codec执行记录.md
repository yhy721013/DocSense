## 2. 请求 Parser 与响应 Presenter

### 2.1 框架无关请求解析

新增 `app/adapters/web/flask/weaponry_requests.py`，但核心解析函数不依赖 Flask Request。它在
进入数据库、文件或网络副作用之前完成：

1. 根对象、`businessParams`、`architectureId`、`fieldList`、INPUT/TABLE 字段和列结构校验；
2. D01～D03 已批准错误文本与校验顺序冻结；
3. `architectureId` 接受正整数或只含 ASCII 十进制数字的字符串，兼容前导零，规范为 64 位
   正整数；拒绝布尔、浮点、符号、空白、Unicode 数字、越界值和超长恶意数字串；
4. `filePathList` 缺失、`null` 或空列表统一表达 category scope；非空列表从 URL path 提取并
   URL decode 文件名，忽略 query/fragment，按大小写不敏感规则拒绝重复；
5. 保留请求中 `status` 和未知扩展键的公开投影，同时递归深冻结，避免请求对象、execution
   快照和并发任务共享可变字典或列表；
6. 在持久化前拒绝 `NaN`、`Infinity`、非字符串对象键和其他非标准 JSON 值。

Parser 只输出 `ParsedWeaponryRequest`。只有调用方显式提供已解析文档范围和 Evidence Selection
profile 后，才能构造领域 `WeaponrySubmission`，防止“先入队、Worker 再猜文档或策略”。

### 2.2 零字节 Presenter

新增 `app/presenters/weaponry_submission.py`：

- 成功受理固定为 HTTP 202、`body=b""`，不返回 TaskId 或内部 execution 标识；
- 参数错误、文档未找到和活动任务冲突分别映射既有 400、404、409；
- 错误体只允许 `{"error": "..."}`，拒绝空消息和非文本消息；
- JSON 编码稳定且不附加内部状态、队列位置、恢复 ID 或调试字段。

上述组件尚未绑定 `app/blueprints/llm.py`，所以当前运行行为未改变。

## 3. Document Scope 冻结

### 3.1 领域与 Port

新增不可变 `WeaponryDocumentScope`，区分：

- `explicit`：严格保留甲方 `filePathList` 顺序，允许跨分类选择；
- `category`：按 `architectureId` 选择当前分类文档，空分类是合法空范围。

每个文档快照冻结连续 `sequence_no`、execution 内唯一 `document_key`、外部文档引用、甲方原名、
实际入库名和来源分类。Scope 构造时拒绝重复文档键、重复外部引用、大小写不敏感重名，以及
explicit 请求顺序与解析结果不一致。

`WeaponryDocumentScopePort` 只使用领域 DTO，并显式区分：

- not found：显式请求文件不存在；
- ambiguity：同名文件或外部引用无法唯一解析；
- integrity：数据库记录缺少实际入库名、外部引用等内部完整性事实。

### 3.2 DatabaseService/SQLite 兼容 Adapter

新增 `DatabaseServiceWeaponryDocumentScopeAdapter`，并提供语义明确的
`SQLiteWeaponryDocumentScopeAdapter` 别名。Adapter 只进行一次只读快照
`DatabaseService.list_document_records(...)` 读取：

- explicit scope 按请求顺序解析，不依赖 Repository 返回顺序；
- category scope 采用显式稳定排序，不依赖 SQLite 默认行顺序；
- 只从权威记录读取实际入库名和外部引用，不从路径或原名猜测缺失事实；
- 不连接 AnythingLLM，不读文件，不写数据库，不访问旧选文快照表；
- 日志只输出 architectureId、模式和数量，不输出文档正文或请求模板。

测试侧新增严格 `FakeWeaponryDocumentScopePort`。任何未配置调用都会失败，不会自动返回空范围
或猜测文档；所有调用参数均可精确断言。

## 4. execution 输入 DTO 与严格 Codec

### 4.1 不可变任务事实

新增：

- `WeaponrySubmission`：受理前冻结原始公开请求投影、规范 architectureId、字段模板、文档范围、
  Evidence Selection profile、固定执行策略、可选辅助策略和 trace；
- `WeaponryInputSnapshot`：在上述事实之外冻结内部 TaskId、Schema 版本和 `accepted_at`；
- 明确的 scope/auxiliary policy/schema 常量，避免字符串在业务层散落。

Submission 会交叉校验公开投影和内部快照：architectureId、业务键、字段模板和 explicit 文件
顺序不一致时不能进入任务表。

### 4.2 Schema v1

`WeaponryTaskCommandCodec` 严格冻结并恢复：

- TaskId、architectureId 和规范业务键；
- 字段及 TABLE 列模板、未知扩展键和原始顺序；
- 精确文档范围、sequence 和 execution 内文档键；
- provider、embedding、reranker、query、score semantics、额外相关性信号、阈值、候选批次和
  同文档精确去重组成的完整 Evidence Selection profile；不包含 Selected Evidence 数量/字符配额；
- Extraction Prompt/模型/上下文、TABLE 合并/答案行数、辅助策略目录指纹/Top-N/语境字符数、
  受理时间和 trace。

Decoder 使用精确键集合，不为旧任务或重试补当前默认值。缺失键、未知键、Schema 行版本不一致、
身份不一致、非有限数字和不合法嵌套值全部失败。原始公开请求只写任务投影所需的
`projection_request_payload`；Worker 的 `input_payload` 不含该原始投影，避免把对外兼容字段当作
执行指令。

结果 Codec 同样只持久化内部 `WeaponryResult` 事实，Callback 由领域 Presenter 另行投影，避免
公开回调结构反向污染任务状态。成功终态在 CAS 前必须证明字段数量、顺序、定义和 TABLE 列均
与输入快照完整一致，且结果 status 与 execution/public terminal 状态一致。

## 5. 原子受理与并发隔离

本波次没有新增武器谱专属 Repository，而是复用阶段 1C 已验证的通用
`LegacyTaskCommandAdapter`：

1. 文档范围、字段和 profile 在进入受理事务前已经冻结；
2. 事务内只做严格 Codec 和本地任务事实写入，不访问 Document Scope、环境变量或外部服务；
3. `llm_tasks` 最新投影与追加式 `llm_task_executions` 同事务提交；
4. Codec/投影任一步失败时整笔回滚，不留下 orphan execution 或旧选文快照；
5. 同一业务键存在活动 execution 时返回 active conflict；旧终态之后的新 execution 只新增事实，
   不能改变旧 execution 的字段、文档或 profile。

并发测试使用 Barrier 同时起跑：

- 50 个相同业务键严格得到 1 accepted、49 active conflict；连接均可在测试后重新获取锁，未
  发现 SQLite lock 泄漏、半提交或孤儿记录；
- 50 个不同业务键全部 accepted，逐项解码后字段 marker、文档引用、document_key 和 profile
  指纹均与各自请求一致，没有共享可变对象或串任务；
- 受理事务测试会让 Document Scope/环境读取函数在被调用时直接失败，以证明事务内零重读。

这些测试验证的是单进程临时 SQLite 的原子语义，不代表 RabbitMQ 可靠投递、多实例数据库锁
或 50 个重型模型任务并行已经完成。

## 6. 审查中补强的问题

实现后的全面检查额外修复了以下边界：

1. 超长十进制 architectureId 可能触发 Python 整数转换位数保护而泄漏非契约异常：现先做长度/
   上界判定并返回批准的参数错误；
2. URL 以 `/` 结尾、percent escape 非法、解码结果不是合法 UTF-8，或解码后没有文件名时
   可能被错误受理：现统一映射既有“无法提取文件名”错误；
3. 文档分类值为 `float`、`str` 或 `bool` 时可能被宽松转换：现只接受真实整数；
4. 实际入库名缺失时可能从路径猜测：现作为基础设施完整性错误失败；
5. 50 同键并发只检查结果数量而未验证锁释放：现增加后续事务探测，防止“结果正确但连接仍
   被占用”的假阳性；
6. Codec 原始公开投影与 Worker 输入可能重复并发生漂移：现物理分离并分别做严格断言；
7. JSON `true` 在 Python 中可能因 `bool` 是 `int` 子类而被当作 Schema v1：现对命令、execution
   行和 payload 三层都要求真实整数 `1`。
8. 初版 Schema 只保存宽泛策略 ID，重试仍可能读取新模型/Prompt/reranker/辅助目录默认值：现
   冻结上述完整策略事实并用精确键集合解码，不为历史 execution 补当前默认值；
9. 主提交、check-task、Progress、快照和遗留 Worker 可能分别规范 ArchitectureId：现复用同一
   领域纯规则，`1`、`"1"` 和 `"0001"` 只形成业务键 `1`，对外身份统一为数值；
10. 成功结果可能漏字段/列或与终态状态矛盾：现于 Repository CAS 前拒绝，execution 保持
    `running`，便于修复后安全重试。

上述补强均是内部实现，没有改变公开参数或错误体结构。
