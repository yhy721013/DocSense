## 2. 已修复问题

### 2.1 多候选审计载荷

- `ArchitectureRecallDecision.rrf_scores` 和 `protected_reasons` 是不可变二元组序列。
- Application 改为直接遍历二元组，不再错误调用 `.items()`。
- 新增真实不可变 DTO 投影测试，锁定 JSON 审计结果。

### 2.2 冻结分类策略

- Worker 现在执行 `classification_prompt_char_limit` 的最终 Prompt 精确门禁。
- `base_leaf_limit`、`parent_candidate_limit` 和 `model_candidate_limit` 直接参与领域召回裁剪，
  不再只在召回结束后拒绝结果。
- 默认 64/16/128 保持拆分前算法上限；小阈值通过任务快照独立生效，不重读环境变量。
- direct/legacy 的 `recall_elapsed_ms` 从 `build_plan` 内部开始计时，继续排除此前已经完成的文件
  下载与正文读取。

### 2.3 外部副作用 fail-closed

- 永久知识库外部调用返回后，`external_location` 缺失被分类为 `OUTCOME_UNKNOWN`，并触发
  Application 保留文档和现场，不再抛普通异常后按“未接管”清理。
- RAG 打开调用返回但缺少 Context/Conversation 引用时，生命周期结果改为 unknown。
- RAG 查询、上传或绑定返回后若成功响应映射失败，统一抛出携带 unknown 生命周期和当前已绑定
  Session 的 `AnalysisRagExecutionError`。
- 新增知识库不完整成功、RAG 不完整成功和打开身份缺失故障注入。

### 2.4 毒快照控制面

- 新增 `AnalysisTaskSnapshotCorruptedError`，稳定区分不可通过普通重试恢复的持久快照损坏。
- 新增 `AnalysisPoisonTaskCommandPort.fail_poisoned_accepted`。
- `LLMTaskService` 新增不读取 `input_payload` 的 Analysis 专用条件终态：同一事务内验证新 file
  批次身份、accepted 状态和 latest owner，原子更新 execution 与公开投影为既有失败状态 `3`。
- 内部 reason 只写诊断列；公开消息和失败 Callback 继续使用既有固定合同，不泄漏 TaskId、异常栈或
  SQLite 细节。
- 1F-5A 必须把 Dispatcher 捕获到的 `AnalysisTaskSnapshotCorruptedError` 接到该 Port；本轮没有
  提前创建 Worker 或改变尚未实施的组合根。

### 2.5 大快照开销

- expected Progress、终态、latest、领取前冷却和毒任务终结改用不包含 `input_payload` 的窄控制面
  查询，避免每次写操作重复重建最多 10,000 节点的领域树。
- Codec 对与冻结 `effective_ranges` 完全相同的显式范围使用内部无损引用；缺失、显式空值或规范化
  前后不一致时仍保留原始值。解码后 `raw_params` 与受理快照完全相等。
- 公开 `llm_tasks.request_payload` 副本继续保留，因为它属于现有 check-task 投影合同。100 节点离线
  样本的 execution 输入加公开投影约为请求 JSON 的 2.14 倍；不能把该单机样本描述为生产容量证明。
