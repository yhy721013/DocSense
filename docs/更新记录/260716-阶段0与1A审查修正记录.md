## 1. 阶段 0 工具修正

### 1.1 WebSocket 容量样本不再误报“连接稳定”

旧工具收到首帧后仅等待固定时间，服务端若马上断开，样本仍可能被记为成功。当前实现：

1. 为 simple-websocket Client 配置 Ping/Pong 周期；
2. 首帧后持续调用 `receive`，保持窗口内反复检查 `connected`；
3. 断连、异常消息、错误消息、错误 business type、错误业务键或非法 progress 均判失败；
4. 分别记录首帧耗时 `readyLatencyMs` 与实际保持耗时 `holdDurationMs`；
5. 客户端 close 只证明本地关闭完成，不再声称服务端 Registry 已清零。服务端清理仍需内部指标验证。

### 1.2 容量执行与统计边界

- Future 使用 `concurrency × 2` 的有界在途窗口，不再为最多十万样本一次性创建对象；
- 成功样本与失败样本延迟分别进入 `latencyMs`、`failedLatencyMs`；
- 增加成功吞吐，避免总吞吐掩盖快速失败；
- 严格校验 schema version、bool 标志、HTTP 方法、timeout、状态码、SSE 事件上限、
  WebSocket message/保持窗口/探测周期；
- 所有 CLI 输出统一经标准输出/错误输出 helper，满足项目禁止散落 `print` 的检查。

### 1.3 SQLite 一致快照和 WAL

盘点器现在使用 `mode=ro`、`query_only=ON` 和显式 `BEGIN` 只读事务。Schema、行数、
状态聚合和完整性检查在同一读快照内完成。报告另行提供：

- `dataVersionBefore/After` 及其是否变化；
- 主文件、WAL、SHM 的存在、大小、mtime 和盘点期间变化标记；
- 盘点结束后主文件 + WAL 的物理内容指纹及计算期间稳定标记；
- `--skip-status-distributions`，允许大库跳过可能扫描整表的 GROUP BY；
- direct API 与 CLI 一致的 `max_status_values` 类型/范围校验。

物理 SHA-256 不是数据库逻辑版本号；是否取得稳定证据必须同时看数据版本、物理文件
变化和 hash 稳定标记。旧执行记录中的六库结果是 2026-07-15 历史快照，不倒推为
“当时已经检查 WAL”。

## 2. check-task 回调恢复一致性

`CheckTaskStatusService` 不再根据 Adapter 自报的 `attempted/final_status` 决定是否重读。
每个已命中任务在恢复调用后都无条件按原 `TaskId` 重读，并校验：

- 重读对象仍是同一 TaskId、同一业务引用；
- 持久化 `callback_status` 必须等于 `CallbackRecoveryResult.final_status`；
- 不一致时抛出 `CallbackRecoveryConsistencyError`，记录安全上下文并停止成功统计；
- `replayed_count` 只可能统计已经通过持久化状态验证的结果。

这消除了 Adapter “内存中报告 success、数据库仍是 failed”时应用层误报成功的问题。
它本身不负责阻止同业务键的旧回调继续外发；该语义已在第 6.1 节 TASK-09 确认为
latest-wins，仍需由阶段 6 的共享 Guard 和 callback Worker 落实。

## 3. Progress 并发和任务隔离边界

### 3.1 初始快照顺序屏障

新增每连接独占的 `ProgressDeliveryBuffer`。应用服务在注册订阅前打开屏障，订阅期间
到达的通知只进入缓冲；Web Adapter 将来发送完全部 `current_items` 后，必须调用
`complete_initial_delivery()` 才能放行通知。放行时会以刚发送的 TaskId/sequence
过滤屏障前后已经排队的重复或旧快照，避免出现“先发 50%，再倒退发 40%”。

### 3.2 慢连接隔离和有界内存

- 任务/Progress 发布线程只执行短临界区入队，不调用 `ws.send`；
- 默认每连接容量为 256，可由内部配置调整，不是公开接口参数；
- 同一 key 的中间快照按最新到达且 sequence 不倒退的规则合并；
- 容量仍不足时淘汰最早的其他 key 快照，并以 1、2、4、8…频率记录警告，避免日志风暴；
- 暴露 queued/dropped/coalesced 指标，供波次 1B 和阶段 7/8 压测调优；
- 关闭后清空内存并忽略迟到通知，避免连接清理与任务线程异常竞争。

该缓冲是可丢中间状态的连接通知设施，不是 RabbitMQ/Celery 可靠任务队列，也不替代
MySQL 任务事实。目标 50 连接的真实容量仍按阶段 0 延期决定在完整集成环境验证。

### 3.3 连接归属和可重试清理

- 每个订阅令牌绑定 `delivery_id`，已有令牌不能在后续消息中切换到另一连接投递器；
- 建立订阅失败时逆序补偿；若补偿失败，`ProgressSubscriptionRollbackError` 携带
  完整失败令牌和原始异常；
- 连接释放会继续尝试全部唯一令牌；`ProgressSubscriptionReleaseError` 同样携带
  完整失败令牌，而不只保留字符串 ID；
- 波次 1B 的 Registry 必须保留这些令牌并重试，禁止日志记录后丢失对象引用。

## 6. 后置边界

### 6.1 TASK-09：已确认 latest-wins，待波次 1B 实现

场景是：业务键 `fileName=A.pdf` 的旧执行已经终态但回调失败；check-task 开始为旧
TaskId 恢复回调；与此同时，相同 `fileName=A.pdf` 又提交了新执行。现有 callback 只
携带业务键和结果，甲方不能用内部 TaskId 区分两次执行。

负责人已确认：`A.pdf` 在前端具有唯一性，同一文件名对应同一逻辑解析任务；不同
TaskId/`execution_id` 只是该任务的不同执行代次。因此采用 **latest-wins**：一旦新的
执行代次已经成为该业务键的最新任务，旧执行回调即判定过期，不再调用甲方 URL，并
在内部持久化 stale/skipped 原因。

仅做 expected TaskId 条件写只能防止旧任务状态覆盖新任务，不能撤回已经发出的 HTTP
回调。严格保证“新执行受理后不再到达旧回调”要求任务提交与回调恢复共享同业务键
Guard：在 Guard 内复核最新 TaskId，随后完成外发或跳过、条件持久化和复读，再释放
Guard。其代价是慢回调期间同一业务键的新提交会短暂等待；不同文件名之间不互相阻塞。

该保证存在冻结 Callback 契约下无法由单方消除的边界：HTTP 请求发出后若读取超时，
甲方可能稍后才处理旧请求；本服务既不能撤回，也没有对外 execution ID 供甲方拒绝旧
代次。此类情况按 TASK-05 记录 `delivery_outcome_unknown` 且不自动重试，但随后是允许
新执行受理，还是继续阻塞/拒绝该业务键，仍需负责人确认。当前阶段尚无
callback Worker 和共享 Guard，故 TASK-09 是**核心语义已决、超时准入边界待确认、
实现待阶段 6 完成**，不得把文档决策误报为现有路由已经具备绝对保证。

> 后续决策补记（2026-07-16）：超时准入边界现已确认。旧 callback 已先取得发送权时，
> 新提交最多等待当前 callback timeout；若投递进入 `delivery_outcome_unknown`，或等待
> 到期仍被占用，则复用对应接口既有 HTTP 409 并冻结该业务键，直至内部人工核查解除。
> 本补记只更新目标策略；当时审查所述“当前尚无 callback Worker/共享 Guard、尚未进入
> 生产”的事实仍然有效。

### 6.2 历史决策：可靠队列异步替换（已被取代）

> 本节记录 2026-07-16 当时的决策轨迹，不再作为施工依据。2026-07-17 甲方明确要求
> 保留请求内同步恢复；当前有效方案见总计划、阶段 0 决策清单及 2026-07-17 修复记录。

负责人于 2026-07-16 确认不建设过渡方案：不实现有界同步并行、批次总超时、本地线程池
或进程内队列，也不新增生产 `LegacyCallbackRecoveryAdapter`。目标调用链固定为：

1. check-task 在 MySQL 事务中读取任务，创建或复用 TaskId 唯一活动 recovery request，
   并写入 `trigger=check_task` 的 Outbox；
2. 事务提交成功后返回 HTTP 200 空响应体，不等待 callback 完成；MySQL/Outbox 未提交
   时不得成功；
3. Outbox Relay 使用发布确认投递 RabbitMQ，Broker 暂停时保留数据库积压并在恢复后
   继续发布；
4. callback Worker 按 recovery request ID 读取事实，在同业务键 Guard 内执行
   latest-wins、外发、条件持久化、delivery 审计和 ACK/DLQ；
5. 同一 TaskId 同时最多一条 pending/queued/running 恢复命令，重复 check-task 调用复用，
   前一命令终态后新的显式调用才可形成下一 attempt。

阶段 1B 只修订框架无关命令边界与 Fake 测试，并继续迁移 Progress；阶段 3 建 MySQL
Schema，阶段 4 建 Outbox/Relay，阶段 5 建 RabbitMQ/Worker，阶段 6 首先一次性切换
check-task 生产路由。接口文档尚未在本轮修改，生产切换前需按既定流程确认“200 表示
可靠登记而非回调完成”的文字；请求参数和 Callback 载荷始终不变。
