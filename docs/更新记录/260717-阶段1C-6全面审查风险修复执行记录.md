# 阶段 1C-6 全面审查风险修复执行记录

## 1. 执行结论

2026-07-17 在 `refactor/concurrency` 开发分支完成阶段 1C-6 的第二次实现级复核与修复。
本轮没有改变任何公开 HTTP、WebSocket、Progress 或 Callback 字段，也没有新增、删除、
重命名前后端接口参数；`docs/接口文档/` 未因本轮内部修复而修改。

本轮关闭了以下会在后续可靠队列、多实例或高并发改造中被放大的风险：

1. Dispatcher `close()` 在执行线程仍存活时误报 `closed`；
2. 报告在共享上传许可中排队时，停机后仍可能突然开始执行；
3. 领取前持续失败的 `accepted` 毒任务形成 CPU/日志热循环并阻塞后续任务；
4. 重型报告执行阻塞资源恢复和队列诊断；
5. 资源恢复首页的坏记录或未就绪记录长期饿死后续记录；
6. 同一进程内并发资源恢复可能重复执行本地 Artifact 删除；
7. Progress 持久化 owner 查询占用全局 Hub 锁，任一慢数据库查询阻塞所有业务键；
8. 仅靠配置声明 `single_instance`，缺少真正的跨进程运行门禁；
9. accepted 顺序依赖可回拨的应用时钟；
10. 路由测试裸调用 `create_app()`，可能隐式创建生产容器和后台线程。

当前代码仍未提交、未发布、未部署到生产服务器。全程未启动 `run.py`，未访问真实
AnythingLLM、模型、文件服务器或甲方回调服务。

## 2. Dispatcher 生命周期与停机语义

`LocalReportTaskDispatcher` 现在明确区分六个生命周期状态：`new`、`starting`、`running`、
`stopping`、`stopped`、`closed`。

- `stop(timeout)` 对一条执行线程和两条维护线程使用同一个总截止时间，不把三次等待各自
  扩大成完整超时；
- 停机时与“任务进入执行态”共用状态锁：停机先取得锁时，尚未开始的任务不会执行；
  Worker 先登记 `current_task_id` 时，该任务被视为合法在途任务并由停机等待；
- 等待共享 `UploadTaskLimiter` 时采用可中断轮询。收到停机信号后退出等待，任务仍保持
  `accepted`，以后由健康实例/重启扫描恢复；
- `close()` 只有在全部后台线程真实退出后才进入 `closed`。有限等待超时时保留
  `stopping` 并记录当前/等待 TaskId 与仍存活线程，不能制造关闭成功的假阳性；
- 后台线程最终退出后自动收敛为 `stopped`，调用方可再次 `close()` 完成幂等关闭；
- 进程锁只在全部后台线程真实结束后释放，避免旧执行线程尚存活时第二个进程取得执行权。

运行快照新增维护线程数、等待许可的 TaskId、accepted 冷却成功/失败计数等内部指标；
这些字段只供测试和监控采集，不进入公开协议。

## 3. 毒任务隔离、稳定 FIFO 与持久冷却

### 3.1 事务内调度序号

`llm_task_executions` 增加内部列：

| 列 | 作用 |
| --- | --- |
| `dispatch_sequence` | 在 `BEGIN IMMEDIATE` 受理事务内分配的稳定 FIFO 序号 |
| `dispatch_failure_count` | 领取前执行异常累计次数 |
| `next_dispatch_at` | 下一次允许扫描的时间 |
| `last_dispatch_error` | 已清洗并限制为 256 字符的内部异常类型 |

旧开发库采用只增列方式兼容，并为既有测试行补齐序号。新受理事务在持有 SQLite 写锁时
分配序号；即使调用方时间回拨，accepted 扫描仍按事务顺序稳定执行。阶段 3 的 MySQL
Repository 必须用数据库原生序列/等价机制重建这一语义，不能继续依赖应用时钟。

### 3.2 领取前故障冷却

Dispatcher 只收集当前有界页中的异常任务，并在批次末尾通过条件更新设置统一重试时间：

- 只有仍为 `accepted` 的 execution 才能冷却；
- 已经 claim 为 `running` 或进入终态时，条件更新返回 `False`，绝不回退状态；
- 成功冷却的坏任务暂时让出 FIFO 首页，当前满批可以立即扫描后续健康任务；
- 冷却事实本身写入失败时，Dispatcher 回到固定扫描周期，不进行无间隔热循环；
- `DOCSENSE_REPORT_DISPATCH_FAILURE_RETRY_SECONDS` 默认 30 秒，只控制坏任务重试节奏，
  不限制正常业务积压数量。

## 4. 执行、资源恢复和诊断隔离

Dispatcher 当前固定创建三条职责互斥的后台线程：

| 线程 | 数量 | 职责 |
| --- | ---: | --- |
| `docsense-report-worker` | 1 | accepted 领取及重型报告执行 |
| `docsense-report-resource-sweeper` | 1 | 启动及固定延迟资源恢复 |
| `docsense-report-queue-inspector` | 1 | accepted/running/terminal 只读诊断与告警节流 |

“单 Worker”只表示重型报告业务并发为 1，不再表示模型执行、资源恢复和队列诊断串在同一
线程。一个长时间模型请求不会延迟 cleanup 恢复或 running 告警；一次慢 sweep 也不会延迟
accepted 领取或队列诊断。三条循环任一发生未捕获异常时都会发出 CRITICAL 日志并停止整个
Dispatcher，持久化 accepted/running 事实保留给进程重启或后续阶段恢复。

## 5. 资源恢复首页饥饿与 Artifact 并发

`report_resource_records` 增加独立于 JSON payload 的调度列：

| 列 | 作用 |
| --- | --- |
| `recovery_deferral_count` | 扫描冷却累计次数 |
| `next_recovery_at` | 下一次允许恢复扫描的时间 |
| `last_recovery_reason` | 最近一次待恢复/异常分类 |

`sweep(limit)` 仍严格有界，但对本页中的 `pending`、`not_ready` 和异常记录统一写入未来重试
时间。即使记录 JSON 已损坏，独立 SQL 列仍能把它移出下一页，让后续健康任务在下一轮被
处理。终态 `cleaned/quarantined` 或已不存在的记录不会被错误延期。

同一 `ReportResourceRecoveryService` 内新增按 TaskId、引用计数且自动回收的 Artifact 副作用
锁。取得锁后重读最新 CAS 事实，仅串行同一任务的本地文件删除；不同任务仍可并发，外部
RAG 删除继续依赖既有持久 token/心跳/fencing。该锁只属于阶段 1C 单实例兼容实现；阶段 3～5
多实例必须以数据库租约和对象存储幂等语义替换，不能把进程锁扩张为集群承诺。

## 6. Progress 按业务键隔离

持久化 latest owner 的只读 Guard 现在运行在“同一业务键”的发布锁内、全局 Hub 状态锁外：

- 同一个 `(business_type, business_key)` 的 Guard、序号和 latest 更新仍保持原子；
- 不同业务键的数据库查询、发布和回调可以并行；
- 全局锁只用于短暂读取/写入内存快照及复制订阅者，不包含数据库或订阅者 I/O；
- 按键锁使用引用计数，最后一个持有者/等待者退出后自动删除，不随历史业务键无限增长。

这不改变 WebSocket 消息内容，只消除一个慢持久化查询拖住所有 Progress 业务键的扩散风险。

## 7. 跨进程单实例门禁与测试隔离

生产组合根为报告 Dispatcher 装配 `FileProcessSingletonGuard`：

- Windows 使用 `msvcrt`，POSIX 使用 `flock`，均为非阻塞内核文件锁；
- 锁文件只作为稳定协调地址，不在释放时删除；进程异常退出后由内核释放锁；
- 同一运行目录只能有一个报告 Dispatcher 取得所有权，第二个应用在公开路由可用前拒绝
  启动；
- Dispatcher 和 Guard 都记录 owner PID，检测到 preload/fork 继承的失效线程/句柄状态时
  明确报错；当前 `single_instance` 模式禁止 preload/fork，Werkzeug reloader 保持关闭；
- 离线测试除同进程双对象竞争外，还启动真实子进程验证文件锁确实跨进程生效。

路由测试统一显式注入临时 SQLite 和 Fake 服务。架构 AST 门禁扫描全部 `tests/test_*.py`，
除专门验证生产应用生命周期的一处测试外，禁止无参 `create_app()`，避免未来测试再次误触
开发 `.runtime`、真实生产容器或后台线程。

## 9. 仍然保留的边界

1. SQLite accepted + Event 仍不是 RabbitMQ 可靠队列，不具备 publisher confirm、late ACK、
   DLQ、跨进程 Worker 或多实例任务租约；
2. 崩溃遗留 `running` 在阶段 2 Attempt/Step/Checkpoint/lease 就绪前只观测，不自动重跑；
3. 进程级 Artifact 锁只服务当前单实例链，不能用于阶段 3～5 多实例正确性证明；
4. 50 个离线 accepted 和线程并发测试证明结构有界，但不代替阶段 10 的 50+ 在途任务、
   50 条长连接、短请求稳态和真实下游限流压测；
5. 当前工作区尚未提交 Git、未发布、未部署，所有阶段 1C 代码均未进入生产。
