# 阶段 2-7 业务恢复策略与有限 Reaper 实施记录

## 1. 实施范围

本记录对应阶段 2 总计划 D2-07、D2-07A、D2-08、D2-19 和 D2-20。Report、Weaponry、
Analysis 均通过唯一 Task Control v2 根控制面完成过期 Attempt 分类、Recovery Case、
Recovery Authority、证据观测、严格 Decision 和有限检查点续跑。本阶段未修改公开路由、
请求参数、响应字段、Header、状态码、Progress、Callback 或 `/llm/check-task` 语义，
未运行 `run.py`，未把旧 Runner 或旧业务入口双写到 v2。

## 2. 过期 Attempt 与 Recovery Authority

- Reaper 只扫描持久化的过期 `running` Attempt，并在短事务内重新核对 Task、Attempt、
  fencing、row version、latest 与证据摘要；
- 三业务显式 Policy 把现场分为 `retry_safe/finalize_from_checkpoint/reconcile_required/
  mark_stale/defer`，未知外部结果不因 lease 过期被当作“从未执行”；
- Coordinator 使用与普通 Executor 分离的 Recovery Authority，以 Case generation、recovery
  fencing、source Attempt/fencing 和 expected row version 阻止旧持有者写入；
- Operation Intent 先提交，网络、文件、模型、AnythingLLM 和 Callback HTTP I/O 保持在
  事务外；Observation、Operation 状态和最终 Decision 均受 fencing 保护。

## 3. 检查点续跑与业务边界

三业务组件 Manifest 升级为 v2，各自管理不可变的 `*_step_continuation_snapshots`。
快照是不超过 16 KiB 的 canonical JSON，只保存稳定引用、basename、序号和 SHA-256，
不保存凭据、正文、Prompt、模型原始响应或宿主根路径。意图与快照在同一业务 UoW 中追加，
恢复时重新校验冻结输入、Execution Profile、前置检查点和来源 Step Attempt。

当前只授权已同时具备 Policy 白名单、Resume Preflight 和真实 Workflow Resolver 的四个恢复点：

- Report `artifact.scope.begin`；
- Weaponry `resource.record.begin`；
- Analysis `source.download`；
- Analysis `document.prepare`。

Analysis v2 已把原组合的 Source Download 和 DocumentProcessing Port 拆分：只有下载成功后
才会提交 `document.prepare` intent；文档恢复只读核对任务目录、basename 和摘要，不补建、
不重下。旧 v1 组合外观仅作历史适配器保留，v2 不借此获得旧 Authority。

## 4. 恢复终态、Callback 与运维入口

`finalize_from_checkpoint` 在同一 SQLite 短事务中核对业务结果快照，并原子提交
Recovery Decision、Task/latest 终态与 Callback eligibility。任一预检、归属、摘要或 Callback
条件不成立都回滚并保持隔离；不会重跑业务副作用以伪造终态。

`scripts/reconcile_stage2_task.py` 默认只读诊断。写模式必须提供完整的 Task/Case/
generation/row version/source Authority/recovery fencing/operator/reason/evidence 和动作所需精确证据身份。
脚本只调用 Application 边界，不直接执行 SQL，不提供“承担重复风险后强制重跑”开关。

## 5. 组合根与数据库策略

生产组合根沿用唯一 `LocalMaintenanceScheduler`，只将原保守 Reaper 动作替换为三业务
Policy 驱动的 Reaper，没有新增线程或改变启停顺序。Event 仍只是可丢唤醒提示，
SQLite 启动/周期扫描才是恢复事实来源。

按已确认的全新部署前提，Report、Weaponry、Analysis 组件 v2 不提供 v1 在线迁移、
兼容读取或双写。旧数据库及 WAL/SHM 必须在经授权的 fresh bootstrap 前被完整废弃；
普通启动遇到 v1、缺表、未知版本或指纹漂移仍失败关闭。

## 6. 离线验证与证据边界

定向验证覆盖过期分类、Case claim/heartbeat/fencing、Intent-before-effect、Observation、
strict Decision、结果终态原子性、三业务 Resume Preflight、新 Attempt/新 Step Attempt、
旧历史不变、冻结输入/Profile、快照摘要漂移失败关闭、Analysis 分 Port 和严格运维入口。
阶段 2 聚合集执行 210 项，失败 0、错误 0；架构门禁执行 32 项，失败 0、错误 0；
运维入口与 `print` 静态门禁执行 6 项，失败 0、错误 0。

最终执行 `python -B -m unittest discover -s tests -t .`：发现并执行 2489 项，失败 0、
错误 0、跳过 13，Python 退出码为 0。另通过 `compileall`、`git diff --check`、22 个
阶段 2 JSON/Manifest 可解析检查和公开接口目录零差异检查。测试中的预期故障注入日志
不代表测试失败。

上述证据只证明当前 Windows、临时 SQLite、Fake/Mock 和单进程协议实现。未调用真实
AnythingLLM、模型、文档下载、Callback 服务或可靠队列；不能据此声称多实例、共享数据库一致性、
高并发容量、生产吞吐、exactly-once 或浏览器/UI 验收。

## 7. 已知保守边界

`TargetEvidenceRetrievalPort.open_scope()` 仍是 Workspace 创建与多文档绑定的生产组合调用。
相关后续 Step 尚无逐效果 Resolver/Observer，因此本阶段不将它们加入自动续跑白名单：
未知结果继续保守隔离。未来如要开放，必须先拆分真实供应商 Port 或引入逐效果观测，
并单独验证旧 Runner Authority 传递。这一保守边界不影响已白名单恢复点的正确性。
