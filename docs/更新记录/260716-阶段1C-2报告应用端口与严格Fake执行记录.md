## 1. 本轮交付

### 1.1 通用 Tasks 写入控制面

新增/扩展：

- `TaskExecutionSnapshot[TInput]`：保存 TaskId、业务引用、执行状态和不可变业务输入；
- `TaskSubmissionCommand/Result`：区分 accepted、活动冲突、callback sending 和 outcome
  unknown，不在 Tasks 层决定 HTTP；
- `TaskClaimResult`：区分 claimed、missing、already running、terminal 和 stale；
- `ExpectedProgressUpdate`、`ExpectedTaskCompletion`：所有写入携带 expected TaskId；
- `TaskCommandPort`：原子受理、按 ID 读取/领取、条件进度/终态、latest 检查和 accepted
  扫描；
- `ProgressPublication/ProgressPublisherPort`：类型化发布已持久化进度，不携带 WebSocket
  JSON，也不公开内部 TaskId。

Task Command 使用泛型命令、输入和结果，`tasks` 生产代码没有导入 report 模块。后续
analysis/weaponry 可以复用同一任务控制面，而不复制一套报告专用状态机。

### 1.2 Report 专用 Port

`app/modules/report/ports/` 已建立：

| Port | 关键语义 |
| --- | --- |
| File | 按请求顺序下载源文件、规范化、展开 RAG 上传文件、下载并提取 Word 模板；规范化使用显式可回退错误。 |
| Artifact | TaskId 隔离命名空间、不透明 ArtifactRef、最终 HTML 持久化和 scratch 清理；不暴露真实路径/URL。 |
| Report RAG | 有序多文档一次生成、最终调用、attempts、生命周期事件、失败现场和 cleanup ref。 |
| Interaction Audit | 主交互、attempts 和初始生命周期事件原子提交；清理事件幂等追加。 |
| Callback | latest 之外的发送权、精确 delivery outcome、Guard Lease 和完成持久化。 |
| Dispatcher | 持久化事实提交后的可丢唤醒；任务事实禁止只存在于内存实现。 |

RAG trace 的 attempt/lifecycle sequence 必须严格递增且不重复。所有 Artifact、Audit
Receipt、Callback Lease 和 RAG 请求都绑定 TaskId；跨任务引用由 Application 或 DTO
立即拒绝。

### 1.3 SubmitReportTask

提交用例执行以下固定顺序：

1. 把不可变 `ReportSubmission` 转成通用 Task Submission Command；
2. 调用 create-if-allowed 原子受理 Port；
3. 若结果为 callback sending，通过 Callback Port 在数据库锁外按既有 callback timeout
   有界等待；released 后只重试一次原子受理，timeout/unknown 保持冲突；
4. 校验执行快照与提交命令的 reportId、完整输入、Schema、accepted time 和 trace；
5. 发布初始 `0.0` Progress；
6. 发送 Dispatcher 唤醒。

Progress 或 Dispatcher 通知发生异常时记录完整内部日志，但不撤销已经提交的 accepted
事实；未来周期扫描负责恢复。活动任务、callback wait 超时和 outcome unknown 都映射为
同一个 `ReportTaskConflictError`，由后续 Presenter 统一输出已经批准的 409，不在应用层
嵌入 Flask。等待 Fake 覆盖 released、timeout、unknown 和等待存储异常。

### 1.4 RunReportTask

执行用例只接收 `TaskId`，并冻结以下编排：

1. 按 TaskId 读取、校验并条件领取；重复派发/终态/stale 幂等停止；
2. 创建 TaskId 隔离 Artifact scope；
3. 以 expected TaskId 条件写 `0.15/0.25/0.35`，成功后才发布同值 Progress；
4. 按 URL 顺序下载与准备源文件；仅显式 normalization 错误回退原 Artifact；
5. 下载/提取 Word 模板，空文本在 RAG 前失败；
6. 使用与遗留 builder 精确等价的纯 Prompt 规则执行多文档 RAG；
7. 完整 trace 原子审计成功后，才构造 HTML、持久化 Artifact 和写成功终态；
8. 终态条件写返回 stale 时禁止最终 Progress 和 callback；
9. callback 前再次 latest 检查，并经过 Guard acquire/deliver/complete；
10. 审计成功后清理 RAG/scratch；清理失败只记录 pending/错误，不反向改写业务终态。

`None`、空字符串和纯空白 RAG 结果继续按既有成功语义生成空 HTML，同时只在内部结果和
日志中标记 `empty_rag_result=true`。审计失败会写报告失败终态、禁止成功 callback，并
保留 RAG/Artifact 现场。

进度或终态条件写“返回 stale”和“抛出异常”被严格区分：前者表示当前执行已经确定过期，
可以幂等停止；后者可能发生在数据库已经提交、但调用方没有收到确认的窗口，因此统一包装为
`ReportTaskPersistenceError`，保留现场并原样向上抛出。应用层不会再补写一次失败终态，
也不会继续发布 Progress、发送 callback 或清理资源，从而避免把一个可能已经成功的终态
覆盖成失败，后续由持久化 Adapter/恢复流程核对真实事实。

业务终态一旦明确提交，latest 查询、Callback Guard 获取、HTTP 投递和 Guard 完成全部
进入独立回调故障域：任一步异常都记录 `port_error` 和完整堆栈，但不会逃逸到业务失败
分支，也不会触发第二次终态写。规范化/RAG Artifact 还会逐项校验 TaskId、类别和源文件
序号，防止未来 Adapter 把跨任务或跨阶段引用静默送入外部服务。

### 1.5 严格 Fake

`tests/fakes/report.py` 为全部 Port 提供共享 `InvocationRecorder`，可观察跨 Port 的完整
顺序。Fake 支持逐步骤异常、stale/冲突、非法返回对象、跨 TaskId/trace/Artifact/Receipt
身份、Artifact 类别/顺序、任务进度/终态写入结果不确定和 cleanup/callback 故障；回调
故障测试逐项断言终态只写一次。Fake 不会访问文件/网络/数据库，也不会替 Application
自动补偿。

## 2. 架构门禁

架构正向白名单现在允许 report 的 Port 复用 tasks domain 中的 `TaskId`，允许 report
Application 复用 tasks domain/ports；仍禁止：

- report Application/Ports 导入 Flask、FastAPI、SQLite、SQLAlchemy、requests、Celery
  或 AnythingLLM Client；
- report 导入 tasks Application/Adapter；
- tasks 任意分层反向导入 report 或其他业务模块；
- Port 暴露真实路径、数据库连接、供应商 DTO 或公开 JSON 字典。

自证测试同时证明 tasks 公共控制面可被 report 使用，而 `tasks.adapters` 会被拒绝。
