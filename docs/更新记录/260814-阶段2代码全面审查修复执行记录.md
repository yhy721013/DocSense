# 阶段 2 代码全面审查修复执行记录

## 1. 范围与契约结论

本次针对阶段 2-0～2-5 的 Domain、Port、Task Control SQLite、UoW、Execution Runtime、Report v2、
Weaponry v2、Analysis/file 兼容链与生产组合根进行修复。公开 HTTP、Callback、SSE、WebSocket 的
路由、参数、字段、Headers、状态码和语义均未修改；`docs/接口文档/` 保持冻结。实施没有运行
`run.py`，没有访问真实供应商、Callback 接收端或现有生产数据库。

## 2. 已修复问题

1. `RoutedTaskReadAdapter` 改为必须显式传入 v2 业务集合；生产固定为 `report/weaponry`，避免
   Weaponry 的 check-task 与 Progress 回退误读旧库。Analysis 继续使用已确认的 `file` 类型。
2. `LocalTaskExecutor` 的未分类 Worker 异常会使实例不健康、停止新领取，并通过 Execution UoW
   写入带次数累计的持久冷却；避免构造异常形成热循环。
3. 修复 stop 与 Runtime 构造之间的竞态：stop 后新构造 Runtime 只接收取消，不再调用 `run`。
   Report/Weaponry 在新 Step Intent 和字段慢调用边界响应正常取消；取消与失权使用不同内部结果。
4. 将 `ConservativeTaskReaper` 作为独立根控制面维护任务接入生产容器的启动、逆序回滚、停止、
   关闭和 readiness。它仍只持久化 `DEFER`，不开放自动业务重试或 Callback 补发。
5. 生产重型容量改由同一 `FairTaskExecutionPermitPool` 为 `report/weaponry/file` 签发不同 Permit；
   组合根验证三条链共享同一容量事实。旧离线夹具仍可注入原 FIFO limiter。
6. SQLite Store 在 scan、claim 与 Task 重建边界重复校验批次身份，异常 Analysis 批次数据失败关闭；
   `MARK_STALE` 在 abandon Attempt 前先拒绝仍为 latest 的 Task，避免部分写。
7. `dispatch_failure_count` 随每次持久派发冷却原子累计，诊断不再永久保持零。

## 3. 明确保留的未来边界

- 阶段 2-7 的自动恢复不得用通用 Task 终态写绕过 Report/Weaponry 业务组合 UoW；必须先验证业务
  Result/Artifact、Step checkpoint 与 latest，再用业务 Store 和 Task Store 原子收敛。
- 本地 Event 只是可丢唤醒，SQLite 持久扫描才是恢复真相；当前 Reaper、公平池与文件锁均不是可靠
  队列、分布式租约或多实例容量控制。
- Python 线程采用协作停止，无法强杀正在执行的不支持取消的供应商调用；旧 Authority 的后续条件写
  仍由完整 lease token、attempt、fencing 与 expiry CAS 拒绝。
