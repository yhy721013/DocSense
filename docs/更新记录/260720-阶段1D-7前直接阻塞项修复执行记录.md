## 2. 外部创建的崩溃窗口

### 2.1 持久 Creation Intent

新增供应商无关 Creation Intent Port 和 SQLite Store。Retrieval workspace、来源 Extraction
workspace 与来源 Thread 在调用 AnythingLLM `create` **之前**先以
`task_id + intent_id` 持久化：

- 确定性预期名称；
- 创建种类、父资源、文档和 call 身份；
- 不含 Prompt、正文、Token 或完整 URL 的身份摘要；
- `pending / resolved / quarantined` 状态与版本 CAS。

相同 intent 的重入只允许完全相同的不可变身份；不同身份立即冲突。这样进程在远端创建已提交、
本地资源登记尚未完成时崩溃，重启后仍能证明“该 create 曾经开始”，不会盲目再建第二份资源。

### 2.2 保守查回与现场隔离

- workspace 使用区分大小写的确定性名称查回；只有恰好一个匹配项才登记为 owned 资源，并把
  任务资源现场隔离等待人工对账；零个或多个匹配项均隔离意图，禁止重发或自动删除；
- Thread 当前没有可靠的唯一查回 API。历史 pending Thread 直接连同父 workspace 现场隔离，
  不猜测、不复用父 Thread、不再次创建；
- 维护扫描有界；同一轮所有 workspace 意图只拉取一次远端 workspace 清单，再按名称索引，
  避免 50 条积压放大成 50 次相同 HTTP 请求；
- 资源已登记/隔离而意图尚未 resolve 时再次崩溃，完全相同的资源登记会幂等返回，下一轮可继续
  resolve，不会形成永久 pending；
- 创建意图恢复暂时失败不阻塞已经登记资源的本地清理恢复。

## 3. HTTP 租约时间预算

新增共享 `required_http_lease_seconds(timeout)` 规则。Requests 的标量 timeout 会分别约束连接和
读取阶段，并非整个调用的墙钟总时限，因此内建 HTTP Adapter 的最小租约为：

```text
lease >= 2 * timeout + 5 秒安全余量
```

报告与 Weaponry Callback 使用 `stream=True`，只根据响应状态行判断结果并显式关闭 Response，
不因甲方意外返回的大响应体占用发送租约；3xx 仍禁止自动跟随。报告/Weaponry 外部资源清理配置
应用相同预算。60 秒 HTTP timeout 的默认 cleanup lease 从 90 秒调整为 130 秒；这只是内部
lease/fencing 安全配置，不改变公开 HTTP 超时或契约。

自定义测试 Transport 无法推断其连接/读取预算，仍要求 lease 严格大于注入 timeout；生产内建
Transport 使用上述完整预算。

## 4. 机器可判定生产门禁与 readiness

新增只读 production attestation 校验器和命令行检查脚本。证明文件必须同时满足：

- Schema 为 `docsense.weaponry.production-readiness.v1`；
- `profileId` 与当前确定性 Selection profile 完全相同；
- provider、embedding、documentProcessing、extractionModel 四类指纹完全相同；
- 环境、验证时间和 64 位小写十六进制 evidence digest 非空合法；
- score/rank 协议、来源身份、空 workspace 隔离和 Provided-Evidence 隔离四项检查均为 true。

`ApplicationServices.readiness_snapshot()` 只读汇总 Report Dispatcher、Weaponry Dispatcher 的
生命周期/致命错误和上述生产门禁。缺失或无效证明不会妨碍当前开发环境构造，但返回稳定原因码、
记录告警并使总体 readiness 为 false。校验过程不发网络请求、不创建/删除供应商资源。

`.env.example` 新增可选证明路径说明；检查脚本输出一行稳定 JSON，就绪退出 0，否则退出 1。

## 5. 诊断与孤儿资源收敛

- Terms 辅助明确失败/降级和 Translation 失败的稳定错误码现在进入字段内部 diagnostics，最终由
  既有任务内部结果聚合；公开 Callback 字段不变；
- tracking 资源找不到对应 execution 时，不再永久热扫描或推测 Worker 已死亡。首次扫描即以
  `weaponry_execution_missing_for_resource` 隔离，禁止自动删除；后续扫描不再反复占用首页；
- 创建意图恢复、资源恢复和 Callback Guard 继续使用互相隔离的有界维护路径，一条异常不阻塞
  同批其他任务。

## 8. 发布与回滚边界

当前仍是 `refactor/concurrency` 开发分支未提交改造，尚未进入生产。正式发布前必须先生成有效
production attestation，并由部署编排把 readiness=false 视为不可接流量。若创建意图或资源记录
处于 quarantined，必须人工对账，不得通过删除数据库行、重发 create 或恢复共享父 Thread 绕过。

回滚应按版本级停止新 Dispatcher、确认没有 running execution、sending/unknown Callback、
pending Creation Intent 或待清理 owned 资源后执行；禁止只把 Flask 路由指回遗留 Worker 而保留
新后台链，以免双执行和双回调。
