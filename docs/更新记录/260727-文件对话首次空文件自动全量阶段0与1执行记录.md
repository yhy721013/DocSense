## 2. 阶段 0：合同与黄金基线

2. 断言首轮 user 历史没有文件、当前 binding 为空，防止后续接线误造附件；

## 3. 阶段 1：全量目录快照

`ChatDocumentResolver` 新增供应商无关的 `resolve_all_available()` 能力，
`DatabaseChatDocumentResolver` 的实现具有以下约束：

1. 只调用一次 `DatabaseService.list_document_records()`，不在循环中按文件二次查询；
2. 沿用数据库的 `file_name ASC, architecture_id ASC` 稳定顺序；
3. 显式列表与全量目录共用同一个记录转换函数，统一 `document_ref`、远端位置和原始文件名规则；
4. 空目录返回空元组，不触发网络 I/O；
5. 跨 architecture 的相同业务 `file_name` 整体拒绝；
6. 重复 `document_ref` 或统一斜杠后的重复远端位置整体拒绝；
7. 缺少业务文件名、文档引用或远端位置的坏记录整体拒绝，不静默跳过；
8. INFO 日志只记录选择模式和数量，目录冲突日志只记录类型与位置索引，不输出完整文件清单。

新增 `ChatDocumentCatalogConflictError` 作为 Application 内部的确定性目录冲突类型。它继承
`ValueError`，不会要求公开 HTTP 结构新增字段；后续接线路由时仍由现有 400 单一 `error`
结构呈现。
