- 执行日期：2026-07-30
- 执行范围：`POST /llm/analysis` 的名称校验、文档准备、RAG 上传、永久知识转交、
  审计与资源恢复
- 当前状态：P0～P7 代码、离线门禁和受控真实 Provider 验收完成
- 发布状态：尚未部署生产环境
- Provider 实测基线：AnythingLLM Desktop `1.15.0-r2`

本次改造已经实现以下结果：

1. 可文本化文档在上传 AnythingLLM 前生成仅供 RAG 使用的内部 Markdown 投影；
2. 投影会移除图片 data URI 的 Base64 payload，但不替换 canonical prepared Artifact；
3. Markdown 投影的 multipart filename 为 `<业务原名主干>.md`；
4. AnythingLLM `metadata.title` 使用业务原名及原后缀，并继续成为 UI 和 Chunk
   `sourceDocument` 的来源；
5. 本地 Artifact 路径、业务显示名、HTTP 传输名和 Provider 身份保持分离；
6. OCR 与 MinerU 均明确失败的 PDF 降级仍上传真实 PDF，不伪装成 Markdown。

## 2. 公开合同

本次没有新增、删除或重命名任何请求、响应、Callback、Progress、SSE 或 WebSocket 字段，
`fileName` 与 `originalFileName` 的既有业务语义保持不变：

- `fileName` 继续承担文件分析业务键和现有兼容语义；
- 非空 `originalFileName` 继续表示调用方提供的原始业务文件名；
- `originalFileName` 缺失、`null`、空字符串或仅含空白时，内部命名统一回退到
  `fileName`，不新增公开字段。

经确认新增的合同仅为入站严格校验：名称候选包含路径分隔、路径导航、控制字符、
Windows 保留名、非法结尾、超长 UTF-8 名称或其他禁止形态时，整批同步返回 HTTP `400`。
校验发生在任务受理、文件下载、任务目录创建和 AnythingLLM 调用之前，因此不会留下部分批次
或外部副作用。合法请求仍返回 HTTP `202` 空响应体。

Callback payload 结构及 `data.status` 语义没有变化；RAG 投影只影响内部检索输入。

## 3. 低耦合实现

### 3.1 Provider 中立名称与上传描述符

Analysis Domain 新增纯名称策略，任务快照 V3 冻结：

- 业务展示标题；
- Markdown 与 PDF 两种合法传输名；
- 命名来源和稳定摘要。

Worker 不重新读取或重新解释原始 mutable payload。最终文档表示确定后，Application 生成
不可变 RAG 上传描述符，显式携带 Artifact identity、representation、media type、
multipart filename、display title 和 projection profile。

这些类型不依赖 AnythingLLM HTTP DTO。Analysis Application 只依赖 RAG/Knowledge/Audit
Port，AnythingLLM 的 multipart、metadata 和 location 规则仍封装在 Integration/Gateway
层，业务代码没有直接承担 Provider 协议。

### 3.2 RAG-only Markdown 投影

Document Processing 新增 `RAG_PROJECTION` Artifact、纯 Application 用例和流式 Adapter。
投影器使用有界状态扫描识别 Markdown 图片 data URI，不用单个贪婪正则一次加载整段
Base64；输出通过既有 Artifact Store 原子发布并核对摘要。

canonical prepared Artifact 继续用于正文解析、翻译、Callback 和结果映射。RAG 投影只作为
检索输入，因此不会把“为向量化优化的文本”升级成业务原文。

### 3.3 上传、审计与恢复

AnythingLLM 上传接口内部支持分别传递：

- 受控本地读取路径；
- multipart filename；
- `metadata.title`；
- 随机 `docSource` 身份标记。

有限重试复用同一不可变上传选项，不会重新派生名称。永久知识记录分别保存业务原名、
实际传输名和 `document_ref`；交互审计与资源事实保存同一上传描述符。Pin、close、删除和恢复
只使用精确 location/Provider identity，不按 UI 标题查找。

这使当前本地 Dispatcher 将来替换为可靠队列时，可以直接序列化任务快照和上传描述符；
多实例执行仍需后续共享数据库、租约、fencing 和可靠消息设施，本次没有虚构这些能力。

## 7. 边界与后续发布

本次证据只覆盖当前 Windows 工作树、临时 SQLite/Fake 和受控 AnythingLLM 单实例。
它不能证明：

- 已接入可靠任务队列；
- 多实例数据库一致性或 Exactly-once；
- 50+ 生产并发容量；
- 生产配置、生产数据迁移或生产发布已完成；
- 未来 AnythingLLM 版本保持相同字段行为。

未来发布应在停服窗口执行独立灰度：核对运行版本与配置，观察 projection failure、
upload rejected、`outcome_unknown` 和孤儿资源，并验证回滚到上一完整版本。禁止新旧投影
profile 在线双跑，也禁止在投影失败时静默恢复上传含 Base64 的 Markdown。
