## 3. 低耦合实现

### 3.1 Provider 中立名称与上传描述符

Analysis Domain 新增纯名称策略。历史任务快照 V3 冻结业务原名传输语义；当前 V4 冻结：

- 业务展示标题；
- 全局唯一 `fileName` 传输候选；
- Markdown 与 PDF 两种合法传输名；
- 展示/传输命名来源和稳定摘要。

Worker 不重新读取或重新解释原始 mutable payload。最终文档表示确定后，Application 生成
不可变 RAG 上传描述符，显式携带 Artifact identity、representation、media type、
multipart filename、display title 和 projection profile。

这些类型不依赖 AnythingLLM HTTP DTO。Analysis Application 只依赖 RAG/Knowledge/Audit
Port，AnythingLLM 的 multipart、metadata 和 location 规则仍封装在 Integration/Gateway
层，业务代码没有直接承担 Provider 协议。

### 3.2 RAG-only Markdown 投影

Document Processing 新增 `RAG_PROJECTION` Artifact、纯 Application 用例和流式 Adapter。
投影器使用有界状态扫描识别 Markdown 图片 data URI，不用单个贪婪正则一次加载整段
Base64；输出通过既有 Artifact Store 原子发布并核对摘要。

canonical prepared Artifact 继续用于正文解析、翻译、Callback 和结果映射。RAG 投影只作为
检索输入，因此不会把“为向量化优化的文本”升级成业务原文。

### 3.3 上传、审计与恢复

AnythingLLM 上传接口内部支持分别传递：

- 受控本地读取路径；
- multipart filename；
- `metadata.title`；
- 随机 `docSource` 身份标记。

有限重试复用同一不可变上传选项，不会重新派生名称。永久知识记录分别保存业务原名、
实际传输名和 `document_ref`；交互审计与资源事实保存同一上传描述符。Pin、close、删除和恢复
只使用精确 location/Provider identity，不按 UI 标题查找。

这使当前本地 Dispatcher 将来替换为可靠队列时，可以直接序列化任务快照和上传描述符；
多实例执行仍需后续共享数据库、租约、fencing 和可靠消息设施，本次没有虚构这些能力。

## 8. 后续修复：Callback 等待与 RAG close 的资源恢复竞态

### 8.1 问题与根因

真实单实例运行日志暴露出以下并发窗口：

1. Analysis Worker 已提交业务终态并进入 Callback 等待；
2. 资源记录此时仍可能处于 `tracking`，或稍后处于
   `cleanup_pending/session_close=running`；
3. Dispatcher 维护线程同时扫描到该记录，把仍由活跃 Worker 推进的资源误判为失联记录；
4. 维护线程先隔离并增加资源版本，原 Worker 随后的 close 意图或结果 CAS 因版本变化失败。

这不是 Callback、公开 `data.status` 或 AnythingLLM 上传命名问题，而是同一进程内业务
Worker 与资源恢复线程缺少显式活跃权协调。只给 close HTTP 调用增加保护仍不完整，因为
最早的竞态发生在 Callback 等待期间、`prepare_close` 之前。

### 8.2 修复策略

- 新增供应商无关的 `AnalysisResourceActivityPort`。当前 SQLite `single_instance`
  组合根注入线程安全的进程内实现；Application 和恢复器共享同一实例。
- `AnalysisResourceLifecycle.register()` 在创建可扫描的 `tracking` 记录前先取得活跃权，
  从而不存在“记录已可见、Worker 尚未登记”的窗口。
- 活跃权覆盖资源登记、Callback 等待、RAG close、close 结果落库和生命周期审计，直到
  Factory 完全退出后才在 `finally` 中幂等释放。
- 维护线程命中当前进程仍活跃的 execution 时只返回
  `pending/resource_owner_active`，不修改 payload、state 或 version。
- close 的 `planned/running` 事实额外保存 `worker_started_at` 与
  `recovery_not_before`。进程崩溃导致活跃权消失后，保护期内仍只观察；期限届满且外部结果
  仍未知时改记 `outcome_unknown` 并隔离，绝不自动重放 AnythingLLM close/delete。
- 已确认 close 结果只允许恢复器补同一幂等审计，不重新调用远端 Provider。

配置项
`DOCSENSE_ANALYSIS_RESOURCE_CLOSE_RUNNING_GRACE_SECONDS` 默认 300 秒，装配时要求为
0～604800 秒范围内的正有限数字。该参数是进程崩溃后的持久保护期，不是多实例租约；
未来可靠队列/多实例部署仍须用共享 owner、lease 与 fencing Adapter 替换进程内实现。

### 8.3 合同与历史数据边界

本修复没有新增、删除或改变任何公开请求、响应、Callback、Progress、SSE 或 WebSocket
参数，因此没有修改 `docs/接口文档/`。`fileName`、`originalFileName`、Callback
`data.status` 以及 HTTP 状态码语义均保持不变。

修复不会自动修改已经隔离的历史资源记录。既有记录可能对应远端清理已经发生、但本地
close 审计未完成的未知事实；未经人工核对不得自动反向改写或重放远端操作。

## 9. `fileName` 唯一传输命名兼容修复

### 9.1 问题与根因

原实现允许 `资料.pdf` 与 `资料.docx` 的 Markdown 投影都以 `资料.md` 上传。AnythingLLM
真实向量来源可能只返回 `file://.../hotdir/<入库文件名>`；武器谱为防止来源错配，会在检索
前拒绝两个不同文档共享同一规范化 `ingested_file_name`，因此同主干文档会确定性失败。

经调用方确认，公开 `fileName` 在整个系统中全局唯一。本修复据此将职责调整为：

- `display_title`：继续使用 `originalFileName` 原值，缺失/空值时回退 `fileName`；
- `transport_file_name`：始终使用 `fileName` 主干和实际 RAG 表示后缀；
- `ingested_file_name`：上传成功后保存实际 `transport_file_name`；
- `metadata.title`、Callback `source`、公开 `fileName` 及所有响应结构保持不变。

### 9.2 内部 Schema 与兼容边界

Analysis Worker 输入升级为 Schema v4。Codec 继续严格读取 v1～v3：

- v3 accepted execution 仍按冻结的业务原名传输名重放，不被新规则追溯改写；
- v4 新 execution 冻结 `fileName` 传输候选、摘要和 Markdown/PDF 两种派生名；
- 未知字段、缺失字段、任务身份或派生名被篡改时继续失败关闭；
- 新旧 Schema 使用同一公开请求、响应、Progress 和 Callback 合同。

### 9.3 安全与回归边界

- 武器谱的重复入库名拒绝逻辑保持不变，继续作为脏数据最后防线；
- 新增同主干、完全同名业务原文件使用不同 `fileName` 时生成不同传输名的领域回归；
- 新增 Analysis 命名结果直接打开武器谱双文档检索范围的跨模块回归；
- `fileName` 作为真实 multipart 候选接受与业务原名相同的路径、控制字符、Windows
  保留名和 255 UTF-8 字节边界校验；错误准确归因到 `fileName`；
- 本修复不运行 `run.py`，不修改外部服务或生产数据。受控真实 Provider 复验和生产发布
  仍属于独立发布门禁。
