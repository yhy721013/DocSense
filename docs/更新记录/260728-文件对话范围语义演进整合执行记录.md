# 文件对话范围语义演进整合执行记录

## 1. 整合说明

本文整合“首次空 `fileNames` 自动全量”和后续“Requested/Active/Effective Scope 分离”两个连续专项的阶段 0～7 执行记录。后一个专项修正并取代前一个专项的部分范围语义，因此按时间分开阅读容易把中间状态误认为当前状态。

- 当前结论：以 Requested Scope、Active Scope、Effective Scope 和 Workspace 累计绑定分离后的语义为准。
- 公开契约：两个专项均未增删请求参数、响应字段、Header 或 SSE 事件结构；本次整合不修改接口文档。
- 证据边界：Windows、SQLite 单实例、Fake/临时数据库离线验证，不代表多实例或真实模型容量。

## 2. 第一轮：首次空数组自动全量

### 2.1 目标与实现

1. 新会话第一次以 `fileNames=[]` 受理时，从知识库读取一次稳定、完整的文件目录快照。
2. 显式范围与首次默认候选使用互斥的不可变 DTO；坏记录、重复身份、冲突或超限整体失败关闭。
3. `session_created`、候选选择、run input 和 pending user message 在同一 SQLite 事务中提交。
4. 自动与显式文件共用执行、attach、binding、lease、流式回答和本地历史链。
5. 受理后的目录变化不修改当前 run；同一会话后续空数组不重新扫描和自动吸收新文件。

### 2.2 阶段结果

| 阶段 | 结果 |
| --- | --- |
| 0～2 | 冻结黄金合同、目录 Resolver、候选 Schema 和已有 session 快速路径。 |
| 3 | 原子选择接入公开受理；同会话 50 并发只有一个首次 accepted。 |
| 4～5 | 验收执行/绑定/历史等价，统一路由日志和 Debug 权威来源。 |
| 6～7 | 修复 SQLite busy timeout 和受理后日志误报，完成关闭验收。 |

关闭时完成 175 项 Chat、67 项契约/网关/容器/架构及安全全仓动态发现 1,847、排除 13、执行 1,834 项；失败和错误为 0。

### 2.3 为什么继续演进

第一轮把“首次默认全量”冻结为不可变快照，但 Workspace 累计绑定、调用方本轮显式选择、模型本轮有效范围和历史展示之间仍容易混淆。尤其在后续显式选择、空数组复用和知识库新增文件时，需要持久、可审计的范围状态机。

## 3. 第二轮：请求范围与活动范围分离

### 3.1 最终术语

| 术语 | 含义 |
| --- | --- |
| Requested Scope | 调用方本轮显式提交的文件集合；空数组保持空，用于历史投影。 |
| Active Scope | 会话最后一次原子 accepted 的持久范围 Head。 |
| Effective Scope | 当前 run 实际传给模型的冻结范围。 |
| Workspace Binding | 为复用和资源管理累计绑定的远端集合，不得直接替代 Effective Scope。 |

### 3.2 最终状态机

1. 新会话首次空数组：以一次目录快照形成初始 Active/Effective Scope；Requested Scope 仍为空。
2. 任意轮次非空数组：整个显式集合原子替换 Active Scope，并成为本轮 Effective Scope，不是增量追加。
3. 后续空数组：复用最后 accepted 的 Active Scope 作为 Effective Scope，不重新扫描知识库。
4. 非空请求一旦原子 accepted，即使随后模型执行失败，新 Scope Head 仍是权威状态。
5. Workspace 可保留历史累计绑定，但模型调用必须显式使用当前 Effective Scope，不能扩大到 Workspace 全部文档。
6. History 只投影 Requested Scope；不得把自动全量或累计绑定的内部文件列表泄漏为调用方显式选择。

### 3.3 数据与事务

- SQLite Schema v4 保存 Scope Revision、Member、Head 和 requested/effective run input。
- Head 使用 CAS；Revision 和 Member 不可变，并由完整性触发器约束会话、run 和范围身份。
- Scope Head、run input、pending message 在同一 `BEGIN IMMEDIATE` 事务提交；超限、坏 Codec 或故障注入全量回滚。
- Worker 只凭 run_id 恢复 requested/effective，不读取当前目录重新计算。

### 3.4 阶段结果

| 阶段 | 结果 |
| --- | --- |
| 0～1 | 冻结状态机黄金资产，建立 Scope DTO、严格 Codec 和纯规则。 |
| 2～3 | 落地 Schema v4/Repository/CAS，并接入原子受理状态机。 |
| 4～5 | 切换执行、绑定、恢复、History、日志与 Debug 语义。 |
| 6～7 | 精确清理开发 Chat DB、空库重建 v1～v4，完成接口文档同步和关闭验收。 |

最终完成 204 项 Chat、70 项契约/网关/容器/架构，并在安全全仓动态发现 1,879 项后精确排除 13 项、执行 1,866 项，全部通过。

## 4. 关键不变量

- 目录 Resolver 只在首次默认选择前执行一次；运行和恢复阶段禁止动态扩张范围。
- Requested、Active、Effective 和 Binding 不互相替代；任何缺失、错会话、坏成员或坏 JSON 均失败关闭。
- 文件数量限制按最终候选整体校验，不截断前 N 个文件。
- 日志只记录选择模式、会话/run 标识和脱敏计数，不输出文件名、远端引用或正文。
- Debug 页面是本地诊断投影，不是业务权威来源；生产环境仍需网络层限制。

## 5. 当前边界

- 当前证据是 SQLite 单实例下的事务隔离，不证明多个进程/实例同时更新 Scope Head 的生产一致性。
- Workspace 远端文档被人工删除时必须失败关闭并保留恢复证据，不能自动替换或扩大范围。
- 可靠队列、跨实例会话锁、共享数据库和容量压测仍属后续阶段。
