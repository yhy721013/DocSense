## 2. 最终审计修复

阶段 7 审计发现：`SynchronousChatRunExecutor.prepare_chat_run()` 在事务已经原子受理并
持久化 run 后，会再次读取 run input，仅用于记录有效文件数量。如果这次可观测性读取异常，
旧实现会向路由抛出错误，使客户端收到 HTTP 500，但 accepted 事实已经存在；调用方重试时
还可能遇到活动运行冲突，形成误导性的失败语义。

现已调整为：

1. accepted 事实仍以 `start_chat_run()` 的事务结果为唯一权威；
2. 日志计数读取失败时记录带 `run_id`、`chat_id` 的异常日志，并把计数标记为 `unknown`；
3. 不回滚、不重放、不改变已受理运行，也不把纯可观测性故障升级为公开接口失败；
4. 新增故障注入用例，证明读取异常后 run input 仍完整，且既有 `chatInfo`、`textChunk`、
   `done` SSE 链可以正常完成。

该修复只收紧内部可靠性边界，不改变公开请求或响应契约。

## 4. 完成定义复核

- 首次空数组由 Chat 受理事务内实际插入 session 的结果唯一判定；
- 全量目录单次读取、严格校验、稳定排序，并冻结到 run input 与 pending user；
- 上限、同名、重复远端身份、坏记录和并发失败不留下部分本地事实或远端调用；
- 后续空数组不重新扫描，也不动态扩张已有会话范围；
- 自动与显式文件共用 Port、资源租约、attach、binding、模型流和本地历史链；
- 首轮历史展示自动选择文件对应的原始文件名；
- HTTP、JSON、SSE、Header、状态码和 `chatId` 契约零变化；
- 日志、调试页、README、接口文档、重构记录和更新记录已与最终代码同步；
- 证据明确限定为 Fake/临时 SQLite 单实例离线环境。

## 5. 回滚

如需回退首次空数组自动全量语义：

1. 必须把候选 DTO、目录解析、Coordinator 事务选择和公开路由接线作为一个完整语义单元回退，
   避免只回退一层造成受理与执行范围不一致；
2. 已持久化的 run input、pending/committed message files、binding revision 和资源租约均属于
   已提交业务事实，不删除、不回写；
3. 已自动绑定文件的会话在回退后继续通过 current heads 引用既有绑定；
4. 接口文档必须与代码在同一次变更中恢复旧语义；
5. 不通过清库、删除 Workspace、批量解绑或删除远端文档伪造回滚；
6. 30 秒 SQLite busy timeout 是独立的并发可靠性修复，如需调整应以容量数据为依据，不应与
   首次空数组业务语义绑定回退。
