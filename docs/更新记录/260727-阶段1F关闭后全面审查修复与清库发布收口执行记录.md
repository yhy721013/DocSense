## 2. 已确认的接口合同

1. file 回调进入 `outcome_unknown` 后，普通 Worker、Dispatcher 维护扫描和后台恢复仍不得自动补发。
2. 新的一次 `/llm/check-task` 请求表示调用方明确接受 at-least-once 语义，可为当前 latest
   execution 补发一次；如果补发结果仍未知，后续新的 check-task 请求仍可再次明确补发。
3. 由于旧 HTTP 请求可能已经到达接收方，上述流程可能产生重复业务回调。接收方必须按
   `fileName` 和业务结果幂等处理。
4. 同一 check-task 请求中，规范化后重复的 fileName 只处理首次出现项，避免同一请求制造两次尝试。
5. report 和 weaponry 的 `outcome_unknown` 规则不随本次修改变化，仍按各自既有合同冻结或人工处置。

## 3. 代码修复

### 3.1 Callback Guard 与投影一致性

- 为 file check-task 增加仅限内部使用的 unknown 显式补发授权。
- 获取发送权时同时校验 latest execution、latest 公开任务投影、attempt、Guard owner 和
  `outcome_unknown` 状态，并以 SQLite 条件更新推进 fencing token。
- 过期 `sending` 不直接被后台接管：本次恢复先冻结为 `outcome_unknown`，由后续新的
  check-task 明确授权补发。
- 完成回调时，Guard、execution 和 latest 公开投影必须在同一事务内共同收敛；投影缺失或条件更新
  失败时整体回滚，禁止只把内部事实写成已完成。

### 3.2 毒快照、资源统计与请求内去重

- accepted execution 的持久快照损坏时，专用毒任务终态现在返回 execution 身份，并继续调用统一
  Callback Recovery；回调异常只记录日志，不把已终态任务重新放回执行退避。
- 资源扫描批次显式携带“解码隔离”和“待恢复失败”数量，`scanned/cleaned/quarantined` 指标不再漏算
  无法解码的资源记录。
- file check-task 按规范化业务键稳定去重并保留首次出现顺序，同时记录重复数量。

### 3.3 Dispatcher 致命故障

- 通用持久 Dispatcher 增加可注入的进程级致命故障处理器。
- Analysis 生产组合根在 Worker 主循环或 execution limiter 释放出现不可恢复异常时，先记录
  `CRITICAL`，再向当前进程发送 `SIGTERM`，使外部进程监管按既有重启策略恢复持久 accepted 任务。
- 离线测试只注入替身处理器验证“一次通知、readiness 关闭”，不会真的终止测试进程。

### 3.4 清库发布可靠性

- `clean.py` 禁止把文件系统根目录或项目根目录识别为运行时删除目标。
- 除运行时目录外，显式删除任务库、知识库和文件对话库兼容覆盖路径对应的 SQLite 主文件、
  WAL 和 SHM。
- 运行时目录或数据库文件在重试后仍无法删除时以异常和非零退出收敛，不再把被占用或权限失败
  伪装成清理成功。

## 4. 当前发布制度

当前约定是每次代码更新均停服并由 `clean.py` 清空重建数据库，因此
`scripts/inspect_analysis_cutover.py` 不再是每次空库发布的重复强制门禁。标准顺序为：

1. 停止 DocSense 进程，避免 SQLite 句柄继续写入；
2. 独立运行 `python clean.py`，且仅在退出码为零时继续；
3. 启动新版本并由新进程重建空库。

只读预检脚本继续保留，并在保留存量数据库、从备份恢复、清理结果存疑或未来改变发布制度时使用。
它仍是诊断与存量切换工具，不会自动修改数据库，也不能被“新旧链路在线双跑”替代。
