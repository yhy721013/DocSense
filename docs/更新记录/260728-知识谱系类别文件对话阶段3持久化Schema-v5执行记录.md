# 知识谱系类别文件对话阶段 3 持久化 Schema v5 执行记录

## 1. 阶段范围

本阶段只落地 Chat SQLite 的会话范围绑定、architecture 范围版本和运行输入持久化事实，
尚未修改 Coordinator、公开路由、历史投影或远端 AnythingLLM 调用。

## 2. Schema v5 与迁移

- 新增 `chat_session_scope_bindings`，以 `chat_id` 唯一绑定 `files` 或 `architecture` 模式；
- architecture 模式必须保存唯一的规范正整数 `architecture_id`，files 模式禁止保存该值；
- Schema v4 既有会话全部回填为 files 模式，不改变既有消息、运行、Scope Revision 或 Head；
- `chat_scope_revisions` 新增 `source_architecture_id`，仅 architecture 首次快照可以保存；
- `chat_run_inputs` 新增 `requested_architecture_id`，并以触发器校验运行、绑定、选择模式和
  Scope Revision 均归属于同一个 chat；
- `chat_messages` 新增 `architecture_id`，用户 architecture 消息必须保存绑定 ID 且禁止
  `files`，assistant 消息两者均不保存；
- binding、Scope Revision 及消息选择器均不可更新；同一 architecture 会话只允许一个
  architecture Scope Revision，防止后续轮次重建快照。

迁移入口在存在待应用版本时显式执行 `BEGIN IMMEDIATE`。故障注入测试曾发现仅依赖 Python
SQLite 隐式事务时，迁移首条 DDL 可能在后续错误前已持久化；显式事务后，版本记录、DDL、
回填与完整性门禁可以统一提交或统一回滚。

## 3. Repository 与 Codec

- 新增 `ChatSessionScopeBindingRepository`，只提供创建和读取，不提供更新；
- `ChatScopeRepository` 严格往返 `source_architecture_id`；
- `ChatRunInputRepository` 严格恢复 `requested_architecture_id`，拒绝与 selection mode 不一致
  的损坏行；
- `ChatMessageRepository` 按消息角色和会话模式校验 `files`/`architecture_id`，加载时再次
  校验持久化身份；
- `ChatStore` 暴露 binding repository，供下一阶段在原子受理事务中装配。

## 4. 测试与门禁

- Scope Repository 定向：14 项通过，0 失败、0 错误；
- Persistence/Container 扩大回归：86 项通过，0 失败、0 错误；
- Chat 动态发现：232 项通过，0 失败、0 错误；
- `compileall` 与 `git diff --check` 通过。

测试覆盖真实 Schema v4 fixture 到 v5 的逐行保留、重复迁移幂等、`foreign_key_check`、
DDL 后故障全量回滚、恢复后重新迁移、binding 不可变性、运行输入/消息组合门禁、错误
chat 归属以及 50 个不同会话的持久化隔离。

全部测试使用临时 SQLite 和 Mock/Fake，未执行 `run.py`，未连接真实服务。

## 5. 门禁结论

阶段 3 验收通过，可以进入阶段 4。当前没有新增待商讨事项；新建会话的 binding 尚未由
生产 Coordinator 创建，因此公开路由仍保持原行为，阶段 4 将在同一 `BEGIN IMMEDIATE`
受理事务中完成创建、校验和快照写入。

回滚点为 Schema v5 迁移、Repository/Codec 扩展及对应测试。证据仅适用于 Windows、临时
SQLite 与单实例离线环境，不代表多实例生产一致性已经完成。
