# 阶段 2-4 Report 试点实施记录

## 1. 实施范围

本记录对应阶段 2-4 第 1～8 步。公开 `/llm/generate-report`、`/llm/check-task`、Progress 与 Callback
合同均未修改；未增删接口参数、字段、Headers、状态码或路由。实施未运行 `run.py`，只使用项目
虚拟环境、临时 SQLite、Fake 和定向离线测试。

## 2. 已完成内容

1. 建立完整 Callback Delivery Port、SQLite Control Store、租约/fencing/unknown/人工解除契约；
2. 冻结 Report Input v2、Execution Profile、Step 与 Recovery Registry；
3. 迁移 Report Runtime Config、下载与模板处理、资源 Store、交互审计身份校验；
4. 将 Callback JSON 迁到共享 Observability History Writer，保持原路径与非权威语义；
5. 实现 Authority-aware `RunReportV2Workflow`、RAG Step Hook 与 Report 组合 UoW；
6. 在 `app/container.py` 一次切换 Report Submit、Execution Runtime/Dispatcher、Progress、终态、
   Callback Control 与 check-task 读取路径；
7. 将 Callback Guard 冻结与资源恢复作为两个独立 Job 接入专用 Store 的周期维护链，业务 Worker
   终态后只发送可丢唤醒提示，不再同步等待资源清理；
8. 删除 `LLMTaskService` 中零生产调用方的 Report 专属 Task/资源 DDL 与读写入口，清理共享审计
   委托后的不可达 SQL，并以永久门禁防止旧控制面复活。

## 3. 第 6 步控制面边界

- Report 新受理只写 `task-control-v2.sqlite3`，输入固定为 `ReportInputSnapshot/v2`；
- `LocalTaskExecutor` 以持久扫描为恢复真相，内存唤醒仅作为可丢提示；
- `TaskExecutionRuntime` 显式传递 task_id、attempt_no、lease_token、fencing_token、lease_expires_at；
- Report Step、Progress 与 terminal 条件写均使用同一 Authority Session；
- terminal、latest、result_ref 与 Callback eligibility 在同一 SQLite 事务提交；
- Callback HTTP、History、资源清理和审计外部 I/O 均在控制事务外；
- Worker 与显式 check-task 共用同一个 v2 Callback Guard；
- Report check-task/Progress 读取 v2，Analysis/Weaponry 在各自迁移前继续读取旧库；
- 旧 `LLMTaskService` 不再接收 Report Task/Callback/资源写入，未建立双写或旧 Runner 补权入口。

成功 Callback 的 HTML 不复制到根 Task 表，而是从 Report 资源记录持有的最终 Artifact 恢复；读取时
复核类别、任务命名空间、大小、SHA-256 与 UTF-8。失败 Callback 继续使用空 details。上述变化只在
内部保存方式发生，不改变公开 Callback payload。

v2 首次创建仍要求旧库无阻塞事实；v2 已发布后的重启只验证新库 Schema/组件身份，避免未迁移业务
在旧库的合法活动任务阻断 Report 重启。该路径不迁移旧行、不修复旧库，也不从旧库补 Authority。

第 6 步全仓回归还修正了两类内部一致性问题：按旧 TaskId 读取非 latest execution 时，Callback
attempt 现在从该 execution 的追加审计事件恢复，不会因同业务键产生新任务而错误回落为 0；Report
Step Registry、恢复矩阵、业务组合 UoW 与 Artifact 终态摘要算法归位到 Application 层，Port 只保留
抽象 DTO/协议，Domain 不再跨模块依赖 Tasks Domain。上述修正均未改变公开字段或 Callback 语义。

## 4. 第 7 步独立维护边界

- Callback Guard 与资源恢复保持两套专用 Store/状态机，只共享一个本地维护调度线程；
- 启动即扫描并持续周期扫描，Event 只合并唤醒且不携带 TaskId 或写权限；
- Callback Job 只冻结过期 `sending`，不发送 HTTP、不自动重发 unknown；
- 资源 Job 只做有界持久扫描，终态 Worker 不等待外部 DELETE；
- 两个 Job 分别隔离暂态故障并记录计数，一方失败不跳过另一方和后续周期；
- Dispatcher readiness 同时覆盖 Executor 与维护线程，停机共享总 deadline 并各自尽力收敛；
- 容器现有启动/停止入口、旧 Runner Authority 传递与公开 Callback 语义均未改变。

## 5. 离线证据边界

定向验证覆盖 v2 单写受理、只读路由、Callback acquire/validate/complete、Schema 重开门禁、Runner
全部 Step、Authority Runtime、依赖容器兼容、架构边界与编译。测试中的预期故障注入日志不代表
测试失败。第 7 步新增定向验收覆盖临时 SQLite 空队列、Fake 双 Job、启动/周期/合并唤醒、故障隔离、
终态异步维护和有限停机。第 8 步新增源码 AST、机器契约、临时 SQLite 历史表保留、v2 Resource Store
并发 CAS/重开恢复，以及 Analysis/Weaponry 共享能力回归门禁。最终执行
`python -B -m unittest discover -s tests -p "test_*.py" -b` 两轮：每轮发现并执行 2400 项，失败 0、
错误 0、跳过 13，Python 退出码均为 0；另通过 `compileall`、`git diff --check` 与公开接口文档哈希
门禁。

这些结果仅证明当前 Windows/SQLite/单进程协议实现；不能证明真实 AnythingLLM/文档转换/Callback
服务、可靠队列、多实例、共享数据库一致性、高并发容量、生产吞吐或 exactly-once。

## 6. 第 8 步旧 SQL 收口边界

- 删除 Report 专属 `create_report_task` 和六个旧资源原始入口；
- 删除 `LLMTaskService` 对 `report_resource_records` 的 DDL、索引和列迁移所有权；
- 既有旧表不执行 `DROP`、清空或内容迁移，历史数据仍可供部署预检和人工核查；
- 交互审计写兼容入口只委托共享 `LLMInteractionStore`，删除返回后的不可达 SQL；
- 删除零生产调用的单条交互写入和 cleanup 更新入口；
- 保留 Analysis/Weaponry 通用 Callback Guard、Analysis 批次/资源记录、共享审计 Schema 与读取能力；
- 旧 Report 投影仅由测试夹具构造，生产模块不得导入该夹具或恢复旧入口；
- 本步骤未修改 `app/container.py`、公开接口、Callback 语义或生产启动策略。

## 7. 阶段结论与后续

阶段 2-4 的 Report 试点自 v2 受理、完整 Authority Runtime、业务 Step/UoW、Callback Control、资源维护
到旧 SQL 收口已经形成单一控制面闭环。后续进入阶段 2-5 前，应以本阶段机器契约和所有权矩阵为基线，
不得复制 Report 业务规则到 Tasks 内核，也不得以本地线程和 SQLite 证据宣称可靠队列、多实例或
生产容量已经成立。
