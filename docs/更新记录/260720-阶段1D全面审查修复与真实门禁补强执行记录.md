## 2. 真实来源身份修复

实际 AnythingLLM `vector-search` 候选携带分数，但来源结构不是冻结的
`custom-documents/<生成名>.json`：其结构化 `url` 为
`file://.../hotdir/<入库文件名>`。旧 Adapter 只信任完整 location/provider ID，导致 8 条真实
Candidate 全部无法映射，字段随后按兼容策略降级为空。

修复后的来源规则按强度组合并检测冲突：

1. `location/docpath/sourceDocument/url` 与冻结完整 location 规范化后精确相等；
2. provider `docId/documentId/source.id` 与任务打开时核验的供应商 ID 精确相等；
3. 仅对结构化 `url`，其完整末段与受理快照的 `ingested_file_name` 精确相等，且该入库名在
   当前任务文档范围内唯一。

title、业务 `original_name`、展示型 `document_ref`、子串和模糊名称仍禁止参与身份判断。多个
权威字段指向不同文档，或两个冻结文档具有相同入库文件名时，在模型抽取前明确失败。只读真实
复核从修复前 `0/8` 变为修复后 `8/8`，8 条候选均携带合法 score；探测不输出名称、正文或密钥，
也未修改远端资源。

## 3. 公平共享限流

Report、Weaponry 与迁移期 analysis 继续共用同一个进程内重型许可，但实现由无法保证唤醒顺序的
`BoundedSemaphore` 改为 Condition + 单调 ticket 的严格 FIFO 队列。已有等待者不会被刚归还许可的
业务反复抢占；停机取消和异常都会原子移除 ticket，避免幽灵等待者阻塞队首；重复 release 仍明确
拒绝。该改动只影响内部执行顺序，不改变积压上限或公开契约。

## 4. production attestation v2

旧证明只读取自声明布尔值，无法证明真实联调发生过。当前唯一 Schema
`docsense.weaponry.production-readiness.v2` 内嵌并摘要绑定五类脱敏证据：score/rank、来源身份、
空 workspace、Provided-Evidence 无文档/无来源隔离、临时资源清理。证明包含带时区
`verifiedAt/expiresAt`，默认有效 24 小时、最长 7 天；篡改、未来时间、过期、profile/四类指纹
漂移或非标准 JSON 均关闭门禁。

`scripts/verify_weaponry_production_readiness.py` 使用两个随机命名临时 workspace 和一个 thread：
只把一份既有全局文档绑定到临时检索范围，不修改既有 workspace/文档；最终必须精确恢复执行前
全量 workspace/文档快照。证明文件先写同目录临时文件，再用 `os.replace` 原子替换。

Docker 示例启用 `DOCSENSE_WEAPONRY_REQUIRE_PRODUCTION_GATE=true`。该模式下证明缺失或无效会在
公开路由和后台线程启动前 fail-fast；开发环境默认仍可构造，但 readiness 明确为 false。
`scripts/check_weaponry_production_gate.py` 会加载根 `.env` 并输出稳定、无凭据的机器 JSON。

## 5. 人工处置闭环

新增 `scripts/manage_weaponry_operations.py`，不新增管理 HTTP 接口：

- `release-callback`：只有显式确认旧 Worker 已停止/隔离时，才可解除 weaponry 业务键的
  callback outcome-unknown 提交冻结；复用已有 Guard 事务与追加式解除审计；
- `resolve-resources`：只有显式确认供应商端状态，且 execution 非 accepted/running 时，才可把
  quarantined 资源转回 `cleanup_pending`，或在确认全部远端资源不存在后转为 `cleaned`；
- `inspect-resources`：只输出资源状态、owned 数量、错误和人工审计，不输出外部引用、幂等键、
  文档正文或凭据。

新增 `weaponry_resource_operator_audits` 追加表，保存前后版本、动作、操作者、原因、时间和原隔离
错误码。禁止直接写 SQLite 绕过 CAS、活跃 execution 和 fencing 检查。

## 7. 尚未关闭与后续边界

1. 四类真实能力指纹（provider、embedding、document processing、extraction model）仍需负责人
   冻结；在此之前不生成或伪造 production attestation。
2. 进程崩溃遗留的 `running` execution 继续只观察告警。安全接管需要阶段 2 的 Attempt、heartbeat、
   execution lease、fencing、checkpoint 和 Reaper；不能在 1D 用任务年龄直接执行
   `running -> accepted`，否则旧 Worker 可能继续写结果或产生重复外部副作用。
3. 当前严格 FIFO 只解决单进程共享重型许可公平性；阶段 2～6 仍需在统一任务内核、MySQL 和
   RabbitMQ 上建立跨进程公平、可靠领取、late ACK、重试与 DLQ。
4. `docker/.env.docker` 存在非占位 AnythingLLM API Key 的风险。该凭据必须在部署前轮换并迁入
   Compose secret/宿主机受控环境，不能仅依赖从当前文件删除来消除 Git 历史泄漏。
