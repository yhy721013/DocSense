# 知识谱系类别文件对话阶段 6 并发、恢复与安全全仓执行记录

## 1. 阶段范围

本阶段不再扩展公开合同，而是对已经切换的 architecture 类别对话生产链执行恢复、并发、
故障关闭、范围隔离和日志安全验收。全部验证使用项目 `venv`、临时 SQLite 与离线 Fake，
未执行 `run.py`，未连接真实 AnythingLLM、模型、知识库或其他后台服务。

## 2. 恢复与范围隔离

- architecture 首轮受理后重建 Store、Command 与 Executor，新的 Worker 仅凭 `run_id`
  从 SQLite 恢复类别 ID 与 Effective Scope；
- 重建后的 Resolver 被设置为“一旦调用立即失败”，实际执行仍成功，证明 Worker 不按当前
  类别目录重新解析文件；
- 已有 Binding 的同 ID 续聊继续跳过目录查询，即使类别当前为空或内容已经变化也复用旧 Head；
- 在 Fake 远端 Workspace 中额外挂入不属于 Scope Revision 的文档后，模型调用仍只携带
  已冻结文档引用，远端累计状态不能扩大 RAG 范围；
- Binding、Revision、Run Input 与 Message 的缺失、错配和跨会话污染继续由 Schema v5
  触发器、严格 Codec 与应用层 fail-closed 门禁共同拒绝。

## 3. 并发矩阵

新增并通过以下 50 线程 Barrier 场景：

1. 同一 chatId、同一 architectureId：仅 1 个 accepted，其余 49 个 busy，只创建一个
   Binding、Scope Revision 与 Head；
2. 同一 chatId、两个 architectureId 各 25 个请求：仅 1 个 accepted，胜方同 ID 的其余
   24 个 busy，败方 ID 的 25 个请求均为 ID conflict，不留下败方消息或 Revision；
3. 同一 chatId、files/architecture 各 25 个请求：仅 1 个 accepted，胜方同模式的其余
   24 个 busy，败方模式的 25 个请求均为 mode conflict；
4. 50 个不同 chatId、同一 architectureId：50 个请求全部独立 accepted，每个会话各自
   持有 Binding、Revision、Run Input 和 pending Message，没有串写或 SQLite lock error。

这些结果证明当前 SQLite 单实例进程内受理事务的隔离，不代表多实例共享队列、跨数据库事务
或生产容量已经完成。

## 4. 日志安全修正

检查完整 architecture 执行链时发现，通用资源租约日志会输出原始 `lease_id`，而文档绑定
租约主键包含业务文件名。持久化主键及幂等规则保持不变，仅把日志关联值改为固定长度
SHA-256 `lease_token`，使同一租约仍可跨日志关联，同时不泄漏文件名、document ref 或供应商
位置。

新增整链日志测试，明确禁止实际文件名、文档引用、外部位置和用户消息正文出现在
`app.services.chat` INFO 日志中；日志仍保留 chat/run 审计键、architecture ID、候选数量、
selection mode 和资源类型。
