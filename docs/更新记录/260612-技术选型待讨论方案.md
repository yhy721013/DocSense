# DocSense 企业级基础设施与治理待讨论方案

## 1. 文档定位

本文档用于汇总 DocSense 在企业级基础设施、任务执行、安全和运维治理方面的候选方案，作为后续讨论基础。

本文档中的内容均来自此前讨论，但相关工具和实施方式尚未最终确定。除 RAGFlow 自身必需的基础设施外，本文档提到的 RabbitMQ、Celery、DocSense Redis、Nginx、ClamAV、Prometheus、Grafana、Alertmanager 和 OpenTelemetry 等组件，均不代表已经完成选型。

---

## 2. 待解决的问题

在核心技术替换之外，DocSense 仍需要进一步解决：

- 长任务如何可靠排队、执行、重试和恢复。
- 如何替代 API 进程内无限创建的 daemon 线程。
- 如何分别控制下载、解析、翻译、抽取、报告生成和回调的并发量。
- 多进程部署后如何提供实时进度。
- 如何安全处理大文件下载和外部 URL。
- 如何实现接口认证、回调安全和内部服务隔离。
- 如何建立监控、告警、备份和恢复能力。
- 在只有一台服务器的条件下，如何合理隔离组件并控制故障影响。

## 3. 文件下载与大文件处理

### 3.1 当前下载方式的问题

当前下载逻辑使用同步 HTTP 请求，并将完整响应一次性加载到内存后写入文件。

主要风险包括：

- 大文件会占用大量内存。
- 无法根据实际流式字节数强制限制文件大小。
- 相同文件名可能相互覆盖。
- 没有统一的文件哈希校验。
- 没有统一验证扩展名、MIME 和真实文件类型。
- 没有统一恶意文件检查。
- 缺少可靠清理机制。
- 接受外部传入任意 URL，存在 SSRF 风险。

`MAX_CONTENT_LENGTH` 只能限制客户端上传到 DocSense 的请求体，不能限制 DocSense 主动下载外部文件。

### 3.2 候选文件流程

优先考虑：

1. 上游系统通过 MinIO 预签名 URL 直接上传文件。
2. DocSense 只接收对象 Key 和 SHA-256。
3. DocSense 创建持久化任务。
4. 独立的文件处理流程从 MinIO 获取文件并进行处理。
5. DocSense 通过 RAGFlow API 提交文档。

如果必须通过 URL 下载：

1. 使用独立的下载执行流程进行流式下载。
2. 校验 URL 协议、域名、DNS 解析结果和每次重定向。
3. 禁止访问内网 IP、环回地址、链路本地地址和云元数据地址。
4. 按流式读取的实际字节数限制文件大小。
5. 校验扩展名、MIME 和文件 Magic。
6. 对不可信文件执行恶意文件检查。
7. 限制压缩包展开大小。
8. 上传至独立的 DocSense 暂存 Bucket。
9. 使用生命周期规则自动清理临时文件。

DocSense 不应直接写入 RAGFlow 内部对象存储 Bucket。

可进一步讨论使用 ClamAV 扫描不可信文件，但是否引入尚未确定。

## 4. API 与安全要求

### 4.1 API 入口

生产环境不应直接暴露 Flask 或 Uvicorn 端口，应通过统一入口访问 DocSense。

统一入口需要承担：

- TLS 终止。
- 请求体大小限制。
- 连接数限制。
- 请求限流。
- WebSocket 和 SSE 代理。
- 隐藏内部服务端口。

Nginx 是此前讨论过的候选方案，但尚未最终确定。

### 4.2 接口认证与回调安全

上线前需要考虑：

- `/llm/*` 使用 API Key、HMAC 签名或 mTLS 认证。
- 请求包含时间戳、随机数和幂等键，防止重放。
- 出站回调使用 HMAC 签名。
- 限制允许回调的目标地址。
- 为不同服务使用独立账号和最小权限。

### 4.3 内部服务隔离

只有统一 API 入口应暴露给外部网络。

以下服务只允许通过内部网络访问：

- MySQL。
- MinIO。
- RAGFlow。
- Elasticsearch。
- vLLM。
- 后续可能引入的任务调度、缓存和实时通知组件。

### 4.4 调试接口与配置安全

生产环境需要：

- 关闭 `APP_DEBUG`。
- 禁用所有 `/debug/*` 路由。
- 不在生产环境公开回调预览和会话调试数据。
- 使用 Docker Secrets 或只读密钥文件注入密钥。
- 不将实际密钥提交到 `.env` 或代码仓库。
- 固定镜像版本或镜像 Digest，不使用 `latest`。

### 4.5 容器与文档内容安全

容器应使用非 root 用户运行，设置 CPU 和内存限制，尽可能使用只读文件系统，仅挂载必要目录，并为每个服务使用独立账号和最小权限。

所有文档内容都应视为不可信输入。需要防止文档中的提示注入影响模型调用、工具调用或导致其他文档数据泄露。业务检索和对话必须严格限制允许访问的文档范围。

## 5. 长任务调度与可靠执行候选方案

### 5.1 当前后台线程模型的问题

当前 API 收到文件分析、报告生成或知识谱系任务后，直接启动 daemon 线程。

这一模式存在以下问题：

- API 进程退出时，daemon 线程会立即终止。
- 请求数量可以直接转化为无限线程数量。
- 无法限制不同任务类型的并发量。
- 无法跨进程共享任务状态。
- 无法在进程重启后自动恢复任务。
- 无法形成可靠的任务重试和死任务处理机制。
- 单进程信号量无法扩展到多个进程。

FastAPI 的 BackgroundTasks 同样不适合承担需要可靠执行的长任务。无论最终采用何种工具，FastAPI API 进程都不应继续运行可靠性要求高的后台长任务。

### 5.2 RabbitMQ 与 Celery 候选方案

此前讨论的候选方案是使用 RabbitMQ 作为 DocSense 长任务的可靠消息代理，使用 Celery 执行后台任务。

RabbitMQ 可用于：

- 持久化任务消息。
- 消费确认。
- 执行进程崩溃后的消息重新投递。
- 根据任务类型路由到不同队列。
- 通过消费速度形成背压。

Celery 可用于执行：

- 文件下载。
- 调用 RAGFlow 解析文档。
- 报告生成。
- 知识谱系提取。
- 翻译。
- 结果回调。
- 周期性恢复和清理任务。

如果采用 Celery，可进一步讨论使用 Celery Beat 调度超时任务恢复、临时文件清理、回调重试和定期巡检。Celery Beat 同样属于候选组件，尚未确定。

该方案的主要价值是将 API 与长任务执行解耦，并提供任务排队、确认、重试和并发控制能力；需要进一步评估的方面包括组件数量、单机资源占用、运维复杂度和任务幂等实现成本。

### 5.3 候选队列划分

如果采用任务队列，可以按负载类型拆分：

| 队列 | 主要任务 | 候选并发策略 |
|---|---|---|
| `download` | 文件下载、校验、恶意文件检查 | 中高并发，并限制总带宽 |
| `rag_ingest` | 向 RAGFlow 提交文档并等待解析 | 初期限制为 1 至 2 |
| `llm_extract` | 分类、知识谱系、报告生成 | 根据 GPU 能力限制 |
| `translation` | 文档翻译 | 独立限制 CPU 或 GPU 资源 |
| `callback` | 向上游系统发送回调 | 较高并发、短超时 |
| `maintenance` | 清理、恢复、巡检 | 单执行进程 |

这种方式可以替代当前全局 `Semaphore(1)`，并避免文件解析任务完全阻塞 AI 对话和其他业务。

### 5.4 Celery 可靠性配置候选

此前讨论过的配置方向包括：

- `acks_late`。
- `task_reject_on_worker_lost`。
- `worker_prefetch_multiplier=1`。
- 最大执行时间。
- 指数退避和随机抖动。
- 每个子进程最大任务数和最大内存。
- 优雅关闭。

延迟确认和重新投递可能导致同一个任务被执行多次，因此所有任务步骤必须具备幂等性。

### 5.5 单机 RabbitMQ 的定位

单服务器部署 RabbitMQ 仍然能够解决 API 与任务执行解耦、执行进程崩溃、应用重启、任务排队和消费确认等进程级问题，但不能解决整台服务器故障或磁盘损坏。

因此，即使未来采用 RabbitMQ，也不应在同一台服务器上模拟多节点集群。具备至少三台独立机器后，才有必要讨论 Quorum Queue。

## 6. Redis 候选职责

### 6.1 当前进度管理的问题

当前实时进度由进程内 `LLMProgressHub` 保存。

这意味着：

- 进度只存在于当前 API 进程。
- 进程重启后最新进度丢失。
- 多个 API 进程之间无法共享订阅。
- 某个进程发布的进度，连接到其他进程的客户端无法收到。
- 内存数据结构不能作为可靠任务状态来源。

### 6.2 DocSense Redis 候选用途

此前讨论过为 DocSense 引入独立 Redis，用于：

- WebSocket 和 SSE 实时进度通知。
- API 限流。
- 短期缓存。
- 短生命周期分布式协调。
- 临时幂等键。
- 必要的并发额度控制。

候选模式是由 MySQL 保存最新任务进度，作为事实来源；Redis Pub/Sub 负责实时推送；客户端断线重连后，从 MySQL 查询最新状态。

Redis Pub/Sub 是“至多一次”投递，消息可能丢失，因此不能作为关键任务队列或唯一任务状态来源。

### 6.3 Redis、RabbitMQ 与 MySQL 的候选分工

| 组件 | 候选职责 |
|---|---|
| Redis | 实时进度、缓存、限流、短期协调 |
| RabbitMQ | 可靠长任务投递、确认、重试和背压 |
| MySQL | 任务状态、业务结果和映射关系的事实来源 |

虽然 Celery 可以使用 Redis 作为 Broker，但此前讨论更倾向于对文档下载、文档解析、报告生成和翻译等长时间关键任务使用 RabbitMQ。

如果 DocSense 最终引入 Redis，建议与 RAGFlow 使用的 Redis 进行实例级隔离。Redis 逻辑数据库无法隔离内存、淘汰策略和性能影响。

## 7. 任务持久化与 Outbox 候选设计

无论是否采用 RabbitMQ 和 Celery，MySQL 都应保存任务状态、当前处理阶段、处理进度、执行次数、下一次重试时间、心跳、超时时间、错误信息、业务结果和回调结果。

此前讨论过的候选任务字段包括：

```text
task_id
idempotency_key
status
phase
progress
attempt_count
next_retry_at
lease_owner
lease_expires_at
heartbeat_at
error_code
error_detail
created_at
started_at
finished_at
updated_at
```

如果采用消息代理，可以进一步考虑事务型 Outbox：

1. API 在同一个 MySQL 事务中创建任务和 Outbox 事件。
2. Outbox Dispatcher 读取未发送事件并发布到消息代理。
3. 消息发布成功后，标记 Outbox 已发送。
4. 定时恢复程序重新处理未发送事件和失去心跳的任务。

回调发送也可以采用 Outbox 和独立回调任务，避免业务任务完成后因回调失败而丢失通知。是否采用 Outbox 仍需结合最终任务调度方案确定。

## 8. 线程管理与并发控制

已经确定的原则包括：

- API 层负责认证、参数校验、创建数据库任务并返回 `202 Accepted`。
- 普通外部 HTTP 调用使用共享异步 HTTPX 客户端。
- CPU 密集型解析和翻译不应占用 API 请求执行线程。
- GPU 相关任务需要设置独立并发限制。
- AI 对话流式接口可以直接调用 RAGFlow 或 vLLM。
- 文件下载、解析、翻译、抽取和回调需要分别设置并发额度。

当任务积压、磁盘空间或资源使用超过阈值时，API 应拒绝继续接收任务，并返回 `429` 或 `503`，而不是无限创建线程和接受任务。

长任务调度、跨进程任务执行和实时进度通知的具体组件尚未确定。

## 10. 备份与恢复

单服务器部署的最大风险仍然是整机故障和磁盘损坏。

所有关键备份必须保存到另一台机器、NAS 或远程对象存储，不能只保存在当前服务器。

建议备份范围：

- MySQL：定期完整备份，并保留 Binlog。
- MinIO：备份原始文档、处理结果和必要中间文件。
- Elasticsearch：使用 Snapshot API 备份，不能直接复制数据目录。
- 配置、部署文件和密钥：加密备份。

任务调度和实时通知组件不应保存唯一业务事实。即使相关组件数据丢失，也应能够根据 MySQL 任务记录恢复状态。

备份系统必须定期进行恢复演练，不能只检查备份文件是否存在。

---

## 11. 单服务器部署原则

当前所有组件部署在一台服务器上，因此目标不是实现真正的基础设施高可用，而是：

- 实现进程级故障隔离。
- 实现任务持久化和重试。
- 实现并发控制和背压。
- 实现清晰的职责分离。
- 为未来扩展到多台机器保留路径。

不应在同一台服务器上部署多个 Elasticsearch、RabbitMQ 或 Redis 节点模拟集群。这种部署无法抵御整机和磁盘故障，只会增加资源竞争和运维复杂度。

应重点做好：

- 容器资源限制。
- 磁盘空间监控。
- 服务自动重启。
- 任务幂等。
- 异机备份。
- 恢复演练。

## 12. 推荐迁移顺序

迁移过程需要避免同时替换所有层，建议按照以下顺序推进。该顺序仍需结合本文件中的候选基础设施方案进一步调整。

### 第一阶段：迁移关系型数据库

- 将 SQLite 迁移到 MySQL 8.4 LTS。
- 建立 DocSense 独立数据库和账号。
- 使用 SQLAlchemy 2.x、`asyncmy` 和 Alembic。
- 建立任务、文档、分类映射、会话和回调记录等业务表。
- 将三个 SQLite 文件中的职责统一迁移到 DocSense 数据库。

这一阶段优先解决 SQLite 在多进程、高并发和统一事务方面的限制。

### 第二阶段：替换 RAG 框架与检索存储

- 部署 RAGFlow。
- 部署 Elasticsearch 单节点。
- 部署 RAGFlow 所需的官方依赖组件。
- 建立 RAGFlow 客户端和业务语义抽象。
- 替换 AnythingLLM Workspace、Thread、文档上传和检索逻辑。
- 迁移文档、分类节点和会话映射。
- 使用真实复杂文档验证 RAGFlow 解析能力。
- 验证 MHTML、图片、表格、复杂 PDF 和 DOCX。
- 验证共享 Dataset 或每分类 Dataset 的组织方式。

### 第三阶段：替换模型推理服务

- 将 Ollama 替换为 vLLM。
- 分别部署语言模型和嵌入模型服务。
- 让 RAGFlow 和 DocSense 直接通过 OpenAI 兼容 API 连接 vLLM。
- 根据 GPU 能力设置模型任务并发额度。
- 验证文件处理和 AI 对话同时运行时的吞吐与延迟。

### 第四阶段：替换 Web 框架

- 将 Flask 路由迁移到 FastAPI。
- 使用 Uvicorn。
- 使用 Pydantic 定义请求和响应模型。
- 将同步外部 HTTP 调用迁移至共享 HTTPX 异步客户端。
- 验证 WebSocket、SSE、AI 对话和普通 API 请求。

### 第五阶段：完善任务、文件与安全能力

- 确定长任务调度、跨进程任务执行和实时进度通知方案。
- 移除 API 进程内 daemon 线程和单进程并发控制。
- 将文件暂存统一迁移至 MinIO，并完善流式下载、文件校验和恶意文件检查。
- 增加接口认证、回调签名、内部服务隔离和生产调试接口控制。

### 第六阶段：完善运维治理

- 确定监控、告警和调用链追踪工具。
- 设置各组件资源限制和容量阈值。
- 建立异机备份、任务恢复和恢复演练机制。
- 根据压力测试结果调整各类任务的并发、超时和重试参数。

## 13. 后续需要确定的问题

1. 是否采用 RabbitMQ 和 Celery 作为长任务执行方案，还是选择更轻量或其他方案。
2. Celery 使用 RabbitMQ 或 Redis 作为 Broker 时的收益、复杂度和单机资源占用差异。
3. 是否为 DocSense 单独部署 Redis，以及实时进度、缓存和限流是否需要由同一个 Redis 承担。
4. 是否采用事务型 Outbox，以及任务状态和回调投递需要达到何种一致性要求。
5. 统一 API 入口是否采用 Nginx。
6. 是否引入 ClamAV，以及需要扫描哪些来源和类型的文件。
7. 监控、告警和调用链追踪工具的最终组合。
8. 各类任务的并发额度、超时、重试和准入控制参数。
9. 单服务器各组件的 CPU、内存、GPU 和磁盘资源分配。
