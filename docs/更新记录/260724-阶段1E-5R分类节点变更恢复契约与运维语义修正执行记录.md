## 2. 已修正问题

### 2.1 恢复 workspace 引用绑定

恢复器按持久化 slug 调用 `probe_workspace_reference()` 后，会再次使用 `casefold()` 校验返回
workspace 引用。Adapter 返回另一个 slug 时，流程在成员关系探测和补偿写之前进入
`recovery_required`，不会对无关永久 workspace 执行解绑。

修正前的离线故障注入曾证明错误引用会被继续补偿并最终返回 `compensated`；该场景现在由
`test_reference_probe_returning_another_slug_is_isolated_before_mutation` 永久锁定。

### 2.2 接管、续租和 claim 强契约

1. `take_over_expired_lease()` 和 `renew_lease()` 必须返回
   `ReassignmentLeaseUpdateResult`；`None`、错误 DTO 或非法字段组合均 fail closed。
2. 接管结果必须精确匹配 operation ID、owner、token、递增后的 fencing 和请求过期时间。
3. 接管或续租返回的 preparation claim 必须匹配 operation、owner、token、fencing、目标分类
   和新 lease 过期时间；调用方未持有 claim 时不接受续租凭空返回 claim。
4. 续租后在同一 UoW 重读 Operation，并确认持久化 lease 与返回 lease 完全一致。
5. 接管提交后再次只读 Operation；读取失败、记录消失或 lease 身份漂移时禁止进入远端流程。

### 2.3 读取失败与不存在分流

恢复初始读取现在使用内部强类型结果区分：

- Repository 明确返回 `None`：`operation_not_found`；
- UoW/SQLite 异常或错误返回类型：`recovery_required`。

未来可靠队列不会再因临时数据库故障把恢复任务误判为永久不存在并停止重试。

### 2.4 诊断脚本退出码

`scripts/inspect_reassign_operations.py --apply` 保留 stdout JSON，同时增加稳定进程退出码：

| 恢复结果 | 退出码 |
| --- | --- |
| `recovered_succeeded`、`recovered_failed_no_side_effect`、`compensated` | 0 |
| `operation_not_found` | 3 |
| `takeover_rejected` | 4 |
| `recovery_required` | 5 |
| argparse 参数错误 | 2 |
| 未捕获的诊断/基础设施异常 | 1 |

因此 Shell、CI 和未来运维编排可以仅凭退出码区分“命令已执行”和“Operation 已恢复”。

## 3. 测试与未来计划

新增故障回归覆盖：

1. Reference Probe 返回另一个 workspace slug；
2. 接管 Port 返回 `None`；
3. 接管 DTO 携带其他 Operation 的 lease；
4. 续租 Port 返回 `None`；
5. 初始 Repository 读取异常；
6. 三个已收口结果和三个未收口结果的 CLI 退出码。

1E-6 及后续队列计划同步增加以下硬约束：

- Container、Dispatcher 和 Worker 只能调用 Application Service，不得绕过它直接写恢复终态；
- 1E-6 生产接线前把恢复内部职责拆分为 Observer、Checkpoint Reconciler、Compensator 和
  Finalizer，同时保留 `RecoverReassignmentOperation` 唯一外观和现有状态机语义；
- 任务结果必须保留已收口、未找到、CAS 未接管、仍待恢复和基础设施异常分类，并设置对应
  重试、退避和人工隔离策略；
- 多实例前必须补齐供应商幂等能力或同文档外部副作用串行化。本地 fencing 不能替代
  AnythingLLM 侧并发控制，也不能把顺序成员探测描述为远端原子快照。
