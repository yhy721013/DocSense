# 阶段 1D-3A 供应商无关端口与严格 Fake 执行记录

## 1. 执行结论

阶段 1D-3A 已于 2026-07-18 完成并通过本波次退出门禁。本次补齐了武器谱运行链所需的
Target Evidence Retrieval、Evidence Extraction、Auxiliary Guidance、Translation、Interaction
Audit、Callback、Resource 和 Dispatcher 供应商无关 Port/不可变 DTO，并建立可编程、线程安全、
默认严格失败的测试 Fake。

本波次只冻结“Application 可以依赖什么”和“外部能力必须证明什么”，没有实现或接线任何真实
AnythingLLM、模型、翻译、Callback、数据库资源表或后台 Worker。其完成结论不等于 1D-3B
生产 I/O Adapter 已完成，也不等于 1D-0 production relevance profile 已获批准。

本次边界如下：

- `/llm/weaponry` 仍由遗留路由和执行链处理，新 Port/Fake 没有绑定 Blueprint 或组合根；
- 没有增删、重命名或改变请求、响应、Callback、Progress 的任何公开参数，当前接口行为未改变，
  因此本波次无需修改 `docs/接口文档/`；
- 没有创建或修改数据库 Schema，没有迁移历史数据；
- 没有启动 `run.py`，没有连接 AnythingLLM、模型、甲方 Callback、MySQL、RabbitMQ、Redis、
  MinIO 或其他生产服务，也没有创建后台线程；
- 没有写入 production relevance profile，测试中的 Candidate、分数和指纹均为显式测试事实；
- 1D-3B 与 1D-6 继续受生产入库、可追溯原始来源、代表性多文档语料、Candidate 标注及独立
  relevance profile 门禁阻塞。

## 2. 稳定调用身份与失败分类

新增 `app/modules/weaponry/ports/common.py` 与 `errors.py`，冻结以下规则：

1. 每次外部交互以 `task_id + field_sequence + document_sequence/scope + operation` 生成稳定
   `call_id`；`attempt_no` 单独递增，因此同一逻辑调用重试不改变调用身份，不同 attempt 又不会
   共用审计幂等键；
2. Retrieval/Auxiliary 属于字段范围调用，Extraction/Translation 必须携带来源文档 sequence；
3. 明确失败与结果未知使用稳定枚举区分，Application 不需要识别 requests、AnythingLLM 或其他
   供应商异常类型；
4. 端口异常只携带内部错误码和不含业务正文的诊断消息，审计/调用轨迹不记录 Prompt、文档正文、
   URL 或 Token。

## 3. Retrieval 与 Extraction 类型边界

### 3.1 Target Evidence Retrieval

`TargetEvidenceRetrievalPort` 冻结为三步：打开 execution 独占 scope、字段级召回、幂等关闭。

- 打开 scope 必须携带冻结的 `WeaponryDocumentScope` 与 `EvidenceSelectionPolicy`；空范围不能创建
  外部检索资源；
- `search_target` 只接受领域 `RetrievalQuery`，类型层拒绝 `ExtractionPrompt`；
- 返回值只允许尚未通过纯 Selection 的 `EvidenceCandidate`，不能直接伪装为 Selected Evidence；
- scope 冻结允许文档集合、selection profile、Provider/embedding 指纹，查询不能越过该集合；
- 关闭失败显式返回稳定错误，重复关闭幂等成功，真实资源事实必须另由 Resource Port 持久化。

### 3.2 Evidence Extraction

`EvidenceExtractionPort` 每次只接受一个来源文档及其 `SelectedEvidence`：

- call 的 `document_sequence`、文档快照、所有 Evidence 的 `document_key` 必须一致；
- Prompt 的 `document_key`、字段类型、`evidence_ids` 和完整 `rows` 必须与 Evidence 逐项同序一致；
- 不允许 Candidate、其他文档 Evidence、截断 rows 或重新排序后的 Prompt 进入抽取端口；
- 只接受已冻结的 `provided_evidence_model_v1` 或 `evidence_only_context_v1`，不提供目标文档
  workspace 二次 RAG 或共享父 Thread 的回退类型；
- 非空回答必须为 `matched`，来源 trace 只能引用本次 Evidence ID；额外、缺失、混合或越界来源
  应在 Adapter 边界失败，不能生成合法 `ExtractionAnswer`；
- 原始模型回答只保存 SHA-256 摘要和字符数，业务层只接触清洗后的结果文本与已验证来源轨迹。

上述约束没有对单条 Evidence、全部 Evidence 或单个文档设置数量/字符配额，继续遵守已批准的
Evidence 全量保留口径。

## 4. 可拔除辅助语境与翻译

`AuxiliaryGuidancePort` 不包含术语目录、workspace、环境变量或供应商 DTO。策略为 `none` 时，
结果只能是零片段的 `empty`；严格 Fake 同时断言 Provider I/O 计数严格为零。术语规则开启路径
只表现为通用 `AuxiliaryGuidance`，未来删除功能时无需修改 Retrieval、Extraction 或 Application
核心类型。

`WeaponryTranslationPort` 是来源级调用，缓存或可变状态不得跨 execution 共享。翻译失败稳定
返回空文本和错误码，不升级为字段/任务失败；成功必须返回非空文本且不得携带错误码。

## 5. 原子交互审计

`WeaponryInteractionAuditPort` 冻结为 `reserve -> 外部调用 -> complete`：

1. reserve 前交叉验证规范 `weaponry` 业务键、TaskId、call/attempt、输入摘要、字符数、允许文档
   和来源 marker 摘要；
2. reserve 成功后才允许 Fake 发起 Retrieval、Extraction、Auxiliary 或 Translation 调用；
3. complete 原子收敛 pending，验证 Candidate/Selected 数量和来源 verified/missing/mismatched
   分类总数；成功必须带输出摘要，失败/拒绝必须带稳定错误码；
4. 重复 reserve/complete 返回相同凭据，不制造第二条审计事实；崩溃遗留 pending 可按 TaskId
   有界诊断，不能被解释为业务成功；
5. 严格 Fake 只在 reserve/complete 真正成功后记录调用，避免“操作被拒绝但调用轨迹看似成功”
   的测试假阳性。

## 6. Callback、资源与 Dispatcher 控制面

### 6.1 Callback

`WeaponryCallbackPort` 与恢复来源 Port 冻结：

- acquire 时原子复核 latest TaskId，旧任务直接 `stale`；
- 发送权使用随机 lease token 和单调 fencing token，迟到旧租约不能覆盖新状态；
- 区分成功、甲方拒绝、明确未发送、投递结果未知、跳过和 stale；unknown 必须冻结，不能自动
  二次发送；
- 甲方明确失败只允许由显式 `/llm/check-task` 恢复原因重试；
- 人工解除 unknown 前必须记录操作者、原因，并确认旧 Worker 已停止或隔离；
- 恢复候选同时携带 TaskId、规范 architectureId 和冻结 payload，禁止用同键新任务替换旧 payload。

### 6.2 Resource

`WeaponryResourceStorePort` 冻结任务级资源事实：

- 每项资源明确 `owned` 或 `shared`；shared 来源映射始终 active，任务清理不得删除它；
- workspace/scope、来源会话、Evidence context、绑定、临时文档和映射均有稳定 resource ID 与
  idempotency key，并可绑定 document_key/call_id；
- 所有状态修改使用 expected version CAS；重复登记幂等，不同身份碰撞失败；
- 清理前先把 owned 资源置为 pending，再获取随机 cleanup lease 与单调 fencing token；同一时刻
  只能有一个清理 owner，释放后下一租约 fencing 必须递增；
- 清理按来源会话/上下文、检索 scope、绑定、embedding、临时文档、映射的冻结顺序推进；
- 结果未知进入 `cleanup_unknown`，不得盲目重试；完成、失败、quarantine 和有界 recoverable
  扫描均为显式状态，数据库事务内不得执行网络或文件副作用。

### 6.3 Dispatcher

`WeaponryTaskDispatcherPort` 只发送常量空间唤醒信号，权威积压必须来自持久任务事实；生命周期
Port 明确 `start/stop/close`，有限停机超时不能把仍在执行的任务盲目重置为 accepted。1D-3A
只提供契约和严格 Fake，没有实现 Worker 或后台线程。

## 7. 严格 Fake 与故障矩阵

新增并拆分以下测试替身：

| 文件 | 关键能力 |
| --- | --- |
| `tests/fakes/weaponry_support.py` | 线程安全调用轨迹；只记录 operation/task/call，不记录正文或凭据。 |
| `tests/fakes/weaponry_processing.py` | Retrieval、Extraction、Auxiliary、Translation、Audit；严格检查审计/资源前置、来源、Evidence 和每 attempt 独立 Session。 |
| `tests/fakes/weaponry_control.py` | Callback latest/Guard/fencing、Resource ownership/CAS/cleanup lease、Dispatcher 生命周期与故障注入。 |
| `tests/fakes/weaponry.py` | 保留 1D-2 Document Scope Fake，并作为武器谱测试替身的稳定聚合导出面。 |

默认未配置调用全部失败，不自动猜测成功值。新增测试覆盖：

- Retrieval 未审计、未登记正确 `retrieval_scope`、允许文档越界、关闭明确失败和重复关闭；
- A/B 两个文档回答文本相同，但 Evidence ID、document_key 和来源 Session 必须分别验证；
- Extraction 来源错配、Session 创建明确失败、Session 创建结果未知及重复 attempt；
- Audit pending、幂等 reserve/complete、计数不一致和失败后调用轨迹零误报；
- owned/shared 清理、CAS 失权、顺序、重复登记、结果未知禁止盲重试、quarantine；
- cleanup lease 并发 busy、释放、单调 fencing 和迟到租约拒绝；
- Callback latest、显式 check-task 重试、unknown 冻结/人工解除、旧任务 stale；
- `none` 辅助策略零 I/O、术语辅助显式调用、翻译失败为空且不串任务；
- Dispatcher 重复 start、stop/close、dispatch 拒绝与执行失败注入。

50 线程 Barrier/线程池测试为每个 TaskId 创建独立调用：最终得到 50 个不同 retrieval scope、
50 个不同 extraction session、100 个 call ID 和 100 个 resource ID，所有 scope 均已关闭且每个
回答只引用本任务 Evidence。该测试验证单进程内存 Fake 的锁、身份和类型隔离，不验证真实网络
连接、模型吞吐、数据库跨进程锁、RabbitMQ 可靠投递或 50 个重型任务并行。

## 9. 日志与敏感数据边界

Port/DTO 是纯契约，没有运行时副作用，因此不在构造器中写生产日志；在纯对象校验中打日志会
造成重复、噪声和正文泄漏风险。严格 Fake 通过不含正文的线程安全 recorder 提供调用证据。
1D-3B 真实 Adapter 和 1D-4 Application 必须在调用开始、结果分类、来源拒绝、审计、资源登记、
清理、重试及 stale 收敛处记录 task/call/attempt、数量、摘要和稳定错误码，禁止记录 Prompt、
Evidence 正文、回调正文、Token 或完整 URL。
