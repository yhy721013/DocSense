## 3. 并发缺陷与修复

### 3.1 首次失败

首次运行 50 个不同 `chatId` 的完整公开路由并发测试时，部分请求在
`ChatRunLockService.try_acquire_chat_run()` 的 `BEGIN IMMEDIATE` 处抛出：

```text
sqlite3.OperationalError: database is locked
```

这些请求形成 HTTP 500。流槽位已经正确配置为 50，根因是 Chat SQLite 唯一连接入口同时把
Python 连接 timeout 和 `PRAGMA busy_timeout` 固定为 5 秒；50 个请求的受理、资源租约、
binding、事件和终态虽然都是短事务，但累计单写入者排队时间可能超过 5 秒。

### 3.2 修复

`app/services/chat/persistence/repositories.py` 现在定义
`DEFAULT_CHAT_SQLITE_BUSY_TIMEOUT_SECONDS = 30.0`，并由 `_connect()` 同时用于：

1. `sqlite3.connect(..., timeout=30.0)`；
2. `PRAGMA busy_timeout = 30000`。

等待仍然有界，不增加业务层自动重试，也不会重放任何远端副作用。修复后 50 个不同会话均
返回 HTTP 200，并完成以下逐会话核对：

- 50 个不同 run ID；
- 50 个不同 Workspace ref；
- 50 个不同 Thread ref；
- 每个会话只含自己的 input/message；
- 每个会话只有自己的 current binding；
- 全部运行收敛到终态，没有 active run；
- 50 个任务级 Fake Port 全部释放，活动租约为 0。

这只证明 Windows 当前环境下 SQLite 单实例的离线短事务排队可以支撑该测试，不表示数据库
获得并行写能力，也不表示多实例、生产延迟目标或真实供应商 50 并发已通过。
