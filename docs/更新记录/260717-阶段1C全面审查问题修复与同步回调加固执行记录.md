## 1. 同步 check-task 与 Callback Guard 统一

### 1.1 新增框架无关同步恢复用例

新增 `RecoverReportCallbackSynchronously` 与 `ReportCallbackRecoverySourcePort`：

1. Recovery Source 只读取当前 latest 报告的终态公开投影，并只接受 `pending/failed`；
2. 内部 execution 结果、审计字段和资源引用不得被当作甲方 Callback payload；
3. 候选读取不是发送授权点，应用服务必须再次通过 Guard 原子 acquire；
4. acquire 携带 `EXPLICIT_CHECK_TASK_RECOVERY` 来源。只有该显式来源可以重新授权一次
   明确失败的 `failed/rejected/definitely_not_sent`，普通 Worker 仍不自动重试；
5. HTTP 外发前再次复核 latest owner、lease token、fencing token 和 deadline；
6. 只有收到 2xx 且 Guard 完成 CAS 成功时，应用服务才返回内部 `replayed=true`；持久化
   未完成不得误报成功。

Flask check-task 的 report 分支现已调用该用例；file/weaponry 暂时继续使用遗留同步兼容
实现。组合根还会验证同步恢复与正常报告 Worker 注入的是同一个 Callback Adapter，避免
未来维护时误装配成两套 Guard。

### 1.2 并发、旧任务与显式重试语义

- 同一 reportId、同一 execution 的 50 个并发同步恢复请求最多一个取得发送权；
- 候选读取后若相同 reportId 已受理新 execution，旧候选 acquire 返回 `stale`，禁止网络
  调用；这符合“同一文件名/报告业务键对应同一解析任务”的 latest-wins 口径；
- `sending` Guard 的正常并发观察返回 `busy`，不再把一致状态误判为损坏；
- execution 已是 `sending` 但 Guard 缺失/idle 的异常事实会 fail closed 为
  `outcome_unknown`，防止重复发送；
- `delivery_outcome_unknown` 永不自动重试，继续冻结同业务键新提交，等待审计化人工解除。

### 1.3 回调结果、历史与连接释放

- HTTP 成功严格限定为 `200 <= status < 300`，302/其他 3xx 不再被 `Response.ok` 误判；
- `InvalidSchema`、`InvalidURL`、`MissingSchema` 和连接建立前超时归类为
  `definitely_not_sent`；读取超时、连接中断等保守归类为 `delivery_outcome_unknown`；
- Callback Guard 先完成数据库 CAS，再写入非权威本地调试历史；CAS 失权时不写历史；
- 未配置 URL 的 `skipped` 没有发生 HTTP，也不再制造看似已投递的历史文件；
- 报告新链和遗留回调客户端均显式关闭 HTTP 响应；关闭异常只记录日志，不覆盖已经得到
  的 HTTP outcome。

## 2. 过期 Guard 的生产维护闭环

此前过期 `sending` 只会在新提交、等待或下一次 acquire 时被动发现；若业务长期无新请求，
Guard 可能永久留在 sending。当前增加有界维护接口：

- `freeze_expired_callback_delivery_guards(business_type, limit, observed_at)` 先短连接读取最多
  `limit` 个候选，再在短写事务中逐项复核并 CAS；
- 维护只把仍过期的 sending 冻结为 `outcome_unknown`，绝不取得发送权或重发 HTTP；
- owner 缺失的损坏 Guard 也会冻结并输出 critical 日志，不能因为损坏而被重新抢占；
- `LocalReportTaskDispatcher` 的资源维护线程周期执行 Guard sweep；资源恢复和 Guard sweep
  分别统计成功/失败，一项异常不会跳过同周期另一项；
- Dispatcher 快照新增扫描次数、失败次数、冻结数、`ready` 与 `fatal_error`，供后续健康
  检查与监控 Adapter 使用。

## 3. 任务事实、Dispatcher 与受理一致性

### 3.1 任务事实修复

- accepted/running 因 latest owner 变化而收敛为 stale 时，同事务补齐 `completed_at`；
- Callback Guard 过期、损坏、完成和人工解除继续以 execution ID 条件写最新投影，旧
  execution 不能覆盖新 owner；
- 队列诊断查询只扫描 `accepted/running` 活动集合，不再每周期汇总持续增长的终态历史；
- 领取前故障的持久冷却继续按 `dispatch_sequence` 保持稳定 FIFO，不引入内存任务积压。

### 3.2 accepted 提交后的返回值防护

业务 Codec 的 encode/decode 往返和领域校验现在全部发生在数据库事务之前，避免 accepted
事实提交后才因输入解码失败返回 500。事务提交后 Repository 读回快照若损坏或不一致：

- 输出 critical 日志；
- 使用事务前已经严格验证的不可变快照返回受理结果；
- 继续发布初始 Progress 并通知 Dispatcher；
- 不把已提交 accepted 伪装成失败，也不让调用方重试后只得到 409。

`accepted_at` 在进入 Codec 前统一规范为 UTC ISO 时间，避免等价时刻因时区文本不同被误判
为快照不一致。

### 3.3 Dispatcher fail-closed 就绪语义

- 执行许可归还失败表示 Limiter 计数已不可信，Dispatcher 设置 fatal、停止后续领取并把
  `ready` 置为 false；
- Worker/维护线程发生未捕获致命异常时统一进入 stopping/fatal，而不是线程已退出但快照
  仍显示可用；
- 正常单任务异常仍按 accepted 条件写冷却并继续处理后续任务，和基础设施致命故障区分。

## 4. 文件下载与 Artifact 补强

### 4.1 下载器改为有界流式写入

- 使用流式响应和 1 MiB 分块，不再一次性把远端文件加载到内存；
- 新增内部配置 `DOCSENSE_REPORT_MAX_DOWNLOAD_BYTES`，默认单文件 512 MiB，允许范围为
  1 字节到 10 TiB；该值只限制单个源文件/模板，不限制持久任务积压数量；
- 同时校验可信的 `Content-Length` 声明和实际累计字节数，超限立即失败；
- 使用 monotonic 总传输期限检查，并把单次连接/读取等待限制为最多 10 秒，慢速响应不能
  永久占用唯一报告 Worker；
- 先写随机 `.part`，flush + `fsync` 后 `os.replace` 原子发布；异常删除部分文件；响应关闭
  异常单独记录，不能覆盖原下载结果。

### 4.2 Artifact 命名空间无副作用分配

`LocalReportArtifactAdapter.begin(task_id)` 现在只计算 TaskId 独占命名空间，不创建目录。
资源记录成功登记后，首次实际写入才惰性创建目录，避免 Store 登记失败时留下没有持久化
所有者的空目录。Windows 下还统一 `C:\...` 与 `\\?\C:\...` 的等价真实路径表示，避免
并发创建目录时 containment 校验出现假失败；越界和符号链接检查仍基于解析后的真实路径。

## 5. 审计凭据与资源恢复重试水位

### 5.1 审计凭据绑定真实 execution

清理生命周期追加除 `interaction_id` 外，还必须携带审计时签发的 execution ID 和审计
幂等键。SQLite 在同一事务读取 `llm_interactions` 并逐项核对；伪造、串任务或陈旧凭据
会抛出 `InteractionAuditError`，不得向其他任务的审计记录追加删除事件。

### 5.2 操作级 attempt 水位持久化

资源记录 payload 升级为内部 Schema v4，新增每个外部清理 operation 的最后 attempt_no：

- v2/v3 记录继续兼容读取，缺失水位按空基线处理；
- v4 严格拒绝非对象、空 operation、布尔/非正整数 attempt 和重复键；
- 恢复用例只接受 `last_attempt + 1`，成功/失败事件提交后都持久化新水位；
- `CleanupReportRag` 把基线传回 AnythingLLM Adapter，进程重启后的下一次尝试不会从 1
  重新计数，也不会与已提交审计事件冲突。
