### 1.2 对外接口契约冻结（2026-07-11 决议）

`/llm/chat*` 已交付的 HTTP/SSE 契约在本计划后续阶段中必须保持不变。这里的“不变”同时包含路径、方法、请求字段、JSON 响应字段、HTTP 状态码、响应头、SSE 事件名、`data` 结构和 SSE 行格式。

- `POST /llm/chat` 仅使用既有的 `businessType`、`params.chatId`、`params.fileNames` 和 `params.message`；不得新增 `requestId`、`runId`、游标或其他前后端字段。
- 不新增事件重放、状态查询或重连接口；不得在响应头、`chatInfo`、其他 SSE `data` 或 SSE `id:` 行中泄漏内部 run 标识。
- `chatId` 是唯一的对外会话定位键，并维持“一会话同时至多一个活跃流、重复请求返回 409”的既有语义。服务端 `run_id` 只用于内部状态、消息、租约和审计关联。
- 当前协议不提供客户端请求幂等或断线续传承诺。没有调用方稳定提交键时，服务端不能可靠区分网络重试与用户主动发送的相同消息；不得以消息摘要、时间窗口等启发式规则伪造幂等。
- 以后若业务确实需要调用方可见的幂等、运行查询或断线恢复，必须单独设计并发布版本化接口；不得修改本计划覆盖的既有接口。

**协议冻结基线修订记录（2026-07-11）：**

- 删除 `ChatRun`、run 仓储和 SQLite 锁服务中没有真实调用方语义的内部 `request_id`。新建 `chat_runs` 表不再创建该列；已存在 SQLite 文件中的历史列保持可读但不再参与任何逻辑或索引，正式数据库迁移时再按选定产品处理物理删列。
- `run_id` 继续作为纯内部键，用于 run 状态、消息、输入快照与资源租约关联；路由、响应头和 SSE 均不输出它。
- 增加路由回归测试，精确断言既有 SSE 只有 `chatInfo`、`textChunk`、`done` 的既定格式，并断言没有 `requestId`、`runId`、SSE `id:` 或内部标识响应头。
- 本次仅完成契约冻结和基线清理，尚未实施阶段 11 的事件账本或调度边界；后续必须按本计划的单阶段限制执行。

## 1. 文档目的

当前文件对话链路已经能支持基础 SSE 对话、历史查询和删除，但内部仍是同步代理式实现：

```text
Blueprint
  -> chat_service.py
    -> ChatDatabaseService
    -> legacy AnythingLLMClient
    -> AnythingLLM workspace/thread/stream-chat
```

该结构不适合继续直接叠加 `/llm/chat/title` 和 `/llm/chat/abort`，也不适合未来的多线程任务隔离、可靠任务队列、多实例部署、数据库一致性保障、高并发性能优化，以及整体 AnythingLLM 低耦合改造。

本文目标是提供一套可以逐阶段执行的重构计划，使文件对话链路最终具备以下能力：

1. 业务层只依赖供应商无关 Port/DTO，不直接依赖 AnythingLLM 具体类、HTTP 路径或原始字段。
2. 每次 `/llm/chat` 请求显式建模为一次 `chat_run`，支持状态机、并发互斥、中断、失败恢复和队列化。
3. 本地数据库成为对话消息、标题生成输入、中断语义和历史查询的权威来源。
4. AnythingLLM workspace/thread/document binding 具备持久化租约和可重试清理。
5. 当前以 SQLite 单实例兼容模式完成业务收口；在不预设具体数据库、消息队列或通知中间件的前提下，为将来的事务型持久化、可靠调度和多实例运行保留稳定边界。

### 1.1 当前范围与延后基础设施的边界

当前尚未确定或部署新的数据库、可靠消息队列和跨实例通知组件。因此阶段 10～12 的交付目标是**消除业务链路中的基础设施假设**，而不是在 SQLite 上模拟多实例或宣称已经具备可靠队列能力：

- SQLite 仅支持单应用实例、单进程的兼容运行模式；不得将数据库文件放在网络共享目录后以多副本方式启动。
- 阶段 10～12 不绑定任何具体产品名称。未来选定的关系型数据库应提供事务、条件更新/唯一约束、索引和可观测的迁移能力；未来选定的调度系统应提供至少一次投递、确认、重试和死信/人工处理能力。
- 数据库、队列和通知系统均为适配器；`Blueprint`、Chat Application Service、领域模型和 Port 不得感知其客户端、SQL 方言或协议。
- 未经单独立项和部署验证，阶段 13 及以后的基础设施阶段只保留设计和验收门禁，不实现伪分布式锁、伪队列或进程内 registry 替代品。

## 3. 改造启动时的结构问题

### 3.1 职责混杂

`app/services/llm_service/chat_service.py` 同时承担：

- SSE 事件格式化；
- `<think>` 流式过滤；
- 新旧对话判断；
- AnythingLLM workspace/thread 创建；
- 文档引用追加；
- 流式模型调用；
- 历史消息转换；
- 删除远端资源。

后续继续在该文件中添加标题生成、中断、队列和补偿逻辑，会使业务状态、协议输出和供应商编排进一步耦合。

### 3.2 Blueprint 承担过多业务和集成职责

`app/blueprints/llm.py` 的 `/llm/chat*` 路由直接：

- 查询 `kb_service` 校验文件；
- 查询原始文件名；
- 实例化 `AnythingLLMClient`；
- 传入具体 client 到业务函数；
- 手写 SSE Response。

这使接口层无法在不改路由的情况下切换 Gateway、队列执行器或消息持久化策略。

### 3.3 数据模型不足

当前 `ChatDatabaseService` 主要只有 `chats` 表：

- `chat_id`
- `file_original_names`
- `turn_timestamps`
- `workspace_slug`
- `thread_slug`
- `created_at`
- `updated_at`

它无法表达：

- 每次请求的 run 状态；
- 同一 `chatId` 活跃流互斥；
- 中断标记；
- user/assistant 消息本地权威历史；
- 被中断的半截 assistant 回答不入库；
- 标题生成输入；
- workspace/thread/document binding 的清理补偿；
- 多实例 owner/heartbeat。

### 3.4 跨进程和多实例不成立

当前 `threading.Lock()` 和未来如果采用进程内 abort registry，都只能在单进程内生效。多实例部署时：

- 第二个实例看不到第一个实例的活跃 SSE；
- `/llm/chat/abort` 可能打到非流式执行实例；
- SQLite 文件锁不能作为高并发分布式协调机制；
- 进程崩溃后没有可恢复的 running run 和资源租约。

### 3.5 历史依赖供应商状态

`/llm/chat/history` 当前从 AnythingLLM Thread 读取历史，再用本地 `file_original_names` 对齐用户轮次。问题：

- AnythingLLM 历史格式变更会影响接口输出；
- 中断后是否保存半截回答由供应商实现决定；
- `/llm/chat/title` 如果依赖供应商历史，会把标题生成建立在不稳定输入上；
- 本地无法准确判断一轮消息是否成功提交。

## 5. 目标数据模型与持久化边界

本节描述逻辑模型，而不是绑定某种 SQL 方言。当前 SQLite schema 是阶段 0～9 的兼容实现；阶段 10 后新增或调整字段必须通过 `ChatPersistenceStore`/事务工作单元表达。未来选定持久化产品后，使用其正式迁移机制演进 schema，禁止把运行时 `CREATE TABLE IF NOT EXISTS` 当作生产迁移方案。

### 5.1 逻辑实体

| 实体 | 关键字段/约束 | 作用 |
| --- | --- | --- |
| `chat_sessions` | `scope_id`、`chat_id`、外部 context/conversation 不透明引用、`active/deleting/deleted/error` | 会话与删除状态的权威记录；具体 cleanup 失败信息由资源 lease 保存。`scope_id` 当前可由配置提供默认值；接入调用方身份后必须纳入唯一性与授权校验。 |
| `chat_runs` | 内部 `run_id`、`scope_id`、`chat_id`、状态、取消请求、错误码 | 一次请求的权威执行记录。`run_id` 不属于 HTTP/SSE 契约，不能作为调用方重试键或事件读取键。 |
| `chat_run_inputs` | `run_id`、message、文件的业务名/原名/document ref/revision 快照 | 在 run 受理时冻结输入，防止文件在排队或重试期间被替换、删除或重新解析后改变本轮语义。 |
| `chat_document_bindings` + `chat_document_heads` | 不可变绑定 revision、当前文件 head、首次绑定 run | 保存会话长期可检索文档及其实际绑定状态；每次文件引用变化追加 revision，后续默认读取 current head，删除时保留完整审计与清理依据。 |
| `chat_messages` / `chat_message_files` | run、role、sequence、`pending/committed/discarded`、附件快照 | 本地历史权威来源；user、assistant 与 run 终态必须能在同一事务内收敛。 |
| `chat_resource_leases` | 资源类型、不透明 external ref、`planned/active/cleanup_pending/closed/cleanup_failed`、尝试次数/下次重试时间 | 外部资源副作用的 saga 记录；资源创建前先写 `planned`，获得引用后立即更新。 |
| `chat_run_events` | 内部 `run_id`、严格递增 `event_seq`、event type、payload、创建时间 | 内部事件账本；事件必须先持久化再展示，且每个 run 只能有一个终态事件。当前不向调用方提供按 run 或游标读取、重放或续传。 |
| `chat_outbox`（延后启用） | 业务事件、投递状态、attempt、可见时间 | 将来可靠调度的事务 outbox；阶段 10～12 只定义边界，不接入外部 broker。 |

### 5.2 一致性规则

- 请求受理、run 输入快照、user pending 消息和序号分配属于一个事务。`run_id` 由服务端生成并保持内部可见；当前接口不实现也不宣称调用方请求幂等。
- 阶段 10 的 `done` 以 user 提交、assistant 写入和 run 成功同事务收敛；`error/aborted` 的 user 留存策略必须写入接口文档和测试。终态事件落库在阶段 11 实施。
- 会话进入 `deleting` 后禁止新 run 与标题生成；删除流程必须先协调活跃 run，再执行远端清理。
- 事件账本、调度器、执行租约和 outbox 都只能使用内部 `run_id` 关联；它们不得反向要求 Blueprint 或调用方增加字段。
- `owner_instance_id`、lease token、心跳和跨实例通知仅在将来具备相应持久化和调度能力后启用；当前 SQLite 单实例不得以这些字段伪造分布式保证。

**阶段 10 执行记录（2026-07-10）：**

### 阶段 14：延后立项——可靠调度系统与 worker 实施

**前置条件：** 阶段 13 完成，且已选择、部署并具备运维能力的消息队列/任务调度产品。

**目标：** 使用事务 outbox 和 worker 将模型执行从 HTTP SSE 请求线程中拆出，同时保持初始 `POST /llm/chat` 连接上的既有 SSE 事件协议兼容。

**设计要求：**

- API 事务内写 `queued run + pending user message + outbox`；outbox relay 再向选定调度系统投递。调度系统不是 run 或消息的事实来源。
- worker 以条件领取和 lease token 执行。崩溃由 lease reaper 收敛并重新调度，不能让重复投递产生并行模型调用。
- 投递和 worker 执行按至少一次设计；外部模型调用结果不明时进入显式 `outcome_unknown`/人工恢复策略，禁止无判定地重发消息。
- 清理 worker 与执行 worker 分离，均采用退避、最大尝试次数和可观测的失败状态。

**验收目标：**

- 杀死 API、relay 或 worker 后，run 不会静默丢失，且不会由两个 worker 同时提交同一 run。
- 初始 `POST /llm/chat` 的 SSE 只消费内部持久化事件；连接断开后不新增调用方重连或指定 run 恢复能力，完成结果仍通过既有 `/llm/chat/history` 获取。
- 重复投递、超时、死信、取消、外部结果不明和清理重试均有集成测试与运维处置手册。

### 阶段 15：延后立项——多实例、取消通知与容量治理

**前置条件：** 阶段 14 的共享持久化和可靠调度已在目标环境验证。

**目标：** 允许 API、SSE gateway、worker 与 cleanup worker 横向扩展，并实现可观测、可限流的高并发运行。

- SSE gateway 无状态化，支持代理心跳和禁缓冲；不得依赖 sticky session，也不得以内部 run 标识新增调用方断线重连能力。

如果需要缩短首轮交付路径，可以先执行阶段 0～8，使新增接口可用；但不得跳过阶段 1～4，否则 `/abort` 会被迫依赖进程内状态，后续多实例和队列化会返工。

## 9. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 改动范围过大导致对外协议回归 | 每阶段只改一层，阶段 0 先冻结接口测试 |
| 新旧 `chats` 表兼容混乱 | 开发阶段不迁移旧 Thread 历史；旧表仅保留资源定位兼容，新表消息作为历史权威来源 |
| SQLite 高并发能力不足 | 阶段 10 限定为单实例并控制写放大；不以共享 SQLite 文件模拟集群。未来根据已选持久化产品实现对应适配器。 |
| 基础设施产品尚未确定 | 阶段 10～12 只定义事务、调度、租约和通知能力协议；不得把任何候选产品 API 泄漏到业务层。 |
| 可靠投递导致重复执行 | 将来使用事务 outbox、条件领取和 lease/fencing；调用方层面没有稳定幂等键时，网络超时后的重复提交不能被自动判定为同一请求，外部模型结果不明时不盲目重发。 |
| abort 在多实例下失效 | 取消请求持久化为事实来源；未来通知组件仅作低延迟唤醒，数据库检查始终为兜底。 |
| AnythingLLM 流关闭后仍保存半截回答 | 本地历史以 committed 消息为准；不依赖上游历史判断中断语义 |
| 删除远端资源失败造成孤儿资源 | 资源创建前登记 lease，失败进入 `cleanup_failed`；未来由可替换 cleanup dispatcher 重试，不能只依赖人工扫描。 |
| 标题生成污染主对话 | 标题必须走独立临时会话或非历史调用，禁止使用主 Thread |
| 继续扩大 legacy Facade | 阶段 2 后新增对话能力只能进入 Chat Gateway，不再新增 `AnythingLLMClient` 方法 |
