## 2. 发现与修复

### 2.1 Callback 明确失败可能被同一并发波次重复发送

原同步恢复在等待已有 owner 后会重新读取候选，明确失败会生成新的可恢复 attempt；多个并发调用可能
依次读取新 attempt 并再次发送 HTTP。现将首次候选的 `callback_attempts` 作为授权快照，在 SQLite
写事务内同时核对 latest execution、状态、lease 与 attempt。只有快照仍匹配的调用可以取得 Guard；
同一并发波次其余调用返回 stale，后续独立检查仍可基于新快照执行有限重试。

同时把恢复候选查询收窄为只读取回调所需控制面和最终结果。损坏或超大的请求正文、execution 输入不再
参与 Callback 恢复解码，也不会阻断合法的终态回调。

### 2.2 资源终态可能被绕过 Port 直接复活

在 Resource Port 和 SQLite Service 两层分别维护显式迁移矩阵：

- `tracking` 只能进入跟踪、待审计、待清理或隔离；
- `cleanup_pending` 只能留在待清理、进入待审计、清理完成或隔离；
- `audit_pending` 只能留在待审计、进入清理完成或隔离；
- `cleaned`、`quarantined` 为不可逆终态。

双层约束防止未来 Adapter、维护任务或直接 Service 调用绕过 DTO 校验，把已完成或隔离记录重新置为
活动状态。

### 2.3 毒资源记录可能阻断整个维护扫描

资源扫描先读取不解析 JSON 的控制面投影，再按需解码 payload。非法 JSON 或结构错误会通过
`execution_id + state + version` CAS 进入 `quarantined`，原始 payload 不改写，并只记录长度与 hash
等脱敏诊断。单条记录还有最后一道异常隔离边界，不能终止后续健康记录的扫描。

延期预算耗尽后的隔离同样使用无 payload 的控制面 CAS，不再重复解析已知损坏快照。瞬时 SQLite
异常不归类为毒数据，仍向上暴露给未来 Dispatcher 的调度与告警边界。

### 2.4 已知 RAG close 结果在 fallback 中可能丢失

当外部 close 已返回明确 outcome 和 lifecycle events、但首次结果事实 CAS 失败时，恢复流程现会从
已知结果完整重建资源事实，再进入 `audit_pending`；只有无法证明外部结果的异常才进入隔离。该策略
保持 fail closed，同时不丢弃已经发生的外部证据。

### 2.5 切换门禁覆盖不完整且只读句柄未确定释放

只读预检新增两类硬阻断：

- 无完整批次身份、但仍有待恢复或失败 Callback 的遗留终态 file 任务；
- 已进入 `running` 的新 execution。

原有活动旧任务、Callback Guard 开放/未知结果、资源恢复积压继续阻断。`accepted` 新 execution 作为
显式观测项输出，由发布人员核对，但它尚未发生不可确定外部副作用，不自动视为硬阻断。

预检函数现使用确定性连接关闭；Windows 下函数返回后即可移动数据库文件，不依赖垃圾回收释放句柄。
历史终态 Callback 采取“切换前由遗留同步恢复排空、预检不为零即阻断”的单 owner 策略，没有引入
新旧 Callback 双路 fallback。

## 5. 后续上线边界

- 1F-5A 仍需实现 Dispatcher、配置和离线组合根；1F-5B 只能在实际目标数据库预检通过后切换唯一
  production owner。
- 发布窗口必须先停止旧 file Worker 和新请求进入，再运行只读预检；五类硬阻断必须全部为零，并
  人工核对 `newAcceptedExecutions`。
- `outcome_unknown`、开放 lease、历史待恢复 Callback、活动旧任务、`running` execution 和资源恢复
  积压均不得通过清表、盲重放或新旧 Worker 双跑来消除。
- 当前结论不代表已具备可靠任务队列、多实例竞争、数据库级跨实例一致性或生产高并发吞吐能力。
- 1F-5B 完成唯一 owner 切换后，方可进入 1F-7B 全阶段关闭验收。
