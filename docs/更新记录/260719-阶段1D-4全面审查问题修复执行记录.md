# 阶段 1D-4 全面审查问题修复执行记录

## 1. 结论与范围

本轮已完成阶段 1D-4 全面审查中获批问题的修复和补强。改动仍属于未接入生产链的
离线实现：没有切换 `/llm/weaponry`，没有启动 `run.py`，没有装配 Dispatcher、Callback

本轮没有新增、删除、改名任何前后端请求参数、响应参数或 Callback 字段。接口文档原本

不需要修改 `docs/接口文档/`；公开字段校验和错误体保持不变。

数据仍处于开发/测试阶段，不需要迁移历史 execution、Audit 或 Resource 记录。

## 2. 已修复问题

### 2.1 HTTP 合法字段不再因隐藏 Query 规则异步失败

`RetrievalQuery` 不再限制 4096 个字符，也不要求字段一定形成两个及以上字符的语义词。

- “长”“宽”“高”等单字字段会保留为合法语义词；
- 即使字段名规范化后没有辅助语义词，Query 正文仍保留原始 `fieldName` 和非空
  `fieldDescription`，可以继续执行向量召回；
- 不在 Worker 内为已受理请求补设接口文档不存在的字符上限；
- 1D-5 的配置层不得重新引入同类隐藏门禁。

这不等于承诺供应商能够处理任意规模输入。如果真实 AnythingLLM/embedding 服务存在自身
容量上限，应在 1D-6 联调中按外部能力事实记录和失败，不得静默截断 Query，也不得擅自新增
公开参数限制。

### 2.2 精确收敛“未找到”哨兵

旧判断只要回答任意位置包含“未找到”就会丢弃整份来源，可能误伤“未找到号”等真实文本，
也可能让 TABLE JSON 中一个单元格影响整行。

现改为：

- INPUT 只有在去除首尾空白后的完整回答精确等于 `未找到` 时才按无信息处理；
- 空字符串仍按无信息处理；
- TABLE 不使用 INPUT 哨兵判断，交给严格 JSON 和既有单元格纯规则处理；
- TABLE 单元格的既有精确空值规则保持不变，但不能再导致整份 JSON 回答提前丢失。

### 2.3 审计预留明确区分首次、pending 与 completed

`WeaponryInteractionAuditPort.reserve` 现在返回显式三态：

| 结果 | 含义 | Application 行为 |
| --- | --- | --- |
| `reserved` | 本次首次原子预留成功 | 唯一允许继续外部 I/O 的结果 |
| `pending` | 历史 Worker 可能已经发出请求，尚无完成事实 | 禁止重放，使用稳定错误码隔离现场 |
| `completed` | 同一 attempt 已有完成事实 | 禁止重新调用外部服务，隔离等待确定性恢复 |

这消除了“数据库幂等返回同一 reservation，就把旧 pending 当成新的调用许可”的双调用风险。
当前 Audit 只持久化摘要，无法据此重建完整业务回答，因此 1D-4 不猜测性恢复。1D-6 必须按
确定性资源名和供应商事实查回；无法唯一证明时继续 quarantine，而不是盲目重放。

### 2.4 慢 I/O 前补充 latest 复核

Guidance、Retrieval、每次 Extraction attempt 和每个 Translation 子项在预留审计和发起慢调用
前都会检查 expected TaskId 是否仍为 latest。旧 execution 一旦失权，不再继续启动后续模型、
检索或翻译调用。慢调用返回后的既有 latest 检查继续保留，防止迟到结果写入终态或 Callback。

### 2.5 先持久化清理意图，再删除远端资源

`RunWeaponryTask` 的资源收敛顺序改为：

1. 先把资源记录原子切换为 `cleanup_pending` 或确认已经 `cleaned`；
2. 只有清理意图可靠持久化后，才允许调用远端 `close_scope`；
3. `prepare_cleanup` 失败、返回非法状态或 CAS 无法收敛时，禁止远端删除并保留现场。

这关闭了“远端删除成功，但进程在本地记录清理意图前崩溃”的不可恢复窗口。SQLite Resource
Store 还会把 `succeeded`、`failed`、`stale` 终态 execution 对应的遗留 `tracking` 记录列为恢复
候选，从而覆盖“终态已提交、清理准备尚未提交”这一相邻崩溃窗口。仍在 `running` 的 execution
和找不到 execution 权威行的资源不会因年龄被猜测性清理。

### 2.6 AnythingLLM 409 按外部副作用结果未知处理

Retrieval 与 Provided-Evidence Extraction 使用 attempt/task 派生的确定性 workspace 名称。
创建请求返回 HTTP 409 可能表示此前请求已成功创建，只是当前 Worker 没有本地登记事实。
因此 409 现在与超时、连接中断等写入不确定场景一样归类为 `outcome_unknown`，禁止自动创建
第二个资源或再次调用模型。

本轮只完成安全分类。1D-6 仍须实现“按确定性名称唯一查找 → 校验归属和内容 → 合法时接管，
否则隔离”的生产对账 Adapter，并为失败扫描设置持久退避，避免坏记录占住恢复首页。

### 2.7 文档位置身份在受理与执行阶段保持一致

Document Scope Adapter 现在使用与 AnythingLLM Retrieval 相同的完整位置规范化函数检查重复
外部引用。URL 编码、NFKC、反斜杠和重复斜杠等不同外观若最终指向同一完整文档位置，会在
受理冻结文档范围时直接报歧义/完整性错误，不再等 Worker 绑定文档时异步失败。快照仍保留
原始不透明引用，不会把不同上传批次按文件名错误合并。

## 3. 后续阶段新增硬门禁

### 3.1 1D-5

- 严格配置必须 fail-fast 校验不支持的 Provider、embedding、文档处理和 score/rank 协议；
- 不得重新添加 Query 4096 字符、语义词最小长度或非空辅助语义词限制；
- 供应商容量错误、业务零结果和输入契约错误必须分开计数，不能用一个“检索失败”指标混合；
- 本地 Dispatcher 仍只负责持久任务唤醒和有界执行，不处理 Audit/资源的猜测性重放。

### 3.2 1D-6

- Audit `pending/completed` 只能走确定性查回、结果重建或 quarantine，绝不能重新取得外部调用权；
- 409、创建超时及登记结果未知必须按确定性名称查找并严格核对 TaskId、call_id、文档和策略；
- 终态 `tracking`、`cleanup_pending`、unknown 和 quarantine 分别处理，恢复扫描有界且持久退避；
- 资源恢复必须先取得 cleanup lease/fencing，再执行外部 I/O，成功/失败/结果未知逐项持久化；
- 真实供应商联调覆盖超长 Query、提示注入边界、A/B 来源隔离、Evidence/rows 同序和空 workspace；
- 公开路由切换仍必须等待 Callback Guard、同步 check-task 恢复和资源对账全部闭环。

### 3.3 阶段 2～3

SQLite 单实例阶段尚未提供跨进程执行租约。迁移可靠队列/MySQL 时必须增加 execution
lease、heartbeat、fencing，以及“领取/创建响应丢失”的事务对账；不能把本轮 Audit 三态误当作
多实例 Worker 的执行所有权。
