## 3. 最终实现事实

### 3.1 原子受理与顺序

1. Web 层解析整个批量请求后，由 `SubmitAnalysisBatch` 在一个 SQLite 事务中写入全部 accepted execution；任一元素失败则整批回滚。
2. batch_sequence、请求内顺序和持久调度顺序均被保存；Worker 只按 TaskId 恢复不可变快照。
3. 受理提交后只发送有界 Event 唤醒；Event 丢失不影响启动/周期 SQLite 扫描恢复。
4. 同一文件的活跃 execution、Callback 恢复和资源关闭通过 Repository 条件写协调，避免旧任务覆盖新任务。

### 3.2 Application 与任务级 I/O

1. Analysis Domain/Application/Ports/Adapters 形成独立垂直切片；Blueprint 不直接构造数据库、供应商客户端或线程。
2. 文件准备、RAG、知识写入、审计、资源和 Callback 均为任务级 Port；有状态 Transport/Session 不跨任务共享。
3. 外部审计成功是知识写入和成功终态的前置条件；失败或结果未知时 fail-closed 并保留可恢复现场。
4. 大型执行用例拆分后，Facade 只协调五个内部协作器；永久 AST、调用轨迹和故障矩阵防止副作用顺序漂移。

### 3.3 资源与 Callback

1. 新 execution 在执行前登记资源意图；close 使用 intent、lease/fencing、条件 CAS 和逐资源隔离。
2. 已知 close 结果、明确失败和 outcome unknown 分开持久化；fallback 不得丢失已知结果或盲目重试未知外部副作用。
3. file 类型 check-task 是同步 Callback 恢复入口，并与 Worker 共享同一 Guard、attempt 和结果投影。
4. 资源扫描分别统计解码隔离和待恢复失败，毒记录不能阻断整批维护。

### 3.4 生产接线与发布制度

1. `/llm/analysis` 已接到唯一新 Application；遗留执行器只保留明确兼容或测试价值，不得重新成为第二生产链。
2. 当前 Dispatcher 仍是本地单实例持久扫描 Worker，不是可靠消息队列。
3. 当前发布制度是先停服排空，再由 `clean.py` 对开发/目标空库执行清库重建；保留或恢复存量数据库、或清理结果存疑时，必须执行只读预检。
4. 清理命令遇到占用、权限或删除失败必须非零退出，不能把未清理状态报告成成功。

## 4. 关键审查修正

- 多候选审计载荷、分类策略、外部副作用和任务输入在 accepted 时冻结，避免运行期读取漂移配置。
- 部分会话打开失败仍可审计；RAG attempt 与活动 Conversation 精确绑定。
- close 使用三态幂等和证据校验；stale 任务在慢 I/O 前再次复核。
- Callback 明确失败的并发波次只允许一个发送者；结果未知由新 check-task 明确授权 at-least-once 重试。
- 资源终态只能通过 Port/CAS 推进，毒资源逐项隔离，不能绕过控制面“复活”。
- Dispatcher 致命故障进入 fail-closed readiness，不能继续接受无法执行的新任务。

## 6. 当前与未来边界

- SQLite `single_instance` 只能证明本地恢复和隔离；Task Attempt、heartbeat、checkpoint、Reaper 与跨实例 fencing 仍属后续阶段。
- 批量原子受理不等于跨数据库/消息队列原子投递；可靠队列接入需 Outbox 或等价一致性协议。
- 真实 OCR/MinerU/AnythingLLM/模型和 Callback 必须在明确资源范围与维护窗口内验收。
- 任何 outcome unknown 都必须保留审计和资源事实，不得用自动重试换取表面成功率。
