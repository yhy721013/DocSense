# 文件解析装备子分类知识库存储归并

本次改造聚焦 `/llm/analysis` 文件解析完成后的知识库存储路径：当文件被解析到某个武器装备下的明细分类时，对外回调仍返回明细分类 ID，但服务端内部知识库统一按武器装备父节点 ID 存储，方便 `/llm/weaponry` 在解析装备知识谱系时一次性纳入该装备下的全部资料。

## 1. 背景与需求

项目当前以 AnythingLLM 为核心构建 RAG 后端。文件解析接口 `/llm/analysis` 会先让模型从 `architectureList` 中识别文档所属分类，再把文档上传并嵌入到该分类对应的 AnythingLLM Workspace，同时在本地 SQLite 中维护 `architecture_id -> workspace_slug` 和 `file_name -> architecture_id` 的映射。

原有逻辑中，`mapped_result["architectureId"]` 同时承担两种职责：
1. **对外解析结果**：作为 `/llm/analysis` 回调里的 `data.architectureId` 返回给业务系统。
2. **内部存储路由**：作为 AnythingLLM Workspace、本地 `documents.architecture_id` 和向量 metadata 的分类 ID。

当模型按现有提示词把装备文档分类到 `CVN68-基础数据`、`CVN68-战技指标`、`CVN68-运用数据`、`CVN68-效能数据` 等具体子分类时，原实现会为这些子分类分别建立知识库 Workspace。这样 `/llm/weaponry` 使用装备级 `architectureId=CVN68` 查询时，只能查到装备级 Workspace 中的文档，无法自动覆盖各个明细子分类 Workspace。

本次需求要求：
- `/llm/analysis` 回调中的 `data.architectureId` 仍保持模型识别出的具体子分类 ID。
- 本地关系库、AnythingLLM Workspace 和向量 metadata 改为按武器装备父节点 ID 存储。
- 触发规则为分类名称严格匹配 `*-基础数据`、`*-战技指标`、`*-运用数据` 或 `*-效能数据`。
- 不处理历史数据迁移。当前项目仍处于开发阶段，测试数据会反复清理。
- 不改造 `/llm/reassign`。前端已约定在调用该接口时把涉及的子分类 ID 自动替换为装备级 ID。

## 2. 核心实现内容

### 2.1 解析结果 ID 与存储 ID 分离

**代码位置**：`app/services/llm_service/analysis_service.py`

在 `run_file_analysis_task()` 中不再直接使用 `mapped_result["architectureId"]` 作为知识库存储 ID，而是拆分为：

```python
result_architecture_id = mapped_result.get("architectureId")
storage_architecture_id = resolve_storage_architecture_id(
    result_architecture_id,
    architecture_list,
)
```

其中：
- `result_architecture_id`：对外返回的解析分类 ID，保持不变。
- `storage_architecture_id`：知识库实际存储使用的分类 ID。

最终回调仍由 `mapped_result` 生成，因此 `data.architectureId` 不会被替换成装备级 ID。

### 2.2 装备明细子分类识别

新增 `resolve_storage_architecture_id()` 作为纯函数，负责根据本次请求的 `architectureList` 判断是否需要做存储归并。

判断规则：
1. 先根据解析结果 ID 找到命中的分类节点。
2. 使用分类节点的 `name` 字段做判断。
3. 通过最后一个 ASCII 连字符 `-` 拆分名称，避免误处理 `F-35-战技指标` 这类装备名自身包含连字符的情况。
4. 只有后缀严格属于以下四项时才触发归并：
   - `基础数据`
   - `战技指标`
   - `运用数据`
   - `效能数据`
5. 优先沿 `parentId` 父链查找名称等于装备前缀的节点。
6. 当 `architectureList` 只包含子分类节点但提供了 `parentId` 时，直接使用该 `parentId` 作为装备级存储 ID。
7. 若缺少父节点、父链矛盾或无法可靠确认装备节点，则回退使用原分类 ID，并记录告警日志。

### 2.3 知识库存储路径改为装备级 ID

以下内部写入逻辑改用 `storage_architecture_id`：

- `kb_service.get_workspace_slug(storage_architecture_id)`
- `client.create_rag_workspace(f"architectureId-{storage_architecture_id}")`
- `kb_service.add_workspace(storage_architecture_id, workspace_slug)`
- AnythingLLM 文档 metadata：

```python
metadata = {
    "file_name": file_name,
    "architecture_id": storage_architecture_id,
}
```

- SQLite 文档记录：

```python
kb_service.save_document_record(
    file_name,
    storage_architecture_id,
    str(doc_id),
    doc_path=doc_relative_path,
    original_name=original_name,
)
```

因此，多个装备明细分类会进入同一个装备级 Workspace：

```
CVN68-基础数据   -> architectureId-CVN68
CVN68-战技指标   -> architectureId-CVN68
CVN68-运用数据   -> architectureId-CVN68
CVN68-效能数据   -> architectureId-CVN68
```

### 2.4 归并日志

当发生归并时，会记录文件名、解析分类 ID、解析分类名称、存储分类 ID 和存储分类名称，便于排查实际入库行为。

示例语义：

```
文件知识库存储分类归并:
file_name=sample.pdf
result_architecture_id=6801
result_architecture_name=CVN68-基础数据
storage_architecture_id=680
storage_architecture_name=CVN68
```

## 3. 对 `/llm/weaponry` 的影响

`/llm/weaponry` 的主逻辑无需修改。

该接口原本就会按请求中的装备级 `architectureId`：
1. 从本地知识库映射中定位对应 Workspace。
2. 从 `documents` 表筛选相同 `architecture_id` 的文档。
3. 以这些文档作为目标文件白名单进行向量检索和字段抽取。

改造后，只要 `/llm/analysis` 新解析的文件符合装备明细子分类规则，它们都会以装备级 ID 存储。因此 `/llm/weaponry` 查询装备级 ID 时可以自然覆盖该装备下的基础数据、战技指标、运用数据和效能数据文档。

**测试文件**：`tests/test_analysis_service.py`
