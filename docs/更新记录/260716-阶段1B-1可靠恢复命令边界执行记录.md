## 2. 核心设计

### 2.1 共享 check-task 请求 DTO

新增 `app/modules/tasks/application/check_task_request.py`，只接收 Web Adapter 已完整
校验并转换后的有序 `TaskLookupItem`：

- 至少包含一项；
- 每项必须是类型化对象；
- 同一请求只能包含一种 `business_type`；
- 不接收 Flask request、任意 JSON 字典或数据库 Row。

阶段 1A 的 `CheckTaskStatusRequest` 现在是 `CheckTaskRequest` 的兼容别名。这样既不破坏
既有测试和内部调用，也避免新的可靠命令服务反向依赖旧同步原型文件中的一份重复规则。

### 2.2 最小可靠命令信封

`CallbackRecoveryCommand` 只包含：

| 字段 | 语义 |
| --- | --- |
| `expected_task_id` | Task Read 观察到的具体执行代次；MySQL Adapter 必须在事务中复核 |
| `business_ref` | latest-wins 所需的稳定业务键 |
| `trigger` | 固定为 `check_task`，与后台自动重试分开审计 |
| `schema_version` | 当前固定为 1，拒绝调用方擅自发送未知版本 |
| `trace_id` / `correlation_id` | 内部追踪信息；只接受字符串且去除首尾空白 |

命令输入刻意不包含公开 `params`、请求正文、Callback 正文、结果正文，也不提前包含
`recovery_request_id`。后者必须由未来 MySQL Adapter 在同一事务内生成或复用；只有
事务提交后的 `created`/`already_active` 结果才允许携带该 ID。

### 2.3 四类事务结果

| outcome | 含义 | recovery request ID |
| --- | --- | --- |
| `created` | 本事务新建了活动恢复请求，并应同时写 Outbox | 必须存在 |
| `already_active` | 同一 TaskId 已有 pending/queued/running 请求，本次复用 | 必须存在且保持不变 |
| `not_needed` | 任务未终态、Callback 已 success/skipped 或其他无需恢复条件 | 禁止存在 |
| `stale` | 同一业务键已有更新 TaskId，旧执行不得创建 Outbox 或外发 | 禁止存在 |

同一 TaskId 同时最多一个活动恢复请求。重复 check-task 请求以及同一批次中的重复项必须
复用同一 ID，避免 Worker 消费前产生多个等价回调任务。

### 2.4 批量原子端口

端口采用 `request_many(commands)`，而不是应用层循环调用单项 `request_recovery()`。
该选择是后续可靠性的必要条件：

- 一个请求中的全部命中项由一次共享数据库事务处理；
- 结果必须与命令等长、同序；
- 事务提交失败时抛出异常，不能返回部分成功；
- RabbitMQ 不在事务方法中直接发布，而由同事务 Outbox 的 Relay 后续发布；
- Task Read 后若发生新代次竞争，Command Adapter 必须在事务中再次读取/锁定事实并
  返回 `stale`，不能信任 Web 请求开始时的旧快照。

阶段 1B-1 Fake 在锁保护下先于局部副本计算整批结果，全部完成后才提交活动命令状态。
故障注入和批内后续项未配置时，先前项也不会留下活动 ID；50 个并发重复登记只产生
一个 `created` 和 49 个复用同一 ID 的 `already_active`。这证明端口幂等契约可测试，
不代表生产 MySQL/RabbitMQ 或真实 HTTP 已通过 50 并发验收。

### 2.5 应用服务编排

`RequestCallbackRecoveryService.request_recovery()` 的固定流程为：

1. 严格接收 `CheckTaskRequest` 和字符串追踪字段；
2. 通过 `TaskReadPort.get_latest_many()` 一次读取，保持输入长度、顺序和缺失位置；
3. 拒绝非 tuple、长度不一致、非 `TaskSnapshot` 和业务键错位的返回值；
4. 缺失项不创建命令；全部命中项组成一个命令批次；
5. Command Port 只调用一次，并验证结果 tuple、长度、类型、业务键和 expected TaskId；
6. 重新映射到原请求位置，记录 outcome 计数后返回框架无关结果；
7. Task Read、数据库事务或端口异常均不转换为成功，日志只记录业务键、TaskId、数量、
   outcome 和 trace，不记录请求/回调正文。

单项缺失与批量缺失的差异仍由结果显式保存：单项缺失供 Presenter 映射既有 404；批量
缺失继续处理其他项，并按已批准目标返回 200 空响应体。

### 2.6 框架无关 Presenter

`app/presenters/task_status.py` 返回 `TaskStatusHttpPresentation`，不导入 Flask/FastAPI：

- 单项或批量成功：`status_code=200`、`body=b""`，严格零字节；
- 单项缺失：404 与 `{"error":"任务不存在"}`；
- Web Adapter 已判定的参数错误：400 与既有 `{"error":"..."}` 结构；
- 批量部分/全部缺失：仍为 200 零字节体；
- 内部 TaskId、recovery request ID、outcome、状态和进度一律不序列化。

严格 `params` 元素校验的目标仍由阶段 0 黄金资产冻结。本阶段没有切换生产请求解析器；
其生产实现与 200 异步完成时点说明必须在阶段 6 路由切换前再次核对接口文档。

## 5. 当前生产边界

阶段 1B-1 完成后，当前生产路径仍然是：

```text
Flask /llm/check-task
  → 旧 Blueprint 参数处理
  → 旧 LLMTaskService
  → 请求线程内同步 replay_callback_if_needed
  → 旧成功 JSON
```

以下能力**尚未进入生产**：

- `RequestCallbackRecoveryService` 的 Container 装配；
- MySQL recovery request / delivery attempt Schema；
- 同事务 Outbox 和 Relay；
- RabbitMQ callback recovery Queue、Celery Worker、ACK/DLQ；
- TASK-09 同业务键 Guard、Worker latest-wins 和 expected TaskId 条件持久化；
- 目标 HTTP 200 空响应体和严格混合 `params` 拒绝的生产路由切换。

因此不得把本记录中的 Fake `created` 理解为任务已持久化、消息已发布或 Callback 已完成。
