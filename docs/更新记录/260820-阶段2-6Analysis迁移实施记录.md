# 阶段 2-6 Analysis 迁移实施记录

## 1. 实施范围

本记录对应阶段 2-6 第 1～8 步。公开文件分析、`/llm/check-task`、Progress 与 Callback 合同均未修改；
未增加、删除或改变接口参数、响应字段、Headers、状态码、路由及同步恢复语义。实施未运行
`run.py`，只使用项目虚拟环境、临时 SQLite、Fake 和离线测试。

Analysis 的业务类型、Executor 名称和未来队列路由按已确认方案统一为 `file`。本阶段没有建立
`analysis` 路由别名，也没有把旧 `LLMTaskService` 或旧 Runner 的事实双写到 v2。

## 2. Input、Profile 与配置所有权

- 新受理输入固定为 `AnalysisTaskInput/v5`，冻结完整 Execution Profile 和既有 Translation Profile；
- v1～v4 只保留严格历史解码能力，普通 Worker 不得从当前环境补齐 Profile 后执行；
- Worker 在第一笔外部副作用前核对完整 Profile，部署事实不一致时失败关闭；
- Analysis Runtime Config 从通用核心配置中迁入 Analysis Adapter，保留现有环境键、默认值和严格校验；
- RAG Provider 与模型只保存 SHA-256 指纹，不在任务输入、日志或数据库中写入 Secret、完整 URL、
  API Key、模型原文或宿主绝对路径；
- Analysis Domain 只精确复用 Translation Domain 的纯值对象，不依赖 Translation Application、Port
  或 Adapter。

## 3. Control Store、批量受理与执行顺序

根 Schema generation 2 安装 `analysis_control/v1`，由唯一 Manifest 管理 Analysis 资源、Recall 决策、
Interaction Audit 引用和结果快照。各 Store 只严格打开已安装 Schema，不自建表、不修复漂移，也不
提交调用方借用的连接。

一次公开请求在单个 `BEGIN IMMEDIATE` 短事务中全有或全无受理 1～32 个文件任务，同时写入 Task、
execution、原始请求投影和批次成员关系。持久化 `dispatch_sequence` 保证跨批 FIFO；同批前序只有进入
确定终态后才释放后继。前序为 `recovery_required`、毒输入隔离或 Callback handoff 未完成时，后继
继续阻塞。进程内 Event 仅作可丢唤醒，启动扫描和周期扫描才是恢复真相。

## 4. Authority、Step、UoW 与失败语义

- `RunAnalysisV2Workflow`、`AnalysisStepRuntime` 和 `AnalysisExecutionUnitOfWork` 落实冻结的 Analysis
  Step/Recovery Registry；
- claim、start、heartbeat、Step、Progress、terminal 与 Callback 条件写均携带完整
  `task_id/attempt_no/lease_token/fencing_token/lease_expires_at`；
- Workflow 只使用 Runtime 下发的 Authority Session，不回查并替换当前租约，不从旧 Runner 补权；
- 失权后协作停止，不以旧 Authority 写终态；所有网络、模型、下载、文件、知识库和 HTTP Callback
  副作用均在控制事务之外；
- 外部写结果未知时保存可证明的 Intent/Checkpoint/资源审计事实，并隔离为
  `outcome_unknown/recovery_required`，普通 Worker 不自动重放；
- 成功或普通失败的结果快照、`terminal.commit`、Task/Attempt 终态和 Callback eligibility 在同一
  SQLite 短事务提交；同步恢复只读取冻结结果，不重跑 Analysis；
- Callback HTTP、Callback History 和资源清理均在终态事务之后执行，终态不等待远端资源删除。

## 5. 生产一次切换与遗留边界

`app/container.py` 已一次性把 Analysis 的受理、执行、Progress、终态、Callback Control、同步恢复和
维护扫描切换到阶段 2 控制面。生产组合根不再构造旧 Analysis 控制链，不存在双 claim、双写或旧
Runner Authority 兼容桥。旧 Task Command、Resource Store、Dispatcher 与 Runner 控制 Adapter 仅可
作为阶段 1 回归夹具存在，不能被生产模块导入或写入 v2。现有名称带 `Legacy` 的 File Preparation、
RAG 和 Knowledge Adapter 仍作为外部能力桥接器被 v2 Workflow 调用；它们不持有任务状态、不生成
Authority，也不构成旧控制面。

Callback Guard 冻结和资源恢复是两项独立、持久扫描驱动的维护工作；其中一项暂态失败不会跳过另一项。
unknown Callback 不自动重发，资源归属不明或关闭结果不明时继续保守隔离。

## 6. 全新部署数据库策略

2026-08-20 已确认：若部署现场完整删除并永久弃用旧版本数据库文件集，采用显式一次性 fresh
bootstrap，而不是让普通应用启动隐式创建 v2 数据库。部署命令必须显式确认放弃旧任务事实，并在同一
Schema 锁下验证旧/目标数据库主文件、WAL、SHM 均不存在，再以临时数据库严格安装和核验 Report、
Weaponry、Analysis 全部组件，最后无覆盖原子发布。

普通应用在旧库和 v2 均不存在时以 `fresh_bootstrap_required` 失败关闭；任一残留成员、组件集合不完整、
重复执行、锁竞争或发布竞态同样失败关闭。该流程不读取、不迁移、不推断不存在的旧事实，也不改变公开
接口或 Callback 语义。非 Task 辅助表的物理拆库仍留待阶段 2-8。

## 8. 阶段结论

阶段 2-6 已形成 Analysis 从受理、持久顺序、Authority Runtime、业务 Step/UoW、结果终态、Callback
到资源维护的单一 v2 控制面，并给出旧数据库永久弃用场景下显式、可审计、失败关闭的 fresh bootstrap
部署路径。后续阶段不得重新引入旧控制面双写，也不得把单机 Event、SQLite 锁或本地线程误当作分布式
租约、可靠队列或生产容量证据。
