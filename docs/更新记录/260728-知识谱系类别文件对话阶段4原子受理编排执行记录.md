# 知识谱系类别文件对话阶段 4 原子受理编排执行记录

## 1. 阶段范围

本阶段将阶段 1～3 的选择器、候选、不可变 Binding 和 Schema v5 串入 SQLite 单实例
Coordinator。公开 `/llm/chat` 路由仍未解析 architecture 请求，远端执行和历史公开投影也尚未
切换。

## 2. 原子受理顺序

`ChatRunLockService.try_acquire_chat_run()` 现在在同一个 `BEGIN IMMEDIATE` 事务中依次完成：

1. 创建或读取 Session，并取得可靠的 `session_created`；
2. 创建新 Session Binding，或严格读取既有 Binding；
3. 先校验 scope mode，再校验不可变 architecture ID；
4. 处理 stale run 并检查活跃运行；
5. 读取 Scope Head/Revision，按模式执行 file 或 architecture 状态机；
6. 新 architecture 会话只接受 `resolved` 非空候选并创建唯一 Revision/Head；
7. 既有同 ID 会话忽略本轮目录候选，严格复用旧 Revision；
8. 对最终 Effective Scope 执行既有文件数量上限校验；
9. 写入 run、run input 和 pending user message；
10. 整体提交；任一步异常均整体回滚。

错误优先级已经固定为 Binding mode/ID 冲突先于 active run 冲突。同模式同 ID 才继续采用
既有活跃运行 409 语义。architecture 候选仍在事务外形成，Coordinator 不在写事务中访问
知识库数据库或远端服务。

## 3. 兼容与可观测性

- `ChatRunCoordinator` 与 `ChatCommandService` 增加内部 `scope_selector`，不改变公开接口；
- 既有未显式传入 selector 的内部 file 调用构造等价 files selector，保持旧测试和调用链；
- architecture 候选必须携带显式 selector，且二者 ID 必须相等，禁止从候选反推公开请求；
- 日志增加 `scope_mode`、requested/bound architecture ID、candidate outcome、selection mode、
  `session_created` 和 Effective Scope 数量；不记录文件名、原名、URL 或正文；
- 测试中手工创建的 Schema v5 Session 若要继续启动 run，必须显式创建 files Binding；生产
  运行时对既有 Session 缺 Binding 坚持失败关闭，不自动猜测或修复。

## 4. 测试与门禁

- Coordinator/Persistence/Infrastructure/Container 定向：87 项通过，0 失败、0 错误；
- Chat 动态发现：237 项通过，0 失败、0 错误；
- `compileall` 与 `git diff --check` 通过。

新增覆盖 architecture 首次冻结、同 ID 复用时忽略当前 not-found 候选、模式/ID 冲突优先级、
空类别、损坏类别、超限全事实回滚，以及 50 个同 ID 并发请求只产生一个 accepted run、一个
Binding 和一个 Revision。既有 file 并发、终止、删除、持久化与容器测试保持通过。

全部测试使用临时 SQLite 和 Mock/Fake，未执行 `run.py`，未连接真实服务。

## 5. 门禁结论

阶段 4 验收通过，可以进入阶段 5。当前没有新增待商讨事项；公开路由仍不会接收
`architectureId`，因此本阶段内部能力尚不可由前端触发。

证据仍限定为 Windows、SQLite 单实例与离线环境。未来多实例部署必须以共享数据库事务、真实
lease/fencing 和可靠任务队列替换当前协调适配器，不能将本阶段结果直接外推为跨实例一致性。
