# 知识谱系类别文件对话全面审查修复执行记录

## 1. 执行结论

本轮针对提交 `19383c899f5335bc743b8be97527100e5a89f244` 与
`539b046e3143a7c88cc46ff5fc9f2e7558f7071b` 所形成的知识谱系类别文件对话链进行全面
审查后修复。改造没有增删任何前后端接口参数，也没有新增路由、响应字段或内部身份泄露；
经负责人确认，只修正以下公开语义：

1. Chat `architectureId` 限制为 `1..9007199254740991`，保证历史 JSON number 在
   JavaScript 中可精确表示；其他业务的 64 位 ID 合同不变。
2. 同一 `chatId` 的 409 冲突在全局流容量 429 之前判断。
3. `/llm/chat` 的权威 SSE 事件表补齐既有 `aborted` 终结事件。

## 2. JavaScript 安全整数边界

- 新增 Chat Domain 单一常量 `MAX_CHAT_ARCHITECTURE_ID`。
- Web Selector、Candidate、Scope、Resolver、运行快照和 Chat Repository 统一使用该上界。
- Schema v6 对 Binding、Revision、run input 和 message 增加数据库兜底，迁移前先审计存量。
- Weaponry、知识谱系解析和分类节点变更继续使用各自原有 ID 规则，没有被 Chat 边界反向
  收紧。
- 合同黄金资产、路由错误文本和权威接口文档同步为
  `architectureId必须为1到9007199254740991之间的正整数`。

## 3. 持久化 Admission Guard 与 409 优先

Schema v6 新增正式 Session/run 之前的短期 `chatId` Guard：

- Guard 创建使用 SQLite `BEGIN IMMEDIATE` 与 `chat_id` 唯一键；它不创建 Session、Scope、
  run、message 或文档 Binding。
- 已有会话先校验不可变模式和 architecture ID，再检查活动运行；同一新 `chatId` 的并发
  失败者在 Guard 唯一键处稳定失败。
- 路由取得 Guard 后再申请进程内全局流容量，因此同一 `chatId` 冲突和容量满同时成立时
  返回 409；不同新 `chatId` 在容量满时仍返回 429。
- 正式受理事务验证 Guard 的 token、模式、ID 和过期时间，并在提交 Session/Scope/run/input/
  message 的同一事务内消费 Guard。
- 受理前失败、容量拒绝或异常路径按 token 幂等释放；崩溃遗留 Guard 由过期回收处理，旧
  token 不能删除后来请求的新 Guard。

该实现只证明当前 SQLite 单实例语义。未来共享数据库适配器仍必须实现条件插入、数据库权威
时间、租约续期和 fencing，不能把本地 Guard 直接宣称为多实例生产许可。

## 4. Schema v6 一致性修复

v5 原触发器只阻止部分 architecture 错配，未对反方向提供同等保护。v6 替换为对称约束：

- architecture Binding 只能写入同 ID 的 `architecture_initial` Revision；
- files Binding 只能写入 `automatic_initial` 或 `explicit` Revision；
- 任一 Revision 缺少会话 Binding 均失败关闭；
- v6 故障注入验证 Guard 表、触发器替换和 migration 版本记录可整体回滚；
- v4 fixture 可继续依次迁移到 v6，重复初始化不会漂移既有 Scope、Head、run input 或消息。

## 5. 有界类别读取

`DatabaseService.list_document_records_by_architecture_id()` 增加内部可选 `limit`，并保持参数化
SQL 和稳定排序。生产 Resolver 只读取 `DOCSENSE_CHAT_MAX_FILES + 1` 条：

- 不超过上限时形成完整候选；
- 多出的唯一一条只用于证明已超限；
- 最终仍由原子受理事务使用既有 HTTP 400 文本整体拒绝，不截取前 N 个文件；
- 已有 architecture 会话继续只读冻结 Scope，不重新查询类别。

## 6. 远端文档绑定失败关闭

旧执行器在供应商回执缺少所请求文档时，会回退到受理快照中的旧 `document_ref` 并写入本地
Binding，存在“远端未确认、本地却成功”的风险。修复后：

1. 以规范化 `external_location` 作为绑定回执匹配键；
2. 每个本轮新文档必须恰好匹配一个回执；
3. 缺失、同位置重复或回执类型无效时整批抛出稳定资源异常；
4. 所有回执完整确认后才开始写本地 Binding 和激活资源租约，避免半批成功；
5. 唯一回执可以提供供应商规范化 `document_ref`，模型选择和本地 Binding 使用该值；
6. 不允许供应商把冻结成员替换为另一个远端位置。

当前离线 Fake 已覆盖缺失、重复和规范引用三种路径；真实 AnythingLLM 列表回执仍列入未来
I7 授权环境门禁。

## 7. SSE `aborted` 文档漂移

运行时和中断接口早已支持 `aborted`，但两份 `/llm/chat` 发送接口的 SSE 事件表只列出了
`chatInfo`、`textChunk`、`done` 和 `error`。权威文档现已明确：

- `done`：完整成功结束；
- `aborted`：中断已经被执行流观察并收敛，回答不完整；
- `error`：执行失败结束。

三者都是终结事件，但业务含义不同。前端收到 `aborted` 后应停止消费，不得把已收到片段视为
完整 assistant 回答。该修订只补齐既有事件，没有增加任何 SSE 字段。
