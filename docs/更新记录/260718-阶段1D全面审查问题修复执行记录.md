## 2. 已确认口径

1. Selected Evidence 不截断单条正文，不限制全部 Evidence 总字符数，也不限制单文档贡献的
   Evidence 数量或字符数。INPUT 8、TABLE 16 仅是一次向检索供应商请求 Candidate 的批次大小；
   `max_table_rows=100` 只限制 TABLE 结构化答案行数。
2. 公开请求出现重复 TABLE 列名时维持既有首次出现列语义；原始模板仍完整保存。业务保证不会
   传入该形状，因此不新增 HTTP 参数错误。
3. “类型”是宽泛分类，不能单独作为 TABLE 行身份。
4. Schema v1 必须保存足以约束重试的完整策略事实，不能只保存宽泛策略 ID。
5. 约 1500 层等极深 JSON 是明确不处理的极端输入，本轮不增加递归深度防护。
6. ArchitectureId 使用统一规则：接受 `1..9223372036854775807` 的 JSON 整数或只含 ASCII 数字
   的字符串，允许前导零；所有入口和输出使用同一规范身份。
7. 成功结果必须完整覆盖受理字段和 TABLE 列，且领域结果状态必须与任务终态元数据一致。

## 3. 代码改造

### 3.1 Evidence 完整保留

- `EvidenceSelectionPolicy` 删除总行数、单文档行数、总字符数和单文档字符数四类配额；
- `EvidenceSelectionResult` 删除截断 Candidate 事实，只保存 Selected Evidence 和拒绝原因；
- `select_evidence` 对通过来源、分数、质量、相关性和同文档精确去重门禁的正文全部完整保留；
- 遗留模式 2 的 Prompt 行规范化仅过滤空白并去除正文首尾空白，不再按数量或字符截断；
- Candidate top-N 与 Selected Evidence 配额在代码、测试和文档中明确分离。

这项决定可能增加单次模型输入规模，但符合已确认业务口径。后续 1D-3/1D-4 只能通过检索质量、
供应商能力和资源限流治理成本，不得在 Adapter 或 Application 中暗中恢复内容截断。

### 3.2 TABLE 行身份与重复列边界

- 显式 row key 优先；随后只使用名称、型号、编号、代号、标识等强身份列；
- “类型”列从强身份和复合身份中排除；仅剩弱类型信息时按稳定输入序号保留独立行；
- 后备复合身份携带列名，避免相同值位于不同列时发生碰撞；
- 请求字段 Specification 继续对重复列采用首次出现列，原始 Frozen JSON 模板不丢失重复项；
- 内部结果容器仍拒绝重复列，防止 Application 自行构造含混结果时被 `dict` 静默覆盖。

### 3.3 Schema v1 确定性重试

execution 输入现在严格冻结：

- provider、embedding、reranker、Retrieval Query、score semantics、相关性信号和阈值；
- INPUT/TABLE Candidate 批次和同文档精确去重策略；
- Extraction strategy、Prompt 版本、上下文策略和模型指纹；
- TABLE 合并策略版本与结构化答案行数；
- 可选辅助语境 policy、术语目录指纹、Top-N 和辅助语境字符数。

Codec 使用精确键集合往返，缺失或未知字段、版本/身份不一致、NaN/Infinity 和不支持策略均失败；
Decoder 不读取当前环境变量为旧 execution 补默认值。Schema v1 尚未进入生产，测试历史数据无需
迁移。

### 3.4 ArchitectureId 单一身份

新增供应商和框架无关的 ArchitectureId 领域规范化函数，由以下路径共同复用：

- `/llm/weaponry` 当前路由和 1D-2 新 Parser；
- weaponry 类型 `/llm/check-task`；
- weaponry 类型 `/llm/progress` 订阅；
- `WeaponrySubmission`/Schema v1 快照交叉校验；
- 遗留 `run_weaponry_task`、Progress payload 和 Callback。

修复前，主路由可将 `"00010502"` 作为业务键 `10502` 受理，但遗留 Worker 仍可能访问业务键
`00010502`。修复后所有内部任务键为 `10502`，Progress/Callback 的 `architectureId` 为 JSON
number。非法超长十进制字符串在调用 `int` 前完成长度和上界判定，不会泄漏 Python 转换异常。

### 3.5 成功结果完整性与终态一致性

- `WeaponryResult` 和成功 Callback 至少包含一个字段对象；
- 终态提交前按不可变输入快照验证字段数量、顺序和完整 Specification；
- TABLE 每个已返回数据行必须逐列、同序覆盖冻结列；空 TABLE 数据行仍是合法成功结果；
- `WeaponryResult.status=2` 只能与 `succeeded/2` 一起提交，失败结果只能与 `failed/3` 一起提交；
- 校验发生在通用 Task Adapter 调用 Repository 终态 CAS 之前；失败时 execution 保持 `running`，
  不会持久化相互矛盾的终态和公开投影。

通用 Adapter 通过可选 Codec 校验钩子调用业务规则，没有反向导入 weaponry 领域模块，继续保持
任务基础设施与业务模型低耦合。
