## 2. 日志口径修正

### 2.1 路由原始请求数量

`/llm/chat` 的 Blueprint 只负责 JSON、文本、数组元素、首次出现顺序去重和显式数量上限的
早期校验。获得流容量许可时，日志将调用方数组长度明确记录为 `requested_file_count`。

因此首次空数组仍会记录 `requested_file_count=0`，但该字段不再被误解为受理事务最终选择了
零个文件。存在性、目录一致性、自动全量展开和最终数量校验继续由 Application/Coordinator
负责，路由层没有复制业务规则。

### 2.2 受理事务最终选择

Coordinator 在事务内确定最终不可变文件范围后统一记录：

- `chat_id`
- `run_id`
- `selection_mode`
- `session_created`
- `explicit_candidate_count`
- `default_candidate_count`
- `effective_file_count`

选择模式区分 `explicit`、`new_session_default`、`existing_session_empty`；兼容内部旧调用的
直接输入标记为 `legacy_input`。最终数量超限时使用相同字段集合记录拒绝原因，便于沿
`run_id` 核对受理事实。

Application 的受理成功日志同步使用 `effective_file_count`，不再使用含义不明确的
`file_count`。以上日志均不记录消息正文、完整文件清单、外部 location 或供应商 document ref。

## 3. 调试页权威来源

`build_chat_debug_bootstrap()` 对每个会话只读取一次 current binding heads，并将其现有
`fileNames` 字段用于初始化会话文件范围；已提交对话消息仍由调试页调用
`GET /llm/chat/history` 获取。两者都不依赖调用方首次传入的空数组，也不读取 AnythingLLM
外部历史。

阶段 5 增加的调试日志仅记录：

- session 数量；
- current binding 数量；
- available file 数量；
- history 消息数量。

已有 `app/templates/debug/chat.html` 正确消费上述 bootstrap/history 数据，因此不需要修改
模板，也不需要为调试显示增加公开 SSE 或 JSON 字段。

## 4. 新增和补强的回归

1. 首次空数组且知识库有两个文件时，同时验证：
   - Blueprint 记录 `requested_file_count=0`；
   - Coordinator 记录 `selection_mode=new_session_default` 和 `effective_file_count=2`；
   - Application 受理日志记录最终有效数量；
   - 选择日志不出现文件名或供应商引用。
2. 显式选择、首次默认全量和既有会话空数组分别记录不同选择模式，并校验事务创建状态和计数。
3. 调试 bootstrap 日志记录 current binding 数量，不泄漏具体文件名。
4. 通过公开 `/llm/chat` 建立首次自动全量会话后，调试 bootstrap 从 binding 展示文件，
   `/llm/chat/history` 从本地 committed 消息展示原始文件名。
5. 公开 SSE 黄金回归继续断言内部 `run_id` 不进入响应。
