# 阶段 1D-4：武器谱 Application 用例与严格 Fake 执行记录

## 1. 执行结论

阶段 1D-4 已完成离线实现与验收，可以进入 1D-5。

本波次实现了框架无关的 `SubmitWeaponryTask`、`RunWeaponryTask(task_id)` 和
`WeaponryFieldExecutor`，把 1D-1～1D-3B 已冻结的领域规则、任务控制面和供应商无关 Port 串成
一条可独立测试的应用链。实现满足以下核心结论：

1. Submit 只提交任务事实；Progress 和 Dispatcher 唤醒发生在事务提交后，通知失败不会撤销
   accepted 事实。
2. Run 只接收内部 `TaskId`，不读取原始 HTTP 请求、Flask context、环境变量或文档 Repository。
3. Candidate 必须经过确定性 Selection 才能进入 Extraction Prompt 和公开 `rows`；零 Selected
   Evidence 时 Extraction 与 Translation 调用次数均为零。
4. 每个来源只接收当前文档最终 Selected Evidence；没有共享父会话、目标文档 workspace 二次
   RAG 或跨文档回退。
5. 进度、终态和 Callback 均绑定 expected TaskId/latest owner；旧 execution 失权后不会发送
   终态 Progress 或回调。
6. 任务业务终态与 Callback 交付终态严格分离。Callback 投影、获取发送权、发送或完成失败都
   不会补写第二业务终态。
7. 审计失败、外部写副作用结果未知、任务事实提交结果未知或崩溃遗留非空资源会保留并隔离
   现场，禁止盲目清理或重建第二套资源。

本波次没有修改、增加或删除任何前后端接口参数，没有修改公开状态码、错误体或 Callback 字段，
也没有把新 Application 绑定到 `/llm/weaponry`。因此无需修改接口文档。公开路由仍执行遗留
`weaponry_service` 和路由线程；路由切换只允许在 1D-6 实施。

## 2. 实际代码结构

### 2.1 Application 稳定错误分类

新增 `app/modules/weaponry/application/errors.py`，集中定义：

- `WeaponryTaskConflictError`：同一 architectureId 的活动任务、Callback sending 或 unknown
  冲突，后续 Presenter 统一映射既有 409；
- `WeaponryPortContractError`：Port 返回类型、身份、顺序或冻结策略不一致；
- `WeaponryTaskPersistenceError`：进度或终态事实提交结果不确定，禁止补写第二终态；
- `WeaponryAuditError`：关键 Interaction Audit 预留或完成未可靠提交；
- `WeaponryExecutionError`：可稳定分类的普通执行失败；
- `WeaponryScenePreservationError`：外部写副作用或崩溃遗留资源需要隔离对账；
- `WeaponryStaleExecutionError`：慢调用返回后发现 execution 已经失去 latest 所有权。

异常只携带稳定内部错误码，不包含供应商 URL、请求正文、Prompt、Token 或响应正文；公开失败
仍使用既有 `status=3`、`msg=解析失败` Callback。

### 2.2 SubmitWeaponryTask

`app/modules/weaponry/application/submit_weaponry.py` 实现了以下顺序：

```text
WeaponrySubmission
  -> TaskSubmissionCommand
  -> TaskCommandPort.create_if_allowed（唯一原子提交点）
  -> 校验完整 accepted execution/input snapshot 身份
  -> 发布初始 Progress（可丢通知）
  -> 唤醒 Dispatcher（可丢通知）
  -> 返回内部 SubmitWeaponryResult
```

`ACTIVE_CONFLICT`、`CALLBACK_SENDING` 与 `CALLBACK_OUTCOME_UNKNOWN` 全部映射为同一稳定应用冲突，
不会在通知失败后把已经提交的任务伪装为未受理。返回结果包含内部 TaskId 供后续 Presenter 使用，
但既有 202 空响应 Presenter 不会把 TaskId 暴露给甲方。

### 2.3 RunWeaponryTask(task_id)

`app/modules/weaponry/application/run_weaponry.py` 的执行顺序为：

1. 按 TaskId 读取、校验并条件领取 execution；missing、already-running、terminal 和 stale 幂等
   收敛，不启动外部步骤。
2. 以 expected TaskId 条件写准备进度；失权立即停止。
3. 创建任务级资源记录；若同一 TaskId 已留下非空资源事实，判定为崩溃现场并隔离，禁止盲目
   重新执行。
4. 打开任务级 Retrieval Scope，并严格核对 TaskId、文档顺序、Selection profile、provider 和
   embedding 指纹；身份不一致时不进入检索。
5. 按输入字段原始顺序调用字段执行器；每个字段完成后重新做 expected TaskId 进度条件写。
6. 构造 `WeaponryResult` 并执行成功完整性校验；只有终态 CAS 成功后才发布终态 Progress 和调用
   Callback Port。
7. 正常成功、业务失败或 stale 后进入幂等 cleanup pending/cleaned；结果未知、审计缺失和崩溃
   遗留现场进入 quarantined。

任务事实写入异常不会被降级为普通业务失败。因为数据库提交可能已经成功、仅响应丢失，代码会
记录 critical、保留资源并向 Dispatcher 抛出，让后续阶段读取权威事实；不会再次写失败终态。

### 2.4 WeaponryFieldExecutor

`app/modules/weaponry/application/field_execution.py` 把字段内职责收敛为：

```text
Auxiliary Guidance
  -> 专用 Retrieval Query
  -> Target Evidence Candidate
  -> select_evidence
  -> 按冻结 document_sequence 的单来源 Extraction
  -> Translation
  -> INPUT/TABLE 纯领域组装
```

主要规则如下：

- `fieldDescription` 同时进入专用 Retrieval Query 和最终 Extraction Prompt；
- Retrieval 结果必须与 call、scope、provider、embedding 和冻结文档范围一致；
- score/rank 协议损坏按已批准的字段级空结果收敛，并保存完整拒绝原因；非法分数不会转成 0；
- 通过门禁的 Evidence 正文完整进入 Prompt 和公开 `rows`，不做单条、总量或单文档字符截断；
- 来源执行顺序固定为受理时 `document_sequence`，公开来源展示顺序固定为 Selection 排名；
- 明确的来源上下文失败最多重试一次；`OUTCOME_UNKNOWN` 不重试，直接隔离现场；
- 空回答、“未找到”或来源校验未通过只丢弃当前来源，其他文档继续；
- TABLE 每个非空单元格具有独立 `item_sequence`，同文档多次 Translation 不再发生审计键碰撞；
- Translation 失败沿用既有空字符串兼容语义，不改变字段或任务成功终态。

## 3. 审计、资源和单终态补强

### 3.1 Interaction Audit

每次 Guidance、Retrieval、Extraction 与 Translation 都先 reserve、后调用、再 complete。审计只保存
输入/输出摘要、字符数、允许文档、来源计数和稳定拒绝原因，不保存正文。

本波次补充：

- Translation `call_id` 增加可选 `item_sequence`，格式为
  `...:{operation}:i{item_sequence}`；attempt 仍单独进入 `attempt_key`；
- Retrieval 审计要求 `selected_count + rejection_reasons` 精确覆盖全部 Candidate；
- SQLite Audit 表和 DTO 同步保存 `item_sequence` 与有序拒绝原因；
- 开发期旧空表允许只增列升级，项目已明确不存在需要兼容的历史数据和旧 Worker；
- 审计 receipt 必须精确匹配 TaskId、attempt key 和 reservation ID，否则禁止成功终态。

### 3.2 资源现场

Application 在任何外部资源创建前先建立 task 级资源记录。Retrieval Adapter 已登记的资源由
Application 使用相同幂等键复核；严格 Fake 则由 Application 补登记相同事实。

以下情况进入 quarantine：

- scope 创建或 Extraction 写副作用结果未知；
- scope 的任务、文档或策略指纹不一致；
- 关键审计完成失败；
- 任务事实提交结果未知；
- 同一 TaskId 已存在非空、非初始资源记录。

普通清理明确失败进入 cleanup pending，由 1D-6 有界恢复继续；shared 资源永不由任务清理。

### 3.3 Callback 单终态

Callback DTO 投影也被纳入终态后的独立交付保护。即使 `result.to_callback()` 本身出现程序错误，
也只记录 `port_error`，不会逃回 Run 主流程补写失败终态。Callback 调用前再次检查 latest，再执行
acquire、deliver、complete；真实 Guard/恢复 Adapter 留到 1D-6 装配。

## 4. 严格 Fake 与测试可信度修复

新增或扩展：

- `FakeWeaponryTaskCommandPort`：线程安全原子受理、领取、expected Progress/终态、latest、扫描、
  冷却和故障注入；默认按真实 Repository 状态自动区分 active、already-running、terminal、stale；
- `FakeWeaponryProgressPublisherPort`：只记录带 expected TaskId 的无敏感通知；
- Retrieval Fake：支持错误 scope 结果注入，并严格检查审计和资源登记前置；
- Audit Fake：暴露只读 completion 轨迹，支持 reserve/complete 身份和故障注入；
- 共享调用记录器：支持显式清空，受理与执行阶段可以独立断言；
- 所有 Fake 都通过运行期 Port Protocol 检查。

审查中纠正了两个会造成测试假阴性的 Fake 行为：

1. 同一业务键已有 accepted/running execution 时，默认受理必须返回 active conflict；
2. 已 succeeded/failed 的任务再次派发时必须返回 terminal，不能重新变为 running。

因此现在能够证明重复提交没有第二个 accepted 事实，重复 Run 没有第二次 Extraction、终态和回调。

## 6. 生产与后续边界

1. 1D-4 代码尚未进入生产链，没有部署，也没有被公开路由或组合根调用。
2. 50 个并发 Application execution 只证明单进程内任务状态和 Port 隔离；不代表 50 个重型
   AnythingLLM/模型任务应并行。生产目标仍是 50+ 在途任务，重任务按资源限流依次排队。
3. 真实 AnythingLLM score/rank、来源身份、空 workspace 模型行为和 Provided-Evidence Context
   仍须在 1D-6 切流前受控联调；失败时停止切流，不回退到目标文档 workspace RAG。
4. 1D-5 下一步实现通用本地 Dispatcher、严格配置和离线组合根；必须保持 accepted 持久积压、
   常量空间唤醒、单执行 Worker、维护任务隔离和单实例门禁。
5. 1D-6 才实现真实 Callback Guard、同步 check-task 恢复、资源有界恢复和公开路由切换；接口文档
   只有在该波次实际切换后才更新实现状态。
6. RabbitMQ 可靠队列、多实例、MySQL 一致性和跨实例容量仍属于后续阶段，不因 1D-4 测试通过
   而提前宣称完成。
