## 3. 最终实现事实

### 3.1 受理与执行

1. 报告请求经严格 Web Parser 转换为内部不可变命令；公开路由只负责解析、调用 Application 和展示结果。
2. SQLite 以追加式 execution 保存 accepted 事实；相同业务键通过原子事务和 expected TaskId 条件写实现 latest-wins。
3. Worker 只接收 TaskId，并从持久化快照恢复输入，不依赖请求线程中的可变对象。
4. 本地 Dispatcher 的 Event 只是常量空间唤醒提示；真正的恢复依据是 SQLite accepted 事实、启动扫描和周期扫描。
5. 当前仍是本地单执行 Worker 和单实例门禁，不是可靠队列，也不具备跨实例全局调度语义。

### 3.2 外部 I/O、审计与资源

1. 文件、Artifact、RAG、审计、Callback 和资源恢复均通过 Port 隔离；任务级 Adapter 不共享有状态供应商 Session。
2. 最终 HTML 采用临时文件、flush、`fsync`、`os.replace` 原子发布，并以大小和摘要校验完整性。
3. RAG 调用保存 trace、Context/Conversation、call_id 和脱敏摘要；审计成功是业务成功的硬前置条件。
4. 外部创建或删除结果未知时进入保守隔离，不得按名称猜测、盲删或直接重放。
5. 资源恢复按逐事件检查点、心跳、lease/fencing 和持久 attempt 水位推进；坏资源与毒任务进入冷却或隔离，不能阻断整批扫描。

### 3.3 Callback Guard 与同步恢复

1. Worker 正常回调和 `/llm/check-task` 同步恢复共用同一套持久化 Guard、attempt、lease 和 fencing。
2. 外发前再次读取最新 execution，旧任务不得发送；HTTP 仅严格 2xx 视为明确成功。
3. 明确失败可以在既定策略下恢复；结果未知默认不自动重放，避免重复业务副作用。
4. 回调发送结果、历史追加和连接释放均有独立门禁；日志只记录任务标识、状态、attempt 和脱敏错误分类。

## 4. 关键审查修正

- 将 reportId 约束统一为已批准的 128 位数字上限，并保持可选文本兼容字符串化。
- 将 execution 内部结果与公开 Callback 投影分离，避免持久层对象泄漏到对外载荷。
- 在慢 I/O、Callback 和终态提交前执行 latest 复核，stale execution 只能收敛，不能覆盖新任务。
- 发送前发现同键新任务时立即返回冲突语义，不等待旧回调网络请求。
- Artifact “已登记”不再等同于“文件完整”；缺失、篡改或所有权不明时进入 pending/quarantine。
- Dispatcher 停机改为真实等待后台线程退出；许可等待可取消，维护线程与业务执行线程隔离。
- FIFO 使用持久调度序号，领取前异常和资源首页坏记录不会造成永久饥饿。
- Progress 的同业务键更新位于同一原子区间，防止旧任务覆盖最新投影。

## 6. 当前与未来边界

- 当前报告任务仍由本地单 Worker 执行；50 线程离线测试只证明隔离和原子性，不证明模型侧吞吐。
- SQLite 单实例锁不是分布式 lease/fencing；阶段 2 以后仍需统一 Task/Attempt/Step/Event、可靠队列、共享数据库和跨实例恢复。
- Callback 只提供持久 Guard 下的 at-most-one-sender 竞争控制；网络结果未知时无法保证 exactly-once，接收方仍需幂等。
- 生产发布必须单独完成目标数据库、后台服务、资源容量、停服排空和回滚门禁。
