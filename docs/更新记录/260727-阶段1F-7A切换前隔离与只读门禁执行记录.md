## 2. 新增切换前门禁

### 2.1 只读预检脚本

新增 `scripts/inspect_analysis_cutover.py`。它只有 dry-run 模式：直接以 SQLite `mode=ro` 和
`PRAGMA query_only=ON` 读取已存在数据库，不导入会初始化 Schema 的 `LLMTaskService`，不创建
HTTP Client，不访问 AnythingLLM，也不启动 `run.py`。

```powershell
venv\Scripts\python.exe -B scripts\inspect_analysis_cutover.py --database <已有SQLite文件> --limit 50
```

脚本必须同时发现 `llm_tasks`、`llm_task_executions`、`callback_delivery_guards` 和
`rag_resource_leases` 四张事实表；缺任一表即失败，不补表、不迁移。输出是稳定排序、每类受 `--limit`
（1～500）限制的 JSON，仅包含内部 execution 身份、状态、lease version 和更新时间，不导出业务键、
文件名、路径、请求正文、回调地址或密钥。

| 阻断项 | 判定口径 |
| --- | --- |
| `legacyActiveTasks` | `business_type=file` 且公开 `status` 为 `0/1`，并且没有同一 execution 的完整 `batch_id + batch_sequence` 新批次事实。 |
| `legacyRecoverableCallbacks` | 没有完整新批次身份、已进入公开终态且 Callback 仍为 `pending/failed` 的历史 file 任务；必须先由当前旧恢复器排空，禁止新旧恢复器猜测性双路补发。 |
| `newRunningExecutions` | 具有完整新批次身份但仍为 `running` 的 file execution；1F 不自动接管 running，必须保留现场并停止切换。 |
| `callbackGuardBlockers` | `business_type=file` 且 Guard 仍为 `sending` 或 `outcome_unknown`。 |
| `openLegacyRagLeases` | `business_type=file` 且资源租约仍为 `planned`、`active`、`audit_failed` 或 `audited`。 |

另行输出 `newAcceptedExecutions` 观测值：accepted 尚未执行外部副作用，可在唯一新 Dispatcher
启动后继续消费，因此不自动阻断，但部署人员必须显式核对。五类硬阻断计数均为零时退出码为 `0`；
存在任一阻断项时退出码为 `3`，部署编排必须停止；读取/Schema
异常为 `1`，参数错误由 `argparse` 使用 `2`。脚本不存在 `--apply` 或自动清理能力。外部副作用未知的
Guard、租约或任务必须由人工确认后处置，不能由预检工具重放 Callback、RAG close/delete、模型或知识库写入。

### 2.2 50 任务共享实例隔离

新增 `tests/test_analysis_stage1f7a.py`。测试使用一个共享的 `RunAnalysisTask` 实例、50 个真正并发的
工作线程，以及按 `TaskId` 维护独立期望队列的严格 Fake。每个样本具有独立的：

- 冻结输入、`batch_id`、任务目录、下载/上传路径；
- Context、Conversation、Document、知识库幂等键和 RAG 生命周期事件；
- Progress、翻译结果、Callback Guard lease 与 Callback payload；
- `state + version` CAS 资源记录及最终清理事实。

测试同时验证 50 个执行全部成功、每个类别恰好覆盖 50 个不同 `TaskId`、5 次 Progress/任务、资源记录
全部独立且最终为 `cleaned`。任一 Application 实例字段缓存、共享最近目录/Session/Callback、或资源 CAS
跨任务覆盖都会导致严格 Fake 或内存 CAS Store 失败。

同一测试文件还以 AST 检查 `app/modules/analysis/` 不得导入旧
`app.services.llm_service.analysis_service` 或旧 Worker 模块，防止新运行链重新污染遗留执行器。

## 3. 故障矩阵复核

本阶段没有以“50 个成功任务”替代故障验证。下列离线测试共同覆盖切换前必须保留的 fail-closed 边界：

| 故障类别 | 主要离线证据 |
| --- | --- |
| 文件、任务目录、RAG 生命周期 | `test_analysis_production_adapters.py`：任务目录隔离、越界下载拒绝、RAG create/upload/bind/query/close 的身份与 unknown 收口。 |
| 模型、召回与审计 | `test_analysis_application.py`：模型修复预算耗尽、召回审计失败禁止建 Session、交互审计失败禁止永久入库并保留现场。 |
| 知识库、翻译与终态 | `test_analysis_application.py`、`test_analysis_translation_isolation.py`：知识库 committed/not-applied/unknown、翻译降级、终态提交后 close/Factory 退出异常不反写终态。 |
| Callback | `test_analysis_callback_guard.py`、`test_analysis_application.py`：空 URL 收敛、unknown 冻结、50 并发成功或明确拒绝均至多一次 HTTP、窄投影读取、终态提交后才投递。 |
| 资源 close 与恢复 | `test_analysis_resource_recovery.py`：close 意图、迁移矩阵/CAS、已知结果 fallback、审计追加、有限退避、非法 JSON/结构毒记录隔离及后续扫描继续，禁止重放删除。 |
| SQLite 受理与调度故障 | `test_analysis_batch.py`：32 项事务回滚、busy、唤醒失败后的持久发现、重复 claim、50 同键/不同键并发及全局顺序。 |

这些均为临时 SQLite、严格 Fake 和替身 Transport 的离线验证；故障日志由显式注入产生，不代表连接过
真实模型、AnythingLLM、OCR、知识库或 Callback 服务。
