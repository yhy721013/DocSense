## 2. 主要实现

### 2.1 纯领域候选快照

新增纯领域内部 DTO：

- `ChatDocumentCandidate`
- `ChatDocumentSelectionCandidates`

DTO 只保存不可变的基础字段，不依赖知识库 Service、SQLite Repository、Flask 或供应商 Port。
显式候选与首次默认候选互斥，并保留严格 Schema v1 序列化/恢复能力，便于未来迁移到可靠队列
时持久化同一份策略快照。原 Application 导入路径继续兼容转发，避免无关调用方迁移。

### 2.2 Application 与协调协议接线

`SynchronousChatRunExecutor.prepare_chat_run()` 现在按以下方式准备候选：

1. 非空 `fileNames`：只解析显式候选，不读取全量目录；
2. 空数组且本地 session 已存在：直接准备空候选，不扫描知识库；
3. 空数组且本地 session 尚不存在：一次读取并冻结全量可用目录，作为仅限首次 session
   使用的默认候选。

候选与数量上限通过 `ChatCommandService` 传入内部协调协议。以上均为内部关键字参数，不进入
Blueprint 请求、SSE、历史响应或供应商 DTO。

### 2.3 SQLite 单事务原子选择

`ChatRunLockService.try_acquire_chat_run()` 在同一 `BEGIN IMMEDIATE` 事务中完成：

1. `INSERT OR IGNORE chat_sessions`，根据实际插入结果得到 `session_created`；
2. 校验 session 状态、收敛过期运行并检查同一 `chatId` 的活跃运行；
3. 显式候选始终优先；只有 `session_created=true` 才采用首次默认候选；
4. 对最终有效文件集合执行 `DOCSENSE_CHAT_MAX_FILES` 校验；
5. 写入 accepted run、不可变 run input 和 pending user 文件快照；
6. 任一步异常均回滚同一事务。

锁服务只消费纯候选快照，不读取知识库，也不持有网络客户端。后续执行仍从已持久化的 run input
读取文档，不会在执行时重新扫描知识库。

## 3. 故障与并发验证

本阶段新增或补强以下离线证据：

- 首次空数组采用默认候选，并按冻结顺序写入 run input 和首轮 pending user；
- 既有 session 不采用默认候选；
- 自动展开后的最终数量超限时，session、run、run input、message 全部不存在；
- 注入 pending user 写入异常时，同样回滚上述全部本地事实；
- 首次运行已受理但后续失败时，相同 `chatId` 重试不再次自动全量；
- 50 个线程并发受理同一新 `chatId`，恰好一个 accepted、其余 49 个 busy，且只存在一份
  run input；
- 公开路由在知识库存在文件时，首次空数组使用全量文件；超限和目录身份冲突保持既有
  HTTP 400 映射；
- 精确 SSE `chatInfo/textChunk/done` 字节结构与内部运行标识不泄露基线保持不变。
