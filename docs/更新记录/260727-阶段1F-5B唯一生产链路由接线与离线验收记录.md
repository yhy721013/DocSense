## 1. 结论

文件分析公开入口已完成代码级唯一链路切换：`POST /llm/analysis` 现在只经过 Flask Parser、
`SubmitAnalysisBatch` 和 Presenter；成功仍返回严格空 `202`，不暴露 `TaskId`、`batchId`、租约或调度状态。
批量受理继续由新 Analysis Adapter 在 SQLite 短事务内原子裁决，提交后只发送一次无身份的 Dispatcher 唤醒。

file 类型 `/llm/check-task` 现在只调用已装配的 `RecoverAnalysisCallbackSynchronously`，与新 Worker 共用同一
Callback Guard。路由不再回退到遗留 `replay_callback_if_needed`，因此不会在新旧恢复器之间产生第二个回调
owner。缺少完整新批次身份的历史终态任务也不会被新恢复器猜测性补发；这类待恢复回调必须在发布前只读预检中
清零并人工处置。

本次只完成代码和离线验证，**没有**停止服务、启动 `run.py`、连接真实后台服务、操作生产 SQLite，或执行生产
切换。当前能力仍仅限 SQLite `single_instance`，不应表述为可靠任务队列、多实例调度、`running` 自动接管或
生产高并发验证。

## 2. 实现内容

### 2.1 `/llm/analysis` 的薄路由

`app/blueprints/llm.py` 新增两个小型内部转换点：

- `_analysis_policy_snapshot()` 从已校验的容器配置冻结本次策略，并持久化到 `AnalysisTaskInputV1`；Worker
  后续不重读环境变量，避免受理和执行期间的配置漂移。
- `_analysis_http_response()` 只把框架无关 Presenter 结果转换为 Flask 响应，确保 `202` 为零字节，错误体仍只
  包含既有 `error` 字段。

`llm_analysis()` 的顺序为：公开请求解析、策略快照、原子批次受理、一次有界唤醒、既有 HTTP 呈现。有效请求在
容器缺少新运行链时会显式失败，绝不为了兼容而恢复遗留线程；未分类的基础设施异常仍交给 Flask 保持既有 HTML
`500` 边界，避免把不确定的受理结果伪装成成功。

### 2.2 file `check-task` 的唯一回调恢复 owner

在保持既有参数验证、单项缺失 `404`、多项缺失不阻断其余项、成功严格空 `200` 的前提下，file 分支改为调用
`ApplicationServices.analysis_callback_recovery`。该用例使用新 execution 的 latest 投影和 SQLite Callback Guard；
它不会读取旧回调 URL 配置后直接发 HTTP，也不会调用遗留任务服务恢复器。

离线容器辅助装配了 Submit、Callback Recovery 和 Dispatcher 的显式 Fake，使路由测试可以验证受理和回调边界，
但不会启动后台线程或访问网络。

### 2.3 永久回归门禁

新增/调整测试锁定以下事实：

- `llm_analysis` 必须调用 Parser、Submit 与 Presenter，且 AST 中不得出现路由线程、`task_service`、
  `progress_hub`、RAG/Knowledge Factory 或旧文件执行入口；
- 合法提交落库后存在新 `batch_id`/`batch_sequence`，路由线程从未创建，Dispatcher 仅收到一次唤醒；
- 所有 400/409/413/503/500、严格空 `202`、请求上限和批量原子性继续符合冻结契约；
- file `check-task` 使用新 Callback Guard，历史无批次身份的终态待恢复回调不允许回退到旧恢复器；
- 显式容器 Fake 的策略快照已持久化，路由受理不取得 RAG 或知识库租约。

## 3. 接口与数据影响

本次不需要修改接口文档，也不需要接口协商。以下公开内容均保持不变：

- `POST /llm/analysis`、`POST /llm/check-task` 的路径、业务类型和参数；
- 成功严格空 `202`/`200`，以及既有 `400`、`404`、`409`、`413`、`503`、`500` 的语义；
- Progress、Callback 的业务键、字段、状态和 Header。

数据库没有新增破坏性迁移或历史数据改写。新受理继续使用既有追加式 execution/batch 事实；历史 file 任务保持原样。
因此发布前不能通过迁移或自动重放把旧任务伪装成新任务，尤其不能清空 `outcome_unknown`、开放资源租约或回调
Guard 来绕过门禁。

## 5. 尚未授权的生产发布步骤

真实发布仍需要负责人确认**目标 SQLite 文件、旧 file 服务/Worker 的控制权和发布窗口**。确认后，必须按设计第 18
节执行：停止接收新的 file 请求，等待旧线程自然结束，对确认目标运行只读预检，核对五类硬阻断项均为零并显式
检查 `newAcceptedExecutions`，备份并校验数据库，再在旧进程完全停止后启动唯一的新 Dispatcher。

建议的只读预检命令为：

```powershell
venv\Scripts\python.exe -B scripts\inspect_analysis_cutover.py --database <已确认的SQLite文件> --limit 50
```

预检退出码 `3`、读取异常、`sending/outcome_unknown`、旧活动任务、历史待恢复回调、开放旧 RAG 租约或新
`running` execution 任一存在时，必须停止发布并人工处置。不得在线双跑新旧链路、盲目补发 Callback、重放
RAG/知识库副作用，或将 `running` 强行改回 `accepted`。
