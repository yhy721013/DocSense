# 文件对话请求与活动范围分离阶段 3 执行记录

## 1. 原子受理状态机

`ChatRunLockService` 已在同一个 `BEGIN IMMEDIATE` 事务内完成：

- 创建或读取会话；
- 回收过期运行并检查活动运行；
- 读取并校验 Scope Head；
- 按首次空、显式非空、后续空三种分支确定 Effective Scope；
- 校验最终生效文件数量；
- 写入 run；
- 必要时追加不可变 Scope Revision 并以 CAS 切换 Head；
- 写入 requested/effective 分离的 run input；
- 只按 Requested Scope 写入 pending 用户消息。

首次空请求创建 `automatic_initial` Revision；任意非空请求创建 `explicit`
Revision；后续空请求只引用当前 Head，使用 `active_scope_reuse`，不创建重复
Revision。

已有 session 缺失 Scope Head 时失败关闭，不扫描知识库或读取 Workspace bindings
进行猜测恢复。

## 2. 回滚与并发

新增并验证以下事务门禁：

- 首次自动范围超限时不留下 session、scope、run、input 或 message；
- 既有范围后的显式请求超限时，原 Head 和 Revision 数量保持不变；
- pending message 故障注入会回滚本次全部受理事实；
- 同一 `chatId` 的 50 个首次空请求只允许一个 accepted，并形成唯一 Head；
- 同一 `chatId` 的 50 个显式范围替换只允许一个 accepted，只追加一个新 Revision，
  Head 精确指向该 accepted run 的 Revision；
- 竞争失败者不留下孤立 Scope Revision 或 run input。

当前并发证据仍仅适用于 SQLite 单实例。

## 3. Requested 与 Effective 执行 DTO

恢复执行 DTO 已同时携带 Requested Scope 与 Effective Scope：

- Effective Scope 继续供绑定和模型调用使用；
- Requested Scope 供消息附件和历史审计使用；
- 持久化恢复路径始终显式传入两套事实；
- 兼容性的内部直接构造路径仍可将旧单一文件输入视为显式请求，但不会影响正式
  run-id 恢复链。

这项分离修复了自动全量范围写入 pending message 后，事件记录器再次按有效范围写入所导致
的幂等身份冲突。
