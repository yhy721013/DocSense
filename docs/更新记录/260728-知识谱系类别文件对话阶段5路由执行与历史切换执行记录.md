# 知识谱系类别文件对话阶段 5 路由、执行与历史切换执行记录

## 1. 阶段范围

本阶段完成已批准 architecture 合同的生产路径切换：既有 `/llm/chat` 解析严格互斥选择器，
Application 形成候选并原子受理，Executor 只按持久化 run input 执行，`/llm/chat/history`
按消息事实互斥投影公开字段。没有增加或修改 SSE 事件。

## 2. 路由与错误映射

- Blueprint 统一调用 `parse_chat_scope_selector()`，按字段是否出现判定 `architectureId` 与
  `fileNames` 冲突；
- architecture ID 继续复用既有 Web 正整数规范化，历史中始终输出 JSON number；
- 新类别为空映射 HTTP 404 与
  `architectureId对应类别不存在或没有可用于对话的文件`；
- 损坏/歧义目录映射 HTTP 400 与
  `architectureId对应类别文件无法形成有效对话范围`；
- mode 和 architecture ID 冲突分别映射获批的两个 HTTP 409 文本；
- 超限继续复用 `fileNames超过文件对话数量上限`；
- fileNames 模式、SSE、chatId、message、429 和活动流 409 行为保持不变。

## 3. 执行与快照不变性

- `SynchronousChatRunExecutor` 仅在尚无 Session Binding 的竞争首轮调用 architecture
  Resolver；
- 已有任意 Binding 时不再查询当前类别，把有界占位候选交给 Coordinator 校验 mode/ID；
- 同 ID architecture 会话始终从原 Scope Head 恢复 Effective Scope，不吸收后来新增文件；
- Worker 继续只接收 `run_id`，从 `chat_run_inputs` 恢复文档引用，不把 architecture ID
  传给 AnythingLLM 作为动态查询条件；
- `ChatRunStreamRequest` 保存 requested architecture 事实，使执行期 pending message 的
  幂等身份与受理事务一致；
- Workspace 仍可累计已经实际绑定的文档版本，但每次模型调用只传冻结 Effective Scope 的
  document refs。

## 4. 历史投影

- file user：继续返回 `files`，不返回 `architectureId`；
- architecture user：返回 number `architectureId`，不返回 `files`；
- assistant：两者均不返回；
- title 仍只消费 role/content，不把 ID 或实际成员加入标题 Prompt；
- history 不查询知识目录，也不从当前类别推导或修复任何字段。

- 合同、Chat Port、AnythingLLM Gateway、Container、架构边界：82 项通过，0 失败、0 错误；
- `compileall` 与 `git diff --check` 通过。

新增 E2E 覆盖字符串前导零 ID、首次直接文件冻结、两轮 SSE、已有 Binding 禁止目录重查、
类别新增后旧快照不扩张、正反向 mode 冲突、不同 ID 冲突、空/损坏类别公开映射，以及
history 的 user/assistant 字段集合精确匹配。全部测试使用临时 SQLite 和 Mock/Fake，未执行
`run.py`，未连接真实服务。
