## 1. Callback latest-wins 与 HTTP 并发修复

### 1.1 外发前再次校验权威事实

Callback Adapter 在真正调用 HTTP Transport 前，按以下身份再次读取并校验持久化 Guard：

- task/execution 仍是同一业务键的 latest owner；
- lease token、fencing version 和发送期限仍匹配；
- Guard 仍处于当前执行可发送状态。

任一条件不满足时返回内部 `stale`，不触达网络。`RunReportTask` 遇到该结果也不会再用旧
lease 完成新 Guard，从而避免旧任务在新任务已经受理后发送过期回调。

数据库复核与实际 socket 写入之间仍存在操作系统调度级的极窄窗口，单实例应用无法对外部
HTTP 接收方建立跨系统原子事务。因此人工解除 `delivery_outcome_unknown` 之前，必须明确
确认旧 Worker/旧进程已经停止或隔离，并把确认、操作者和原因写入追加式审计。该要求不是
新增公开参数，而是内部运维安全条件。

### 1.2 Web 请求线程不等待旧回调

`SubmitReportTask` 现在只执行一次原子受理：

- active execution、callback sending、callback outcome unknown 均立即映射到已经批准的
  HTTP 409；
- 不在 Flask 请求线程中轮询 Guard，不睡眠，不在同一请求内重试；
- 甲方仍按原接口稍后重新提交，没有新增重试参数或响应字段。

该修复避免 50 个并发短请求被同步等待占满 Web Worker。

### 1.3 回调历史调试副本

- 历史文件改为排他原子创建，消除“先检查存在、再写入”的竞争窗口；
- `reportId=0` 不再被布尔表达式误判为缺失；
- 调试副本在 HTTP 尝试之后保存，避免本地磁盘 I/O 扩大发送前权威复核到网络调用之间的
  时间窗口；
- 历史保存失败仍只记录日志，不改写真实 HTTP outcome。

## 2. Artifact 所有权不再等同于文件完整

`LocalReportArtifactAdapter.cleanup_unretained()` 对终态 retain 集合中的最终报告执行三项复核：

1. 对象仍然存在；
2. 实际字节大小与持久化引用一致；
3. 实际 SHA-256 与持久化引用一致。

缺失或被篡改的最终报告进入 `pending` 并输出错误日志，不能把资源记录误标为 `cleaned`。
该语义也已写入阶段 3 MinIO 门禁：未来对象存储 Adapter 必须保持同样的存在性、大小、
checksum 和所有权校验，不能只因 object key 存在就宣称成功。

---

## 3. AnythingLLM 写副作用结果未知

AnythingLLM 的创建/上传是外部写操作。超时、连接中断、408/425/429/5xx 或成功响应协议
损坏时，不能统一解释为“没有发生副作用”。本轮做了以下分类：

- Workspace 创建结果不明：用任务级唯一名称查询；只有唯一精确匹配时才恢复其引用；
- Workspace 无法唯一查回：先持久化失败 trace，再将资源记录隔离；
- 全局文档上传后拿不到 location：由于现有供应商接口没有可靠全局查询键，先审计再隔离，
  禁止盲目重传或猜测性删除；
- Conversation 创建结果不明但 Workspace 引用已知：后续删除 Workspace 可以覆盖其子资源，
  仍保留完整 lifecycle 证据。

`ReportRagExecutionError.external_outcome_unknown` 是内部安全标记，不进入公开 callback。未知
写副作用进入 `quarantined` 后不会被自动恢复器越过，需后续受控运维流程处理。

## 4. 资源清理恢复从“整批猜测”改为逐步事实

### 4.1 token、心跳和逐事件检查点

每次外部清理 attempt 现在持久化：

- 最长 128 字符的 attempt token；
- 开始时间和最新心跳时间；
- 每一项幂等 DELETE 的 lifecycle event；
- 连续 `sequence_no` 和 CAS version。

每个删除事件必须在下一项外部删除前落库。进程若在中途退出，下一轮先把已经持久化的事件
追加到交互审计，再从后续连续序号恢复。最后一个“外部删除成功、事件尚未落库”的窄窗口
通过再次 DELETE 的 404 幂等成功收敛。

### 4.2 到期接管竞态

过期恢复者关闭旧租约时使用 CAS。若旧 Worker 恰好先完成续心或检查点：

- 新恢复者只捕获精确的 `ReportResourceConcurrencyError`；
- 重读最新事实后让出，不覆盖旧 Worker 的新版本，也不重复删除；
- 数据库、解码或领域错误不会被当成正常并发冲突吞掉；
- 若 Adapter 声称 CAS 冲突但版本没有变化，按端口协议错误上报。

测试增加了确定性的“到期边界旧 Worker 先续心”场景，断言没有第二次 RAG 或 Artifact 清理。

### 4.3 有界扫描

`ReportResourceRecoveryService.sweep(limit)` 已提供 1～1000 的内部硬上限，并保证：

- Store 返回超过上限、重复或错误类型的 task ID 时立即报端口错误；
- 单任务恢复异常被记录，不阻断同批其他任务；
- 返回 cleaned、pending、quarantined、not-ready、missing 和 failed 分类统计。

该能力目前只是可装配 Application，尚未由生产启动流程调用。1C-6 必须配置启动扫描、周期
扫描、批量大小、轮询间隔和指标。外部清理租约超时还必须大于单次 AnythingLLM DELETE 的
HTTP 最坏超时并留出调度余量；当前逐步骤心跳不能在一个阻塞中的 HTTP 调用内部续租。

## 5. 其他并发与兼容补强

1. 最长 128 位的完整 `reportId` 继续作为公开值和数据库业务键，不截断、不缩成 64 位。
   只有供应商名称超过限制时，才使用带 SHA-256 摘要的确定性短名称；不同完整 ID 不会因
   前缀相同而碰撞。
2. Callback history 使用 50 线程验证同名毫秒时间戳下仍全部原子保存，不覆盖、不产生半文件。
3. Callback 人工解除必须显式携带内部 `worker_stopped_confirmed=True`，并由领域命令、
   Adapter、TaskService 和审计表逐层校验。
4. 正向架构白名单精确增加 Domain 所需 `hashlib` 和 Application 所需 `uuid`；其余未列入的
   基础设施客户端仍默认拒绝，未放宽分层方向。

## 7. 后续阶段硬门禁

### 7.1 1C-6

- 装配数据库 accepted 扫描 + 常量空间 Event 唤醒的单实例 Dispatcher；
- 启动和固定周期调用有界 `sweep(limit)`，输出分类指标；
- 只自动领取从未执行的 accepted 任务；遗留 running 只盘点、告警或人工隔离；
- 停止新受理并排空/隔离遗留 daemon 线程后，才能切换唯一组合根和薄路由；
- 证明不存在双执行、双 callback、请求线程同步等待和内存无界积压。

### 7.2 阶段 2～6

- 阶段 2 先建立 Task Attempt、Step、Checkpoint、lease/fencing 和 attempt 级审计幂等键，
  再允许 Reaper 判断 running 是否可重试；禁止通用 `running -> accepted` 批量更新；
- 阶段 3 把当前数千行兼容 `LLMTaskService` 拆为窄 Repository/Unit of Work 契约，并以
  SQLite/MySQL 双实现契约测试保护；接入 MinIO 时复用本轮 Artifact 完整性语义；
- 阶段 4～6 完成事务 Outbox、Publisher Confirm、RabbitMQ/Celery、late ACK、DLQ、可靠
  callback/cleanup Worker 和逐业务单写切换；
- 阶段 10 才能以真实 50+ 在途任务、50 长连接、短请求并发、重型任务限流积压和故障注入
  证明生产容量。本轮 50 线程单元测试只证明并发正确性，不是吞吐结论。

## 8. 当前仍存在但已受控的边界

1. 新 Report Application 尚未装配公开生产路由，当前代码全部仍属于开发阶段。
2. SQLite、本地 Artifact 和单进程 Guard 不具备多实例生产一致性。
3. AnythingLLM 全局文档上传结果未知时只能隔离，供应商没有可靠幂等键/查询能力前不能
   自动猜测恢复。
4. 发送前二次 Guard 校验不能创造跨数据库与外部 HTTP 的原子事务；人工解除必须执行旧
   Worker 停止确认，后续由可靠 callback Worker、lease/fencing 和运维命令进一步收口。
5. URL 安全策略和对象保留天数继续按已确认决定暂不实施；未确认期限前不启用自动 TTL。

下一实施子波次仍为 1C-6，不得把本记录解释为阶段 1C 已全面完成或已经具备可靠队列、
多实例、MySQL/MinIO 与生产 50+ 稳态能力。
