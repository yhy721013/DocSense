# 阶段 1C-3：SQLite 任务事实与原子受理执行记录

## 0. 执行结论

阶段 1C-3 已于 2026-07-16 完成。报告任务现在具备一套尚未接入生产路由的兼容
SQLite Task Command Adapter：它以追加式 execution 保存不可变输入，以一次短事务完成
同业务键受理判定和最新公开投影更新，并用 expected TaskId 阻止旧执行覆盖新执行。

本阶段完成的是内部持久化与并发门禁，不是 `/llm/generate-report` 的生产切换：现有
Blueprint、daemon 线程、遗留报告服务、公开响应和真实外部 I/O 均未改动。下一子波次为
1C-4（`RunReportTask(task_id)` 所需的生产 I/O Adapter）。

## 1. 范围与契约边界

### 1.1 本阶段实施范围

- 增量建立报告任务 execution 事实表、扫描索引和 Callback Guard 表；
- 实现原子 `create-if-allowed`、按 TaskId 读取/领取、latest 判断、accepted 扫描；
- 实现 execution 与 `llm_tasks` 最新投影的原子进度/终态条件写；
- 建立 tasks 通用 SQLite Adapter 与 report 严格 JSON Codec；
- 以 50 线程 Barrier、触发器故障注入和扩大离线回归验证事务及隔离语义。

### 1.2 明确未实施

- 未切换 `/llm/generate-report` 路由，公开 HTTP 202 空体/409 仍待调整后的 1C-6；

- 未实现本地 Dispatcher、RabbitMQ、Outbox、Worker、MySQL、Redis 或 MinIO；

- 未修改 `docs/接口文档/`，未增删或重命名任何前后端参数；
- 未启动 `run.py`，未连接真实 AnythingLLM、模型、文件服务器、回调方或其他后台服务。

## 2. 数据与事务实现

### 2.1 追加式 execution

`llm_task_executions` 以内部 `execution_id` 为主键，保存：

- 业务类型和业务键；
- 输入 Schema 版本及不可变 JSON 快照；
- accepted/running/succeeded/failed/stale 执行状态；
- 公开状态、进度、消息和内部结果；
- Callback 状态/结果、trace、受理/开始/完成/更新时间。

`llm_tasks` 没有删除或改名，继续承担现有查询和 Progress 所需的“同业务键最新公开
投影”。因此旧 file/weaponry/check-task 代码和测试数据仍可使用原表；报告 Worker 将只从
execution 输入恢复，不把可覆盖的最新投影当成执行输入。

### 2.2 原子受理

受理路径在进入写事务前完成参数校验和 JSON 编码，然后使用独立 SQLite 连接执行短
`BEGIN IMMEDIATE` 事务：

```text
读取 Callback Guard
  -> sending / outcome_unknown：返回内部冲突分类，不写任务
  -> idle：读取同业务键最新投影
       -> 公开状态仍活动：返回 active_conflict，不写任务
       -> 非活动或不存在：插入 execution + upsert 最新投影 -> accepted
```

事务内没有下载、文件处理、Progress 发布、线程唤醒、RAG 或 Callback。投影写入失败时，
execution 插入会随同一事务回滚，不能形成“任务事实存在但最新投影缺失”的孤儿状态。

### 2.3 领取和 expected TaskId 条件写

- 领取只允许当前最新 owner 的 `accepted` execution 进入 `running`；
- 50 个并发领取者只有一个获得 `claimed`，其余得到 `already_running`；
- 若最新投影已属于新 execution，旧 accepted/running execution 在领取时收敛为 `stale`；
- 进度写只允许当前最新且处于 running 的 execution，同时更新 execution 与公开投影；
- 终态写只允许当前最新且处于 running 的 execution，同时提交结果与公开投影；
- 缺失、旧 owner、未领取或已终态 execution 返回 `False`/稳定分类，不覆盖新任务；
- 两张表任意一侧写失败均抛出异常并回滚整次事务，不把部分提交误报为成功。

## 3. 分层与编码实现

### 3.1 tasks 通用 Adapter

新增 `LegacyTaskCommandAdapter`，实现通用 `TaskCommandPort`。Adapter 只认识 tasks 的
TaskId、业务引用、受理/领取/条件写语义；业务输入和结果由注入 Codec 编解码，因此 tasks
没有反向依赖 report，未来增加 analysis/weaponry Codec 或替换 MySQL Adapter 时无需把
业务 DTO 塞入通用 Repository。

### 3.2 report Codec

`ReportTaskCommandCodec` 使用严格 Schema v1：

- 保存不受 32/64 位限制、但最多 128 位十进制数字的 `reportId` 公开整数值及规范化业务键；
- 保留源 URL 的顺序和重复项、模板 URL/描述、需求、TaskId、受理时间和 trace；
- 对字段集合、行级 Schema 与 payload Schema 一致性执行严格校验；
- 生成与既有 `llm_tasks.request_payload` 兼容的最新投影，但 Worker 不使用该投影恢复输入；
- 结果只保存供应商无关 Callback/Report/Artifact 信息，不保存真实本地路径或供应商 DTO。

## 5. 测试与检查结果

### 5.1 阶段 1C-3 定向验收

`tests.test_report_task_adapter` 共 11 项通过，覆盖：

- Schema 重复初始化与旧投影保留；
- 128 位上限内的大整数 reportId、不变输入快照、读取、领取、进度和终态往返；
- Callback Guard、活动投影和受理分类；
- `SubmitReportTask` 使用真实 SQLite Adapter 后的通知顺序与重复冲突；
- 受理投影失败时 execution 不留孤儿；
- 进度投影失败时 execution 更新同步回滚；
- 遗留投影替换、旧 execution 领取收敛和旧写拒绝；
- 50 同键并发：1 accepted、49 active conflict、1 条 execution、1 条最新投影；
- 50 并发领取：1 claimed、49 already running；
- 50 不同键并发：50 条任务全部持久化且可扫描。

上述并发测试没有随机 sleep，统一使用 Barrier 同时起跑；未发生 `database is locked` 泄露。

## 6. 审查结论与后置责任

### 6.1 已满足的 1C-3 门禁

- 同一 reportId 的 50 个内部并发受理恰好一个 accepted；
- 没有 SQLite 锁错误向调用方泄露；
- 受理或条件写异常时没有 execution/投影半提交；
- 旧 execution 不能更新新 owner 的进度和终态；
- tasks 不反向依赖 report；report Application/Domain/Ports 未引入数据库或 Web 框架；
- 旧表、旧路由和旧服务没有破坏性修改。

### 6.2 不能据此宣称的能力

- 50 个内部 SQLite 线程通过不等于 50 个真实 HTTP 请求、长连接或重型模型任务容量已验收；
- SQLite `BEGIN IMMEDIATE` 是开发阶段单实例兼容实现，不是多实例一致性方案；
- execution 可持久扫描不等于 Dispatcher、Outbox 或可靠队列已经完成；
- 内部冲突分类存在不等于生产接口已经返回 202/409；
- Guard 表存在不等于 Callback 发送权、结果不明冻结与人工解除闭环已经完成。

上述能力分别由 1C-4～1C-7、阶段 3～7 和阶段 10 继续完成。阶段 1C-4 实现报告生产
I/O Adapter；全面审查后先在 1C-5 完成 Callback Guard/资源闭环，再由 1C-6 装配本地
Dispatcher、Container 和薄路由并切换公开 202/409；原计划的 1C-5/1C-6 顺序已调整，避免
在 Callback Guard 和资源收口完成前暴露新路由。1C-7 再完成全量验收与清理证据。
