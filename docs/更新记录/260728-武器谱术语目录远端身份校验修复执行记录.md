# 武器谱术语目录远端身份校验修复执行记录

## 1. 故障现象

启用 `WEAPONRY_TERMS_RULE_CONTEXT_ENABLED` 后，启动门禁成功创建版本化术语 workspace，
并完成 61 张本地术语卡的上传与绑定，但最终抛出
`TermsCatalogSynchronizationError: 术语 workspace 完整性校验失败`。应用随后按统一生命周期
回滚并停止已启动的 Dispatcher。

本地 SQLite 恢复事实显示 61 张卡全部处于 `bound`，目录总状态停留在 `preparing`。真实
AnythingLLM 只读预检同时显示远端存在 61 个文档，但旧实现把 61 张卡全部判断为缺失，并把
远端 61 个文档全部判断为意外文档。

## 2. 根因

旧协调器使用 `AnythingLLMDocument.title` 与本地确定性上传文件名做集合比较。真实
AnythingLLM 会把 workspace 文档的 `title` 改写成规范化后的 `document_location` 文件名，
其中包含 Provider 生成的 UUID 和 `.json` 后缀；该展示字段不再等于上传请求中的文件名。

上传后的精确查回本来已经使用完整 `document_location`，但启动复用、只读预检和最终完整性
校验仍依赖 `title`，导致同一模块内部使用了两套不一致的身份规则。离线 Fake 又原样保留
上传标题，未呈现真实 Provider 行为，因此此前回归未发现该问题。

## 3. 修复内容

1. 启动同步、`--dry-run` 预检和最终完整性校验统一使用规范化后的完整
   `document_location`，展示 `title` 仅用于诊断日志。
2. 每张卡必须由当前目录指纹、`card_id`、确定性上传名和 SQLite 持久化 location 共同证明
   归属；状态身份发生漂移时失败关闭。
3. 已取得确定 location、但进程在绑定前退出的 `uploaded` 状态会复用原上传继续绑定，不会
   创建第二份全局文档。
4. `uploading` 或无法精确查回的 `outcome_unknown` 继续禁止自动重放；精确 location 已在
   workspace 可见时，允许收敛为 `bound`。
5. 若版本化 workspace 非空但本地恢复事实丢失，协调器拒绝按标题或文件名猜测归属，避免
   重复上传和污染版本化目录。
6. 完整性失败日志增加期望数、实际数、非法状态数、缺失数、意外数及有界样例，便于运维
   快速定位，同时避免输出文档内容。

## 4. 验证证据

- `tests.test_weaponry_terms_catalog`：13 项通过。
- 术语目录、Weaponry 生产适配、Dispatcher、生产门禁、Container 与 AnythingLLM
  Workspace 联合回归：123 项通过。
- 修复后的真实 AnythingLLM `--dry-run` 只读结果：
  - `expectedCardCount=61`
  - `missingCardIds=[]`
  - `unexpectedDocumentTitles=[]`
  - `blockedOutcomeUnknown=false`
  - `writeRequired=false`
- `py_compile` 与 `git diff --check` 通过。

真实预检只读取 AnythingLLM；受控环境无法直接打开工作区外的运行数据库，因此先把已停止
服务的 `llm_tasks.sqlite3` 复制到临时目录，再通过 `DOCSENSE_LLM_TASK_DB` 让本次 dry-run
只读临时副本，结束后已删除副本。未执行 `run.py`、`--apply` 或任何真实远端写入。

## 5. 契约与部署边界

本次只修改内部 Weaponry Adapter 的身份和恢复语义，没有修改公开路由、请求参数、响应字段、
状态码、Header、WebSocket、SSE 或 Callback 契约，`docs/接口文档/` 无需改动。

当前进程锁、恢复事实和 Dispatcher 仍是 SQLite `single_instance` 实现。此次修复不能作为
可靠队列、多实例并发控制或共享数据库一致性的生产证明；未来迁移时必须保留精确远端身份、
恢复事实和失败关闭语义。
