### 1.2 “无业务积压上限”的准确边界

“不设置积压上限”不等于物理存储无限，也不等于允许无界线程、无界进程内队列或无界
模型并发。目标语义是：

1. API 成功返回前，任务和不可变请求快照已经进入数据库事实；阶段 4 后还必须与 Outbox
   在同一事务提交。
2. 本地兼容 Dispatcher 和未来 RabbitMQ 消息只用于唤醒/派发，数据库任务事实是恢复
   依据；不得把全部积压只放在 Python 内存。
3. 不配置基于“待处理任务数量”的业务拒绝阈值，也不配置 RabbitMQ `x-max-length` 一类
   会因正常积压丢弃或拒绝消息的策略。
4. Worker 并发、AnythingLLM 会话数、GPU/模型并发和下载并发仍是有界资源；积压依次
   等待，资源释放后继续处理。
5. 数据库、磁盘或 Broker 已无法完成可靠写入时，系统不能返回 202。这属于基础设施失败，
   不是正常积压限流；必须告警并保留既有错误结构。
6. 队列间优先级和公平性在阶段 5 L3 结合真实任务耗时确定；当前不承诺三个业务之间的
   全局严格 FIFO，但同一队列内必须有稳定、可审计的领取顺序。

### 1.3 保留周期延期的临时安全口径

- 持久对象默认不自动过期，`eligible_for_deletion_at`/`expires_at` 为空。
- queued、running、retrying、死信待处理、待回调、恢复中和人工处理中的对象始终受保护。
- 保留期不得从对象 `created_at` 直接起算；只能在任务终态、无租约、无重试、无 Outbox、
  无回调恢复和无其他引用后计算删除资格。
- 只有已确认可重建、持久产物已提交且没有执行器继续使用的任务私有 scratch 才可立即
  清理。崩溃或提交结果不明时进入隔离/待清理状态，不直接删除。
- 阶段 3 Schema 预留 `retention_class`、删除资格时间、删除状态、尝试次数和审计字段。
- 在启用第一条非测试自动删除规则前必须确认具体期限。回调载荷若设置期限，会限制
  `/llm/check-task` 的可补发窗口，届时必须先确认是否需要同步接口文档。

### 1.4 阶段 1C 全面审查后的新增门禁

1. 最终报告进入终态所有权后，清理器仍须复核对象存在性、大小和 SHA-256；缺失或篡改
   必须保持 `cleanup_pending/failed` 并告警，不能因“位于 retain 集合”而误报完成。
2. AnythingLLM 写请求超时、连接中断、5xx 或成功响应协议损坏时，必须区分“明确失败”
   与“供应商副作用结果未知”。Workspace 创建可按任务唯一名称精确查回；无法唯一查回、
   或全局文档上传后拿不到 location 时，先审计再隔离，禁止猜测性清理或盲目重放。
3. 外部清理仅允许编排幂等 DELETE；每个生命周期事件必须在下一项删除前以 CAS 持久化，
   清理租约包含 token、开始时间和逐步心跳。过期后先审计已持久事件，再以连续序号重放；
   最后一个“删除成功但事件未落库”窗口依赖供应商 404 幂等收敛。
4. 1C-6 必须装配 `sweep(limit)` 的启动扫描和周期扫描。该门禁已完成：每批有硬上限，
   单任务失败不能阻断同批其他任务，扫描结果输出 cleaned/pending/quarantined/failed 分类指标。
5. `running` execution 在阶段 2 建立 Task Attempt、Step、Checkpoint、lease/fencing 以及
   attempt 级审计幂等键前，禁止通过 SQL 或扫描器直接重置为 `accepted`。1C-6 已按此只恢复
   从未领取的 `accepted`；对遗留 `running` 只告警、盘点和人工隔离。
6. 128 位 `reportId` 只在供应商名称超限时使用稳定摘要，公开值和数据库业务键不截断；
   回调历史文件采用原子排他创建，50 个并发写入不得互相覆盖。

## 3. 总体依赖路径

```text
1C report ─────────┐
1D weaponry ───────┤
1E reassign ───────┼─→ 1G 业务结构收口 → 2 统一任务与进程内隔离 → 3A MySQL / 3B MinIO
1F analysis ───────┤                    → 4 Outbox → 5 RabbitMQ/Celery → 6 逐业务可靠切换
1H document process┘                                           ↓
                                  7 跨实例通知 → 8 FastAPI
                                                    ↓
                                  9 chat 闭环 → 10 容量/故障验收 → 11 生产上线
```

主依赖原则：先稳定业务内核和事务边界，再替换数据库、消息、通知和 Web 框架。FastAPI
继续位于可靠队列之后，避免在迁移 Web 框架时同时重写业务和持久化语义。

- chat 保持 ChatRun 唯一领域事实；阶段 2 只冻结语义映射，阶段 9 可靠派发时 Task 才引用 ChatRun。
- 明确终态不可逆、重试创建新 attempt、同业务键活动唯一和 latest-wins 条件写。
- 为每次业务 Step/模型/外部副作用建立各自命名空间的 attempt 审计和幂等键；
  `task_attempts` 只表达整任务 Worker 执行权。
- Report/Weaponry/Analysis 分别冻结版本化 Step/Recovery Registry：`effect_kind` 与 `replay_policy`
  正交建模，每个 Step 明确 Intent/Checkpoint/ExternalRef Schema、幂等键、探测/补偿和恢复矩阵；
  Input Profile 使用确定性 Canonical JSON，不从当前环境补写旧任务默认值。
- 同时冻结 `app/services` 职责/调用方/目标所有者/退出阶段、SQLite 表唯一写入者和 Runtime Config
  归属矩阵。Tasks、Report、Analysis 的阶段 2 配置归各自 `adapters/runtime_config.py`；Weaponry
  在自身迁移波次等价规范命名；`.env` 只是本地环境来源，`.env.example` 记录非秘密键和约束。
- 冻结结构边界：`knowledge_workspace.py` 归 `app/shared/domain`；顶层 `app/adapters/web` 保留；
  `DatabaseService`/Knowledge 物理迁移延期到 3A；Callback 本地 JSON 是 Debug 诊断副本而非恢复真相。

### 2-1 本地兼容执行器

- 在现有通用持久 Dispatcher 内核上形成一个共享 `LocalTaskExecutor` 实现，并按 Report、Weaponry、
  Analysis 分别实例化；业务内保持 FIFO，跨业务由共享公平容量仲裁保证无饥饿而不承诺严格全局 FIFO。
- 每个业务独立 worker slots/readiness/Runner/未来队列路由；AnythingLLM ingestion、模型、文档处理、
  Callback 分层限流，初始真实重型总并发仍为 1；重型执行与维护 Scheduler 分离。
- 待处理任务保存在数据库；内存只保存有界唤醒信号，可丢唤醒但不可丢任务事实。
- 启动和周期扫描重新发现 accepted/runnable 任务；`queued` 属于阶段 4～5 的派发/消息事实，
  阶段 2 不伪造该状态；停止时有界等待并记录未完成任务。
- 不设置业务积压数量上限；FIFO 键、扫描游标和最老等待时间必须可观测。
- 新 Task Control Store 直接拥有 SQL；只允许旧入口短期单向委托新 Store，禁止新 Store 回调
  `LLMTaskService`。Progress 纯规则/Hub 归入 Tasks，阶段 2 触达的资源、审计和 Callback Control
  随 Report -> Weaponry -> Analysis 波次迁入明确所有者。
- SQLite 事务采用共享 Connection Factory/Transaction Manager + Admission/Execution/Recovery 等窄
  UoW；同一用例 Store 共用连接、Store 不自行 commit、未显式 commit 默认 rollback，禁止嵌套 UoW、
  跨线程 Connection、事务内网络 I/O 和隐藏事务重放。
- `ClockPort` 统一持久 UTC 时间；owner 带每次启动 UUID 世代；heartbeat、SQLite busy、时钟抖动、
  lease、scan 和 stop 满足完整不等式。时钟异常暂停 claim/Reaper 并 fail closed。
- 每个迁移单元按“等价路径移动 -> 定向/合同测试 -> 新位置语义改造 -> 删除旧入口”执行；
  兼容导入不得跨波次保留。

### 2-2 隔离、租约与 fencing 预演

2026-08-12 已确认本节的落地分界：2-2 完成新空 v2 的 Schema/Bootstrap、Repository/UoW/CAS 与
离线双连接验证，不切生产 `LegacyTaskCommandAdapter/LLMTaskService`；2-3 实现完整 Authority
Runtime；2-4～2-6 分业务把 Task 全生命周期与 Callback Control 作为不可拆单元切换，禁止双写。

- 每个任务拥有独立目录、依赖实例和日志上下文；当前异步业务没有已批准的通用取消合同，
  阶段 2 不新增公开取消状态或入口。
- 引入本地 attempt、lease owner、lease expiry、fencing token 和心跳的可测试语义。
- 旧 attempt 的进度、Step、结果和产物引用必须被完整 task/attempt/lease/fencing Authority 拒绝；
  Callback 继续使用独立 Delivery Guard，不并入 Task Attempt。
- 在 Reaper 可以重领 `running` 前，先持久化 Step/Checkpoint：至少区分“未产生外部
  副作用”“副作用引用已登记”“结果不确定”“终态已提交”。只有可证明可重试的步骤才
  创建新 attempt；不能用通用 `running → accepted` 更新代替恢复判定。
- `recovery_required` 不可被普通 Executor 领取。恢复协调器以独立 recovery lease/fencing 追加
  Observation 和 Decision；只有确认未生效、幂等重放安全或补偿完成并复核通过，才原子写入
  `retry_authorized`、保持当前 recovery generation、冻结 retry checkpoint 并把 Task 改回 accepted。
  随后的普通 claim 创建新 Attempt；禁止直接改 running、复用旧 Attempt 或通过 check-task 重跑。
- `recovery_generation` 只在进入新的独立恢复现场并创建 Case 时递增；Case re-claim/关闭不递增，
  新执行和新恢复 owner 分别由 attempt/Task fencing 与 Recovery fencing 表达。
- 核心业务 unknown 保持既有活动投影并复用同键冲突；终态 cleanup unknown 独立且在资源隔离成立时
  不阻塞；Callback unknown 沿用 Guard/check-task；不同键不全局阻塞。无法保持既有公开语义时先
  确认接口文档。

### 2-3 故障与验收

- 覆盖重复派发、Worker 异常、进程停止、超时、失权、失联任务分类恢复和清理失败。
- 覆盖 Recovery Case 并发 claim、探测后崩溃、证据不足继续隔离、Decision CAS 冲突、
  retry_authorized 原子回滚且 generation 不变、新 Attempt/fencing 单调和恢复后公开 Progress 不倒退。
- 覆盖新旧 DB 路径/metadata/fingerprint/WAL 文件集、窄 UoW 原子组、FakeClock/owner/租约不等式、
  三业务 Executor 公平无饥饿、Step Registry 完整性及 recovery admission 矩阵。
- Analysis 在多个本地 Worker 下仍须通过持久 runnable 资格保持请求内严格顺序。
- 50 个 Fake 重任务同时在途，执行并发受限但全部最终被处理，且无输入/进度/文件串扰。

  Task/Callback SQL、双 Progress Hub、Store 循环委托或一表多写入者。`LLMTaskService` 的剩余
  阶段 3 职责必须先拆成明确过渡 Store，职责清零时物理删除。

## 6. 阶段 3：共享 MySQL 与共享 Artifact（3A/3B 独立门禁）

阶段 3A 先验证 MySQL/Alembic/同步 SQLAlchemy Repository，阶段 3B 再验证 MinIO/Artifact
Catalog。两项可以滚动实施但必须分别验收；外部 Worker 切换前两项都要满足，不能用其中一项
成功替代另一项。

### 3-0 集成测试环境

- 新增测试专用 Compose 并按阶段启用 profile：3A 只启动 MySQL，3B 启动 MySQL + MinIO，
  阶段 5 再加入 RabbitMQ，阶段 7 再加入 Redis；固定镜像版本和健康检查。提前启动某个容器
  只能证明依赖可达，不能作为可靠队列、跨实例通知或多实例能力完成的证据。
- 应用测试由 `/venv` 解释器从宿主机运行；测试不得启动 `run.py`。
- 每次测试使用独立 database/schema、bucket prefix、queue/vhost 或命名空间并可重复清理。

### 3A-1 SQLAlchemy/Alembic 基线

- 单一 SQLAlchemy 2 Metadata 描述生产表；Alembic 从空库升级，不在应用启动时隐式改表。
- 冻结 MySQL 版本、字符集、数据库权威时间、事务隔离级别、连接池参数、锁等待/死锁分类和
  有界重试条件；数据库时间用于 lease/过期判断，不能信任各实例本地时钟作为共享 Authority。
- 第一版统一使用同步 Engine/Session/Repository；每个请求或 Worker 任务独占 Session，
  禁止跨线程、跨进程或异步任务共享。
- Unit of Work 控制一次业务事务的 commit/rollback；Repository 不自行提交，不执行网络 I/O。
- `reportId` 业务键使用规范化十进制文本，不能因 MySQL `BIGINT` 缩小为 64 位；Schema
  必须容纳可选负号与最多 128 位数字，并由 Web/领域双层执行已批准上限。

### 3A-2 Schema 和 Repository 逐模块等价

- 按 Task/Attempt/Step/Event、Callback/Delivery、Chat、Knowledge/Resource 顺序建立并切换表、
  外键、唯一约束和索引；一个模块通过门禁后再迁移下一个模块，避免 Task、Callback、Chat、
  Knowledge 和 Artifact 同时改变导致无法定位回归。
- SQLite 兼容实现和 MySQL 实现运行同一套 Repository 契约、并发唯一性和事务回滚测试。
- 使用空库和版本化测试种子；历史 SQLite 测试数据不迁移。
- 将当前兼容期聚合在 `LLMTaskService` 的任务、回调 Guard、资源恢复和审计能力拆为窄
  Repository/Unit of Work；Application/Adapter 不再依赖一个数千行具体服务类。拆分过程
  必须先跑 SQLite/MySQL 双实现契约测试，不能在路由中直接散落 SQLAlchemy Session。

### 3A-3 唯一写路径、备份恢复与回切

- 按模块切换唯一写路径，禁止长期 SQLite/MySQL 双写；MySQL 成为权威后，旧 SQLite 仅保留为
  测试适配器或短期证据，不能继续承接生产新写入。
- 验证连接池耗尽、死锁、事务回滚、唯一冲突、数据库暂时不可用和多实例条件写。
- 完成空库升级、数据校验、备份恢复、Alembic 升降级和回切演练；已经产生需保留的新任务、
  外部副作用或 recovery 现场后不得简单回切旧 Adapter，必须先停止领取并前向收敛。

### 3B-1 Artifact Catalog 与不可变状态机

- 把 1H 的通用 Artifact Catalog 作为 Artifact 所有权真相，保留 source、prepared、normalized
  及同一步骤多 ordinal；旧“一步骤一个主产物”表只作为兼容投影，不得据此实施 GC。
- 为输入、任务 scratch、中间产物、最终报告和不可变 Callback 载荷定义对象 key、metadata、
  size、系统计算的 SHA-256、所有权、引用和 retention class。内容变化创建新 Artifact，不覆盖
  已经 `available` 的对象。
- 冻结 `staging -> available` 正常路径，以及 `orphan_candidate`、`reconcile_required`、
  `deleting` 异常/维护状态；MinIO/S3 ETag，特别是分片上传 ETag，不得直接当作 SHA-256。

### 3B-2 MinIO Adapter 与 staged upload

- 先在 MySQL 登记 upload intent/`staging` Artifact，再上传 staging key，核验 size 与 SHA-256，
  最后以短事务绑定业务引用并标记 `available`。MinIO 写入与 MySQL 提交不是原子事务，任一中间
  崩溃都必须留下可由 Reconciler 识别的稳定事实。
- 将 1D weaponry 仅冻结身份/引用的文档快照升级为 execution-owned 内容 Artifact：受理后保存
  不可变对象引用、size、SHA-256 和所有权，Worker 不再依赖可被替换的单机路径或同名文档。
- 为 1H DocumentProcessing 的 Artifact/Profile/Lineage 实现同步 SQLAlchemy Repository 和 MinIO
  ArtifactStore Adapter；处理 Application/Port 不因存储替换而改变。
- 数据库保存对象引用和删除资格，MinIO 不作为业务状态真相。
- 具体 7/30/180 天等期限保持未启用；自动删除前必须另行确认。
- `retain` 必须对 MinIO 对象执行存在性、size、系统 SHA-256 语义校验；校验失败与本地
  Artifact 一样保持 pending 并告警。数据库记录为所有权真相，不能只因对象 key 存在就
  宣称完整，也不能依赖单机本地路径作为多实例共享事实。

### 3B-3 对账、孤儿对象与保守 GC

- Reconciler 覆盖对象写成功但数据库绑定失败、数据库引用存在但对象缺失、size/hash 不一致、
  重复上传和长期 staging；孤儿对象经过宽限期与重新对账后才能成为删除候选。
- GC 使用 lease/fencing 领取删除权；删除前重新检查业务引用、任务/Attempt、恢复状态、Outbox、
  Callback、Lineage 与其他租约，删除和引用状态变化均写审计。
- 验证 MinIO 暂停以及“上传前、上传后、校验后、数据库绑定前后”的强制中断。自动 GC、对象
  TTL 和生产删除扫描默认关闭，直到保留期与删除规则另行确认。

## 7. 阶段 4：事务 Outbox 与可靠派发

### 4-0 事件契约

- 消息只携带 task ID、attempt/command ID、schema version、trace ID 和最小路由信息。
- 不把完整请求、密钥、文件正文或公开响应对象复制进消息。
- Consumer 必须兼容重复消息并拒绝未知 schema version。
- 阶段 4 冻结三种独立命令：初次 Task 执行派发、Reaper 分类后允许的新 Attempt 恢复派发、
  Callback 后台恢复派发。每条命令保存稳定 `command_id`、聚合对象 ID、`dispatch_generation`、
  `schema_version`、路由、可投递时间、触发来源、负载摘要/校验值、尝试次数和状态。
- 阶段 2 的 `task_events` 是内部追加审计，不是 Outbox。两者受众、保留周期、Payload 和重放
  副作用不同，禁止通过重放审计事件触发业务执行或 Callback。

### 4-1 同事务事实

- 任务受理、不可变输入和 Outbox 在同一 MySQL Unit of Work 提交。
- Reaper 的恢复分类、新 generation/Attempt 与恢复 Outbox 在同一事务提交；没有持久恢复决定
  时，Broker/Celery 不得自行创建新业务 Attempt。
- 后台 callback recovery request 与 Outbox 在同一事务创建/复用；MySQL 未提交不得把该
  后台命令视为可靠登记。`/llm/check-task` 仍在请求内同步执行必要恢复，其 HTTP 200 不以
  Broker 或后台 Outbox 成功为前提，也不新增公开结果字段。
- Report 活动任务唯一、callback unknown 冻结和 Outbox 登记均使用数据库条件/约束，不能
  依赖进程锁作为最终正确性依据。

### 4-2 Relay

- Relay 用短事务批量领取 Outbox，发布时启用 publisher confirm。
- 数据库领取与 Broker 发布之间允许重复、不允许静默丢失；确认后条件标记 published。
- Broker 暂停时保留数据库积压，并监控最老事件年龄、失败率和重试次数。

### 4-3 故障注入

- 提交前崩溃、提交后发布前崩溃、发布成功但确认丢失、确认后标记前崩溃均需验证。
- 重复发布不得重复创建外部资源或绕过 callback Guard。
- 覆盖毒消息、未知 schema、同一 `command_id` 重复送达、Relay 失权和 Broker 已确认但数据库
  尚未标记；允许重复投递，不允许静默丢失。

## 8. 阶段 5：RabbitMQ/Celery Worker 与可靠消费

### 5-0 队列拓扑

- analysis、report、weaponry、callback、cleanup 使用可独立限流和观测的路由。
- 不设置正常业务积压数量上限或溢出丢弃；实际磁盘水位、RabbitMQ flow control 和资源
  告警属于基础设施保护。
- 每类队列定义 durable、persistent message、DLX/DLQ、prefetch、优先级和重放权限。

### 5-1 薄 Celery Task

- Celery Task 只校验信封、建立日志上下文并调用 `RunXxxTask(task_id)`。
- 使用 late ACK；只有业务事实安全提交后 ACK。Worker 丢失、超时和重投必须创建/复用
  受控 attempt，不能直接重开终态。
- Task Attempt、Authority、lease/fencing、Checkpoint 和 Reaper 复用阶段 2 语义并替换为
  MySQL/多实例 Adapter；禁止建立 Celery 专用的第二套任务状态机。
- 冻结 Broker Delivery/Redelivery、Celery retry、Task Attempt、Step Attempt、Recovery Dispatch
  的决策矩阵。一次重投递或 Celery retry 不等于新 Task Attempt；Consumer 必须先查询 MySQL
  Authority，并校验 `command_id`、generation、当前 Attempt、租约和 fencing。
- Task 已终态或命令过期时直接 ACK 且不执行；合法 Attempt 正由其他 Worker 持有时不重复推进；
  只有持久恢复事务判定 `retry_safe` 并创建新 Attempt/Outbox 后才可执行。租约过期但副作用结果
  未知时持久化 `recovery_required` 并隔离，不允许热重排队。
- MySQL 暂时不可用、无法完成 Authority 判断时不 ACK；Celery Result Backend 不是真相源，自动
  retry 不得无条件包裹 AnythingLLM、模型、MinIO 或 Callback 外部副作用。

### 5-2 资源隔离

- AnythingLLM、模型、下载、预处理和 callback 分别配置并发许可与超时。
- analysis/report 当前共享的重型上传资源继续按真实安全容量限流；队列可以积压，不能
  为追求吞吐放大下游雪崩。

### 5-3 Callback Worker

- 投递前在同业务键串行化边界内复核 latest task ID。
- 自动恢复 Worker 与 `/llm/check-task` 的同步恢复必须调用同一应用服务、使用同一
  execution 级 Callback Guard，并分别记录 `background`/`check_task` 触发来源；禁止形成
  两套发送状态机或独立发送权。
- 仅明确未送达错误有限重试；非 2xx 进入人工/DLQ；发送后结果未知标记
  `delivery_outcome_unknown`，不自动重试并冻结同业务键新提交。
- 人工解除必须是内部运维命令，记录操作者、原因、前后状态和审计时间；不新增公开接口参数。

### 5-4 故障验收

- 覆盖重复消息、Worker kill -9、ACK 丢失、Broker 重启、DB 短暂失败、AnythingLLM 超时、
  MinIO 暂停、callback unknown 和 DLQ 重放。
- Worker kill 分别注入在外部意图登记前、登记后发送前、发送后响应前、响应后数据库提交前、
  终态提交后 ACK 前。租约过期只产生恢复候选；Fencing 只能拒绝旧 Worker 的数据库条件写，
  不能撤回已经发出的外部请求。
- 验证积压可持续增长并在资源恢复后持续排空，且 Web 进程内存不随积压线性增长。

## 9. 阶段 6：逐业务切换到可靠队列

切换顺序：callback 后台兜底 → cleanup/compensation → report → analysis → weaponry。

Report 是阶段 2 的统一执行内核试点，先验证长耗时 Step/Artifact；Analysis 随后验证批次顺序；
Weaponry 最后验证复杂外部资源、供应商能力证明和保守隔离。该顺序不改变任何公开优先级。

每类业务必须独立完成：

1. 新旧路径黄金样例和副作用对比。
2. 确认只有一个 Dispatcher/Consumer 拥有执行权，禁止双执行者。
3. 小流量切换、队列/任务/回调/产物观测、故障回滚演练。
4. 回滚只切组合根绑定；已进入新队列的任务由新 Consumer 排空，不能让旧执行器重复接管。
5. 稳定观察后删除对应本地任务执行路径；甲方规定的 check-task 同步恢复不在删除范围。

派发切换采用 MySQL 中按任务类型保存、可审计且带 `policy_version`/生效 generation 的全局状态：

```text
local_only
-> shadow_publish
-> queue_active
-> local_drain
-> local_removed
```

- `shadow_publish` 只验证信封、路由、指标和去重，影子 Consumer 没有副作用执行权；
- `queue_active` 后新任务只进入 RabbitMQ；`local_drain` 只允许本地执行器完成切换前已持有任务；
- 每个 Task 在受理事务中冻结 dispatch path、policy version 和 generation；旧实例读到过期策略时
  fail closed，不能使用实例本地默认值领取新任务；
- 回滚只改变回滚后新任务的派发方式，已经进入新队列的任务继续由新 Consumer 排空，不能交回
  旧执行器；确认旧任务、旧 Outbox、旧消息和回滚窗口清空后才进入 `local_removed`。

验收覆盖不同版本 Web/Worker 同时在线、部分实例重启、shadow 消息重复、queue backlog 回滚和
旧策略实例；任一时刻同一 Task 只能有一条具备数据库 Authority 的执行路径。

check-task 不再安排“由同步切为异步”的生产切换。报告类型当前已在请求内使用共享 Guard
完成必要恢复；阶段 4～6 只增加 MySQL recovery request + Outbox + callback Worker 后台
兜底。同步请求和后台消息并发命中同一 execution 时最多一方取得发送租约，旧任务在新任务
提交后必须判定 stale 并跳过。既有 HTTP 200 空响应体、400/404、请求参数和回调载荷不变。

## 10. 阶段 7：跨实例 Progress 与事件通知

### 7-0 事实与唤醒分离

- MySQL 保存任务/ChatRun 进度和有序事件真相；Redis 只发送轻量唤醒，不承担唯一事实。
- Redis 消息丢失时，连接端按游标/版本定期回查 MySQL，不产生永久漏通知。
- 建立“订阅—快照”屏障：先订阅并缓冲通知，再读取带单调版本的 MySQL 快照；发送快照后
  丢弃版本不大于快照的缓冲项，只交付更新版本，再进入实时模式。等价实现必须证明快照读取
  期间发生的更新不丢失、不倒退。
- Redis 重复、乱序通知按版本过滤；重连后执行有界数据库补查。Redis 版本/游标只用于内部
  协调，不能进入现有公开响应或要求调用方回传。

### 7-1 进程级订阅聚合

- 同一进程对同一业务键只维持一份 Redis 订阅/监听，再扇出到多个本地连接。
- 每连接继续使用有界合并缓冲和单写入原则；慢连接只影响自身。
- 验收覆盖通知发生在订阅前、快照读取中和快照发送后，以及重复、乱序、Redis 重连、50 个
  同键/不同键连接和慢连接；Redis 完全不可用时仍能通过有界数据库补查得到最终事实。

### 7-2 契约保持

- `/llm/progress` 不新增事件 ID、游标或 ack，不恢复已删除的显式 action。
- Progress/WebSocket 连接断开只释放本地订阅，不取消原异步业务 Task。Chat SSE 断线不套用
  此规则，必须按阶段 9 和现有对话合同停止本轮生成。
- Chat SSE 保持事件名称、顺序和终态格式；内部事件补查不能变成对外断线续传，也不能泄露
  task/run ID、内部版本或游标。

## 11. 阶段 8：迁移 FastAPI Web 适配层

| 子波次 | 内容 | 门禁 |
| --- | --- | --- |
| 8-0 | Bootstrap、lifespan、配置和异常映射 | 与 Flask 共用同一 Application/Port/Repository 契约 |
| 8-1 | 普通 JSON HTTP 路由 | 请求、状态码、空响应体、错误 JSON 完全等价 |
| 8-2 | WebSocket Progress | 错误后保持连接、无 ack、释放和慢连接隔离等价 |

| 8-4 | 双栈灰度 | 同一时刻每个任务类型仍只有一个受理/执行所有者 |
| 8-5 | Flask 下线 | 静态引用、运行配置、回滚窗口和观察期证据齐全 |

阶段 9 的 ChatRun 多实例 lease/fencing 关闭前，普通 HTTP、任务受理和 Progress 可以逐步多实例
灰度，但 `/llm/chat*`、`/llm/weaponry-chat*` 必须由网关或数据库全局策略路由到单一受理所有者；
普通粘性会话不能作为正确性门禁。FastAPI Chat 可先做合同测试、影子验证或单实例受理。阶段 8
负载测试只证明 Web Adapter、事件循环和长连接承载，不证明 Chat 多实例执行完成。

同步 SQLAlchemy Repository 在 FastAPI 中只能通过受控线程池执行短事务，不能直接阻塞
事件循环。阶段 8 压测若证明数据库线程池是瓶颈，再为 Web 查询路径增加 AsyncSession
Adapter；同步 Celery Repository 保持不变，两者共享 Schema 和 Repository 语义，不共享 Session。

Web lifespan 只初始化 Web Adapter、数据库/Redis/HTTP Client 和连接资源，不得重新启动本地业务
Dispatcher 或重型执行线程；阶段 6 已切出的业务只能由独立 Worker 推进。双栈验收必须证明 Chat
对外仍只有一个合法受理者，且任一 Web 进程退出不会产生新的本地执行所有者。

## 12. 阶段 9：Chat 可靠派发与多实例闭环

1. ChatRun 受理事实、用户 pending 消息、输入快照和 Outbox 同事务。
2. Task 只承担可靠派发和 Worker Authority，ChatRun 继续唯一拥有消息、Chunk、流终态、中断和
   历史；两者通过内部引用和同一恢复协议协作，禁止形成两套可独立成功的终态。
3. Worker 不依赖 Flask/FastAPI 请求线程执行，但现有公开合同仍规定：调用方在成功终态前关闭
   SSE 后必须停止本轮。Web 持久化断线/中断事实，Worker 通过数据库或可丢通知观察后收敛为
   failed/aborted；不保存不完整 assistant/Chunk，也不继续后台生成。
4. 显式调用 `/llm/chat/abort`、`/llm/weaponry-chat/abort`，SSE 传输意外关闭和 Web 进程终止是
   三种不同触发来源；跨实例实现必须分别记录和处理，但均不得绕过现有断线合同。
5. 内部事件账本用于当前仍存活连接在 Redis 通知丢失时从 MySQL 补取、Worker/Web 解耦交付和
   故障审计；不向重连调用方提供 SSE 回放或断线续传，不新增公开 TaskId、RunId、cursor、
   Last-Event-ID 或其他参数/字段。
6. 冻结终态竞态：完整 assistant/Chunk 与成功终态先提交时，随后断线不得回滚历史；中断/断线
   条件写先成功时，Worker 后续成功提交必须被 CAS/fencing 拒绝。
7. abort 跨实例通知、连接存活租约、执行 lease/fencing 和终态条件写形成闭环；Web 进程终止时
   不能因来不及写断线事实而让生成无限继续，必须由有界租约过期和恢复分类最终停止。
8. delete/title 产生的清理任务进入可靠队列；同步公开语义保持，补偿可审计。
9. Chat 文件与产物统一使用 MinIO；不得删除尚被会话、run、消息或清理任务引用的对象。

验收覆盖：执行权领取前关闭、生成中关闭、显式 abort、成功事务与断线竞争、Web/Worker 强杀、
Redis 丢失和实例重启。任何场景都不得保存不完整 assistant/Chunk、对外回放旧 SSE，或泄露内部
任务/运行/事件标识。

## 13. 阶段 10：容量、稳态与故障验收

### 10-0 冻结环境和 SLO

- 记录 CPU、内存、GPU、磁盘、网络、MySQL/RabbitMQ/Redis/MinIO/AnythingLLM 版本和配置。
- 冻结 workload mix：任务类型比例、到达率、文件大小、上下文/输出长度、供应商 Fake/真实模式、
  warm-up、soak 时长、短请求成功率、P50/P95/P99、最大排队时间、积压恢复时间、Worker 恢复时间
  和 Callback 最终完成时间。
- 若保留周期仍未确定，容量模型必须按“不自动删除”最坏情况计算；启用 TTL 前另行确认。

### 10-1 分层负载

- 分别验证至少 50 个持久化在途任务、50 条 WebSocket/SSE 长连接和 50 个短请求稳定并发；
  分别报告三个结果，不能合并成一个“并发 50”。
- 重型 AnythingLLM/模型 Worker 实际并行度按下游容量独立冻结和报告；50 个在途不等于 50 个
  同时推理或摄取，排队任务必须最终处理或进入明确隔离状态。
- “取消”只验证现有 Chat/Weaponry Chat abort 与断线合同；不得为 Analysis、Report、Weaponry
  虚构通用取消接口、参数或状态。
- 分别测 Web 受理能力、数据库/Outbox、Broker、Worker、外部模型和积压恢复，不能只给总吞吐。

### 10-2 稳态和资源泄漏

- 长时间运行并观察内存、线程、文件描述符、连接池、临时文件、对象存储和队列趋势。
- 验证慢连接、超大积压、Worker 扩缩和持续 callback 失败不会拖垮无关业务。

### 10-3 故障矩阵

- 注入应用、Worker、MySQL、RabbitMQ、Redis、MinIO、AnythingLLM 和网络分区/超时故障。
- 不允许任务静默丢失、旧执行覆盖、重复终态、不可解释积压或未经审计的人工修复。
- 单物理服务器上的多进程实验只证明进程隔离、共享状态竞争和进程重启恢复；不得据此宣称
  主机级高可用、跨主机网络分区容错或存储节点故障切换。

   schema 至少兼容当前与上一版本，未知版本进入隔离/DLQ 而不是错误执行。
6. 确认新写入不需要回切后，依次下线 Flask、SQLite 生产写路径、本地 Dispatcher 和无调用

7. 输出生产 Runbook：积压、DLQ、callback unknown、业务 `recovery_required`、人工解除、备份
   恢复、扩容和故障升级；运维动作必须鉴权、记录操作者、原因、前后状态和审计时间。
8. 生产语义明确为“至少一次投递 + 条件写 + 幂等副作用 + 未知结果隔离”。系统不承诺
   exactly-once，不能把“数据库只有一个成功终态”扩张成“所有外部副作用恰好执行一次”。

## 16. 全局完成判据

- 业务层不依赖 Flask/FastAPI、Celery、SQLAlchemy 实现、Redis、RabbitMQ 或 AnythingLLM Client。
- 所有异步任务以持久化 task ID 恢复；Web 不创建业务后台线程。
- 正常积压不触发业务数量阈值拒绝，且积压不会造成 Web 进程内存线性增长。
- 任务、输入、Outbox、回调、进度和产物的事务/引用关系可审计、可恢复。
- 至少 50 在途任务、50 长连接和 50 短请求稳定并发通过真实环境验收。
- 无任务串扰、静默丢失、重复终态、旧回调覆盖和未记录的人工修复。
- 所有已批准公开契约通过自动化黄金样例；没有新增或删除任何前后端接口参数。
