## 1. 结论摘要

阶段 1G 是阶段 1 的结构关闭波次，不是新的业务功能波次，也不是可靠队列、多实例或数据库迁移波次。
它要把阶段 1C～1H 已经切换的新运行链收口为可维护的模块化单体，并用可复核证据处置旧路径。

本阶段必须完成以下结果：

1. Debug 路由只保留协议解析和响应呈现，查询、聚合、文件读取与本地数据库读取进入专用
   Debug Application、Port 和 Adapter。
2. app/container.py 成为不导入 Flask 的框架无关生产组合根；Flask current_app 访问仅存在于
   Web Adapter。
3. 正式蓝图继续保持 Parser -> Application -> Presenter，不创建后台线程、不直接访问 SQLite、
   不直接构造或编排 AnythingLLM Client。
4. 把旧 Analysis、Report、Weaponry、Translation 和文档处理测试中的有效断言迁到新模块，
   不以删除测试代替迁移测试价值。
5. 对每个遗留文件分别取得运行、兼容源码、测试、配置/脚本和当前说明文档证据；只有满足删除
   门禁并确认回滚观察期结束后，才允许物理删除。
6. 输出阶段 1 的模块所有权、依赖方向、暂保留 Adapter、条件删除项和阶段 2 输入清单。

推荐执行顺序如下：

~~~text
1G-0 契约与引用基线
  -> 1G-1 Debug 查询边界
  -> 1G-2 框架无关组合根
  -> 1G-3 正式蓝图关闭审查
  -> 1G-4 遗留测试价值迁移
  -> 1G-5 条件物理删除

~~~

1G-5 是条件波次。若仓库外调用、运行配置或回滚观察期无法确认，则本阶段只输出明确的保留清单，

## 4. 不可改变的契约

### 4.1 公开业务契约

1G 必须保持 docs/接口文档/ 中全部 HTTP、Callback、Progress、SSE 和 WebSocket 契约。
尤其不得改变：

- /llm/analysis、/llm/generate-report、/llm/weaponry 的严格空 HTTP 202。
- /llm/check-task 的整批预校验、业务键规范化、稳定去重和严格空 HTTP 200。
- report/file/weaponry 的冲突、callback sending/outcome_unknown 和 latest-wins 规则。
- /llm/progress 的无 action 协议和错误后保持连接语义。
- /llm/chat* 的请求字段、SSE 事件、history 投影、abort/delete/title 行为。
- /llm/reassign 的同步 200/400/500 契约。
- 所有回调字段、状态和值域。

### 4.2 Debug 行为冻结

/debug/* 不属于甲方协议接口，但被本地调试页面依赖。1G 将其作为内部稳定契约冻结：

| 路由 | 固定输入 | 固定输出/行为 |
| --- | --- | --- |
| GET /debug/callback | 无 | HTTP 200，渲染现有 callback.html |
| GET /debug/api/callback | 可选 query 参数 record，仍只接受单个 JSON 文件名 | HTTP 200；保持 ok、message、payload、records、selectedRecord 五个顶层字段 |
| GET /debug/chat | 无 | HTTP 200，渲染现有 chat.html，页面继续调用既有 /llm/chat、history、delete |
| GET /debug/api/chat/bootstrap | 无 | HTTP 200；保持 ok、message、data.sessions、data.availableFiles，session 的 chatId/fileNames/createdAt/updatedAt 不变 |

还必须保持：

- callback 历史默认最多 50 条，按 mtime_ns 和文件名稳定倒序。
- record 路径穿越、嵌套路径、非 JSON、缺失记录继续返回既有失败载荷，不抛出 500。
- 非法 JSON、非对象根节点和读取失败的既有 message 保持不变。
- Chat Debug 的 fileNames 继续表示 Active Scope，而不是累计 Workspace bindings。
- deleted 会话不展示；不兼容字符串 chatId 不回显。
- 调试日志只能记录状态、计数和错误类型，不记录回调正文、文件正文、凭据、document_ref、
  workspace/thread 引用、内部 run/lease/scope/task 标识。

现有 Chat Debug 失败消息包含底层异常文本。1G 为避免未经确认改变内部调试响应，暂保持现状；
如安全审查要求改为固定脱敏文案，必须作为单独行为变更向负责人确认。

### 4.3 接口文档门禁

本计划不修改 docs/接口文档/。实施中出现以下任一情况必须停止：

- 需要修改公开 URL、方法、参数、字段、类型、状态码、Header 或消息文本。
- 需要修改 Callback、Progress、SSE、WebSocket 的格式或时序。
- 需要让前端传入新的调度、调试、租约、执行或兼容参数。
- 内部重构无法保持现有空响应体、批量原子性、冲突和错误映射。

## 6. 通用实施与证据规则

### 6.1 小步提交原则

- 每个子波次单独提交并可独立回退。
- 先加新边界和等价测试，再切调用，最后删除旧实现。
- 不在同一提交中同时迁移 Debug、重组容器并删除业务旧执行器。
- 不保留在线双执行、双写或影子外部副作用。
- 物理删除提交只做删除、导入/导出清理、测试迁移和必要文档更新，不夹带业务修复。

### 6.2 引用证据分类

引用检查器必须分别报告：

1. 生产 Import：app/、run.py、实际启动脚本中的 Python Import。
2. 生产 Call：通过别名、属性或动态导入形成的调用。
3. 兼容源码引用：旧模块彼此调用、薄 Facade 转发或导出。
4. 测试执行引用：Import、patch、直接调用、动态 import_module。
5. 禁止项字符串：AST/文本门禁中仅用于断言“不应出现”的名字。
6. 配置与脚本引用：tracked env 示例、Docker、PowerShell/Shell、运维脚本和入口。
7. 当前说明引用：README 中把旧实现描述为当前能力的内容。
8. 历史审计引用：历史计划、更新记录和冻结资产中的名称，仅记录、不要求删除。

不得把纯文本 rg 数量直接当作可删除结论。最终结论必须结合 AST、调用点人工复核和测试。

### 6.3 物理删除门禁

每个删除对象必须同时满足：

- 生产 Import/Call 为 0。
- 兼容源码执行引用为 0。
- 测试执行引用为 0；只允许禁止项字符串和历史资产引用。
- tracked 配置、启动脚本和运维脚本不选择旧实现。
- 本机忽略配置由负责人确认不存在旧模块路径或旧模式选择。
- 仓库外 Python 调用方由负责人确认不存在，或已完成版本化迁移。
- 回滚观察期已由负责人明确宣布结束。
- 迁移后的等价测试和扩大回归通过。
- 删除不需要改变公开接口文档。

任一项不满足时，输出“保留原因、当前引用、下一责任阶段”，不删除。

## 17. 并发、数据库和未来架构边界

1G 只改善依赖方向和可替换性，不提升运行能力结论：

- 当前 Dispatcher 仍是进程内固定 Worker 与 SQLite 持久积压。
- OS 文件锁和进程内活动标记不是分布式 lease/fencing。
- Debug Adapter 的 50 并发 Fake 只证明无进程内共享状态串扰。
- SQLite WAL/BEGIN IMMEDIATE 结果不证明 MySQL、多实例或跨数据库一致性。
- 删除旧 Worker 不等于获得可靠队列；阶段 2～6 仍需 Attempt、Outbox、Broker、ACK/DLQ 和切换。
- ApplicationServices 框架无关不等于 FastAPI 已迁移；阶段 8 只替换 Web Adapter。

## 22. 设计审查结论

### 22.1 已通过的审查项

- 契约边界：本设计不需要修改接口文档，也不增删公开参数。
- 阶段边界：没有把可靠队列、MySQL、多实例、FastAPI 或容量验收提前到 1G。
- 依赖方向：Debug 和正式 Route 都以 Application/Port/Adapter 为边界。
- 生命周期：保留 create_app 对生产/注入容器的现有所有权和 fail-fast。
- 删除安全：物理删除由五类仓库证据、仓库外确认和回滚观察期共同门禁。
- 测试价值：明确先迁断言再删旧实现。
- 历史审计：区分当前说明与历史记录，避免要求历史文本“零引用”。
- 活跃基础：明确 task_service.py 等当前生产依赖不能整文件删除。

### 22.2 审查中发现并已在设计中修正的问题

1. 旧总计划只写“运行、测试、配置三类引用”，1F 交接又包含文档引用。本文统一为：
   当前说明和可执行示例必须更新，历史审计文档保留并单列。
2. app/container.py 的生产装配已经基本框架无关，实际 Flask 耦合仅集中于 getter。本文采用最小迁移，

3. task_service.py 虽含旧兼容 API，但仍被多个现行业务 Adapter 使用。本文禁止整文件删除，只允许
   按方法级证据清理。
4. rag_pipeline.py 虽含旧 AnythingLLM 编排，prepare_upload_files 仍被 Report Adapter 使用。本文先
   迁窄能力，再删除旧编排。

   被误解为可任意改变。
