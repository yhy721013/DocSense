## 1. 范围与非目标

### 1.1 范围

- `/llm/check-task` 的请求解析、任务读取、回调补发编排和响应 Presenter。
- `/llm/progress` 的无 action 订阅解析、快照查询、订阅管理、消息 Presenter 和连接释放。
- tasks 模块最小骨架、框架无关 DTO/Port 和兼容 Adapter。
- 当前 `LLMTaskService`、`LLMProgressHub` 的兼容封装和必要并发保护。
- 架构导入测试、契约测试和离线并发测试。
- `ApplicationServices`/Bootstrap 增加新用例装配，但保留旧依赖供未迁移业务使用。

### 1.2 非目标

- 不迁移 analysis、report、weaponry 的提交和执行流程。
- 不改变内部任务状态或 callback 状态；这些值不再由 check-task 成功响应公开。
- 不在 1A～1B 实现 report 重复提交策略；D0-08 已确认活动 `reportId` 返回 409，由波次 1C 实现和验证。
- 不增加任务取消、租约、fencing、Outbox 或队列。
- 不修改 `/llm/chat*`。
- 不物理移动整个 Blueprint、`services/chat` 或 `llm_service`。
- 不删除旧 `LLMTaskService`；本阶段只建立可替换边界。

## 2. 现有调用链与目标调用链

### 2.1 `/llm/check-task` 现状

```text
Flask route
  → 解析 businessType/params
  → LLMTaskService.get_task
  → LLMTaskService.replay_callback_if_needed
      → requests.post Callback
      → 更新 callback_status
  → 再次 get_task
  → 路由拼装单项/批量 JSON
```

主要问题：协议解析、恢复副作用、存储、HTTP 回调和 Presenter 位于同一调用链，且“查询”名称容易掩盖回调写操作。

### 2.2 `/llm/check-task` 目标

```text
Flask CheckTaskRequestAdapter
  → CheckTaskStatusService
      → TaskReadPort
      → CallbackRecoveryPort（必要时）
      → TaskReadPort（恢复后重读）
  → CheckTaskResponsePresenter
  → Flask empty response/status
```

### 2.3 `/llm/progress` 现状

```text
WebSocket route
  → json.loads
  → Blueprint helper 解析 action/keys
  → 直接访问 LLMProgressHub
  → Hub/LLMTaskService 选择快照
  → 路由拼装并 ws.send
```

### 2.4 `/llm/progress` 目标

```text
Flask WebSocket Adapter
  → ProgressRequestAdapter
  → ProgressSubscriptionService
      → ProgressSnapshotPort
      → ProgressSubscriptionPort
      → TaskReadPort fallback
  → ProgressMessagePresenter
  → Connection-local Subscription Registry
  → ws.send
```

## 5. 内部类型与职责

### 5.1 domain/models.py

建议定义不可变对象：

- `TaskId`：非空内部执行 ID。
- `TaskBusinessRef`：business_type + 规范化 business_key。
- `TaskSnapshot`：任务、公开状态原值、progress、callback 状态和时间。
- `TaskLookupItem`：保留请求顺序和公开响应键/值。
- `ProgressKey`：业务类型和内部字符串键。
- `ProgressSnapshot`：内部 task ID、progress、message、sequence 和更新时间。

领域对象不接受 Flask request、任意未校验 `dict` 或 SQLite Row。

### 5.2 TaskReadPort

职责仅为读取：

- 按 TaskId 读取。
- 按业务引用读取最新可见任务。
- 按有序业务引用批量读取并保留缺失位置。

禁止执行 Callback、发布 Progress 或修改状态。

### 5.3 CallbackRecoveryPort

职责为：

- 判断指定 TaskId 是否需要补发。
- 使用当前配置和现有 Callback Presenter 执行一次恢复。
- 持久化当前 TaskId 对应的 success/failed/skipped。
- 返回 `attempted`、`replayed` 和最终状态，不返回 HTTP Response。

兼容 Adapter 必须使用 expected execution ID 做条件保护，防止 check-task 查询期间业务键被新提交覆盖后，补发错误执行的结果。

本阶段的 CallbackRecoveryPort 只表示由 `/llm/check-task` 明确触发的一次恢复，不实现后台 callback Worker 自动重试。若发送后结果未知，内部 callback 状态兼容落为 `failed`，并在内部结果/日志中区分 `delivery_outcome_unknown`，供阶段 4～6 持久化；check-task 成功响应不公开这些字段。

### 5.4 CheckTaskStatusService

标准算法：

1. 对每个有序 TaskLookupItem 读取最新任务。
2. 单项缺失记录为 not found；批量缺失保留空位置。
3. 对存在的 task ID 调用 CallbackRecoveryPort。
4. 若恢复可能写状态，则按同一 task ID 重读。
5. 生成框架无关内部结果供日志、审计和单元测试使用；成功 Presenter 统一输出 HTTP 200 空响应体。

任何一项恢复失败时的异常分类必须与当前行为一致，不能悄悄吞掉并返回成功。

### 5.5 ProgressSubscriptionService

职责包括：

- 接受已经解析的 `ProgressSubscriptionRequest`。
- 按 keys 顺序查询当前快照并注册订阅。
- 每个 key 产生一个当前快照。
- 返回待发送消息序列和订阅变更，不直接调用 ws.send。
- 连接关闭时幂等释放当前连接 Registry 中全部订阅。

WebSocket Adapter 负责 JSON、连接循环、发送和 finally 释放。

## 6. 波次 1A 执行步骤

### 1A-1：接口契约清单

补齐 `/llm/check-task` 测试：

- businessType 非法。
- params 缺失、空数组、非数组和无效元素。
- fileName/reportId/architectureId 缺失。
- 单项存在、单项缺失 404。
- 批量全部存在、部分缺失、顺序保持。
- file/report/weaponry 的内部业务键类型和状态原值；Presenter 不再通过成功响应输出它们。
- pending/failed 回调成功重放。
- 重放失败后内部 callbackStatus 仍为 failed。
- 无 Callback URL 时内部 pending → skipped 且 replayed=false。
- skipped 在以后配置 URL 后仍不重放。
- 单项/批量成功均为 HTTP 200 空响应体；单项缺失 404、参数错误 400。

补齐 `/llm/progress` 测试：

- 非法 JSON、出现 action、非法 businessType、空 params。
- 无 action 订阅：按 params 顺序发送快照，不发送 ack，并建立订阅。
- 连接关闭：移除当前连接全部订阅，不发送控制消息。
- 批量顺序与 count。
- Hub 最新值优先，Hub 无值回退任务快照。
- 缺失任务 exists=false。
- 目标公开契约冻结 file/report 的业务键和值类型；weaponry Progress 仅作当前内部兼容回归，不升级为公开承诺。
- progress 归一化。
- 连接关闭释放所有订阅。
- 两个连接订阅同一任务互不影响。

### 1A-2：模块骨架和导入规则

创建空模块与 README，架构测试至少拒绝：

- `app.modules.*.domain` 导入 Flask、FastAPI、Celery、SQLAlchemy、sqlite3、requests。
- `app.modules.*.application` 导入 Blueprint、Flask request/current_app、具体 Adapter。
- modules/tasks 导入 chat persistence 或其他业务 Adapter。
- presenters 导入具体数据库和 AnythingLLM Client。

### 1A-3：内部契约测试

先用 Fake Port 实现 `CheckTaskStatusService` 和 `ProgressSubscriptionService` 的测试，不接现有 SQLite/Hub。以此证明内部契约不依赖框架。

### 1A-4：阶段门禁

- 所有新增测试在旧生产路径未切换时通过。
- 没有修改数据库文件或接口文档。
- 新模块只包含类型、Port、Fake 测试和文档，不宣称已接管路由。

## 7. 波次 1B-1：迁移 check-task

### 1B-1.1：execution-scoped 兼容能力

在旧 Task Service 内新增或提取：

- 按 execution ID 读取任务。
- 按 expected execution ID 条件更新 callback 状态。
- 按 execution ID 构造当前回调上下文。
- 重放前后检查业务键最新投影仍指向同一 execution ID。

原有方法暂时保留，供未迁移调用方使用；新 Adapter 只能调用 execution-scoped 能力。

### 1B-1.2：实现 LegacyTaskReadAdapter

- 把旧字典行转换为 `TaskSnapshot`。
- 规范化 business key，但保存公开响应原值。
- 批量读取保留输入顺序和 None。
- 不把 request_payload、结果正文等无关大字段交给 Presenter。

### 1B-1.3：实现 LegacyCallbackRecoveryAdapter

- 封装当前 callback 配置和发送能力。
- 保持 pending/failed/skipped 规则。
- 结构化记录 task ID、业务键、attempt、`trigger=check_task`、投递阶段和结果；发送后超时不得在本次请求之外递归重试。
- 不在 TaskReadAdapter 中混入网络调用。

### 1B-1.4：实现 Presenter

Presenter 必须精确处理：

- 单项/批量成功：HTTP 200、零字节响应体，不序列化任务 JSON。
- 单项缺失：当前 404 JSON 错误。
- 参数非法：当前 400 JSON 错误。
- 批量缺失：其余存在项仍执行必要恢复，整批完成后返回 200 空响应体。

### 1B-1.5：切换路由

路由只做：读取 JSON → Request Adapter → Application Service → Presenter → empty/error response。切换后删除 Blueprint 内相应业务循环，但先保留内部用例测试，确认无调用后再删。

### 1B-1.6：回滚

本波次不改 Schema。回滚方式为恢复容器绑定和旧 route handler；已产生的 callback 状态仍是合法现有状态，不执行数据库反向变换。

## 8. 波次 1B-2：迁移 progress

### 1B-2.1：请求和消息 Presenter

- 把无 action 订阅解析移入 Flask Request Adapter；出现 `action` 时按不支持的控制消息处理，不再执行旧分支。
- 把 `_build_progress_snapshot` 和 error 消息格式移入 Presenter，不再构造 ack。
- 保留无 action 请求格式、错误文本、进度消息顺序和字段类型。

### 1B-2.2：线程安全 InMemory Adapter

实现要求：

- 使用锁保护 subscribers/latest。
- 在锁内复制订阅者和快照，在锁外调用订阅者。
- subscribe、unsubscribe 和连接 finally 释放幂等。
- 一个 subscriber 抛错时记录并隔离，不阻断其余订阅者。
- 不把慢 WebSocket send 放在 Worker 持有的内部锁中。

若直接增强 `LLMProgressHub`，必须保持原类测试和调用接口；若新增 Adapter，则旧类只作为兼容 Facade，生产容器只能有一个权威实例。

### 1B-2.3：实现 ProgressSubscriptionService

- 无 action 订阅使用统一快照选择规则，并按请求顺序建立订阅。
- 不支持显式 action，不产生 ack。
- Registry 由每个 WebSocket 连接持有，服务不保存连接对象。

### 1B-2.4：切换 WebSocket 路由

路由只负责 receive、JSON 错误映射、调用用例、send 和 finally 清理。业务线程和应用服务不得持有 ws 对象。

### 1B-2.5：离线并发验证

使用 Fake subscriber 和线程执行：

- 50 个不同 key 并发 publish/subscribe。
- 多订阅者同 key。
- publish 与 unsubscribe 竞争。
- subscriber 抛错。
- 重复释放。
- 快照始终为归一化值且不串 key。

该测试只验证内存适配器隔离，不代表已实现 50 个真实 WebSocket 或跨实例通知。

### 1B-2.6：回滚

恢复旧 Hub/handler 的容器绑定和路由调用。因为本波次没有持久化 Schema 变化，回滚不需要数据转换。

## 9. 日志要求

### check-task

- 请求级：business type、item count、trace ID。
- 项目级：business key、task ID、found、callback before/after、replayed。
- 禁止记录完整 request/result/callback 正文。
- 回调网络错误记录错误类型、耗时和 attempt，不记录 URL 中的敏感信息。

### progress

- 连接建立/关闭、connection ID、订阅数量。
- business type、key count、当前订阅数；不记录完整消息正文。
- subscriber 异常、释放失败和当前订阅计数。
- 高频 progress publish 默认使用 debug/metric，避免 info 日志洪泛。

## 12. 必须停止确认的情况

- 当前代码与接口文档在 check-task/progress 字段或类型上出现冲突。
- execution-scoped 回调保护会改变调用方目前依赖的可观察行为。
- 需要新增公开 task ID、事件 ID、游标或恢复参数。
- 需要改变 reportId/architectureId 的公开类型。
- 需要改变无 action 订阅不发送 ack 的行为。
- 需要把回调补发从 check-task 移除或改为完全异步。
- 发现甲方或生产前端实际依赖已批准删除的 check-task 成功字段或 Progress 显式 action/ack。
