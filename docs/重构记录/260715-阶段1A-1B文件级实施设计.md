## 2. 现有调用链与目标调用链

### 2.1 `/llm/check-task` 现状

```text
Flask route
  → 解析 businessType/params
  → LLMTaskService.get_task
  → LLMTaskService.replay_callback_if_needed
      → requests.post Callback
      → 更新 callback_status
  → 再次 get_task
  → 路由拼装单项/批量 JSON
```

主要问题：协议解析、恢复副作用、存储、HTTP 回调和 Presenter 位于同一调用链，且“查询”名称容易掩盖回调写操作。

### 2.2 `/llm/check-task` 最终目标（阶段 4～6 实现并切换）

```text
Flask CheckTaskRequestAdapter
  → RequestCallbackRecoveryService
      → TaskReadPort
      → CallbackRecoveryCommandPort
          → MySQL transaction: recovery request + Outbox
  → CheckTaskResponsePresenter
  → Flask empty response/status

Outbox Relay
  → RabbitMQ callback.recovery
  → CallbackRecoveryWorker(recovery_request_id)
      → 同业务键 Guard / latest TaskId 校验
      → CallbackDeliveryPort
      → callback delivery/result 条件持久化
      → ACK / DLQ / outcome_unknown
```

波次 1B-1 已实现和测试上半段的框架无关 DTO/Command Port 形状，不提供能够假装可靠登记的
进程内 Adapter，也不切换 Flask route。只有 MySQL 事务、Outbox Relay、RabbitMQ、
Worker、幂等和故障注入门禁全部通过后，阶段 6 才允许将旧同步路由直接替换为上述链路。

### 2.3 `/llm/progress` 现状

```text
WebSocket route
  → json.loads
  → Blueprint helper 解析 action/keys
  → 直接访问 LLMProgressHub
  → Hub/LLMTaskService 选择快照
  → 路由拼装并 ws.send
```

### 2.4 `/llm/progress` 目标

```text
Flask WebSocket Adapter
  → ProgressRequestAdapter
  → ProgressSubscriptionService
      → ProgressSnapshotPort
      → ProgressSubscriptionPort
      → TaskReadPort fallback
  → ProgressMessagePresenter
  → Connection-local Subscription Registry
  → ws.send
```

## 5. 内部类型与职责

### 5.1 domain/models.py

建议定义不可变对象：

- `TaskId`：非空内部执行 ID。
- `TaskBusinessRef`：business_type + 规范化 business_key。
- `TaskSnapshot`：任务、公开状态原值、progress、callback 状态和时间。
- `TaskLookupItem`：保留请求顺序和公开响应键/值。
- `ProgressKey`：业务类型和内部字符串键。
- `ProgressSnapshot`：内部 task ID、progress、message、sequence 和更新时间。

领域对象不接受 Flask request、任意未校验 `dict` 或 SQLite Row。

### 5.2 TaskReadPort

职责仅为读取：

- 按 TaskId 读取。
- 按业务引用读取最新可见任务。
- 按有序业务引用批量读取并保留缺失位置。

禁止执行 Callback、发布 Progress 或修改状态。

阶段 1A-3 的实际签名以 `TaskBusinessRef` 作为单项/批量输入，而不是传递松散的
business type/key 字符串。批量返回值必须与输入等长、同序，并以 `None` 保留缺失
位置；应用服务会把长度、业务键或 TaskId 不一致视为端口契约错误。

### 5.3 CallbackRecoveryCommandPort（最终目标）

职责为：

- 根据 TaskId 判断是否需要登记显式恢复命令。
- 在同一 MySQL 事务中创建或复用该 TaskId 唯一的活动 recovery request，并写 Outbox。
- 返回 `created/already_active/not_needed/stale` 内部登记结果，不执行外部 HTTP，也不返回
  Flask Response。
- 数据库事务未提交时必须抛出异常，禁止 Presenter 返回成功；RabbitMQ 暂时不可用但
  Outbox 已提交时仍属于可靠登记成功，由 Relay 恢复后发布。

阶段 1A 已实现的同步 `CallbackRecoveryPort.recover_if_needed()` 继续作为已完成审查的
原型和测试证据，但不再是生产目标，不得为其新增 `LegacyCallbackRecoveryAdapter`。
波次 1B-1 已以 Fake Command Port 修订应用契约；MySQL Adapter 在阶段 3～4 实现，
RabbitMQ/Worker Adapter 在阶段 5 实现，阶段 6 才进行组合根和路由切换。

阶段 1B-1 实际采用批量 `request_many(commands)`，为一个 HTTP 请求保留单次共享事务
边界。输入命令携带 expected TaskId、业务引用、固定触发源、Schema 版本和追踪信息；
recovery request ID 不由 Web/Application 提前生成，而由持久化 Adapter 在事务内创建
或复用，并只通过 `created/already_active` 结果返回。该差异避免请求线程伪造一个尚未
提交的持久化身份。

2026-07-16 已确认 TASK-09 采用 latest-wins：`fileName` 是前端唯一逻辑任务键，同一
文件名的多个 `execution_id` 只是不同执行代次。callback Worker 必须在同一
`TaskBusinessRef` 的共享 Guard/租约内重新读取最新 TaskId；不匹配时不调用外部回调，
持久化 stale/skipped 后 ACK。匹配时才允许外发并按 expected TaskId 条件持久化。

Guard 不能撤回已经交给网络的 HTTP 请求。发送后读取超时继续记录
`delivery_outcome_unknown` 且不自动重试。2026-07-16 已确认其后准入规则：旧 callback
已先取得发送权时，新提交最多等待当前 callback timeout；结果未知或等待到期仍被占用时，
返回对应接口既有 409 并冻结同键，直至内部人工解除。该策略仍不能把 latest-wins 描述
为绝对零迟到保证。

### 5.4 RequestCallbackRecoveryService

最终标准算法：

1. 按既有协议接收有序 `TaskLookupItem`，执行整批类型和业务键校验。
2. 在 MySQL 事务内读取相应最新任务；单项缺失交给 Presenter 映射 404，批量缺失保留
   位置但不为其创建命令。
3. 对 callback 已 success/skipped 或任务未终态的项记录 `not_needed`；对 eligible TaskId
   创建或复用唯一活动 recovery request，并在同一事务写 Outbox。
4. 整个事务提交成功后才生成框架无关成功结果；Presenter 返回 HTTP 200 空响应体，
   不等待 Outbox 发布或外部回调完成。
5. callback Worker 按 recovery request ID 读取事实，执行 latest-wins、投递、条件写、
   delivery 审计与 ACK/DLQ；这些不在 Web 应用服务调用栈中。

阶段 1A 的 `CheckTaskStatusService` 和“恢复后按原 TaskId 复读”测试继续证明同步 Adapter
不得误报持久化结果，但会在后续实现中由 Web 侧命令登记一致性测试和 Worker 侧投递
一致性测试取代。1B 不删除该证据、不把原型装配生产，也不提前修改当前 route。

### 5.5 ProgressSubscriptionService

职责包括：

- 接受已经解析的 `ProgressSubscriptionRequest`。
- 按 keys 顺序查询当前快照并注册订阅。
- 每个 key 产生一个当前快照。
- 返回待发送消息序列和订阅变更，不直接调用 ws.send。
- 连接关闭时幂等释放当前连接 Registry 中全部订阅。

WebSocket Adapter 负责 JSON、连接循环、发送和 finally 释放。

阶段 1A-3 采用“先注册缺失订阅，再读取当前快照”的内部顺序，避免在旧快照读取与
订阅建立之间完全漏掉一次发布。应用服务返回 current items、active subscriptions
和 added subscriptions；连接 Registry 仍由 Web Adapter 持有。订阅中途失败会逆序
补偿本次新增令牌，已有令牌不受影响。

2026-07-16 审查修正已增加 `ProgressDeliveryBuffer`：每个连接使用固定容量、绑定
`delivery_id` 的通知队列；应用服务在注册前打开初始屏障，Web Adapter 发送完当前
快照后调用 `complete_initial_delivery()` 才放行并发通知。任务发布线程只进行短临界
区入队，不执行 `ws.send`；饱和时按 key 合并或淘汰最早中间快照并记录指标。补偿和
连接释放异常携带完整失败令牌，Registry 必须保留并重试。

2026-07-16 阶段 1B 全面审查后的修复又为每个连接增加“已接受同 TaskId sequence
水位”。水位在通知入队或初始快照确认时更新，队列出队、合并或淘汰后仍保留到连接
关闭；因此 Hub 锁外 subscriber 回调即使乱序完成，迟到的旧序号也不能重新入队。
不同 TaskId 的过期判断仍等待阶段 1C 持久化 latest-wins Guard，不能由本地序号猜测。

## 6. 波次 1A 执行步骤

- fileName/reportId/architectureId 缺失。
- 单项存在、单项缺失 404。

- progress 归一化。
- 连接关闭释放所有订阅。
- 两个连接订阅同一任务互不影响。

## 8. 波次 1B-2：迁移 progress

> 执行状态（2026-07-16）：**已完成**。已接入无 action 请求 Adapter、Progress
> Presenter、线程安全单实例 Adapter、遗留 Task 只读 Adapter、连接级 Registry/有界
> 缓冲、Container 与 WebSocket 单写入路由；补齐 50 键离线并发、新旧 TaskId 屏障竞态、
> 多连接隔离和释放失败重试测试。未引入 MySQL、Redis、RabbitMQ 或真实后台服务。
> 实际结果见 `../更新记录/260716-阶段1B-2Progress控制面迁移执行记录.md`。

### 1B-2.1：请求和消息 Presenter

- 把无 action 订阅解析移入 Flask Request Adapter；出现 `action` 时拒绝整条消息，发送既有结构的 error 消息、保持连接且不发送 ack，不再执行旧分支。
- `params` 任一元素不是对象时拒绝整条消息，不建立部分订阅；发送 error 消息并保持连接。
- 把 `_build_progress_snapshot` 和 error 消息格式移入 Presenter，不再构造 ack。
- 保留无 action 请求格式、既有 error 字段结构、进度消息顺序和字段类型；错误原因文字不冻结为稳定枚举值。

### 1B-2.2：线程安全 InMemory Adapter

实现要求：

- 使用锁保护 subscribers/latest。
- 在锁内复制订阅者和快照，在锁外调用订阅者。
- subscribe、unsubscribe 和连接 finally 释放幂等。
- 一个 subscriber 抛错时记录并隔离，不阻断其余订阅者。
- 不把慢 WebSocket send 放在 Worker 持有的内部锁中。

若直接增强 `LLMProgressHub`，必须保持原类测试和调用接口；若新增 Adapter，则旧类只作为兼容 Facade，生产容器只能有一个权威实例。

### 1B-2.3：实现 ProgressSubscriptionService

- 复用阶段 1A 已实现的服务、连接有界缓冲和初始快照屏障；无 action 订阅使用统一快照选择规则，并按请求顺序建立订阅。
- 不支持显式 action，不产生 ack。
- Registry 和唯一 `ProgressDeliveryBuffer` 由每个 WebSocket 连接持有，服务不保存连接对象。
- 初始 current items 全部发送成功后才完成屏障；发送失败则撤销屏障、关闭缓冲并释放令牌。
- release/rollback 异常携带的失败令牌必须留在 Registry 中重试，不能只写日志后丢弃。

### 1B-2.4：切换 WebSocket 路由

路由只负责 receive、JSON 错误映射、调用用例、从有界缓冲取通知、单写入者 send 和 finally 清理。业务线程和应用服务不得持有 ws 对象。

### 1B-2.5：离线并发验证

使用 Fake subscriber 和线程执行：

- 50 个不同 key 并发 publish/subscribe。
- 多订阅者同 key。
- publish 与 unsubscribe 竞争。
- subscriber 抛错。
- 重复释放。
- 快照始终为归一化值且不串 key。

该测试只验证内存适配器隔离，不代表已实现 50 个真实 WebSocket 或跨实例通知。

### 1B-2.6：回滚

恢复旧 Hub/handler 的容器绑定和路由调用。因为本波次没有持久化 Schema 变化，回滚不需要数据转换。
