## 3. 阶段 2 新表的唯一 Writer

- `task_control_schema_metadata` 只由 `app/bootstrap/task_control_schema.py` 在启动锁内初始化/验证；
  普通 Store 无权修改数据库身份。
- `task_attempts`、`task_steps`、`task_step_attempts`、`task_recovery_cases`、
  `task_recovery_observations`、`task_recovery_decisions`、`task_events` 只由
  `app/modules/tasks/adapters/sqlite/control_store.py` 写入，并通过同一连接的窄 UoW 参与原子组。
- `llm_tasks/llm_task_executions` 在 v2 仍由同一 Control Store 写；不新建第二张 `tasks` 主表。

## 4. 迁移期删除条件

每个表的迁移顺序固定为：新 Store 直接拥有 SQL和行转换 → 旧入口单向委托 → 调用方逐个切换并跑
专项测试 → 搜索生产/脚本/测试/动态引用 → 删除旧 SQL和兼容入口。任何时刻同一表不能存在两个
可达写实现；新 Store 禁止调用 `LLMTaskService`，Store 之间只能通过共享 UoW/Connection 协作，
不能互相提交或循环调用。

当前复核未发现目标所有权与既定事务边界冲突。Report 与 Analysis 共享的模型交互表明确收敛到
一个 Observability Store，避免两个业务模块复制相同 SQL；业务只通过各自 Port 传入审计命令。
