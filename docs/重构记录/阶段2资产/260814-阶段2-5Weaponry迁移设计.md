# 阶段 2-5 Weaponry 迁移设计

## 1. 文档性质与边界

本文落实阶段 2 总设计的 2-5 波次。公开权威仍是 `docs/接口文档/知识谱系解析.md` 与
`docs/接口文档/文件处理和报告生成.md`；本设计不增加、删除或改变 HTTP、Progress、Callback
字段、状态码、错误文本和同步恢复语义。阶段内只使用临时 SQLite、Fake 和离线测试，不运行
`run.py`，不把单实例证据表述为可靠队列、多实例或生产容量证明。

Weaponry 必须在同一业务波次内把受理、执行、Progress、终态和 Callback Control 一次切到阶段 2
控制面。切换前允许新实现离线存在，但不得接生产；切换时不得双写、双 claim、从旧库读取“当前
Authority”补权，也不得让新 Store 反向调用 `LLMTaskService`。

## 2. 实施顺序

1. 保持 `WeaponryInputSnapshot/v2` 语义不变，锁定 Codec Port；
2. 将 `infrastructure_config.py` 等价迁移为 `runtime_config.py`；
3. 把文档快照、资源、Creation Intent、交互审计迁入 Weaponry 自有组件 Store，并切换共享
   Callback History Writer；
4. 按冻结 Registry 落实 Step、Checkpoint、ExternalRef 与业务组合 UoW；
5. 复用现有 ownership/cleanup fencing，建立与业务执行分离的专用维护链；
6. 依据资源、Creation Intent 和审计事实对失联任务分类，unknown 一律隔离；
7. 前置全部通过后，一次切换生产控制面并立即删除调用清零的旧 SQL；
8. 固化术语目录 startup gate、Provider/Profile 门禁并完成阶段验收。

每一步完成后均重新检查公开接口、生产启动、旧 Runner Authority、Callback 与恢复语义。出现需要
改变上述任一语义的情况时停止，不进入下一步。

## 3. 步骤 1：Input v2 与 Codec Port

Weaponry 与 Report 不同：当前 v2 已经冻结 `document_scope`、`evidence_selection_policy`、
`execution_policy` 和 `auxiliary_guidance_policy`，足以表达运行决策，阶段 2 通用改造不得升版。
内部版本 3 继续保留给直接父节点专项。

新写 payload 的顶层字段固定为：

```text
schema_version, task_id, architecture_id, business_key, field_templates,
document_scope, evidence_selection_policy, execution_policy,
auxiliary_guidance_policy, accepted_at, trace_id
```

`request_projection` 只服务旧公开投影兼容，不是 Worker 输入。Worker 只能通过 Tasks Port 所定义的
`TaskCommandCodec` 解码持久 payload，不读取当前环境补造 Profile。历史 v2 唯一允许的兼容是
`evidence_selection_policy.reference_filter_strategy` 缺失时使用已冻结的
`legacy-reference-filter-v1`；该固定历史语义不是当前环境默认值。

`WeaponryTaskCommandCodec.write_schema_version` 必须恒为 2，供后续 v2 Admission 在组合构造期失败
关闭错误 Codec。步骤 1 不接生产、不修改 `app/container.py`，机器契约为
`tests/contracts/stage2_weaponry_v2_contract.json`。

## 4. 步骤 2：Runtime Config 等价迁移

Weaponry 配置所有权由 `app/modules/weaponry/adapters/runtime_config.py` 持有，类型与加载入口分别为
`WeaponryRuntimeConfig`、`load_weaponry_runtime_config`。旧路径和旧符号物理删除，不保留转发壳；
生产组合、离线组合、运维脚本和测试统一改用新入口。

本步骤只改变内部文件与符号名称。32 个既有环境键、默认值、严格解析、错误触发条件、错误文本、
Runtime Policy/Capability 构造以及脱敏日志保持等价；不在此步骤接入阶段 2 Executor 新字段，也不读取
新的环境变量。历史阶段 1D 文档保留当时文件名作为事实记录，当前所有权机器契约更新为新路径。

## 5. 步骤 3：Weaponry 组件 Schema 与 Store 所有权

Weaponry 在根 Schema generation 2 上发布组件 `weaponry_control/v1`。组件 Manifest 固定声明以下
六张表，启动时由 Task Control Bootstrap 原子安装、登记并严格复核：

```text
weaponry_task_document_snapshots
weaponry_creation_intents
weaponry_interaction_audits
weaponry_resource_records
weaponry_result_snapshots
weaponry_resource_operator_audits
```

文档快照的新身份是 `task_id + sequence_no`，并通过外键绑定唯一 execution；同一业务键的历史
execution 不再互相覆盖。Store 会在同一短事务内核对 `business_type=weaponry` 与 business key，
拒绝把其他任务或架构的文档写入当前 execution。`weaponry_result_snapshots` 按 TaskId 保存完整且带
SHA-256 摘要的既有 Callback JSON，使进程重启后的同步恢复无需猜测或重算业务结果；它必须与
terminal Step、Task/Attempt 终态及 Callback eligibility 在同一事务提交。组件 Store 不创建表、不
修复漂移，也不在事务内
执行网络、文件或供应商副作用。

Creation Intent、Interaction Audit 与资源 Store 的代码所有权迁入
`app/modules/weaponry/adapters/sqlite/`。在步骤 7 原子切换前，它们仍以旧数据库模式作为生产唯一
Writer；新组件只参加离线验证，禁止提前接线、双写或复制旧活动任务。步骤 4 再为这些 Store 增加
借用同连接的业务组合 UoW，使 Task/Step/资源事实能够由最外层一次提交。

Callback Guard 直接调用共享 `app/infrastructure/observability/callback_history.py` 保存非权威历史；
History 不参与幂等、Authority、终态或重试判定。权威 Callback Control 在步骤 7 才与 Weaponry 其余
控制面一起切换，公开 Callback payload、投递与 unknown 语义均不改变。

机器契约为 `tests/contracts/stage2_weaponry_component_contract.json`。步骤 3 结束时生产启动策略、
旧 Runner Authority 传递与公开接口均未改变，因此不存在需要扩大评审的决策项。

## 6. 步骤 4：Step/Recovery Registry 与业务组合 UoW

`WEAPONRY_STEP_REGISTRY` 逐项落实阶段 2-0 冻结的十二类步骤，覆盖资源记录、文档范围、检索
workspace、文档绑定、辅助语境、检索、证据选择、模型抽取、翻译、交互审计、结果映射和终态。
动态序号只接受无前导零的正整数，`call_id` 只接受既有内部稳定标识字符；未知或歧义 Key 在开始
外部操作前失败关闭。

每个 Step 绑定 `effect_kind`、`replay_policy`、Schema、成功结果引用与五类恢复矩阵。纯规则矩阵
覆盖 `retry_safe`、`finalize_from_checkpoint`、`reconcile_required`、`defer`、`mark_stale`，但本步骤
不读取供应商现场、不直接授予恢复权；外部结果未知仍不得由普通 Worker 自动重放。

`WeaponryExecutionUnitOfWork` 在一条 `BEGIN IMMEDIATE` 短事务中组合 Task Execution、Callback
Control、文档快照、Creation Intent、Interaction Audit 与资源 Store。各组件 Store 的连接借用模式
不提交、不回滚、不创建 Schema，最外层 UoW 是唯一事务所有者；网络、模型、文件和 Callback HTTP
始终位于事务之外。`WeaponryStepRuntime` 只通过 `TaskWorkflowContextPort.session` 取得完整
Authority，并支持 Step Intent、Checkpoint、Progress、unknown 隔离以及终态/Callback 资格原子组。

步骤 4 的实现仍未接入生产组合；旧 Runner 继续使用既有 Authority 语义，待步骤 7 一次切换，因而
没有形成双 claim 或双写。离线验收同时验证了根表与组件事实统一提交/回滚，以及旧路径 Store 的
既有 CAS、清理 fencing 和 Creation Intent 恢复回归。

## 7. 步骤 5：资源 Ownership 与 Cleanup Fencing

步骤 5 复用阶段 1D 已验证的逐资源清理状态机，不创建通用 Task Reaper 删除能力。维护器只能从
`WeaponryResourceRecord.owned_cleanup_candidates` 取得候选，并将精确 `external_ref` 交给清理
Adapter；`shared` 资源永不进入删除。Creation Intent 的确定性名称只用于唯一查回，查回逻辑没有
workspace/thread 删除入口。

资源维护的独立短事务 Store 已支持严格 Task Control `SQLiteTransactionManager`，每次领取生成随机
lease token 并单调递增 cleanup fencing token。外部 DELETE 在事务外单次执行，结果写回必须同时匹配
TaskId、资源 ID、expected version、lease token、fencing token 和租约有效期；新的 owner 产生后，旧
owner 即使晚到也不能提交。结果未知转为 `cleanup_unknown` 并隔离，禁止自动重发 DELETE。

## 8. 步骤 6：失联任务事实分类

`WeaponryRecoveryFactCollector` 有界读取单个 Task 的资源、Creation Intent 和 pending Interaction
Audit，只形成计数、状态与 SHA-256 证据摘要，不持久化外部名称、URL、Prompt 或响应正文。
`WeaponryDisconnectedTaskClassifier` 再结合 Task Step 投影作纯分类：

- latest 已合法变化：`mark_stale`；
- cleanup lease 正在观察：`defer`；
- 完整 terminal checkpoint：`finalize_from_checkpoint` 候选；
- 没有外部效果事实且未启动 External Write：`retry_safe` 候选；
- 资源隔离/unknown、pending/recovering/quarantined Intent、pending Audit、已记录外部引用、已启动
  External Write 或事实页截断：一律 `reconcile_required`。

本分类器不会直接修改 Task、创建 Recovery Case、调用供应商或授权业务重试；阶段 2-7 的通用
Recovery Coordinator 仍需以独立 recovery lease/fencing 和 Observation/Decision 完成最终条件写。
因此步骤 6 没有提前扩大 Reaper 权限，也不改变 `/llm/check-task` 语义。

## 9. 步骤 7：生产控制面原子切换与旧 SQL 清理

步骤 1～6 的离线门禁全部通过后，生产组合根一次性切换以下整条链路，不存在新旧双写或双
claim：

```text
SubmitWeaponryV2Task
  -> Task Control Admission + weaponry_task_document_snapshots
  -> LocalTaskExecutor
  -> TaskExecutionRuntime(claim/start/heartbeat/Authority Session)
  -> RunWeaponryV2Workflow + WeaponryStepRuntime
  -> result snapshot + terminal Step + Task/Attempt terminal + Callback eligibility
  -> TaskControlWeaponryCallbackAdapter
```

受理使用专用 `WeaponryAdmissionUnitOfWork`，在一个短事务内提交 accepted Task、Callback 冲突门禁
和按 TaskId 隔离的文档快照。执行只消费 `CodecTaskExecutionSnapshotLoader` 解码的冻结 Input v2；
完整 `task_id/attempt_no/lease_token/fencing_token/lease_expires_at` 由通用 Execution Runtime 领取并
交给 Authority Session，Weaponry Runner 不再读取或补造旧 Authority。

成功或普通业务失败的终态事务同时提交完整 `weaponry_result_snapshots`、`result.map`/`terminal.commit`
Step、Task/Attempt 终态和 Callback eligibility。HTTP Callback 位于事务外，并在发送前以 Guard
lease/fencing 再次验权。同步 check-task 恢复从 latest Task 与完整结果快照重建原有公开 payload，
不从摘要猜测字段，也不重新执行模型。

字段外部操作保持“审计先于隔离”的固定次序：模型或翻译结果未知时，先提交对应 Interaction
Audit 终态，再把外部 Step 标记为 `outcome_unknown` 并使 Task 进入 `recovery_required`。辅助语境
和检索的结果未知不再沿用普通容量降级；它们同样停止在业务终态前。这样既不会丢失审计事实，
也不会在 Authority 已失效后补写 Step 或 Callback。

生产 Worker 使用持久 lease/fencing 后，不再取得旧进程文件锁；这属于阶段 2-3 已冻结的
Authority 替换，而不是多实例能力声明。SQLite、进程内 Event 和本地线程仍只构成单机实现；可靠
队列、多实例时钟与数据库级部署能力继续留在后续阶段验证。

切换完成后，`LLMTaskService` 中仅 Weaponry 使用的旧文档快照 DDL、迁移、读写方法已经删除。
历史数据库若仍含旧表，旧 Service 只保留现场且不再创建或写入；通用 Task/Callback SQL 暂为尚未
迁移的 Analysis 保留。旧 Runner/Dispatcher 类仍作为阶段 1 回归夹具存在，但生产组合根不再构造
它们，也不能回写 v2。

Weaponry 运维脚本同步改为只读严格验证既有 Task Control v2 根 Schema、Report/Weaponry 组件
Manifest 后再取得专用 Store；它不安装/修复 Schema，也不再经 `LLMTaskService` 释放 Callback Guard
或连接旧资源表。这样人工恢复入口与生产 Writer 使用同一 Authority/Fencing 事实，且不会因运维
命令悄然重建已经清理的旧 SQL。

## 10. 步骤 8：Startup Gate、能力门禁与验收边界

Task Control Bootstrap 在任何 Weaponry 维护或 Worker 线程启动前同时校验根 Schema、Report 组件和
Weaponry 组件 Manifest。术语目录 `prepare` 仍是 Dispatcher 的前置 startup gate；失败时不启动
任何维护/执行线程。Provider、Embedding、Document Processing、Extraction Model、Query、score、
rank、reference filter 与 extraction context 仍按现有 Runtime Config/Capability 契约严格匹配，
没有增加环境键、默认值或宽松回退。

定向验收使用临时 SQLite、严格 Fake 与确定性时钟，覆盖：受理回滚、完整 claim/start Authority、
全部 Step、结果/终态/Callback 资格原子提交、v2 Guard 投递、失败 Callback 精确恢复，以及 Guidance、
Retrieval、Extraction、Translation 四类结果未知的停止与隔离。验收未运行 `run.py`，未访问真实
Provider、Callback 接收端或现有 AnythingLLM 资源，也不证明浏览器、多实例、可靠队列、生产容量
或恰好一次副作用。

Dispatcher 可观测性把每次已进入 v2 Workflow 的运行计入执行总数；`recovery_required` 虽不是公开
failed 终态，仍计入本次执行失败数，避免外部结果未知现场从运行健康度中消失。具体 unknown 原因
继续由 Task/Step/Recovery Case 指标表达，不与 Callback/cleanup 指标混算。

步骤 8 检查未发现需要改变公开接口、生产启动顺序、旧 Runner Authority 传递或 Callback payload/
同步恢复语义的新增决策项。公开接口文档保持冻结，机器契约最终状态为
`tests/contracts/stage2_weaponry_v2_contract.json` 的 `2-5-completed`。
