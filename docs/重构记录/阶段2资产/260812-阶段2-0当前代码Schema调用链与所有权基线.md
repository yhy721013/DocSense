## 1. 当前正式调用链

### 1.1 Report

```text
POST /llm/generate-report
  -> Flask Parser / Presenter
  -> SubmitReportTask
  -> LegacyTaskCommandAdapter.create_if_allowed
  -> LLMTaskService.create_task_execution_if_allowed
  -> SQLite 提交 accepted execution/latest 投影
  -> LocalReportTaskDispatcher.dispatch（Event 合并唤醒）
  -> LocalPersistentTaskDispatcher 启动/周期扫描 accepted
  -> RunReportTask.execute(TaskId)
  -> TaskCommandPort.claim(TaskId)
  -> 文件/Artifact/RAG/Audit/Callback/Resource Ports
  -> expected TaskId 条件 Progress/终态写
```

当前保护只覆盖 TaskId/latest；不存在整任务 attempt、完整 Authority、heartbeat 或 Task fencing。
Report 资源和 Callback 各有独立的局部 lease/fencing/检查点，不能表述为整任务执行权。

### 1.2 Weaponry

```text
POST /llm/weaponry
  -> Flask Parser / Presenter
  -> SubmitWeaponryTask
  -> LegacyTaskCommandAdapter.create_if_allowed
  -> LLMTaskService.create_task_execution_if_allowed
  -> 文档范围快照 + accepted execution/latest 投影
  -> LocalWeaponryTaskDispatcher
  -> LocalPersistentTaskDispatcher 启动/周期扫描 accepted
  -> RunWeaponryTask.execute(TaskId)
  -> TaskCommandPort.claim(TaskId)
  -> Resource/Creation Intent/Retrieval/Extraction/Audit/Callback Ports
  -> expected TaskId 条件 Progress/终态写
```

Creation Intent、资源记录和 Callback Guard 已能保守保存部分外部副作用事实，但普通 Dispatcher
仍没有 Attempt/heartbeat/Reaper；未知资源所有权不得由未来通用 Reaper 按名称推断或盲删。

### 1.3 Analysis

```text
POST /llm/analysis
  -> Flask Parser / Presenter
  -> SubmitAnalysisBatch
  -> SQLiteAnalysisBatchCommandAdapter.create_batch_if_allowed
  -> LLMTaskService.create_analysis_batch_if_allowed（BEGIN IMMEDIATE）
  -> 整批 execution/latest 投影一次提交
  -> LocalAnalysisTaskDispatcher
  -> LocalPersistentTaskDispatcher 启动/周期扫描 accepted
  -> RunAnalysisTask.execute(TaskId)
  -> SQLiteAnalysisBatchCommandAdapter.claim(TaskId)
  -> Workspace/DocumentProcessing/RAG/Recall/Audit/Knowledge/Translation/Callback Ports
  -> expected TaskId 条件 Progress/终态写
```

当前请求内顺序主要由单 Worker、连续 `batch_sequence` 和持久 `dispatch_sequence` 共同维持；
尚无支持多 Worker 的“同批最小未终态 sequence 才可领取”持久 runnable 查询。

### 1.4 check-task 与 Progress

```text
POST /llm/check-task
  -> ExecuteCheckTask / CheckTaskStatusService
  -> LegacyTaskReadAdapter
  -> SynchronousCallbackRecoveryRouterAdapter
  -> Report/Analysis/Weaponry 各自同步 Callback Recovery
  -> 共享 Callback Guard CAS

WS /llm/progress
  -> ProgressSubscriptionService
  -> InMemoryProgressAdapter
  -> LLMProgressHub
```

`/llm/check-task` 是既有 Callback 恢复入口，不是业务 Task 重跑入口。`LLMProgressHub` 是单实例
低延迟通知和 latest 内存投影，不是恢复真相、跨实例广播或可靠事件日志。

## 2. 当前任务控制 Schema

以下表由 `app/services/llm_service/task_service.py` 当前直接建表或写入：

| 表 | 当前作用 | 当前权威写入者 | 阶段 2 处置方向 |
| --- | --- | --- | --- |
| `llm_tasks` | 按业务键保存 latest 公开投影、结果与 Callback 兼容字段 | `LLMTaskService` | 迁入新 Task Control Store，继续作为兼容投影 |
| `llm_task_executions` | 追加 execution、输入、批次/调度顺序、状态和结果 | `LLMTaskService` | 新 v2 库中的 Task 主事实，扩展控制字段 |
| `callback_delivery_guards` | Callback 发送权、租约与 unknown | `LLMTaskService` | 迁入窄 Callback Control Store |
| `callback_guard_release_audits` | 人工解除追加审计 | `LLMTaskService` | 保持独立审计语义并迁移写入所有权 |
| `callback_delivery_attempt_events` | 初次/显式恢复投递事件 | `LLMTaskService` | 保持 Callback Attempt 命名空间，不合并 Task Attempt |
| `report_resource_records` | Report 资源恢复事实 | `LLMTaskService` | 迁入 Report 自有 SQLite Store |
| `analysis_resource_records` | Analysis 资源恢复事实 | `LLMTaskService` | 迁入 Analysis 自有 SQLite Store |
| `weaponry_task_document_snapshots` | Weaponry 受理文档范围快照 | `LLMTaskService` | 迁入 Weaponry 自有 SQLite Store |
| `llm_architecture_recall_decisions` | Analysis Recall 追加/终结审计 | `LLMTaskService` | 迁入 Analysis Recall Audit Store |
| `llm_interactions` | Report/Analysis 模型交互主审计 | `LLMTaskService` | 迁入明确的 Observability Store |
| `llm_interaction_attempts` | 模型交互尝试历史 | `LLMTaskService` | 保持模型 Attempt 命名空间 |
| `llm_interaction_lifecycle_events` | 模型交互生命周期事件 | `LLMTaskService` | 保持独立审计事实 |

当前 `llm_task_executions.execution_state` 的 CHECK 仅允许
`accepted/running/succeeded/failed/stale`，不能容纳 `recovery_required`。这也是阶段 2 必须使用
独立新空库而不能依靠普通加列原地升级的直接 Schema 证据。

## 4. 当前运行拓扑与限制

1. `app/container.py` 创建一个 `LLMTaskService`、一个 `LLMProgressHub` 和一个
   `UploadTaskLimiter(max_concurrency=1)`。
2. Report、Weaponry、Analysis 各自拥有本地 Dispatcher；它们复用持久扫描内核的部分算法，
   但尚不是“统一 Executor 内核的三个受 Authority 约束实例”。
3. Event 只负责合并唤醒；SQLite accepted 事实、启动扫描和周期扫描才是恢复依据。
4. Dispatcher 对孤儿 running 只做观察/告警，不执行整任务接管。
5. 进程文件锁、内存 activity marker、FIFO limiter 和本地 Hub 都只具有单实例含义。

## 5. 阶段 2 开工差距清单

- 生产源码尚无 Task/Attempt/Step/Event/Recovery Case 物理模型；
- `TaskCommandPort.claim()` 只返回 Task 快照，不返回完整执行 Authority；
- Progress、Step、产物和终态写只校验 TaskId/latest，无法区分同 Task 的新旧 Attempt；
- 三业务 Runner 在各自 Application 内部自行 claim，领取与 heartbeat 生命周期尚未由统一 Runtime 承担；
- `LLMTaskService` 约 7,000 行并混合多个数据所有权；
- Codec 协议仍定义在 `tasks.adapters.legacy_task_commands`，业务 Codec 依赖 Adapter；
- Progress 规则/Hub 分散在 `app/services/core` 与 Tasks；
- Report/Analysis 运行配置仍位于 `app/services/core/config.py`；
- 阶段 2 新数据库路径、数据库身份、Clock、owner 启动世代和租约不等式尚未实现；
- 当前没有支持 Recovery Observation/Decision 的内部命令或诊断脚本。
