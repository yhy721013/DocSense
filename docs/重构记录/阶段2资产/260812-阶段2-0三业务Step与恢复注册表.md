# 阶段 2-0 三业务 Step 与恢复注册表

## 1. 文档性质

本文是阶段 2-0 的内部编码门禁，机器可读权威为
`tests/contracts/stage2_business_step_registry.json`。本文不修改任何 HTTP、Callback、SSE 或
WebSocket 合同，也不增加或删除前后端参数。当前运行代码尚未实现统一 Step Runtime；下文的
“最终 Step”表示后续 2-4～2-6 必须逐项落实的注册表，不表示现状已经具备跨进程恢复能力。

冻结原则如下：

1. `effect_kind` 只描述副作用发生位置，`replay_policy` 独立描述是否允许重放；
2. 所有外部写必须先提交 intent，网络 I/O 结束后再提交 checkpoint 和 external ref；
3. `TaskRecoveryPolicyPort` 只能读取调用方传入的冻结事实并作纯决策，不访问数据库或网络；
4. Callback、资源清理、模型调用审计、DocumentProcessing External Operation 和 Reassign Step
   Attempt 保持各自状态机，只关联 Task/Attempt/Step 身份，不强行合并；
5. 不能证明 `definitely_not_sent` 的外部写一律不得判为 `retry_safe`。

## 2. 当前调用链审计结论

### 2.1 Report

当前 `RunReportTask` 的实际顺序是：创建本地 Artifact Scope 并登记资源，按请求顺序下载、规范化并
准备源文件，下载并提取模板，调用一个粗粒度 `ReportRagPort.generate`，提交完整交互审计，净化并
渲染报告，发布最终 HTML Artifact，最后以 latest CAS 提交业务终态。终态后 Callback 和资源清理
分别走独立 Guard/Recovery，不属于业务 Step 重跑。

当前 AnythingLLM Adapter 在一次 `generate` 内部依次创建 Workspace、创建 Thread、逐文档上传、逐文档
绑定和模型查询。它会返回生命周期轨迹和清理引用，但模型 `call_id` 与文档 marker 当前是随机值，
供应商调用也没有可证明的端到端幂等结果。因此最终注册表将这条粗粒度调用拆成
`rag.session.open`、`rag.document.upload:*`、`rag.document.bind:*` 和 `rag.generate`；其中生成结果
未知时只能对账或隔离，禁止自动再问一次模型。

最终 Step 顺序为：

```text
artifact.scope.begin
source.download:{source_sequence}
document.prepare:{source_sequence}
template.download
template.extract
rag.session.open
rag.document.upload:{artifact_sequence}
rag.document.bind:{artifact_sequence}
rag.generate
interaction_audit.commit
report.render
artifact.publish
terminal.commit
```

`document.prepare:*` 保存父 Task 对 DocumentProcessing 记录和 Artifact 的引用，不复制其内部 Step；
源地址再次读取后如内容摘要变化，进入 `recovery_required`，不得把变化后的字节继续用于原任务。

### 2.2 Weaponry

当前 `RunWeaponryTask` 先创建任务级资源记录，再使用受理时冻结的文档范围打开检索 Scope。真实
Retrieval Adapter 已在 Workspace 创建前保存 Creation Intent，并在创建返回后登记稳定资源；历史
pending 只能按确定性名称探测，不能再次发送 create。文档绑定完成后，Field Executor 按字段顺序执行
术语辅助、检索、证据选择、逐文档模型提取和翻译。每次可能触发模型的调用都先 reserve 审计身份，
pending 或已完成但无法重建响应时拒绝重复调用。

最终 Step 顺序为：

```text
resource.record.begin
document_scope.load
rag.workspace.create
rag.document.bind:{document_sequence}
auxiliary_guidance.load:{field_sequence}
retrieval.execute:{field_sequence}
evidence.select:{field_sequence}
field_model.execute:{field_sequence}:{document_sequence}:{model_attempt}
translation.execute:{field_sequence}:{document_sequence}:{item_sequence}
interaction_audit.commit:{call_id}
result.map
terminal.commit
```

字段模型 Adapter 内部创建的临时 Workspace/Thread 作为 `field_model.execute:*` 的 external ref 和资源
事实保存，不另造可被通用 Reaper 猜测重跑的业务 Step。Weaponry 继续复用当前 Input v2；直接父节点
专项保留 v3，阶段 2 通用内核不得占用该版本。

### 2.3 Analysis

当前 `RunAnalysisTask` 的顺序是：下载并通过 DocumentProcessing 准备文件，构建确定性工作计划，
reserve Recall 审计，登记 RAG 资源意图，打开隔离 Session，在首个模型 execute 内上传并绑定文档，
执行分类/修复、可选身份重选、抽取/修复或 legacy combined，终结 Recall，提交完整交互审计，映射结果，
把同一已准备文档转交永久知识库，执行可降级翻译，最后提交终态。RAG close 是终态后的独立资源维护。

当前首个 `rag.execute` 同时跨越“上传/绑定”和“模型调用”；永久知识 Adapter 也在一次 `persist` 中同时
确保永久 Workspace 并绑定文档。后续实施必须用 Step 回调/窄 Port 把持久边界显式化，不能因为当前
调用是一个函数就合并恢复事实。最终 Step 顺序为：

```text
source.download
document.prepare
recall.reserve
rag.session.open
rag.document.upload
rag.document.bind
classification.execute:{attempt_number}
identity.reselect
extraction.execute:{attempt_number}
combined.execute:{attempt_number}
recall.finalize
interaction_audit.commit
result.map
knowledge.workspace.ensure
knowledge.document.bind
translation.execute
terminal.commit
```

`classification.execute:*` 覆盖 classification 与 classification repair；`extraction.execute:*` 覆盖
extraction 与 extraction repair；`combined.execute:*` 明确保留当前 legacy 模式，避免它成为未登记模型
操作。身份重选和全文翻译保持现有“可降级”业务语义：只有核心结果检查点完整并已持久记录降级决定时，
Recovery 才能不重放外部调用而从检查点收敛；否则仍进入对账隔离。

## 3. 恢复矩阵

每个 Step 都在机器契约中引用一张完整矩阵，矩阵必须同时定义以下五个结论：

| 结论 | 允许条件摘要 |
| --- | --- |
| `retry_safe` | 没有跨越副作用边界，或持久证据明确证明请求未发送。 |
| `finalize_from_checkpoint` | 结果、摘要、owner、外部引用与冻结 Profile 已完整校验，不重新调用外部系统。 |
| `reconcile_required` | 外部结果未知、归属不明、内容漂移、探测歧义、Profile 冲突或检查点损坏。 |
| `defer` | 已保存 probe intent，但 Observation 尚未返回或外部系统暂不可用；不延长旧执行权。 |
| `mark_stale` | latest 已合法变化，并且旧副作用已经隔离、补偿或证明不会污染新任务。 |

机器契约定义 `deterministic.v1`、`local_idempotent.v1`、`external_read.v1`、
`external_write_reconcile.v1`、`optional_degrade.v1` 和 `terminal.v1` 六张矩阵。步骤不能只根据
`effect_kind` 临时推断恢复结果；所有 unknown 先形成 Recovery Case，再由 Coordinator 在事务外执行
已持久化的 probe/compensation intent，保存 Observation 后调用纯 Policy。

## 4. Intent、Checkpoint 与 ExternalRef

所有 Step 复用六类版本化 Schema。字段只保存有上限、可脱敏的身份和摘要：

| Schema | Intent 核心字段 | Checkpoint 核心字段 | ExternalRef |
| --- | --- | --- | --- |
| `pure.v1` | Profile fingerprint、输入摘要 | 结果摘要/引用 | 无 |
| `local_artifact.v1` | 目标 Artifact key、owner | Artifact ID、SHA-256、大小、表示类型 | 无 |
| `external_read_artifact.v1` | 来源身份摘要、目标 key | 完整 Artifact 与来源摘要 | 仅脱敏来源引用 |
| `external_write.v1` | operation identity、请求摘要、幂等键、intent 时间 | 三态结果、响应摘要、Observation 引用 | provider、资源类型、稳定引用、owner、父引用 |
| `audit_write.v1` | audit kind、幂等键、payload 摘要 | audit ID、版本、提交时间 | 无 |
| `terminal.v1` | 结果检查点、latest、Attempt/fencing 期望值 | 终态、公开投影、结果引用、提交时间 | 无 |

秘密、正文、完整 URL 查询串、模型原文和 Callback 正文均不得进入通用 Step 表；需要保存的完整模型
轨迹继续由独立交互审计 Store 管理。

## 5. Canonical Input Profile

### 5.1 Report v2

Report 新写内部 Input v2，在 v1 字段上增加 `execution_profile`。Profile 冻结 Source Transport 与
下载上限、DocumentProcessing 身份、模板提取器、RAG provider/model/workspace/upload 策略以及
Prompt、Sanitizer、Renderer 和空结果策略。v1 仅保留离线兼容读取，禁止用当前环境默认值补字段后
恢复旧任务。

### 5.2 Weaponry v2

Weaponry 的 `document_scope`、`evidence_selection_policy`、`execution_policy` 和
`auxiliary_guidance_policy` 已构成完整决策快照，本阶段不升版。运行时 Capability 必须与其中的
provider、embedding、模型、检索和术语目录指纹精确匹配。

### 5.3 Analysis v5

Analysis v5 在 v4 上增加 `execution_profile` 与 `translation_profile`。前者冻结 Source Transport、
RAG provider/model/workspace、RAG projection、Prompt、Knowledge provider/protocol；后者严格复用
现有 `TranslationProfile` 的八个字段。v1～v4 只作兼容解码和诊断，不从当前环境补齐 v5 后执行。

三类 Profile 均沿用阶段 2 总设计的 Canonical JSON 与 SHA-256 规则；Worker 必须在第一笔外部 I/O
前完成 Capability 精确比较。

## 6. 步骤完成后的商讨检查

本步骤没有发现需要修改公开接口、公开状态映射或前后端参数的事项。审计发现的三个复合边界均已有
保守且确定的处理方式：Report 模型生成 unknown 禁止自动重放；Analysis 首轮上传/模型调用拆分保存
事实；Knowledge ensure/bind 分步检查并共享稳定业务幂等身份。它们是后续内部实现约束，不构成进入
阶段 2-0 第 10 步的阻塞项。
