# 阶段 2-7：业务恢复策略与有限 Reaper 设计

日期：2026-08-21  
状态：已确认并实施，已完成离线关闭验证  
适用分支：`feat/weaponry-chat`

## 1. 决策结论

本设计落实阶段 2 总计划 D2-07、D2-07A、D2-08、D2-19 和 D2-20。负责人已确认：

1. Report、Weaponry、Analysis 均实现真正的检查点续跑；恢复后的业务执行必须由普通
   Executor 重新 claim，创建更大的 Task Attempt 和 Task fencing；
2. `finalize_from_checkpoint` 必须与既有 Task/latest 终态、业务结果快照核验和 Callback
   eligibility 在同一事务收敛；
3. 自动探测仅覆盖控制库和业务本地持久事实；没有稳定只读探测能力的供应商操作保持
   `recovery_required`，不得把“查不到”解释为“从未执行”；
4. 沿用现有唯一 `LocalMaintenanceScheduler`，只替换内部 Reaper 动作，不增加线程、公开路由、
   参数、响应字段、状态码、Header、Callback 字段或 `/llm/check-task` 权限。

## 2. 不可突破的边界

- 公开接口文档零修改；内部 `task_id`、Attempt、lease、fencing、Recovery Case 和证据不得公开。
- `/llm/check-task` 只恢复 Callback Delivery；不得用于业务 Step 重跑或 Recovery Decision。
- lease 过期本身永远不构成重试证据。
- Recovery Case、Operation、Observation、Decision 只写 Task Control v2；不双写旧入口。
- 事务内禁止网络、文件、模型、AnythingLLM、Knowledge 或 Callback HTTP I/O。
- 旧 Task Attempt、旧 Step Attempt 和原始 Observation 只追加、不可覆盖。
- Callback unknown、终态后资源清理 unknown 与核心业务 recovery 必须保持独立。

## 3. 过期 Attempt 分类

Reaper 每轮执行以下固定流程：

1. 只读扫描 `running` 且当前 Attempt lease 已过期的 Task；
2. 加载 Task、当前 Attempt、全部 Step 当前投影和只读证据摘要；
3. 按 `task_type` 路由到唯一业务 `TaskRecoveryPolicyPort`；
4. 通过 `classify_candidate_if_current` 重新核对 source Attempt、Task fencing、Task row version、
   latest 和证据摘要后原子写入分类结果；
5. 对正常竞争、旧快照和已收敛现场返回有限结果，不抛出伪业务成功。

### 3.1 `retry_safe`

阶段 2-7 的自动 `retry_safe` 只允许“尚未创建任何 Step”的 Task。此时能够证明业务副作用边界
尚未开始，Store 原子 abandoned 旧 Attempt、把 Task 退回 `accepted`、设置有限退避并追加 Event。
已存在任意 Step 的现场不得使用该捷径；即使 Step 是纯计算，也必须先建立 Case 并以精确 Step
身份形成证据，避免 Store 越权猜测业务恢复点。

### 3.2 `finalize_from_checkpoint`

只有以下事实同时成立才进入该分类：

- latest 仍指向当前 Task；
- 没有 `running/outcome_unknown/failed` Step；
- 存在可验证的成功结果检查点；
- 业务 Policy 确认结果引用和冻结 Profile 可供终态预检。

分类只建立 Recovery Case，不直接写终态。终态必须由 Coordinator 取得 Recovery Authority 后，
通过携带内部 Terminal Projection 的 Decision 收敛。

### 3.3 `reconcile_required`

存在下列任一事实必须隔离：

- Step 已开始但结果不确定；
- 外部写、`never_auto`、`reconcile_only` 或未知所有权；
- 输入、Profile、内容摘要、latest 或资源身份不一致；
- 审计不完整、证据被截断、Operation Intent 未收敛；
- 未登记 Step 或恢复矩阵不唯一。

建立 Case 时，当前 Attempt 收敛为 `abandoned`。若存在属于 source Attempt/fencing 的活动 Step，
其当前投影和对应 Step Attempt 在同一事务收敛为 `outcome_unknown`，从而明确未知发生的位置；不得
静默保留 `running` Step 后让新 Attempt 绕过。

### 3.4 `mark_stale` 与 `defer`

- 只有 latest 已由合法新 Task 取代且业务现场已满足隔离规则时才可 `mark_stale`；
- `defer` 只用于证据收集正在进行或本地只读探测暂不可用，必须写入有限的下一检查时间；
- 两者均不得解锁同键新业务副作用。

## 4. Recovery Coordinator

Coordinator 是唯一恢复应用服务，按以下短事务序列工作：

1. 以 expected Case/generation/current recovery fencing 领取 Case；
2. 获得独立 `RecoveryAuthority`，与 Task Execution Authority 完全分离；
3. 在每次事务外 I/O 前提交稳定 Operation Intent；
4. 事务外执行有界 Probe/Compensation；没有注册能力时形成 unknown，不执行猜测性动作；
5. 追加 Observation，并在同一事务把 Operation 标为 `observation_recorded`；
6. 重新加载 Task、Step、Operation、Observation 和业务结果预检快照；
7. 业务纯 Policy 形成 `keep_quarantined/retry_authorized/finalize_from_checkpoint/mark_stale`；
8. Store 以 Recovery fencing、Task row version、source Attempt/fencing、Step row version和证据引用
   原子提交 Decision。

Recovery heartbeat 成功后旧 Authority 立即失效。heartbeat 失权时停止尚可停止的探测/补偿；旧
fencing 的 Observation 和 Decision 必须被 Store 拒绝。

## 5. 检查点续跑

`retry_authorized` 只把一个精确 `outcome_unknown` Step 当前投影改回 `pending`，并在 Task 保存
`retry_from_step_key`。下一次普通 Executor claim 后：

1. Runner 使用原 Task 冻结输入和 Execution Profile，不读取当前环境默认值替代；
2. `retry_from_step_key` 之前的 Step 只能通过业务 Checkpoint Resolver 复核并恢复业务对象；
3. 目标 Step 以相同稳定 idempotency key 创建新的 Step Attempt；
4. 目标之后按普通流程继续；
5. 任一必要检查点无法恢复、摘要漂移或资源所有权未知时立即重新隔离，禁止从头盲重放；
6. 公开 status/progress/message 保留最后可信投影，恢复执行只允许进度向前。

各业务 Resolver 只恢复有界引用，不把正文、凭据或供应商原始响应放入通用 Task Control 表。

### 5.1 业务续跑快照契约（确认后的细化）

Report、Weaponry、Analysis 分别在自己的组件 Schema v2 中拥有
`*_step_continuation_snapshots`，根 Task Control 不拥有、解释或复制业务 payload。每条记录：

- 以 `(task_id, step_key, step_attempt_no)` 为不可变主键，并外键绑定原 Step Attempt；
- 同时冻结 `task_attempt_no`、Task fencing、`source_step_attempt_no`、输入 payload SHA-256、
  Execution Profile SHA-256、前置 checkpoint SHA-256 和 payload SHA-256；
- payload 必须是至多 16 KiB 的 canonical JSON object，只保存 Artifact/Audit/Resource 的稳定引用、
  basename、序号和摘要，不保存 URL 凭据、正文、Prompt、模型原始响应或宿主根路径；
- 初次执行在目标 Step intent 的同一业务 UoW 中追加快照；恢复执行先只读加载原 Step Attempt
  快照，解析器复核成功后，目标 Step intent 与新 Step Attempt 快照在同一 UoW 中追加；
- Authority、Step 状态、输入/Profile、payload 摘要或来源 Attempt 任一漂移均失败关闭。

`retry_authorized` 还必须经过同一 Recovery Decision 事务中的业务 Resume Preflight。Policy 白名单、
Resume Preflight 和真实 Workflow Resolver 三者必须同时存在；只登记 Registry 或只存在快照都不能
授权续跑。阶段 2-7 当前开放范围为：

| 业务 | 已授权 Step | 解析器事实 |
| --- | --- | --- |
| Report | `artifact.scope.begin` | 复核冻结 Task/BusinessRef/Profile 后重新进入首个任务专属 Artifact Scope intent |
| Weaponry | `resource.record.begin` | 复核冻结 Task/BusinessRef/三类执行策略后重新进入首个资源记录 intent |
| Analysis | `source.download` | 复核冻结输入/Profile 后重新进入首个受控下载 intent |
| Analysis | `document.prepare` | 只读复核既有任务目录、source basename 与 SHA-256；不补建、不重下，再创建新 Step Attempt |

其他 Step 即使 Observation 为 `definitely_not_sent/no_effect_confirmed/compensation_confirmed`，也保持
`recovery_required`，直到其业务对象解析器、快照 Schema、正反测试和恢复跳转全部完成。

### 5.2 Analysis Source 与 DocumentProcessing 分界

Analysis v2 不再在一次 `FilePreparationPort.prepare()` 前同时开启 `source.download` 和
`document.prepare`。生产 Adapter 保留旧 v1 的组合外观，但 v2 固定使用两个内部 Port：

1. `AnalysisSourceAcquisitionPort.acquire_source()` 只在任务目录内下载并计算 Source SHA-256；
2. `source.download` 成功收敛后，才提交 `document.prepare` intent 及其续跑快照；
3. `AnalysisDocumentPreparationPort.prepare_document()` 只接收已取得 Source，复核路径包含关系、
   basename 和 SHA-256 后调用 DocumentProcessing；
4. 恢复时 `resolve_source()` 只读解析既有 Source，不访问原 URL；任务目录或文件缺失、摘要漂移均
   重新隔离。

因此任一时刻不会因一个组合 Port 调用同时留下两个活动未知 Step。

### 5.3 组件版本与 fresh-only 边界

三业务组件 Manifest 均由 v1 提升为 v2，以安装各自的续跑快照表。由于负责人已明确确认旧版本
数据库和旧文件集不再使用，本阶段不提供组件 v1 到 v2 的在线迁移器或兼容读取：

- 独立 fresh bootstrap 一次安装 Report/Weaponry/Analysis v2；普通启动只严格打开完整 v2；
- 任一 v1 组件、未知组件版本、缺表、指纹漂移或旧文件残留均失败关闭；
- 不在运行期执行 `ALTER TABLE`、自动备份、猜测迁移或 v1/v2 双写；
- 该策略只适用于已经确认放弃历史控制事实的部署，不可外推到未来生产滚动升级。

## 6. 恢复终态与 Callback

`finalize_from_checkpoint` 使用 Recovery 专用原子组：

- Recovery Decision Store；
- 业务结果快照只读预检；
- Task/latest 终态写；
- Callback Control Store 的 Recovery eligibility 写。

Recovery eligibility 命令必须携带 Recovery Authority、Task/BusinessRef、source Attempt/fencing、
来源检查点身份和 eligible 时间。Callback Store 重新核对 Task 已由同一 Recovery Decision 变为
latest 终态，且 Guard 仍可安全归属该 Task；它不接受旧 Task Execution Authority 冒充权限。

若业务结果快照不存在、摘要不匹配或无法重建既有公开 Callback payload，Policy 只能
`keep_quarantined`，不能写终态。Callback eligibility 失败会回滚整个恢复终态事务。

## 7. 业务策略

### 7.1 Report

- 纯计算和本地 Artifact 必须通过稳定 Artifact ref、SHA-256、size 和 Task owner 核验；
- RAG create/upload/bind/generate 的未知结果进入 Case；`rag.generate` 永不自动重放；
- 已确认 Report result/artifact 才能形成 Terminal Projection；
- 临时资源清理 unknown 不回滚已可信业务终态。

### 7.2 Weaponry

- Workspace/Thread/Document 必须使用稳定远端 ID、Task owner 和 fencing 证明归属；
- 同名资源不构成所有权证据；未知资源不得认领或删除；
- 模型、检索和翻译 `never_auto` Step 结果未知时保持隔离；
- 永久 Knowledge 资源不进入任务清理或猜测性补偿。

`TargetEvidenceRetrievalPort.open_scope()` 当前仍是 Workspace 创建和多文档绑定的组合调用。这些
后续 Step 没有加入续跑白名单：任一结果未知均保守留在 Recovery Case，不能自动重放。若未来要为
它们开放检查点续跑，必须先按真实供应商能力拆分 Port 或引入逐效果 Observer，并另行验证旧 Runner
Authority 传递；本阶段不擅自改变该生产调用语义。

### 7.3 Analysis

- 每个文件独立恢复；不得整批隐式 supersede；
- 较小 `batch_sequence` 的 `recovery_required` 继续阻止同批后继；
- Source、DocumentProcessing、Recall、RAG、Knowledge、Translation 均复核冻结身份；
- Knowledge/Translation 外部结果未知时不得自动重放；
- Analysis 的内部存储和执行路由继续统一使用 `file`。

## 8. 运维命令

`scripts/reconcile_stage2_task.py` 默认只读。任何写模式必须显式提供：

- `task_id`、`case_id`、`generation`；
- expected Task row version、source Attempt、source Task fencing；
- expected current Recovery fencing；
- operator、reason code、evidence digest；
- 精确 action 及其所需 operation/observation/checkpoint 身份。

缺失、漂移、重复、越权或证据不完整均失败关闭。脚本只调用 Application Port，不直接执行 SQL；
不提供公开 HTTP 路由，也不接受“承担重复风险并强制重跑”的通用开关。

## 9. 组合根与运行拓扑

生产组合根只把现有 `conservative_task_reaper` job 替换为 `business_task_reaper`：

- 保持一个 `LocalMaintenanceScheduler` 和一个维护线程；
- 保持原扫描间隔、停止 grace、readiness 和启动/停止顺序；
- 三业务 Policy 通过显式映射注入，不使用动态 import 或默认回退；
- Event 仍是可丢唤醒提示，SQLite 周期扫描是恢复事实来源；
- 阶段 2 证据只证明 Windows/SQLite/单实例/Fake，不宣称多实例、可靠队列或生产容量。

架构门禁只精确放行两类纯执行内核依赖：业务 `recovery_policy.py` 复用统一 Registry Policy，业务
`step_runtime.py` 复用 retry Decision 解析；Tasks Ports 仅允许 `step_continuation.py` 使用
`hashlib/json` 执行 canonical payload 契约。不得由此推导业务 Application 可以导入 Tasks 的其他
Application/Adapter，也不得把 I/O 放入 Port。

## 10. 分步门禁

1. 设计与机器契约：JSON 可解析、接口文档哈希零差异；
2. Domain/Port：纯单元测试通过，不导入 SQLite/threading/Web；
3. Store/UoW：临时 SQLite 双连接验证 Case claim、heartbeat、旧 fencing 拒绝和原子回滚；
4. 业务 Policy：每个 Step Registry 五类矩阵正反例覆盖；
5. Coordinator：Intent 先提交、I/O 在事务外、Observation 与 Operation 原子收敛；
6. 续跑：新 Attempt、新 Step Attempt、旧历史不可变、冻结输入/Profile 和 Progress 单调；
7. 终态：结果预检、Task/latest、Decision、Callback eligibility 任一失败全部回滚；
8. 运维：默认 dry-run、严格参数、无直接 SQL；
9. 组合根：线程数和启动策略不变；
10. 定向测试、全量离线测试、`compileall`、接口资产和 Schema 完整性全部通过。
