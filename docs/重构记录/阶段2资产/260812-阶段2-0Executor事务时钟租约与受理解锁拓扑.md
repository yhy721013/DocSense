# 阶段 2-0 Executor、事务、时钟租约与受理解锁拓扑

## 1. 文档性质

本文冻结阶段 2-0 第 10 步的内部实现约束。机器可读权威为
`tests/contracts/stage2_runtime_topology_contract.json`。本文没有改变公开路由、参数、字段、状态码、
Callback 或 Progress 语义；所有拓扑均标记为“尚未实现”，后续阶段必须用代码和 Fake/临时 SQLite
验证，不能把本文当成当前生产能力证明。

## 2. 统一 Executor 内核与三业务实例

组合根只创建一个 `LocalTaskExecutor` 实现的三个独立实例：

| 实例 | 唯一可扫描类型 | Runner | Worker 配置 |
| --- | --- | --- | --- |
| `ReportExecutor` | `report` | `RunReportTask` | `DOCSENSE_TASK_REPORT_WORKER_COUNT` |
| `WeaponryExecutor` | `weaponry` | `RunWeaponryTask` | `DOCSENSE_TASK_WEAPONRY_WORKER_COUNT` |
| `FileExecutor` | `file` | `RunAnalysisTask` | `DOCSENSE_TASK_ANALYSIS_WORKER_COUNT` |

三者复用相同的 claim、heartbeat、fencing、停止和故障收敛算法，只注入业务 Runner、Recovery Policy、
runnable 查询和未来队列路由。现有三个业务 `local_dispatcher.py` 只保留装配、唤醒和指标映射，禁止
继续拥有第二套调度算法。

每个实例内存中最多保存 `worker_count` 个在途 TaskId 和一个合并唤醒；不缓存 accepted 全量 ID。
唤醒是可丢提示，启动扫描和周期扫描才是恢复来源。毒任务的 `next_dispatch_at/reason_code` 必须落库，
不能靠内存集合跳过。Analysis runnable 查询继续保证同批次前序门禁；业务内按 dispatch sequence，跨
业务不承诺严格全局 FIFO。

## 3. 分层容量与公平性

共享重型容量采用 `strict_round_robin_over_nonempty_business_queues_v1`：默认三个业务权重均为 1；
当其他业务也在等待时，同一业务最多连续获得一个 grant。初始
`DOCSENSE_TASK_HEAVY_CONCURRENCY=1`，因此三个业务持续有资格等待且许可持续释放时，每个业务最多
跨过另外两个 grant。该约束只证明“按 grant 无饥饿”，不承诺绝对等待时长、完成顺序或供应商容量。

容量分为七个有明确含义的层级：业务 Worker Slot、跨业务公平重型许可、AnythingLLM ingestion、
模型调用、DocumentProcessing、Callback Delivery 和资源维护。重型总许可与具体操作许可必须由同一
协调器原子授予，禁止持有一个许可再阻塞等待另一个许可。等待期间不得持有数据库事务；取消、停止和
许可释放均必须可中断并在 `finally` 中收口。

Callback 属于业务终态后的独立交付，不消耗业务重型许可；资源维护不占业务 Worker Slot，但访问同一
供应商时仍受相应 provider limiter 约束。这样既避免最快扫描器长期抢占唯一许可，也避免用一个含义
模糊的总 Semaphore 覆盖所有 I/O。

## 4. Maintenance Scheduler 与 readiness

`LocalMaintenanceScheduler` 独立周期运行 Task Reaper、Callback Guard sweep 和三业务资源恢复。维护
唤醒同样只是提示，持久扫描不可省略。某一业务 Runner/readiness 失败只关闭该业务的领取；Task
Control DB 或时钟异常则对所有新 claim fail closed。时钟异常期间还必须阻止 Worker 开始新的外部
Step，已有 Worker只能保存已发生事实并停止向前推进。

## 5. SQLite 事务与窄 UoW

`SQLiteConnectionFactory/SQLiteTransactionManager` 只负责连接、Schema 身份、`BEGIN IMMEDIATE`、
busy/locked 分类、commit/rollback 和关闭，不理解业务。Admission、各业务 Execution 和 Recovery
使用窄 UoW；同一 UoW 的 Store 必须共享同一 Connection。

冻结的强制规则：

- Store 不得自行 commit、rollback、close，也不得隐藏 busy 重试；
- Application 必须显式 commit；正常退出未提交、异常或取消均 rollback；
- 禁止嵌套 UoW、业务 SAVEPOINT、跨线程共享 Connection 和写事务外写命令；
- 只读 Query 可以用独立短连接，但旧读结果不授予写权限；
- 网络、模型、转换、对象删除和阻塞许可等待全部在事务外；
- Transaction Manager 不自动重放包含调用方逻辑的事务；
- 迁移兼容仅允许旧 Facade 单向调用新 UoW，新 Store/UoW 不得反向调用旧 Service。

机器契约冻结 13 组原子操作：admission、claim、start、heartbeat、begin external step、complete step、
progress、business terminal、reaper classify、recovery claim、recovery heartbeat、recovery observation
和 recovery decision。尤其 begin step 必须把 Authority、Step intent/attempt、业务资源或 External Operation
intent 和 Event 同事务提交后，才能在事务外发起 I/O；complete step 再原子提交结果、Checkpoint、
ExternalRef 和业务资源/审计事实。`MARK_OUTCOME_UNKNOWN` 还必须在该事务撤销旧 Attempt、隔离 Task
并创建 Recovery Case；Recovery 长探测必须用独立 heartbeat 续约，不能复用 Task heartbeat。

## 6. Clock、owner 与租约不等式

所有持久时间只由 `ClockPort.now_utc()` 提供，写成带六位微秒和 `Z` 的 UTC RFC3339。Repository
严格拒绝 naive datetime、本地时区和格式外字符串。monotonic clock 只用于进程内等待、超时预算和
wall-clock 异常检测，绝不持久化或跨进程比较；租约测试使用 FakeClock，不用真实 `sleep` 证明。

每次进程启动生成一次 `instance_start_id` UUID；诊断 owner 固定为：

```text
{instance_start_id}/{pid}/{executor_name}/{worker_slot}
```

claim 调用方必须先构造不可变
`TaskOwnerIdentity(instance_start_id, process_id, executor_name, worker_slot)`；`owner_id` 仅由该对象
规范派生，Store 将组合文本与四个拆分字段一起持久化，禁止从任意字符串反向猜测进程世代和 Worker。
owner/PID 都不是写权限。完整 Authority 仍为 `task_id + attempt_no + lease_token + fencing_token +
lease_expires_at`；lease token 必须高熵且禁止日志输出，fencing 按 Task 严格单调。Task Lease 与
Recovery Lease 使用不同 token/fencing 命名空间。

冻结默认值为 heartbeat 5 秒、SQLite busy budget 2 秒、clock jitter 3 秒、Task/Recovery lease
各 30 秒、Reaper scan 5 秒、stop grace 10 秒，并必须满足：

```text
task_lease >= 3 * heartbeat + 2 * sqlite_busy + clock_jitter
recovery_lease >= 3 * heartbeat + 2 * sqlite_busy + clock_jitter
reaper_scan <= task_lease
reaper_scan <= recovery_lease
stop_grace >= heartbeat + sqlite_busy
```

非法组合必须在线程启动前失败。wall clock 相对 monotonic 的回拨或跃迁超过 jitter 时，暂停新 claim、
Reaper 和新外部 Step，readiness 进入 degraded，并输出不含 token/正文的 CRITICAL 稳定原因码；绝不
在时钟异常时猜测租约已过期。

## 7. 新受理与解锁矩阵

| 现场 | 同键受理 | 无关键 | 解锁依据 |
| --- | --- | --- | --- |
| Report 核心 RAG/产物 unknown | 沿用活动冲突 409 | 允许 | 唯一效果确认、补偿确认或 `definitely_not_sent`，再提交 Recovery Decision |
| Weaponry Workspace/模型核心 unknown | 沿用 processing 冲突 | 允许 | 稳定远端 ID + Task owner + fencing，或补偿/未发送证据 |
| Analysis 核心 unknown | 同 fileName 冲突；同批后序继续阻塞 | 完全无关 fileName/批次允许 | 逐 Task 对账、补偿、未发送或 mark-stale 证据，禁止整批隐式 supersede |
| 任一业务终态后 cleanup unknown | 不因清理阻塞新业务提交 | 允许 | 只由独立资源维护收敛或隔离 |
| Callback delivery unknown | 沿用现有 Callback Guard | 允许 | 仅既有 check-task/内部恢复授权处理 Callback，不重跑业务 Step |

超时不能解锁，禁止人工直接改 SQL、禁止把内部 unknown 伪装成公开 failed、禁止让
`/llm/check-task` 偷渡业务重跑。解锁必须来自持久化 Observation/补偿结果和 Recovery Decision；旧
unknown 历史即使解锁后也继续保留。该矩阵不新增公开状态或参数。

## 8. 步骤完成后的商讨检查

本步骤没有发现需要修改接口文档的事项，也没有未确定的 Executor、事务、时钟、租约或解锁动作。

值。至此阶段 2-0 的十个步骤均具备可执行的内部黄金资产和 fail-closed 门禁，可以进入阶段 2-0 总体
