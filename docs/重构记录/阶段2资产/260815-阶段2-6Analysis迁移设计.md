# 阶段 2-6 Analysis 迁移设计

## 1. 文档性质与冻结边界

本文落实阶段 2 总设计的 2-6 波次。公开权威仍是
`docs/接口文档/文件处理和报告生成.md`；本设计不增加、删除或改变 HTTP 请求参数、响应字段、
状态码、Progress、Callback payload、错误文本及 `/llm/check-task` 同步恢复语义。验证只使用临时
SQLite 与 Fake，不运行 `run.py`，也不把单机 SQLite/线程测试表述为可靠队列、多实例或生产容量证明。

Analysis 的持久化类型、Executor 名称和未来队列路由统一使用 `file`。受理、执行、Progress、终态和
Callback Control 必须在步骤 7 一次切到阶段 2 控制面；此前新实现只参加离线验证，禁止生产双写、
双 claim、从旧 Runner 补造 Authority，或把 v2 事实回写 `LLMTaskService`。

## 2. 严格实施顺序

1. 冻结 Input v5、Canonical Execution/Translation Profile 及 Step/Recovery Registry；
2. 等价迁移 Runtime Config、Source 注入、资源、Recall/Interaction Audit 与 Callback History 所有权；
3. 实现 1～32 项批量全有或全无 Admission；
4. 在数据库中实施跨 Worker 的批内严格顺序和跨批 FIFO 领取；
5. 落实 Authority-aware Workflow、全部 Step、Checkpoint、终态和 Callback 链；
6. 补齐毒输入、前序 `recovery_required`、Callback handoff 与资源恢复；
7. 前置门禁全部通过后，一次切换生产控制面并删除调用清零的旧 SQL；
8. 固化机器契约、文档和离线验收证据。

每一步结束均复核公开接口、生产启动顺序、旧 Runner Authority 与 Callback 语义；若必须改变任一项，
立即停止并扩大评审。

## 3. Input v5 与 Canonical Profile

新写 Worker 输入固定为 `AnalysisTaskInput/v5`，在 v4 顶层字段上增加
`execution_profile` 与 `translation_profile`。v1～v4 只允许严格解码和诊断，普通 Worker 不得读取
当前环境补齐 Profile 后执行。

`execution_profile` 字段严格采用阶段 2-0 Registry：Source Transport、下载字节上限、RAG Provider、
模型、Workspace、Markdown 投影、Prompt，以及永久知识 Provider/协议的稳定身份。Profile 不保存
Secret、完整 URL、Prompt 正文、供应商响应或宿主路径，Canonical JSON 与 SHA-256 必须稳定。

`translation_profile` 直接复用 Translation 模块既有八字段 `TranslationProfile`，从受理到执行完整
比较。Worker 在第一笔外部 I/O 前同时验证两个 Profile；任一不匹配都失败关闭且不做外部调用。

## 4. Runtime Config 与组件所有权

现有 16 个 Analysis 环境键等价迁入 `app/modules/analysis/adapters/runtime_config.py`，保持键名、默认值、
严格解析、错误类型和错误文本。经步骤 3 评审确认，Input v5 另新增部署必填的
`DOCSENSE_ANALYSIS_RAG_PROVIDER_FINGERPRINT` 与 `DOCSENSE_ANALYSIS_RAG_MODEL_FINGERPRINT`；两者只接受
64 位 SHA-256，禁止保存 URL、API Key 或模型名原文。永久知识库当前与 Analysis RAG 使用同一
AnythingLLM 部署，故知识 Provider 复用前者；未来拆分部署必须升版 Profile，不能静默复用。
`DOCSENSE_ANALYSIS_SCANNED_PDF_ENGINE` 继续归 DocumentProcessing/OCR，不迁入 Analysis。Source URL
由组合根注入 Port；业务代码不直接读取环境。

根 Schema generation 2 发布 `analysis_control/v1` 组件。组件表承载资源、Recall/Interaction Audit、
结果快照及必要运维审计；Store 不创建表、不自愈漂移、不提交借用连接，也不在事务内执行网络、
文件或供应商副作用。非权威 Callback 观测历史统一写共享 Observability History Writer；Authority、
幂等和重试资格只来自 Task Control Callback 表。

## 5. 批量 Admission 与严格顺序

一次公开请求预分配唯一 `batch_id` 和 1～32 个 TaskId，在单个 `BEGIN IMMEDIATE` 短事务中完成：全部
冲突门禁、全部 accepted Task/execution、原始请求最新投影及批次成员关系。任一活动任务、Callback
handoff 或写入错误都整体回滚，成功后仅发送一次可丢 Event 提示。

领取排序以持久化 `dispatch_sequence` 保证跨批 FIFO；同一批次只有所有更小 `batch_sequence` 已进入
确定终态，后继才可被 claim。前序为 `recovery_required`、输入损坏或 Callback handoff 未完成时，
后继保持不可运行，不允许其他 Worker 越过。Event 只是提示，启动扫描和周期扫描才是恢复事实来源。

## 6. Step、组合 UoW 与 Workflow

`ANALYSIS_STEP_REGISTRY` 逐项落实阶段 2-0 冻结的 17 类 Step；阶段 2-7 另增加一个纯本地
`result.snapshot` 终态前检查点。外部写结果未知必须先保存可证明的审计
事实，再把当前 Step/Attempt 隔离为 `outcome_unknown/recovery_required`；普通 Worker 不得自动重放。

`AnalysisExecutionUnitOfWork` 在同一短事务组合 Task Execution、Step、Callback Control、资源、
Analysis 组件引用与结果快照。共享 Interaction Audit 正文继续由独立审计库的
`LLMInteractionStore` 单写，不伪装为跨 SQLite 原子事务：执行器必须先提交 Step intent，再在事务外写审计，
最后以同一 Authority 提交 checkpoint 和组件引用。最外层是每个短事务的唯一所有者；网络、模型、
下载、文件处理、知识库和 HTTP Callback 全在事务之外。所有条件写使用 Runtime 传入且可轮换的完整
`task_id/attempt_no/lease_token/fencing_token/lease_expires_at`，旧 Runner 不再传递或补造 Authority。

成功/普通失败的终态事务同时提交结果快照、`terminal.commit`、Task/Attempt 终态和 Callback
eligibility。HTTP Callback 在事务外重新取得 Guard lease/fencing 后发送；同步恢复只读取完整结果快照，
不得重跑分析或由摘要猜测公开 payload。

## 7. 原子切换与验收

步骤 1～6 全部通过后，生产组合根一次性切换 `file` 的 Batch Admission、Executor、Progress、终态、
Callback 与同步恢复。新 Worker 不再取得旧进程文件锁。旧 Adapter/Runner 可暂作阶段 1 回归夹具，
但生产组合根不得构造旧 Task Command、Resource Store、Dispatcher 或 Runner 控制对象，也不得写 v2；
仅 Analysis 使用且调用清零的旧 SQL 随即删除。名称带 `Legacy` 但只负责 File Preparation、RAG 或
Knowledge 外部 I/O 的 Adapter 不属于旧控制面；允许在 v2 Workflow 后继续作为能力桥，前提是它们
不持有 Task 状态、不生成 Authority 且不回写旧任务事实。

专项验收覆盖批量 1～32、冲突整体回滚、跨批 FIFO、多 Worker 批内严格顺序、v1～v4 历史读取、v5
Canonical round-trip、Profile 门禁、毒输入、失权停止、unknown 隔离、结果/终态/Callback 原子提交与
同步恢复。公开接口文档只做哈希冻结检查，不在本阶段修改。

### 7.1 首次部署的 fresh bootstrap 决策

2026-08-20 用户确认：部署现场若已经完整删除并永久弃用旧版本数据库文件集，不再对不存在的旧库
执行普通 WAL 只读预检。部署方必须先运行阶段 2-2 定义的一次性 fresh bootstrap，原子发布包含
Report、Weaponry、Analysis 三组件的 v2 数据库；随后生产组合根只严格打开该数据库。普通应用启动
不得自动推断 fresh，旧/目标任一文件成员残留都失败关闭。本决策不修改公开接口或 Callback 语义，
剩余非 Task 辅助表的物理拆库仍属于阶段 2-8。

## 8. 实施结果（2026-08-20）

严格实施顺序第 1～8 步均已完成：

1. `AnalysisTaskInput/v5`、Execution/Translation Profile 和机器契约已经落地；
2. Runtime Config、Source、资源、Recall/Interaction Audit 与 Callback History 已迁入目标所有者；
3. 1～32 项批量受理已由一个 `BEGIN IMMEDIATE` 事务保证全有或全无；
4. 持久 `dispatch_sequence` 与批次前序门禁已经落实跨批 FIFO 和批内严格顺序；
5. Authority-aware Workflow、Step Runtime、组合 UoW、结果/终态与 Callback 链已经实现；
6. 毒输入、失权停止、unknown 隔离、Callback handoff 和资源恢复均有定向离线门禁；
7. `app/container.py` 已一次切换 Analysis 生产控制面，未保留双写、双 claim 或旧 Runner 补权桥；
8. `analysis_control/v1`、最终 Analysis 机器契约、fresh bootstrap 命令与实施记录均已固化。

公开接口、生产启动/停止入口和 Callback 语义均未因本实施改变。全新部署增加的是应用外显式
bootstrap 前置操作；普通应用仍只严格打开已发布的 v2 数据库，并在未初始化时失败关闭。

可靠队列、多实例、共享数据库、高并发、真实供应商或生产容量结论。
