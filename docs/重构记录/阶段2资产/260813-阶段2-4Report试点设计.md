# 阶段 2-4 Report 试点设计与实施契约

## 1. 范围与冻结边界

本阶段按 `260809-阶段2统一任务执行内核文件级实施设计.md` 的 2-4 八个步骤执行。Report 是第一个
完整切换到阶段 2 Task Control/Execution Runtime 的业务；它验证统一内核，但不把 Report 的
Callback、资源、审计和产物状态机并入通用 Task 状态机。

本阶段保持以下公开合同不变：

- `/llm/generate-report` 的请求参数、HTTP 202 空体、400/409 错误结构不变；
- `/llm/check-task` 保持请求内同步恢复和 HTTP 200 空体，不增加结果字段；
- Report Progress 的业务键、公开状态与消息结构不变；
- Report 成功/失败 Callback 的字段、字段类型、消息和值域不变；
- `delivery_outcome_unknown` 仍是内部事实，不新增公开状态；显式 check-task 补发仍是
  at-least-once，接收端继续按规范化 `reportId` 与业务结果幂等处理。

本阶段不运行 `run.py`，只使用临时 SQLite、Fake 与定向离线测试。阶段 2 SQLite/Windows/Fake
证据不能外推为多实例、可靠队列、真实供应商容量、生产吞吐或 exactly-once 证明。

## 2. 步骤 1：Callback Delivery Port/Store

机器契约为 `tests/contracts/stage2_callback_delivery_contract.json`。完整持久化端口位于
`app/modules/tasks/ports/callback_delivery_control.py`，SQLite 唯一 Writer 位于
`app/modules/tasks/adapters/sqlite/callback_control_store.py`。业务 Callback Adapter 继续拥有公开
payload 与 HTTP 结果分类；Control Store 禁止导入 `requests`、执行网络调用、等待或写诊断文件。

### 2.1 权威身份

一次 Callback 发送权必须完整携带：

- `task_id` 与 `TaskBusinessRef`；
- 随机 `lease_token`，不得进入 repr、普通日志、事件或公开结果；
- 业务键内单调递增的 `fencing_token`；
- 严格 UTC 的 `lease_expires_at`。

TaskId、owner 名称、业务键或“数据库当前 owner”任一单独值都不能授权 HTTP。初次投递与
check-task 显式补发竞争同一 Guard；禁止另建进程内锁、第二张发送权表或旧/新双写。

### 2.2 原子事务

业务终态 UoW 在同一个 SQLite Connection/事务中依次提交 Task/Attempt 终态、latest 公开投影、
结果引用、Event 和 `callback eligibility/Guard`。任一写入失败或未显式 commit，整组回滚。
Callback HTTP、历史 JSON 与资源清理均发生在事务外。

Callback acquire 在一个短事务中复核 latest、业务终态、callback attempt 快照和 Guard，随后原子
写入 `sending` 租约、execution/latest callback 投影、attempt 计数与 authorized 事件。complete
同时条件更新 Guard、execution/latest 投影和 completed 事件。网络调用前必须通过独立短事务
`validate`；未来长耗时 Transport 可通过同一 fencing lease 的 `heartbeat` 续期，旧 deadline 的
Heartbeat 在新 deadline 生效后必须失权。

### 2.3 过期、unknown 与人工解除

发送租约到期不能证明请求未到达。acquire、validate、observe 或有界 sweep 发现过期 `sending`
时，只能冻结为 `outcome_unknown`，同步 execution/latest 并追加 `lease_expired_unknown`；不得自动
重抢或重发。显式 check-task 补发必须携带首次读取的 `expected_callback_attempts`，且只有
execution/latest/Guard owner 三者一致时才能把同一 Guard 从 unknown 变为新 sending lease。

人工解除必须确认旧 Worker 已停止或隔离，并在同一事务追加不可变 release audit 后把 Guard 置
idle。旧 execution/latest 的 unknown 事实继续保留；受理冲突只以 Guard 为权威，因此解除后可以
受理同键新 Task。新 Task 成为 latest 后，旧 lease/acquire 必须返回 stale/失权。

### 2.4 History 边界

`callback_delivery_attempt_events` 与 Guard 是发送控制权威。本地 Callback JSON 仍只是 Debug
诊断副本，不参与是否发送、重试、unknown、准入或终态判断。History Writer 的路径迁移属于步骤 4，
不得在步骤 1 提前改变现有生产调用链。

## 3. 后续步骤前置门禁

步骤 2～5 只能在前一步合同、专项测试、编译和差异检查通过且没有公开语义疑问后开始。步骤 6 是
Report 受理、执行、Progress、终态和 Callback Control 的不可拆一次切换；禁止只切受理、旧新库
双写、从数据库为旧 Runner 补 Authority，或让 check-task 与 Worker 使用两套 Guard。步骤 8 只删除
已确认零调用方的 Report SQL，不提前删除其他业务仍使用的 `LLMTaskService` 能力。

## 4. 步骤 3 已冻结的基础设施决策

### 4.1 组件感知的原子 Bootstrap

Report Control 以 `report_control` v1 组件 Manifest 声明 `report_resource_records` 及其索引。全新数据库
必须在未发布的临时文件中一次安装并校验根 Schema 与全部必需组件，成功后才原子发布；已有根库必须
在任何后台线程启动前完成缺失组件安装。安装使用独占事务，先校验根身份和对象全集，再创建组件
对象、复核对象全集，最后注册组件身份。发现未注册的残缺对象时 fail closed，不做猜测性修复。

Manifest 采用 `canonical_json_v1`，冻结 canonical UTF-8 长度 `3346`、组件 fingerprint
`509A3274DFDA23E1C8DFBDC53380064B682E869E28E4D59A1B87D99323AAE8BC`。任何 DDL 变化必须升级
组件版本并更新契约，不能静默覆盖同版本身份。

### 4.2 Report 资源与终态引用

`SQLiteReportResourceStore` 是 `report_resource_records` 的唯一 SQL Writer。完整产物元数据只保存在
Report 组件表中；根 Task 终态只保存由 canonical 产物引用计算出的稳定 `result_ref`，不把业务产物
复制进根表。资源状态更新使用版本 CAS 和短事务，为后续多实例清理、恢复和 fencing 留出明确边界。

### 4.3 共享 Interaction Store

`LLMInteractionStore` 是三张 Interaction 审计表的唯一物理 SQL Writer，继续写入现有审计数据库，
以保持 Analysis 与现有诊断链路兼容。Report v2 通过注入的精确 Task 身份校验器证明 Authority，禁止
为满足旧外键或校验而向旧 `llm_tasks` 双写。Task Control v2 与审计库不宣称跨库原子事务：执行器
必须先持久化 Step 外部操作意图，再写审计，最后在同一 Authority 条件下提交 checkpoint；恢复时按
已冻结的 Step 恢复矩阵处理不确定结果。

### 4.4 执行能力指纹

Report v2 启动时要求内部配置 `DOCSENSE_REPORT_RAG_PROVIDER_FINGERPRINT` 与
`DOCSENSE_REPORT_RAG_MODEL_FINGERPRINT` 均为 64 位十六进制 SHA-256。它们进入执行 Profile，用于
恢复与多实例能力匹配；不得退化为可选值，也不得记录 Provider 密钥、原始 URL 或其他敏感信息。

## 5. 步骤 4 Callback History Writer 迁移

Callback 本地 JSON 的唯一物理 Writer 迁移到
`app/infrastructure/observability/callback_history.py`。Report 直接使用新 Writer；旧
`callback_client.py` 暂时只保留兼容门面，并把 Analysis、Weaponry 与 Mock Server 的旧调用委托给
新 Writer，避免在其他业务切换前破坏内部导入。默认目录仍为 `RUNTIME_DIR/callback`，文件名、公开
payload、UTF-8 格式、同名原子追加和不覆盖语义均不变，Debug Reader 也继续读取同一路径。

History 仍严格是 best-effort 诊断副本：只有权威 Guard 完成成功后才尝试写入；写失败不改变业务
结果，不触发 HTTP 重发，也不参与投递、latest-wins、unknown、任务恢复或 Callback 重试判断。

## 6. 步骤 5 Report v2 Runner、Step 与事务契约

机器契约为 `tests/contracts/stage2_report_v2_runner_contract.json`。本步骤新增的
`RunReportV2Workflow` 只实现供统一 `TaskExecutionRuntime` 注入的内部 Workflow，不 claim、不 start、
不读取环境变量，也不从数据库查找“当前 owner”为旧调用补权。步骤 5 完成时生产组合根与旧 Runner
尚未切换；步骤 6 已完成不可拆的一次切换，机器契约现以 `productionWired=true` 记录最终装配状态。

### 6.1 Input/Profile 门禁

Runner 只接受 `ReportInputSnapshot/v2`，并在创建 Artifact 作用域或执行任何文件、网络、审计动作前，
严格比较受理时冻结的 `execution_profile` 与组合根注入的 Worker 当前 Profile。不同即 fail closed；
不得用当前环境补造历史 Profile，也不得降级执行 v1。该失败只证明当前 Worker 不具备执行能力，不得
伪造业务失败 Callback。

### 6.2 Step 与 RAG Hook

下载、文档准备、模板、RAG session/upload/bind/generate、交互审计、渲染、产物发布和终态只能创建
`REPORT_STEP_REGISTRY` 已登记的 Key。每个外部或本地效果均先在短事务中提交 intent，再在事务外
执行效果，最后以完整 Authority 提交摘要型 checkpoint。AnythingLLM Adapter 通过内部
`ReportRagStepObserverPort` 暴露其细粒度动作；该 Hook 不改变公开 HTTP、Callback 或供应商协议。

普通 Worker 遇到已存在 Step 时不自行复用 checkpoint 或重放，而是失败关闭并等待阶段 2-7 的持久
Recovery Decision。RAG Adapter 明确报告 unknown、审计提交结果未知，或已经提交 RAG intent 后漏出
未分类异常时，活动 Step 与资源现场进入 `recovery_required/quarantined`，禁止写失败终态、Callback
或自动清理。

### 6.3 Report 专用 UoW 原子组

`SQLiteReportExecutionUnitOfWork` 在同一 SQLite Connection 上组合 Task Execution、Callback Control
与 Report Resource Store。Store 无权提交、回滚或关闭连接；外部网络、文件转换、Callback HTTP 和
资源 DELETE 均不得进入事务。以下事实必须分别一次提交、任一失败整组回滚：

- Artifact scope Step checkpoint 与资源记录登记；
- `rag.generate` checkpoint 与 RAG cleanup ref；
- Audit Step checkpoint 与 Audit Receipt 引用；
- Artifact publish checkpoint 与完整最终产物引用；
- terminal Step checkpoint、最终产物引用、Task/Attempt 终态、latest 公开投影、稳定 result ref 与
  Callback eligibility。

成功或失败 Callback HTTP、Callback History 和资源清理只能在终态事务完成后执行。临时 SQLite 与
Fake 验证只证明当前单进程协议实现及回滚边界，不证明真实供应商、可靠队列、多实例或生产容量。

## 7. 步骤 6 Report 生产链一次切换

生产组合根已把 Report Submit、Dispatcher/Executor、Progress 持久事实、终态与 Callback Control
作为同一波次切换到 `task-control-v2.sqlite3`。新受理只写 `ReportInputSnapshot/v2`；
`LocalTaskExecutor` 只扫描 v2 accepted，`TaskExecutionRuntime` 负责 claim/start/heartbeat 与失权停止，
业务 Runner 的全部写仍携带 Authority Session。旧 `LLMTaskService` 不再接收 Report Task、Callback
Control 或资源写入，且不存在旧新数据库双写。

公开 `/llm/check-task` 与 Progress 订阅使用按业务路由的只读 Adapter：Report 读取 v2，尚未迁移的
Analysis/Weaponry 继续读取旧库。Report 成功 Callback 的 HTML 正文从资源记录持有的最终 Artifact
重建，并在发送前严格复核路径、大小、SHA-256 与 UTF-8；失败 Callback 仍保持空 details。该内部
重建不改变 Callback 字段、值域、消息或同步恢复语义。

v2 数据库首次发布前仍执行旧库无阻塞事实预检；数据库已经发布后的正常重启只严格验证 v2 根
Schema 与 Report 组件身份，不再要求未迁移业务的旧库保持为空，也不会迁移、修复或从旧库补造
Authority。组合根仍只创建一个 Progress Hub；Report 新旧发布器不得并存。

本步骤只使用临时 SQLite、Fake、编译和定向离线测试，未运行 `run.py`、未调用真实 AnythingLLM、
Callback 或文档转换服务。因此验收不能外推为多实例、可靠队列、真实供应商容量、生产吞吐或
exactly-once 证明。

### 7.1 分层归属与旧 TaskId 回读

`REPORT_STEP_REGISTRY`、恢复矩阵、Report 业务组合 UoW 和 Artifact 终态引用算法属于 Report
Application 的编排契约；Report Domain 只保留本业务纯类型与规则，Report Port 只保留抽象 DTO/协议。
Application 可以依赖通用 Tasks Domain/Port，但不得依赖 Tasks Adapter；该方向由全仓架构门禁锁定。

按 TaskId 读取已经离开 latest 的旧 execution 时，Callback attempt 必须按 `owner_execution_id` 从
`callback_delivery_attempt_events` 的追加事实恢复，不能读取当前 latest 的计数，也不能无条件降为 0。
这保证显式 check-task 恢复在新任务并发成为 latest 时仍保持“after attempts 不小于 before”的一致性。

## 8. 步骤 7 Callback Guard 与资源维护

Report v2 的 Callback Guard 与资源恢复继续是两套独立状态机：前者唯一写入
`SQLiteCallbackControlStore`，后者唯一写入 `SQLiteReportResourceStore`。二者只通过已经持久化的
Task 终态上下文关联，不共享状态字段、事务或执行权限。为控制本地线程数量，组合根让二者共享一个
`LocalMaintenanceScheduler` 调度线程，但注册为两个独立 Job；任一 Job 的暂态异常分别记录指标和
脱敏日志，不跳过另一 Job，也不永久关闭后续周期。

Callback Job 只执行有界 `freeze_expired`：把租约已过期的 `sending` 冻结为 unknown，绝不获取发送权、
不调用 HTTP，也不自动重发 unknown。显式 `/llm/check-task` 恢复仍沿用步骤 6 已冻结的同步语义与同一
Callback Adapter，本步骤未改变任何公开字段、状态码、消息或 Callback payload。

资源 Job 只执行有界 `sweep`，从专用 Store 扫描已经持久化且满足恢复条件的 terminal 资源事实。业务
Worker 在终态与 Callback 处理完成后只发出无 TaskId 的可丢唤醒提示，不再同步调用外部 DELETE；
启动扫描和周期扫描才是恢复真相。因此清理延迟、失败或进程在提示前退出均不能反转已提交终态，也
不会阻塞业务 Worker，后续重启仍可从 Store 继续收敛。

Dispatcher 启动时先启动维护扫描，再启动业务 Executor；Executor 启动失败会回收本轮维护线程。
停机时 Executor 与 Maintenance 使用同一总 deadline 并分别尽力停止，一条通道异常不得跳过另一条。
readiness 同时要求 Executor 与维护调度器健康。该装配沿用现有容器后台生命周期，没有新增生产启动
入口、旧 Runner Authority 传递或 Callback 语义。

机器契约继续使用 `tests/contracts/stage2_report_v2_runner_contract.json`，当前阶段标记为
`2-4-step-7`。离线验收覆盖临时 SQLite 空队列生命周期、Fake 双 Job 故障隔离、启动/周期/合并唤醒、
终态不等待同步清理及非法超时后的可恢复停机；这些证据仍不证明可靠队列、多实例或生产容量。

## 9. 步骤 8 旧 Report SQL 与入口收口

完成 Report 单写切换和独立维护链后，重新按生产调用图确认：`LLMTaskService` 上的 Report 专属任务
创建入口、`report_resource_records` DDL/索引/列迁移及六个原始资源读写入口均为零生产调用方，统一
删除。Report 资源表的唯一创建者和写入者保持为 v2 Report 组件 Schema 与
`SQLiteReportResourceStore`；不得把旧入口改成委托，因为这会继续保留可被误接的第二控制面。

该收口是非破坏性的：`LLMTaskService` 初始化不再创建或迁移旧 Report 资源表，但绝不执行 `DROP`、
清空或重写已经存在的历史表。旧任务投影只在测试夹具中通过私有通用持久化入口构造，用于验证历史
读取、迁移预检和共享 Guard 兼容；该夹具不是生产能力，也不得被生产模块导入。

交互审计仍是 Analysis 与 Report 的共享横切事实。`create_llm_interaction_with_trace` 和
`append_llm_interaction_lifecycle_events` 兼容入口继续单向委托 `LLMInteractionStore`，只删除委托返回后
不可达的旧内联 SQL；零生产调用的单条交互写入/cleanup 更新入口删除。审计 Schema 和读取兼容暂留
`LLMTaskService`，直至 Analysis 在阶段 2-6 完成迁移。

Analysis/Weaponry 仍使用的通用 Callback Guard、Analysis 批次/资源记录、Weaponry 快照与审计能力
全部保留。永久 AST/机器契约同时约束“Report 专属入口不得复活”和“共享能力不得提前消失”。本步骤
没有修改公开接口、Callback 语义、生产启动策略或 `app/container.py`，也没有把旧入口双写到 v2。
机器契约阶段更新为 `2-4-step-8`。
