## 1. 改造目标

### 1.1 必须达成的目标

1. 将 `app/services/chat/` 的对话主体迁移到 `app/modules/chat/`，形成与 Report、Weaponry、
   Analysis 等业务一致的模块化单体垂直切片。
2. 新增并只通过 `/llm/weaponry-chat*` 提供知识谱系对话的发送、标题、历史、中断和删除能力。
3. 知识谱系对话以 `userId + architectureId` 为公开唯一身份，不再公开或接收 `chatId`。
4. 文件对话和知识谱系对话拥有独立 Web 请求模型、身份规则和展示合同，但共用一套对话领域
   状态机、应用用例、持久化抽象、AnythingLLM 对话适配和资源清理代码。
5. 保留知识谱系类别“直接文件、首次冻结、后续不刷新”的范围语义；删除完成后再次进入才创建
   新对话和新快照。
6. 正确消费 AnythingLLM v1.15.0 `/stream-chat`：不能在最后一个
   `textResponseChunk(close=true)` 提前结束；常规回答继续读取 `finalizeResponseStream.sources`，
   同时严格支持 v1.15.0 查询拒答分支的 `textResponse(close=true, sources=[])` 成功终态。
7. 知识谱系成功 SSE 在全部文本之后返回一次 `sourceChunks`，并在历史 assistant 消息中保存
   同一份 Chunk 快照。
8. assistant 正文、Chunk 快照、运行成功终态和终结事件账本在同一事务内收敛；失败、中断或
   缺失最终来源事件不得留下部分 assistant/Chunk。
9. 通过内部 `conversationId`、Port、组合根和能力声明，为未来可靠队列、共享数据库、多实例、
   跨实例取消通知与高并发执行保留可替换边界。
10. 使用详细中文注释和必要的脱敏结构化日志；日志不得包含消息正文、Chunk 原文、文件名、
     `docSource`、远端 URL、DocSense `userId` 或凭据。
11. 把可信调用方传入的 `userId` 作为 DocSense 权威业务身份，但不把它当成 AnythingLLM 用户；
    调用方/网关负责在请求到达前完成用户真实性和类别权限校验。
12. 删除成功后物理删除消息正文和 Chunk，只保留不能恢复正文的最小删除审计事实；只有该事务
    完成后才释放 Weaponry 活动复合身份。

### 1.2 明确不做

- 不兼容旧的 `/llm/chat + chatId + architectureId` 知识谱系模式。
- 不迁移现有 Chat SQLite 数据，也不导入旧会话、消息、Scope、运行或清理任务。
- 不改变文件对话 `/llm/chat*` 的公开字段、状态码、SSE 事件或历史结构。
- 不向文件对话增加 `sourceChunks` 或历史 `chunks`。
- 不把 DocSense `userId` 作为 AnythingLLM 用户标识向下游传递。
- 不实现公开 `requestId`/`runId`、断线续传、SSE 回放、幂等键或后台继续生成。
- 不在本阶段选型或宣称已经接入可靠队列、共享数据库、分布式锁或跨实例通知。
- 不以 SQLite、进程内 Semaphore、内联 Dispatcher 或本地轮询结果证明多实例和生产高并发。
- 当前暂不增加 Chunk 数量/字符数、对话累计历史大小或 History 分页上限，也不静默截断来源；
  该决定必须作为明确容量风险记录，不能据此宣称生产容量已经验证。

## 2. 已冻结的公开合同

实现和测试必须直接引用权威接口文档，以下仅列不可被内部设计反向修改的核心规则：

| 维度 | 文件对话 | 知识谱系对话 |
| --- | --- | --- |
| 路径 | `/llm/chat*` | `/llm/weaponry-chat*` |
| businessType | `chat` | `weaponryChat` |
| 公开身份 | `chatId` | `userId + architectureId` |
| 范围输入 | `fileNames` | 首次按 `architectureId` 选择直接文件 |
| 范围演进 | Requested/Active/Effective Scope 既有规则 | 首次冻结，后续永不刷新 |
| SSE 来源 | 不公开 | `sourceChunks` 恰好一次，位于文本后和 `done` 前 |
| 历史来源 | assistant 无 `chunks` | assistant 必有 `chunks` 数组 |
| 历史外层 | 裸消息数组 | 裸消息数组 |
| 删除后再进入 | 调用方使用新的/既有 `chatId` 规则 | 同一业务身份创建新的内部对话和快照 |
| 删除后原文 | 保持既有文件对话合同 | 消息正文和 Chunk 物理删除，仅留最小审计事实 |
| GET 十进制 | 既有 file chat 规则不变 | userId/architectureId 允许前导零并按整数值规范化 |
| 未知字段 | 既有 file chat 规则不变 | POST/Query 严格拒绝；重复 Query 参数严格拒绝 |
| 来源/历史上限 | 文件对话既有限制不变 | 当前无 Chunk/History 专属上限，不截断 |

任何阶段如发现必须增加请求参数、响应字段、Header、状态码或 SSE 事件，立即停止实施并重新确认
接口合同，不能以“内部重构需要”为理由绕过。知识谱系成功 SSE 已冻结
`Content-Type: text/event-stream`、`Cache-Control: no-cache` 和 `X-Accel-Buffering: no`；冻结
范围中的任一文件缺少非空 `originalFileName` 时整体拒绝，禁止回退为 `fileName`。

## 3. 当前实现审查结论

### 3.1 可以保留的能力

当前 Chat 链已经具备以下可复用基础：

- 本地权威 Session、Run、Run Input、Message、Scope、Binding、Lease、Cleanup Job 和事件账本；
- 同一对话 Admission Guard、活动运行互斥和 409 优先于全局容量 429；
- 首次类别直接文件有界读取、稳定排序、候选整体校验和不可变 Scope Head；
- 运行只按持久化 `run_id` 重新加载输入，不捕获 Flask Request 或网络 Session；
- 标题临时线程租约、中断持久标记、删除同步清理和失败恢复事实；
- AnythingLLM Transport、Workspace/Thread 原子 Client 与任务级 Factory；
- SQLite 单实例能力声明和显式禁用的事务 Outbox。

### 3.2 必须修复的结构问题

| 编号 | 当前问题 | 风险 |
| --- | --- | --- |
| C1 | 对话主体位于 `app/services/chat/` | 与模块化单体目录和依赖门禁不一致，组合职责继续堆积在全局 Container |
| C2 | Chat Port 位于全局 `app/ports/chat.py`，Chat 专属 AnythingLLM Gateway 位于全局 integrations | 模块所有权分散，业务 DTO 和供应商适配难以独立演进 |
| C3 | 全部业务实体和子表以公开 `chat_id` 关联 | 无法自然支持 `userId + architectureId` 复合公开身份，也会让未来新增对话类型继续污染子表 |
| C4 | `/llm/chat` 路由同时解析 file 和 architecture 范围 | 两类公开合同耦合，任一需求容易反向改变另一接口 |
| C5 | `AnythingLLMThreadClient.stream()` 在任意 `close=true` 时返回 | 实际停在空来源的最后一个文本事件，永远读不到随后到达的 `finalizeResponseStream.sources` |
| C6 | 上游和 Chat Port 都只返回 `Iterator[str/ChatChunk]` | 即使继续消费最终事件，也没有类型化通道传递来源列表 |
| C7 | 来源 DTO 没有面向 Chat 的可信冻结映射 | `title`/`id` 无法唯一匹配文件；模糊猜测会造成跨文件错误归因 |
| C8 | assistant 消息没有 Chunk 子表和原子提交命令 | SSE 来源无法在历史中稳定重放，容易出现正文与来源不一致 |
| C9 | Presenter 只理解 `chatId` 身份事件 | 新 SSE 无法安全输出复合业务身份，容易泄露内部 conversation/run ID |
| C10 | Container 逐个构造和公开 Chat 实例 | 生产和测试可能形成不同对象图，未来替换 Adapter 时缺少模块级一致性门禁 |

### 3.3 AnythingLLM v1.15.0 实测事实

当前项目环境的脱敏取样得到如下顺序：

```text
textResponseChunk(close=false, sources=[]) × 多次
textResponseChunk(close=true, textResponse="", sources=[])
finalizeResponseStream(close=true, textResponse缺失, sources=[...])
```

最终来源对象在当前实例包含 `text`、`docSource`、`title`、`url`、`id`、`score` 等字段。一次
取样中的全部四条 `sources[].docSource` 都与工作区文档记录的 `metadata.docSource` 精确对应；
`title` 不等于工作区 `filename`，`id` 也不等于工作区文档 ID。因此目标实现必须：

1. 将 `finalizeResponseStream` 作为成功完整终点；
2. 使用 `text` 作为当前版本 Chunk 原文，同时在供应商适配层保留对已知字段别名的严格兼容；
3. 把结构化 `docSource` 规范化为供应商无关的内部来源键；
4. 用该键与本轮冻结/绑定的文档来源键精确匹配；
5. 不使用标题、URL、正文、模糊文件名或供应商行 ID 进行授权和归因。

官方 v1.15.0 源码还存在两个无来源成功短路：Workspace 没有向量数据，或者 Query 检索没有
上下文时，`streamChat()` 直接发送 `textResponse(close=true, sources=[])` 后返回，不产生
`finalizeResponseStream`。因此“实测带来源正常路径”不能被扩大为“所有成功都只有一种终态”。
Adapter 必须把这类显式成功对象规范化成一个 Text Delta 和一个空来源 Finalization，同时仍禁止
把普通 `textResponseChunk(close=true)` 当成整个流结束。

这项实测只证明当前 AnythingLLM Desktop v1.15.0 和当前向量存储配置；协议规则仍须由固定 Fixture
和官方 tag 源码形成长期回归资产。

## 4. 目标架构与职责划分

### 4.1 目标调用关系

```text
Flask 路由
  ├─ File Chat Request Adapter / Presenter
  └─ Weaponry Chat Request Adapter / Presenter
          ↓
app.modules.chat.application（共享用例）
          ↓
app.modules.chat.domain + app.modules.chat.ports
          ↓
app.modules.chat.adapters
  ├─ SQLite / 运行协调 / 内联调度
  ├─ 知识目录文档解析
  └─ AnythingLLM Chat Adapter
          ↓
app.integrations.anythingllm
  └─ 通用 Transport、Workspace/Thread 原子 Client、供应商协议 DTO
```

### 4.2 独立层与共享层

| 层次 | 是否独立 | 设计理由 |
| --- | --- | --- |
| HTTP 路径和请求解析 | File/Weaponry 独立 | 两套路径、businessType、公开身份和参数完全不同，禁止互相兼容 |
| HTTP/SSE Presenter | File/Weaponry 独立 | 文件对话不能暴露 `sourceChunks`；知识谱系身份事件必须输出复合键 |
| 公共身份值对象 | 类型独立、统一接口 | `FileChatIdentity(chatId)` 与 `WeaponryChatIdentity(userId, architectureId)` 规则不同，但都解析为内部 Conversation Identity |
| 调用方信任/授权 | Weaponry Web 边界声明 | `userId` 是可信 DocSense 业务身份；真实性和类别权限由调用方/网关先行保证，Chat 核心不把它下传为 AnythingLLM user |
| 范围选择策略 | 独立 | 文件对话范围可替换/继承；知识谱系只在首次冻结直接文件 |
| Application 用例 | 共享 | 受理、执行、历史、标题、中断、删除、清理生命周期一致，通过身份/范围/展示策略注入差异 |
| Domain 状态机 | 共享 | Session、Run、Message、Lease 和终态语义与供应商、公开路径无关 |
| 持久化 Port 与 SQLite Adapter | 共享 | 所有子事实使用内部 `conversationId`，公开身份只存在于身份绑定表 |
| Chat Provider Port/Gateway | 共享 | 两类对话使用同一 AnythingLLM 创建、绑定、流式、标题和清理过程 |
| AnythingLLM 原子 Client/Transport | 全项目共享 | 只负责供应商 HTTP/SSE 协议，不包含文件或知识谱系业务规则 |

### 4.3 `modules/chat/composition.py`

新增唯一 Chat 组合入口：

```text
compose_chat_application_services(...)
  -> ChatApplicationServices(
       commands,
       run_executor,
       dispatcher,
       history,
       title,
       abort,
       delete,
       cleanup,
     )
```

组合函数必须满足：

- 不导入 Flask，不读取 Request，不注册路由；
- 构造时不访问 AnythingLLM、不启动后台线程、不运行模型；
- 所有 Application 用例共享同一个 Store、Conversation Factory、Run Coordinator 和 Cleanup
  Executor；
- 通过构造期断言阻止“双 Store”“双 Dispatcher”“标题与删除使用不同 Factory”等错误装配；
- 当前 SQLite/内联实现的能力声明不满足多实例配置时启动失败关闭，不能静默降级。

## 5. 目标内部身份和数据模型

### 5.1 内部 Conversation Identity

所有业务子实体改用不可公开的 `conversation_id` 关联。建议使用随机 UUID 文本，不从
`userId`、`architectureId` 或 `chatId` 拼接，避免远端资源名和日志泄露业务身份。

公开身份值对象：

```text
FileChatIdentity(chat_id: int)
WeaponryChatIdentity(user_id: int, architecture_id: int)
```

Repository 提供统一能力：

```text
resolve_active(identity) -> Conversation | None
resolve_any(identity) -> Conversation | Tombstone | None
reserve_admission(identity) -> AdmissionLease
create_conversation(identity, ...) -> Conversation
finalize_completed_delete(conversation_id)
```

`resolve_active()` 只供活动 Weaponry 会话查找；公开文件 `chatId` 还必须通过 `resolve_any()` 或
等价墓碑查询区分“从未存在”和“已经删除”。文件对话删除后不得释放或复用同一 `chatId`，不能
因为活动查询返回空就尝试插入新 Conversation。只有 Weaponry 删除成功后释放活动复合身份。

### 5.2 新 Chat 数据库世代

由于本次明确不兼容和迁移旧数据，实施时建立新的 Chat Schema 世代，不编写 v1～v6 数据迁移。
新数据库必须有独立的 generation/version 标识，启动时遇到旧世代数据库应失败并提示先执行已确认
的停服清理流程，不能自动删除或猜测转换。

建议逻辑表：

| 表/聚合 | 核心字段 | 约束与作用 |
| --- | --- | --- |
| conversations | `conversation_id`、kind、status、远端引用、时间 | 内部会话根；不以公开 ID 做主键 |
| conversation_identities | `conversation_id`、identity_kind、`chat_id`、`user_id`、`architecture_id`、active | CHECK 保证两种身份字段互斥；文件 chatId 全世代唯一且删除后保留墓碑；活动 weaponry `(user_id, architecture_id)` 部分唯一 |
| conversation_admissions | identity key、token、expires_at | 在创建业务事实前解决同身份首轮竞态；未来可替换数据库时间和 fencing |
| scope_revisions / scope_members / scope_heads | `conversation_id`、revision、成员快照 | 保留文件对话 Scope 状态机与知识谱系首次冻结 |
| runs / run_inputs / run_input_files | `conversation_id`、run、消息、不可变文件和来源键 | 未来 Worker 只凭 run ID 恢复完整输入 |
| document_bindings | `conversation_id`、文件身份、远端引用、结构化来源键 | 记录精确绑定回执和来源映射，不以标题/文件名猜测 |
| messages | `conversation_id`、run、role、content、status、sequence | 本地权威历史 |
| message_source_chunks | `message_id`、position、content、file_name、original_file_name | assistant 来源快照；`(message_id, position)` 唯一 |
| run_events | run、sequence、event、data | 追加式内部事件账本 |
| resource_leases / cleanup_jobs | `conversation_id`、资源和清理状态 | 删除、临时标题和失败恢复；Weaponry 清理成功后随在线聚合物理删除 |
| conversation_deletion_audits | `conversation_id`、identity kind、删除终态、清理结果、删除时间 | 独立最小审计事实，不以外键依赖已经物理删除的 Weaponry 在线聚合 |

所有外键开启并通过 `foreign_key_check`；身份范围、角色、状态、Chunk 顺序和 JavaScript 安全整数
应有数据库 CHECK 兜底。SQLite 写事务继续使用显式 `BEGIN IMMEDIATE`，但该事实不得被描述为
共享数据库方案。

### 5.3 删除与重新进入

1. 删除开始后，会话进入独占 deleting 状态，活动身份仍被占用。
2. 远端资源和本地租约全部成功清理后，执行一个删除终态事务：物理删除 user/assistant 消息
   正文、`message_source_chunks`、可恢复历史投影以及不再需要的正文副本；不能留下半孤儿子表。
3. 同一事务只保留不能恢复正文的最小审计墓碑，例如内部 Conversation 身份、identity kind、
   删除时间、删除终态和清理结果。墓碑不得包含消息正文、Chunk 原文、文件名、原文件名或完整
   供应商资源引用。
4. Weaponry 仅在上述事务完整成功后释放活动 `(user_id, architecture_id)`；清理或正文删除失败
   时保持占用并返回 500/409 语义，后续 delete 精确重试尚未完成步骤。
5. 文件对话永不释放公开 `chatId` 的全世代墓碑；同一 `chatId` 的发送/标题/历史/中断/删除行为
   必须逐字段保持既有合同，不能被 Weaponry 再进入规则反向改变。
6. Weaponry 再次发送成功创建新的随机 `conversation_id`、新的 Scope Head 和新远端
   Workspace/Thread；公开查找不得穿透到旧墓碑。

### 5.4 Chunk 原子性

新增一个存储级原子命令，例如：

```text
complete_run_with_reply(
    run_lease,
    user_message_id,
    assistant_message,
    ordered_source_chunks,
    terminal_event,
)
```

同一事务必须完成：

- user pending → committed；
- 插入完整 assistant；
- 按上游顺序插入全部 `message_source_chunks`；
- Run → succeeded；
- 写入内部最终事件；
- 条件校验执行 lease/fencing，并要求 `abort_requested=false`（当前单实例为能力受限实现）。

任一步失败整体回滚。SSE `sourceChunks` 和 `done` 只能在该事务成功后输出。本地事务提交是唯一
完成线性化点：提交后即使网络断开导致终结事件未送达，也不能撤销已提交历史；提交前已观察到
Abort 或断线则不得提交 assistant/chunks。

## 6. AnythingLLM 流协议和来源映射设计

### 6.1 原子 Client 事件模型

`AnythingLLMThreadClient.stream()` 不再返回字符串，应返回严格类型事件，例如：

```text
AnythingLLMTextDelta(text)
AnythingLLMStreamFinalization(sources)
```

解析规则：

1. `textResponseChunk` 的非空 `textResponse` 形成 Text Delta；它的 `close` 值不决定整个 SSE
   是否结束。
2. `textResponseChunk(close=true, textResponse="")` 只表示供应商文本阶段结束，继续读取。
3. 常规模型回答只接受唯一 `finalizeResponseStream` 作为完整终点，并严格读取显式 `sources`
   数组。
4. v1.15.0 Query 无向量数据/无上下文分支允许唯一
   `textResponse(close=true, error=null, sources=[])` 作为显式完整终点；其完整正文转换成一个
   Text Delta，Adapter 再把它规范化为 `ordered_sources=[]` 的 Provider-neutral 完成事件。供应商
   事件审计仍必须如实记录它不是 `finalizeResponseStream`，不得伪造“已收到供应商 Finalization”；
   也不得把该兼容扩大到缺少 `sources` 或携带错误的对象。
5. 显式 `sources=[]` 是合法完成；缺少字段、非数组、来源元素非对象、重复/冲突终态或流结束仍
   未收到上述任一合法终态，均抛出协议错误。
6. 供应商 abort/error 事件映射为稳定异常或终止事件，不伪装为成功空来源。
7. 调用方提前关闭时，生成器必须向 Transport 传播 close 并释放 HTTP Response。
8. 来源正文使用专用严格提取器：只接受 JSON string，不调用会字符串化或 `strip()` 的
   `first_text()`；在内部 DTO、公开 SSE 和持久化历史之间保留首尾空白、换行和 Unicode 码点。

同步 `ask()` 如继续复用相同事件协议，也必须审查其最终事件判断；不能只修流式方法而留下同类
提前结束问题。

### 6.2 供应商无关 Chat Provider Port

Chat Port 返回：

```text
ChatTextDelta(content, sequence_no)
ChatReplyFinalization(ordered_sources)
```

来源 DTO 至少包含：

```text
ChatRetrievedSource(
    content,
    structured_source_key,
    sequence_no,
)
```

`structured_source_key` 是供应商无关的内部身份，AnythingLLM Adapter 当前从结构化
`docSource` 提取；Domain/Application 不读取 `title`、`url`、score 或 AnythingLLM 字段名。

### 6.3 冻结来源键

仅保存 `external_location/document_ref` 不足以映射最终 `docSource`。绑定阶段需要：

1. 以冻结的 `external_location` 精确匹配 AnythingLLM 工作区文档回执；
2. 从唯一回执的结构化 metadata 提取 `docSource`；
3. 规范化为内部 `structured_source_key`，与文件名、标题和 URL 分离；
4. 将其写入 Document Binding 和 Run Input File 快照；
5. 后续轮次只复用持久化来源键，不根据工作区当前标题重新推导；
6. 首次绑定缺少/重复来源键时，知识谱系模式整批失败；文件模式按其现有合同执行，但不得让
   宽松结果进入知识谱系来源映射。

### 6.4 最终来源映射

收到 Finalization 后：

- 构建本轮 Run Input `structured_source_key → frozen file snapshot` 映射；
- 冻结成员之间来源键必须唯一；
- 按上游 sources 顺序逐项精确查找；
- 每项生成 `content/fileName/originalFileName`；
- 不去重、不排序、不截断、不模糊回退；
- `originalFileName` 缺失、类型错误、为空或仅含空白时整体拒绝，不创建部分范围，也不回退为
  `fileName`；
- 任一来源无键、空正文、无法映射、映射歧义或越出本轮 Scope 时整体失败。

合法来源正文只以“不是空字符串且不全为空白”进行质量门禁，门禁通过后保存原始字符串值；不能
把用于判空的 `strip()` 结果当成最终 `content`。映射后的 SSE Chunk 和 History Chunk 必须按位置
及三个字符串字段逐值相等。

日志只输出 `source_count`、`mapped_count`、`unresolved_count`、错误类型和内部 run correlation；
不输出来源正文、来源键、文件名或 URL。

- 将最终来源逐项映射到冻结的 DocSense 文件。

**实施**

1. 提取 File Scope Policy 和 Weaponry Architecture Scope Policy。
2. Weaponry 首轮有界读取精确类别直接文件，稳定排序并整体验证。
3. 在受理事务内以“是否创建新 Conversation”裁决候选；并发失败者若发现已存在会话，复用
   已提交 Scope，不用事务外候选覆盖。
4. 绑定回执捕获并持久化结构化来源键。
5. 新增纯 Application `SourceMapper`，按 Finalization 顺序生成公开 Chunk Snapshot。
6. 来源为空成功；来源非法、缺失、越界或歧义整体失败。

**测试**

- 只选直接文件、不含子类；空类别 404；坏记录/同名/重复远端身份整体 400；超限不截断；
- 首次冻结后新增、删除、重分类文件不改变后续 Scope；
- 删除完成再进入使用新目录快照；
- docSource 一对一映射、空列表、同一文件多个 Chunk、顺序保留、不去重；
- SSE 与 History 的 Chunk 逐位置、逐字段字符串值完全相同；
- 首次范围中 `originalFileName` 缺失、类型错误、空字符串或全空白均整批失败，不创建部分事实；
  不允许回退 `fileName`；
- title/id/url/正文相似但 docSource 不匹配必须失败；
- 来源键冲突、缺字段、空正文和越出本轮 Scope 失败关闭。

**验收**

- `SourceMapper` 为纯函数/纯应用服务，不导入 AnythingLLM 或 SQLite；
- 映射结果只含 content/fileName/originalFileName；
- 不存在基于模糊标题的 fallback；
- 后续消息不查询当前类别目录。

**达成效果**

Chunk 展示建立在可审计的冻结身份关系上，而不是供应商标题的偶然一致性上。

### 阶段 5：共享运行、历史、标题、中断、删除用例扩展

**目标**

- 让五个知识谱系接口使用共享 Application 生命周期；
- 保证正文/来源历史与终态一致。

**实施**

1. Run 用例消费 Text Delta，暂存正文；收到 Finalization 后严格映射并执行原子完成命令。
2. Weaponry 成功输出内部 `source_snapshot` 再输出 completed；File Policy 抑制公开来源但仍等待真正
   Finalization。
3. History 根据 Conversation kind 投影：file 保持原结构；weaponry user 为基础三字段，assistant
   增加 chunks。
4. Title/Abort/Delete 接收统一 Identity，不再依赖公开 chatId。
5. 标题临时线程和主远端资源使用随机内部 conversation ID 命名，不拼接 userId。
6. 删除完成先清除消息正文/Chunk，再释放 Weaponry 复合身份；清理失败保留恢复记录并阻止
   重建，重复 delete 只重试未完成步骤。
7. 五个用例共同实现接口合同中的状态矩阵；Title 与 Run/Title/Delete/Cleanup 状态互斥，History
   在非删除终态始终只读已提交事实。

**测试**

- success：正文 + chunks + run/event 同事务，历史立即可读；
- empty sources：SSE/历史都是空数组；
- error/abort/disconnect：无 assistant/chunks；user 保留规则与合同一致；
- title 成功、空对话、空历史、临时线程清理失败；
- abort true/false、上游长间隔、通知失败仍保留持久化标记；
- delete success/not-found/busy/cleanup-failed/re-entry；
- 删除后消息/Chunk 行为 0、最小墓碑不可恢复正文、重复 delete 为 404、cleanup_failed delete
  可精确重试；
- 状态矩阵逐单元测试，包括 running/title/deleting/cleanup_failed 下五接口结果；
- 提交后、`sourceChunks` 前断线，以及 `sourceChunks` 后、`done` 前断线：History 已有完整成功
  事实；提交前断线则没有 assistant/chunks；
- File/Weaponry Policy 交叉测试，禁止一种身份访问另一类 Conversation。

**验收**

- 五个用例不重复实现 AnythingLLM 交互；
- 历史不读取 AnythingLLM 作为权威来源；
- 删除或标题失败不泄露远端引用；

**达成效果**

两套公开接口共享真正的业务核心，而不是复制五套 Service 或通过大量 `if businessType` 互相污染。

### 阶段 6：Web 适配、SSE Presenter 和独立路由切换

**目标**

   严格拒绝未知字段和重复 Query，GET 两个 ID 允许前导零并按整数值规范化。
2. 新增知识谱系 HTTP/SSE Presenter，所有身份字段输出 number。

4. title/abort/delete 回显 `userId + architectureId`；history 保持裸数组。

**测试**

  标准字符集参数），并精确包含 `Cache-Control: no-cache` 和 `X-Accel-Buffering: no`；
- history 裸数组，不加身份 envelope；
- 文件对话黄金路由回归，architectureId 旧模式不再可用；
- 前端快速切换场景由调用方 correlation 测试验证，不要求后端向历史增加身份字段。

**验收**

- 权威合同的全部示例都有路由测试；
- 新旧路径参数不能串用；
- File SSE/历史逐字段等于阶段 0 基线；
- 未经确认的 Header、字段和错误响应均未出现。

**达成效果**

前端获得语义独立且可稳定演进的知识谱系对话接口，文件对话不再承担第二种身份模型。

## 10. 实施风险与控制

### 10.1 大规模路径迁移掩盖行为变化

**控制：** 阶段 1 只做机械迁移；身份、Schema、来源和路由分别提交。每阶段先跑定向测试，再跑
相邻回归。移动失败时不同时重写算法。

### 10.2 最终文本关闭与完整响应完成混淆

**控制：** 类型中明确区分 Text Delta、Text Phase Close 和 Finalization；永久 Fixture 固定真实
v1.15.0 顺序；日志变量不再把第一个 close 命名为 `final_event_received`。

### 10.3 来源映射跨文件错误

**控制：** 只信任结构化来源键与冻结回执；唯一约束、纯映射测试和失败关闭；严禁 title/url/id/
正文 fallback。

### 10.4 已向前端输出文本但最终来源失败

**控制：** 文本片段始终标记为流式临时展示；最终来源失败发送 `error`，不提交 assistant/chunks；
前端只在 `done` 后确认完整回答。

### 10.5 删除后身份过早释放

**控制：** 仅在所有远端租约成功关闭的终态事务释放活动 Identity；cleanup_failed 保持 409 阻塞，
先恢复清理再重试。

### 10.6 成功提交后终结事件未送达

**控制：** 本地事务提交是唯一完成线性化点；`sourceChunks`/`done` 只作提交后的网络通知。分别
测试提交前断线、提交后但来源前断线、来源后但 done 前断线；后两者通过 History 恢复完整事实，
不得尝试跨数据库和网络做伪原子回滚。

### 10.7 清库造成远端资源失联

**控制：** 先根据旧租约清理和核对远端资源，再删除精确 Chat DB；任何未确认租约都触发停止。

### 10.8 无 Chunk/History 上限导致响应膨胀

**控制：** 当前按负责人决定不设置业务上限、不分页、不截断；测试和真实联调只记录脱敏尺寸与
趋势。出现内存、代理帧、数据库或响应时间不可接受证据时必须停止发布并重新确认合同，不能临时
截断或隐藏部分来源。

### 10.9 以内部预留冒充未来能力

**控制：** Capability 对象和启动门禁继续区分 single/shared、inline/reliable、polling/cross-instance；
没有真实 Adapter、迁移和拓扑验收时保持 false。

### 10.10 远端清理成功与本地删除终态之间崩溃

**控制：** 当前同步路径在本地终态事务中重新验证 `deleting`、删除清理成功事实和全部租约关闭，
禁止在证据不完整时释放身份；但远端清理与本地事务无法组成跨系统原子提交。后续可靠任务阶段必须
增加持久化 Reconciler/Finalizer，扫描严格满足上述条件但仍停留在 `deleting` 的会话，并幂等
提交本地最小审计和聚合删除。当前公开合同规定 `deleting` 下 delete 返回 HTTP 409；若希望由
公开重试直接触发终态恢复，必须先确认并修改接口文档，不能作为内部实现细节静默改变。

---

## 11. 停止条件

出现以下任一情况必须暂停并与负责人确认：

1. 实现需要改变本文任一公开路径、字段、类型、状态码、Header 或 SSE 事件/顺序；
2. AnythingLLM 目标环境的常规回答不再提供唯一 finalization，Query 拒答无法被唯一识别，或
   结构化来源无法与冻结文档建立唯一映射；
3. 发现 `userId` 必须传给 AnythingLLM 才能工作；
4. 文件对话若不增加公开字段就无法继续使用共享核心；
5. 旧 Chat 数据或远端资源不能按已确认的清库策略安全处理；
6. 同步删除合同必须改成异步任务或新增公开任务 ID；
7. 需要选择共享数据库、可靠队列、跨实例通知或分布式锁产品；
8. 工作树存在与本计划重叠且所有权不明的用户修改；
9. 真实测试可能读取、输出或破坏非隔离业务数据。
10. 当前无 Chunk/History 专属上限的真实响应规模已经不能满足目标部署容量。

## 12. 完成定义与最终效果

只有同时满足以下条件才可关闭本专项：

- 权威接口文档与五条真实路由逐字段一致；
- 旧知识谱系 `/llm/chat` 模式已删除，不存在双路由或隐式兼容；
- `app/modules/chat/` 是唯一 Chat 业务实现，composition 是唯一生产装配入口；
- File/Weaponry Web 边界独立，Application/Domain/Persistence/AnythingLLM 链复用；
- 内部 Conversation Identity、复合唯一约束、首次快照和删除再进入状态机通过并发/故障测试；
- AnythingLLM 常规 finalization 与 v1.15.0 Query 空来源终态均被完整读取，Chunk 无损严格映射、
  原子持久化，并按合同输出/回放；
- 文件对话全部公开行为保持不变；
- 定向、相邻、安全全仓、编译、静态差异和架构门禁通过；
- 清库和真实联调有独立证据，临时远端资源残留为 0；
- 文档清楚标注 SQLite 单实例、无可靠队列、无多实例和未完成生产容量验证的边界。

最终达成的结构是：前端获得一套独立、清晰、可展示检索原文的知识谱系对话合同；后端只维护
一套供应商无关的对话生命周期和 AnythingLLM 交互代码；未来替换共享数据库、可靠队列和多实例
通知时，只替换明确 Port/Adapter，不再修改两套公开接口的业务语义。
