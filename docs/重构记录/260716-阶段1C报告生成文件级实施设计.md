## 1. 目标与非目标

### 1.1 目标

1. 把报告生成从 Flask 路由和巨型 Service 拆成 Report Domain、Application、Ports 和 Adapters。
2. 提交用例原子完成活动任务判断、不可变 execution ID/请求快照创建和最新投影更新。
3. 同一 `reportId` 并发提交时只允许一个 HTTP 202，其余返回既有 HTTP 409。
4. 执行入口只接收内部 `task_id/execution_id`，从持久化快照恢复全部业务输入。
5. 所有进度、结果、回调和公开投影写入都携带 expected execution ID，旧执行不得覆盖新执行。
6. 路由不创建 daemon thread；正常积压保存在数据库，内存只使用常量空间的有界唤醒。
7. 把下载、模板提取、文件规范化、多文档 RAG、Progress、Callback 和 Artifact 变成显式 Port。
8. 保持既有报告 Prompt、HTML、进度、公开状态和回调载荷；只应用已批准的 202/409 差异。
9. 为阶段 2 统一任务隔离、阶段 3 SQLAlchemy/MySQL、阶段 4 Outbox 和阶段 5 Worker 提供
   可替换边界，不把阶段 1C 描述成可靠队列已经完成。

### 1.2 非目标

- 不部署或接入 MySQL、RabbitMQ、Redis、MinIO、Celery 或 FastAPI。
- 不修改 `/llm/check-task` 生产路由；可靠回调恢复仍等待阶段 4～6。
- 不给 analysis、weaponry、chat 或 reassign 顺带做业务迁移。
- 不实现多实例执行、跨进程租约、fencing token 或 Redis 通知。
- 不新增 URL 白名单、DNS 重绑定、重定向校验或其他 URL Policy。
- 不冻结 MinIO 7/30/180 天等具体保留周期，也不启用自动 TTL。
- 不迁移 SQLite 历史测试数据，不删除旧 Service 或旧表。
- 不新增、删除、重命名或改变任何前后端请求参数、回调字段或 Progress 消息。

## 2. 当前代码事实与问题

### 2.1 当前调用链

```text
POST /llm/generate-report
  → app/blueprints/llm.py::llm_generate_report
      → 解析/修改 request dict
      → LLMTaskService.create_report_task(reportId, payload)
      → LLMProgressHub.publish(...)
      → threading.Thread(daemon=True)
          → UploadTaskLimiter.run(run_report_task, request_payload=整份请求)
              → 下载源文件/模板
              → normalize_file_for_llm / extract_text_from_word
              → 直接创建 AnythingLLMClient
              → run_anythingllm_rag
              → 按 reportId 更新任务/进度/结果
              → post_callback_payload
```

### 2.2 已核实的结构和并发缺陷

| 事实 | 风险 |
| --- | --- |
| 路由在 `app/blueprints/llm.py` 直接创建 daemon thread | 请求量会转化为线程量；Web 进程退出时任务丢失；路由承担执行策略 |
| `run_report_task` 接收整份可变请求字典 | 无法由队列仅凭 task ID 恢复；调用方与执行器共享数据形状 |
| `llm_tasks` 以 `(business_type, business_key)` 为主键并 upsert | 新执行覆盖旧执行行；没有追加式 execution 事实 |
| `create_report_task` 无活动状态原子检查 | 两个并发请求都可能受理，且后一次覆盖前一次 execution ID |
| 进度、结果和 callback 更新只按 `reportId` | 旧线程可写入新任务投影，破坏 latest-wins |
| `get_task_by_execution_id` 仍从最新投影表读取 | 同业务键创建新执行后，旧执行输入无法再按 ID 恢复 |
| 报告 Service 直接创建旧 `AnythingLLMClient` 和读取全局配置 | 业务层依赖供应商与运行环境，难以测试和替换 |
| 旧 Client/RAG 流程没有由报告执行器显式关闭任务级 Transport，workspace/thread/上传文档清理也不完整 | 长时间运行可能泄漏连接或外部临时资源，失败后遗留现场不可追踪 |
| RAG 返回 `None`/空字符串时仍会被包装为空 HTML 并按成功回调 | 当前行为可能是旧缺陷，也可能是允许的空报告语义；接口文档没有给出判定依据，1C 开工前必须确认 |
| 文件名包含 reportId/index，缺少 task 级命名空间 | 同业务键重跑、崩溃清理和并发下载容易相互覆盖 |
| callback Client 把所有 RequestException 折叠成 `False` | 无法区分明确未送达、非 2xx 和发送后结果未知 |
| 当前 limiter 只限制实际执行，不限制等待线程数量 | 大量积压时可能创建大量阻塞线程，内存与调度不可控 |

### 2.3 当前行为必须保留的部分

- `businessType` 必须为 `report`。
- `params` 仍必须是非空数组，并保持“过滤非对象元素后取第一个对象”的现有解析顺序；
  1C 不借重构之机改成“出现任意非对象元素即整次拒绝”。后者只适用于已经确认的
  `/llm/check-task` 契约，不能自动扩展到报告接口。
- `reportId` 仍接受 JSON 整数或十进制整数字符串，不设业务数值范围并按整数值规范化。
- `filePathList` 必须为非空数组，`templateOutline` 必须为非空字符串。
- MHTML/MHT 规范化失败时继续回退到原下载文件。
- Word 模板提取不到有效文字时任务失败，不调用 RAG。
- 报告纯文本结果仍由既有 HTML 规则包装。
- 成功回调 `status="1"`、`msg="生成成功"`；失败回调 `status="2"`、`details=""`、
  `msg="生成失败"`。
- Progress 仍使用 `businessType="report"`、既有 `reportId` 和 0～1 `progress`，不新增字段。

## 3. 已确认契约和停止条件

### 3.1 请求与响应

| 场景 | 目标行为 |
| --- | --- |
| 合法且可靠受理 | HTTP 202，响应体零字节；不公开内部 task ID |
| 同 reportId 最新任务公开状态为 `0` | HTTP 409，`{"error":"任务正在处理中"}` |
| 同 reportId callback 为 `delivery_outcome_unknown` | HTTP 409，复用同一既有错误体，直至内部人工解除 |
| 旧 callback 正在发送 | 新提交最多等待当前 callback timeout；期间释放则继续受理，超时仍占用则返回同一 409 |
| 参数错误 | 保持接口文档既有 HTTP 400 和错误文本 |
| 持久化受理失败 | 不得返回 202；保持既有单字段服务端错误边界，不新增公开字段 |

### 3.2 202 的准确含义

阶段 1C 当前开发适配下，202 表示：

1. execution ID 和规范化请求快照已在 SQLite 事务中提交；
2. 最新 report 投影已指向该 execution ID；
3. 本地数据库扫描执行器能够发现 accepted 任务；
4. 不表示源文件已下载、输入字节已冻结、RAG 已开始、报告已生成或 callback 已完成。

阶段 4 以后，202 还必须表示任务事实与 Outbox 同事务提交。1C 不得提前声称这项能力。

### 3.3 必须立即停止并确认

- 实现需要改变任一请求字段、字段类型、必填性或回调字段。
- 需要为 stale、cancelled、outcome unknown 增加新的公开报告状态。
- 不能复用既有 409 错误体，需要新增错误字段或新状态码。
- 多文档 RAG 迁移无法保持当前 Prompt、上传顺序或最终 HTML/回调。
- 可靠受理无法在不启动无界线程/内存队列的前提下完成。
- Callback Guard 无法在不改变公开参数的前提下实施已确认的 unknown 冻结语义。
- 需要把 RAG `None`/空字符串从当前“空 HTML 成功”改为失败，但尚未取得明确确认。
- 需要把报告顶层非对象 JSON、`params` 混入非对象元素或 `filePathList` 元素类型的现有处理
  改得更严格；这些都属于公开参数错误语义，必须先确认并同步接口文档。
- 发现本轮必须迁移真实历史数据或必须启动外部后台服务才能继续。

## 4. 目标模块和依赖方向

```text
Flask Report Adapter
  → SubmitReportTask
      → Report Domain
      → Task Submission/Unit of Work Port
      → Progress Publisher Port
      → ReportTaskDispatcher Port
  → Report Presenter

Local Report Worker Adapter
  → RunReportTask(task_id)
      → Task Execution/Input Port
      → SourceFile Port
      → ArtifactStore Port
      → TemplateExtractor Port
      → ReportRag Port
      → CallbackDelivery/Guard Port
      → Progress Publisher Port
```

依赖规则：

- `report/domain` 只依赖 Python 标准库和本模块纯类型。
- `report/application` 只依赖 report domain、report ports 和 tasks 对外 Port。
- report application 不导入 Flask、SQLAlchemy、sqlite3、requests、Celery、AnythingLLM 或旧 Service。
- Adapter 可以依赖遗留实现，但必须把供应商/数据库异常映射为稳定内部错误。
- Flask Adapter 不访问 SQLite、不创建线程、不执行下载/RAG/callback。
- tasks 模块拥有通用任务身份与执行事实；report 拥有报告输入规则、Prompt、结果和回调载荷规则。

## 6. 内部契约

### 6.1 ReportId

- Web 边界继续接受 JSON `int` 或十进制整数字符串，拒绝 bool、float 和非十进制字符串。
- 内部业务键使用规范化十进制文本，例如 `"+00132" → "132"`、`"-0002" → "-2"`。
- 公开回调和 Progress 中继续输出既有 JSON number；不得把内部规范化字符串泄露为新类型。
- 范围不限意味着阶段 3 MySQL 不能用 `BIGINT` 作为唯一业务表示；Repository 使用文本键。

### 6.2 不可变报告输入

```text
ReportInputSnapshot
├── schema_version
├── task_id
├── report_id_key          # 规范化内部文本
├── public_report_id       # 公开 JSON number 所需值
├── source_urls[]          # 保持请求顺序和重复语义
├── template_outline_url
├── template_desc
├── requirement
├── accepted_at
└── trace_id
```

请求快照在 202 前持久化，但源文件字节在 Worker 执行时下载。URL 在排队期间内容变化、失效
或权限变化时，本次执行使用执行时结果；下载失败按既有报告失败语义收敛。

### 6.3 任务命令 Port

概念签名如下，实际命名可在保持语义的前提下调整：

```python
class TaskCommandPort(Protocol):
    def create_report_if_allowed(self, submission: ReportSubmission) -> TaskSnapshot: ...
    def get_execution(self, task_id: TaskId) -> TaskExecutionSnapshot | None: ...
    def claim(self, task_id: TaskId) -> ClaimResult: ...
    def update_progress_if_current(self, update: ExpectedProgressUpdate) -> bool: ...
    def finish_if_current(self, completion: ExpectedTaskCompletion) -> bool: ...
    def is_latest(self, task_id: TaskId, business_ref: TaskBusinessRef) -> bool: ...
    def list_accepted(self, task_type: TaskType, limit: int) -> tuple[TaskId, ...]: ...
```

契约要求：

- 所有写入按 task ID 定位 execution，并按 latest projection owner 条件更新公开投影。
- 返回 `False/stale` 是正常并发结果，Application 必须停止后续公开写和 callback。
- Repository/Adapter 不执行下载、RAG、callback、Progress 通知或线程创建。
- 一次业务事务由 Unit of Work 统一提交/回滚，Repository 方法不得私自 commit。

### 6.4 多文档 Report RAG Port

```text
ReportRagRequest
├── task_id
├── ordered_source_files[]
├── prompt
├── context_name
└── conversation_name

ReportRagResult
├── raw_content
├── execution_trace
└── cleanup_reference
```

报告是多文档一次生成，不能强行套用当前单文档 `DocumentRagSession.analyse(file_path)` 并
改变上传/查询语义。Report Port 由 report 业务表达“按顺序准备多文档并生成一次报告”，
AnythingLLM Adapter 再复用现有 Client/Gateway 原子能力。

RAG Adapter 必须返回完整 `execution_trace` 和仍待处置的外部资源引用；打开 Session 的部分
成功、上传失败、查询失败和清理失败均不能只抛一个丢失现场的普通字符串异常。报告模块沿用
AnythingLLM 总计划中的审计硬门禁：完整 trace 原子落库成功之前，不得写任务成功、发布成功
Progress 或发送成功 callback。

### 6.5 交互审计 Port

```python
class ReportInteractionAuditPort(Protocol):
    def persist_trace(self, command: PersistReportRagTrace) -> AuditReceipt: ...
```

约束如下：

- `PersistReportRagTrace` 使用 execution ID 生成幂等键，并携带最终调用以及完整 attempts、
  lifecycle events 和 trace 摘要。
- 主交互、attempts 和初始 lifecycle events 必须由一个原子入口提交；只拿到主记录 ID 不代表
  审计成功。
- 审计失败时任务进入失败语义，禁止成功 callback，并保留 Context、Conversation、全局文档
  和本地 Artifact 现场；不得先清理再尝试补审计。
- 审计成功后才允许按结果执行资源清理；close 新产生的 lifecycle/cleanup 事件以幂等追加方式
  写入。
- Port 不暴露 SQLAlchemy Session、SQLite connection 或 AnythingLLM 的供应商字段。

### 6.6 Callback outcome

内部至少区分：

| Outcome | 含义 | 自动重试 | 新提交 |
| --- | --- | --- | --- |
| `success` | 收到 2xx | 否 | 允许 |
| `rejected` | 收到非 2xx | 否，进入人工/DLQ | 允许；不会再有迟到 2xx |
| `definitely_not_sent` | 能确认请求未送达 | 阶段 5 可有限重试；1C 不新增后台重试 | 当前发送权释放后允许 |
| `delivery_outcome_unknown` | 请求可能已送达，但响应丢失/读取超时/连接中断 | 否 | HTTP 409 冻结，人工解除后才允许 |
| `skipped` | 未配置 callback URL | 否 | 允许 |
| `stale` | 外发前发现已不是最新 task ID | 否且禁止网络调用 | 新任务已拥有业务键 |

`delivery_outcome_unknown` 是内部结果，不新增公开 callback 状态。旧 check-task 生产路由在
阶段 1C 仍不切换；可靠 recovery command/Worker 到阶段 4～6 才接管。

### 6.7 待确认：空 RAG 结果

当前 `run_anythingllm_rag` 返回 `None` 或空字符串时，旧实现会调用
`ensure_report_html("")`，得到空 `<pre>` HTML，并发送 `status="1"` 成功回调。目标行为
尚不能从接口文档确定，因此 1C 在确认前必须保持当前黄金样例，不得自行改成 `status="2"`。

开工前需要负责人在以下两种语义中明确选择：

1. 空内容仍算成功：保留当前行为，但增加日志/指标以识别空报告；或
2. 空内容算生成失败：返回既有失败 callback 载荷，不增加字段，但属于公开结果变化，需
   同步接口文档和黄金契约。

## 7. 兼容 SQLite 数据设计

阶段 1C 需要解决旧行覆盖和按 task ID 恢复，不能只给现有 `llm_tasks` 增加几个方法。
建议以增量表保存最小追加事实，同时保留旧表作为现有查询/Progress 的最新投影：

### 7.1 `llm_task_executions`

| 字段 | 语义 |
| --- | --- |
| `execution_id` PK | 一次不可变执行身份 |
| `business_type/business_key` | report 和规范化 reportId 文本 |
| `input_schema_version/input_payload` | 202 前提交的不可变请求快照 |
| `execution_state` | accepted/running/succeeded/failed/stale |
| `progress/message/result_payload` | 本 execution 的内部事实，不因新提交被删除 |
| `callback_status/callback_outcome` | 回调兼容状态与精确内部 outcome |
| `created_at/started_at/completed_at/updated_at` | 排序、耗时和恢复审计 |

索引至少覆盖 `(business_type, execution_state, created_at, execution_id)` 和
`(business_type, business_key, created_at)`。阶段 3 使用 Alembic 重新建立 MySQL Schema；
本表不是生产迁移脚本的替代品。

### 7.2 `llm_tasks` 最新投影

- 继续服务现有 check-task、Progress 和其他尚未迁移业务。
- 增加/复用 `execution_id` 作为最新投影 owner。
- Report 公开写入使用 `WHERE business_type='report' AND business_key=? AND execution_id=?`。
- 创建新 report execution 时，在同一事务插入 execution 并更新投影。
- 旧 execution 终态/进度只能更新自己的 execution 行；若不再拥有投影，不能更新公开行。

### 7.3 `callback_delivery_guards`

| 字段 | 语义 |
| --- | --- |
| `business_type/business_key` PK | 同一业务键唯一 Guard |
| `owner_execution_id` | 当前取得发送权的 task ID |
| `state` | idle/sending/outcome_unknown |
| `lease_started_at/deadline_at` | 新提交等待边界和超时审计 |
| `last_outcome/error_stage` | 已清洗结果，不保存敏感响应正文 |
| `released_at/released_by/release_reason` | 人工解除审计；普通释放为空操作者 |

SQLite 通过短 `BEGIN IMMEDIATE` 事务串行化同键受理/Guard 变更；网络请求绝不在数据库事务
内执行。多实例最终正确性由阶段 3 MySQL 条件写和阶段 5 Worker Guard 实现。

### 7.4 历史数据

- 当前历史数据仅用于测试，无需把旧 `llm_tasks` 行推导成完整 execution 历史。
- 旧 file/weaponry/check-task 查询继续读取 `llm_tasks`，不能因 report 增量表而中断。
- 新测试使用空库初始化；Schema 创建必须幂等。
- 不删除、不重命名旧表或列，回滚时允许保留未使用的增量表。

## 8. 原子受理和并发规则

### 8.1 受理事务

```text
SubmitReportTask.handle(command)
  1. 使用 callback Guard 查询同键状态
     - sending：事务外等待并重查，最长 callback timeout
     - outcome_unknown：冲突
  2. 开启短写事务
  3. 再次检查 Guard（防止等待后的竞态）
  4. 读取最新 report 投影
     - status=0：冲突
  5. 生成 execution ID
  6. 插入 llm_task_executions accepted + input snapshot
  7. upsert llm_tasks 最新投影 status=0/owner=execution ID
  8. commit
  9. 发布初始 Progress（带 task ID）
 10. dispatcher.dispatch(task_id) 仅做常量空间唤醒
 11. Presenter 返回 202 空体
```

步骤 3～7 必须同一事务；不能 Web 层“先 get_task 再 create”。初始 Progress 和唤醒发生在
提交后。唤醒失败不删除已提交任务；周期扫描会恢复，必须记录 ERROR 和最老 accepted 年龄。

### 8.2 50 同键并发

- 50 个线程使用 Barrier 同时提交相同 reportId。
- SQLite Adapter 使用独立连接和短写事务；不得共享 Connection/Session。
- 恰好一个返回 accepted，其余全部是相同领域冲突；不允许数据库锁异常泄露为随机 500。
- 数据库只有一个新 execution、一个最新投影 owner、一个初始 Progress owner。
- 任何失败事务不得留下孤儿 execution 或已改变的投影。

### 8.3 旧执行写保护

每次进度、结果、callback 和清理提交都携带 task ID：

```sql
UPDATE llm_tasks
SET ...
WHERE business_type = 'report'
  AND business_key = :report_id
  AND execution_id = :expected_execution_id;
```

rowcount 为 0 时必须记录 stale 并停止公开写；不得回退成只按 reportId 重试。

## 9. 无积压数量上限的本地 Dispatcher

### 9.1 设计

阶段 1C 仍没有 RabbitMQ，但不能继续“每请求一个线程”或把积压放入
`ThreadPoolExecutor` 的无界内存队列。兼容 Adapter 使用：

- 数据库 `llm_task_executions.execution_state='accepted'` 作为待处理事实；
- 一个固定 Report Worker（当前 AnythingLLM 上传安全基线仍为并发 1）；
- 一个 `threading.Event` 或等价常量空间 wake signal，不保存 task 列表；
- 周期按 `created_at, execution_id` 扫描 accepted 任务；
- 条件 `accepted → running` 领取，rowcount=1 才执行；
- 每次完成/异常后继续扫描，直到当前积压排空。

`dispatch(task_id)` 只校验 task ID 并设置 wake signal。重复唤醒可以合并，唤醒丢失由周期
扫描兜底。因此积压数量增长只增加 SQLite 行，不增加等待线程或 Python Queue 元素。

### 9.2 能力边界

- 当前只支持一个应用实例；组合根必须声明并校验 `single_instance`。
- accepted 任务可在进程重启后由扫描发现。
- running 任务在进程崩溃后的 lease/reaper 恢复仍属于阶段 2；1C 不冒充完整可靠队列。
- callback check-task 不使用本 Dispatcher，继续等待 MySQL Outbox + RabbitMQ Worker。
- 不配置业务 backlog 上限或正常积压 503；基础设施无法可靠写入时不得返回 202。

### 9.3 生命周期

- Dispatcher 在 Bootstrap 中创建、显式 `start()` 一次，并提供幂等 `stop()/close()`。
- 单元测试默认注入 Fake/Manual Dispatcher，不启动真实后台线程。
- 进程退出时停止领取新任务，有限等待当前函数返回并记录未完成 execution ID。
- 不使用 `run.py` 测试生命周期；通过直接构造 Bootstrap/Dispatcher 完成离线验证。

## 10. RunReportTask 执行步骤

### 10.1 主路径

1. 按 task ID 读取 execution 和输入快照，校验类型为 report。
2. 条件领取 `accepted → running`；重复派发、终态或 stale 直接幂等返回。
3. 创建 `runtime/tasks/{task_id}/` 任务级目录和 Artifact 上下文。
4. 按 `source_urls` 顺序在执行时下载源文件；文件名使用 task ID + sequence，不能只用 reportId。
5. 调用规范化 Port；保持 MHTML 规范化异常回退原文件的既有行为，并记录 warning。
6. 下载 Word 模板，提取文字；空文字抛出稳定输入错误，不调用 RAG。
7. 使用提取文字替换内部 Prompt 输入中的 templateOutline；不改变原始持久化快照。
8. 构建与当前等价的报告 Prompt；完整 Prompt 不写普通日志。
9. 通过任务级 `ReportRagPort` 上传有序文档并生成一次报告，取得完整 trace 和外部资源引用。
10. 通过 Audit Port 原子持久化交互、attempts 和初始 lifecycle events；审计失败立即阻断成功路径并保留现场。
11. 使用纯规则生成 HTML 和既有成功 callback payload。
12. 先条件提交 execution 结果和最新公开投影；若 stale，停止 Progress/callback。
13. 发布 task ID 归属的最终 Progress。
14. 获取 callback Guard；获取前再次检查 latest。stale 时禁止网络调用。
15. 保存不可变 callback payload，执行 HTTP 投递并持久化精确 outcome。
16. 根据 outcome 释放 Guard 或进入 outcome_unknown 冻结。
17. 审计已经成功后，清理可安全删除的 scratch 和临时 RAG 资源；清理失败写 cleanup pending/audit，不反向改写业务成功。

### 10.2 失败路径

- 捕获应用已分类错误和未知异常，日志使用 `logger.exception`，不得吞掉类型和 task 上下文。
- 生成既有报告失败 payload，并按 expected task ID 条件提交 status=2。
- RAG/业务失败也要先尝试持久化失败 trace；审计成功后才能清理未转交的外部资源。
- 审计本身失败时禁止调用正常 close/cleanup，保留外部资源和 Artifact 现场并记录 critical 日志。
- 如果失败提交发现 stale，不更新最新公开投影，也不发送旧失败 callback。
- 只有失败结果成功成为最新事实后，才发布最终 Progress 和尝试失败 callback。
- 清理/审计失败与业务失败分维度保存，不允许一个异常覆盖前一个更重要的失败事实。

## 11. Callback Guard 时序

### 11.1 新任务先提交

```text
new Submit commit(owner=new task)
old task tries acquire callback Guard
  → latest task ID mismatch
  → record stale/skipped
  → no HTTP request
```

### 11.2 旧 callback 先取得发送权

```text
old callback Guard = sending
new Submit sees sending
  → transaction outside wait/poll, no DB lock held
  → callback completes with known outcome: continue submit
  → still sending at deadline: HTTP 409
```

最大等待使用当前 callback timeout；不能无限阻塞 Web 请求。等待过程记录耗时但不输出新字段。

### 11.3 结果未知

```text
old HTTP request may have arrived
response timeout/lost
  → Guard = outcome_unknown
  → no automatic retry
  → subsequent same-key submit = HTTP 409
  → internal operator reviews and explicitly releases
```

人工解除不通过新前端参数或公开路由实现。阶段 1C 先提供 Application/Repository 能力和
测试入口；阶段 5/11 再提供受控运维命令、权限、审计和 Runbook。

## 12. 文件、Artifact 与保留语义

### 12.1 任务级命名空间

```text
runtime/tasks/{task_id}/
├── input/
│   ├── source-0001{suffix}
│   └── template{suffix}
├── normalized/
├── rag/
├── output/
│   └── report.html
└── quarantine/
```

对象 key/路径不得使用未清洗 URL 或只使用 reportId。日志记录 task ID、对象类别、大小和
校验值，不记录带凭据的完整 URL、Authorization、文件正文或完整 Prompt。

### 12.2 当前本地 Adapter

- 下载目标必须位于已解析的 task root 内，禁止路径穿越。
- 写入采用临时文件 + 原子替换，避免把半文件当作有效输入。
- 产物持久化成功后返回不透明 ArtifactRef；Application 不拼接真实路径。
- 1C 不新增 URL host 安全校验，继续使用当前受控离线 URL 和既有超时行为。

### 12.3 保留期暂不确定

- 持久输入引用、最终报告、callback payload 和审计元数据不启用自动过期。
- 只有任务终态且无执行/回调/恢复引用后才可产生删除资格。
- scratch 仅在输入/结果已持久化、数据库提交已确认且没有调用方使用时清理。
- 崩溃、提交不明或清理异常进入 quarantine/cleanup pending，不直接递归删除。
- 阶段 3 MinIO Adapter 复用相同 ArtifactRef 和 retention class；具体天数后置确认。

## 13. 失败矩阵

| 失败点 | 对外/任务结果 | 持久化与补偿 | 重试 |
| --- | --- | --- | --- |
| 请求参数错误 | HTTP 400 既有错误 | 不创建 execution | 不重试 |
| 活动 task/unknown Guard | HTTP 409 既有错误 | 不创建 execution、不发 Progress | 人工解除 unknown 后可重提 |
| 受理事务失败 | 不返回 202 | 整体回滚，无孤儿 execution | 调用方可重提 |
| commit 后唤醒失败 | HTTP 202 | accepted 事实保留，ERROR 告警，周期扫描恢复 | 自动扫描 |
| 下载失败/URL 失效 | task status=2 | 失败 payload 条件提交，清理已下载文件 | 1C 不自动重跑整个任务 |
| MHTML 规范化失败 | 继续执行 | warning，回退原文件 | 无 |
| 模板提取为空 | task status=2 | 不调用 RAG | 无 |
| RAG 部分资源创建失败 | task status=2 | Adapter 补偿并保存 trace/cleanup pending | 遵循既有 RAG 策略 |
| RAG/业务失败 trace 审计成功 | task status=2 | 保存完整失败证据后清理未转交资源 | 无业务重试 |
| 交互审计失败 | task status=2；禁止成功 callback | 保留 Context/Conversation/全局文档和 Artifact，critical 告警 | 仅对短暂数据库锁有限重试 |
| 结果条件写 stale | 不改变最新公开状态 | 旧 execution 标记 stale，禁止 callback | 不重试公开写 |
| callback 2xx | 业务状态不变 | success + attempt 审计，释放 Guard | 无 |
| callback 非 2xx | 业务状态不变 | rejected/failed + 审计，释放 Guard | 不自动重试 |
| callback 明确未送达 | 业务状态不变 | definitely_not_sent/failed，释放 Guard | 1C 不新增自动重试；阶段 5 有限重试 |
| callback 发送后结果未知 | 业务状态不变 | outcome_unknown，Guard 冻结 | 不自动重试，人工处理 |
| cleanup 失败 | 不反向改写业务终态 | cleanup pending/quarantine + 告警 | 后续 cleanup Worker |
| Worker 进程崩溃 | accepted 可恢复；running 可能滞留 | 阶段 2 lease/reaper 处理 | 1C 明确能力限制 |

## 14. 日志和指标

### 14.1 日志字段

所有报告应用/执行日志至少包含：

- `trace_id`
- `task_id/execution_id`（仅内部）
- 规范化 `report_id` 业务键
- `task_type=report_generation`
- `step`
- `execution_state`
- `artifact_type`（涉及文件时）
- `callback_outcome/error_stage`（涉及回调时）
- `duration_ms`

普通日志不得记录完整请求、带 query/credential 的 URL、文件正文、完整 Prompt、完整模型
响应、Authorization 或密钥。错误信息进入数据库前也必须清洗。

### 14.2 指标

- report 受理总数、202/400/409/500 分类。
- 活动冲突、callback sending 等待、unknown 冻结冲突数量和等待时长。
- accepted/running/terminal 数量、最老 accepted 年龄、每分钟排空数。
- 下载/模板/RAG/产物/callback 各步骤耗时和失败分类。
- 交互审计成功/失败、有限重试、trace 完整性和待恢复资源数量。
- stale 条件写拒绝数量；大于 0 必须可追踪到 task ID。
- callback success/rejected/definitely_not_sent/outcome_unknown。
- scratch/quarantine/cleanup pending 数量和最老年龄。
- Dispatcher wake 合并、扫描轮次、领取冲突和停止超时。

## 17. 灰度与回滚

阶段 1C 仍是开发分支改造，不进入生产。路由切换时仍需保持可回滚：

1. 新旧实现通过组合根绑定切换，不在同一请求中双写、双执行或双 callback。
2. 增量 SQLite 表只新增不删除；回滚旧绑定时可以保留，无需破坏性降级。
3. 旧 `report_service.py` 在 1C 观察期保留，但新路由不能同时调用它。
4. 若新 Dispatcher/执行器需回滚，先停止 report 新受理，列出 accepted/running execution，
   排空或明确处置后再切旧路径；禁止让旧线程重复执行已被新路径领取的任务。
5. 202 空体和已确认 409 属于目标接口契约，不因内部实现回滚恢复成旧成功 JSON。
6. 任何无法安全排空的任务保留 execution/input/Artifact/Guard 审计，不删除现场。
