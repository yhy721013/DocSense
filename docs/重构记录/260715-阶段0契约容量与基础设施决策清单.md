## 1. 当前已核实基线

以下内容已经能够从当前代码、README 和更新记录中确认：

- Web 入口当前为 Flask，正式 LLM 路由集中在 `app/blueprints/llm.py`。
- analysis、report、weaponry 当前仍由进程内 daemon thread 执行；Web 进程退出会中断执行。
- file/report 共用上传类并发限制，AnythingLLM Document Processor 当前安全基线为并发 1。
- 任务、知识库映射、文件对话分别使用三个 SQLite 文件。
- 文件对话当前只允许 `single_instance`，没有事务 Outbox、可靠队列、跨实例通知或 fencing。
- `/llm/check-task` 不只是查询：它会对满足条件的终态任务补发回调，并返回 `callbackReplayed`。
- 未配置 `CALLBACK_URL` 时，已完成且仍为 `pending` 的任务会被幂等标记为 `skipped`；以后再配置 URL 也不会由 check-task 自动补发。
- `/llm/progress` 当前支持 legacy subscribe，以及显式 subscribe/query/unsubscribe；显式 action 会收到 ack。
- `/debug/*` 始终注册，`APP_DEBUG=false` 不会自动关闭，生产环境必须在网络或反向代理层限制。
- 目标生产环境已确认为单台物理服务器；MySQL、RabbitMQ、Redis、MinIO 与应用组件最终使用 Docker Compose 部署。完整计划实施前，开发阶段继续使用当前环境，不提前切换基础设施。

### 2.1 2026-07-15 决策纪要

- 单服务器是已知约束，因此首期只承诺进程隔离、可靠重启、数据可恢复和多应用实例验证，不宣称基础设施节点级高可用。
- “50 并发”不等于 50 个 AnythingLLM/模型重任务同时执行。重任务必须进入独立队列并受资源配额、速率和下游容量限制。
- SQLite 仅保存测试数据，不做历史行迁移；仍需用测试证明 MySQL 新 Schema 能表达全部现有业务状态和查询。
- MinIO 是目标唯一共享产物存储；当前本地目录通过 `ArtifactStorePort` 兼容，直至相应阶段切换。
- report 活动任务的判定沿用公开状态：`status="0"` 表示生成中；同一 `reportId` 再提交时返回 HTTP 409 和既有单字段错误体，不创建线程或新任务。
- Docker Compose 只描述最终生产编排方向，不授权当前开发阶段启动或接入这些基础设施。

### 2.2 D0-06：回调幂等约束与保守投递策略

可靠回调采用“至少一次尝试”时，会出现以下无法仅靠发送方判断的情况：

1. DocSense 向业务系统发送报告成功回调。
2. 业务系统已经按 `reportId` 保存结果并触发后续处理。
3. 业务系统返回的 HTTP 2xx 在网络中丢失，或发送方等待响应超时。
4. DocSense 只能看到“超时”，无法知道对方是否已经处理；若自动重试，对方可能收到完全相同的第二次回调。

现有回调不能新增 delivery ID，因此接收方需要基于既有字段实现幂等：file 可使用 `businessType + fileName + status`，report 可使用 `businessType + reportId + status`，weaponry 可使用 `businessType + architectureId + status`。如果接收方是按业务键执行 upsert，重复载荷只覆盖同一结果，通常安全；如果每次回调都会新增记录、重复通知或再次触发下游任务，则不安全。

接收方无法确认上述能力，因此后续实现不得假定重复投递安全，也不得依赖接收方结果查询。采用以下保守策略：

- 每次投递都按内部 task ID 持久化 attempt、开始/结束时间、错误分类、HTTP 状态和脱敏响应摘要；不向公开回调增加 delivery ID。
- 只有能确定 HTTP 请求尚未送达的错误才允许有限自动重试，例如 DNS 解析失败、建立连接前超时或连接被拒绝；重试必须有指数退避、次数上限和告警。
- 请求可能已经发出后发生的读取超时、连接中断或响应丢失，内部标记为 `delivery_outcome_unknown`，不由 callback Worker 自动重试。
- 接收到非 2xx 响应时记录为明确失败并进入人工/死信处理，不在未知幂等前提下自动重复发送。
- `/llm/check-task` 当前是已有的显式恢复入口，仍按公开契约允许调用方触发一次补发；这类补发必须记录 `trigger=check_task` 和重复副作用风险，不能被后台循环再次放大。
- 公开 `callbackStatus` 继续使用现有 `pending/success/failed/skipped`，内部 `delivery_outcome_unknown` 不新增公开状态；未收到 2xx 时兼容映射为 `failed`，业务任务自身的成功/失败状态不受影响。

## 3. 阶段 0 的执行分解

### 0A：接口契约资产化

**目标**

把接口文档和当前代码的可观察行为转成自动化契约资产。

**工作内容**

1. 建立正式接口清单、路由方法和协议类型。
2. 为每个接口记录合法请求、边界请求、非法请求、状态码、JSON 类型和错误文本。
3. 对 `/llm/progress` 记录 legacy/显式 action、批量顺序、快照、ack 和关闭行为。
4. 对 `/llm/chat` 记录响应头、SSE 行格式、事件顺序、终态和断连行为。
5. 对 `/llm/check-task` 记录回调补发、`skipped`、单项/批量和缺失任务差异。
6. 对出站回调保存脱敏黄金载荷和字段类型。
7. Debug 接口单独建立“非生产协议”清单，不混入甲方正式接口。

**产物**

- 接口契约矩阵。
- JSON/SSE/WebSocket/Callback 黄金样例。
- 路由测试与 Presenter 测试清单。
- 接口文档与代码差异清单；发现差异先停止并确认，不直接修改接口文档。

### 0B：当前单实例性能基线

**目标**

记录改造前真实瓶颈，避免仅比较框架名称。

**采集范围**

- 短请求吞吐、P50/P95/P99、错误率。
- 活跃 WebSocket/SSE 数量、连接建立和释放时间。
- file/report/weaponry 的排队、运行和总耗时。
- SQLite 锁等待、失败和慢操作。
- 线程数、内存、CPU、文件句柄、临时磁盘增长。
- AnythingLLM 429/5xx/超时、Document Processor 失败和上传等待。
- 回调耗时、成功率和 check-task 补发次数。

本步骤需要真实后台服务时必须另行取得授权；在授权前只建立脚本、数据集和采集定义，不执行 `run.py`。

### 0C：目标容量与 SLO 决议

以下分层并发范围已经确认；成功率、P95/P99、最大排队时间等数值 SLO 在取得当前基线后再评审确定：

| 维度 | 已确认验收范围 | 仍需确认 |
| --- | --- | --- |
| 短请求 | 100 并发测试，50 并发稳定基线 | 请求混合、延迟阈值、成功率 |
| 长连接 | 50 条同时在线 SSE；WebSocket 按现有接口补测 | 连接持续时间、消息频率、断连率 |
| 在途任务 | 50 个 accepted/queued/running 混合任务 | 各业务比例和最大队列等待 |
| AnythingLLM 摄取 | 初始并发 1，压测后尝试 2、4 | 提升门槛、错误率和数据完整性阈值 |
| 重任务 | 按模型/GPU/AnythingLLM 实测限流 | 是否要求 50 个同时执行 |

正式 SLO 至少写明：成功率、P95/P99、最大队列等待、任务恢复时间、回调最终成功时间和允许积压。

### 0D：基础设施与部署能力确认

每个目标组件必须确认：

- 部署位置、版本、CPU/内存/磁盘、端口和网络路径。
- 生产账号、最小权限、密钥保存和轮换方式。
- 备份、恢复、监控、日志、升级和责任人。
- 单机故障边界；同机多实例不宣称基础设施高可用。
- 测试环境与生产环境隔离方式。
- Web、Worker、Relay、Scheduler 的进程数量和优雅退出要求。

目标生产已确认为单服务器，首期目标是进程级隔离、可靠重启和可恢复，不虚构 RabbitMQ/Redis/MySQL 多节点高可用。

### 0E：数据与产物基线

在阶段 3 设计迁移前完成：

- 三套 SQLite 的表、行数、索引、触发器、Schema 版本和文件大小盘点。
- 非法历史状态、孤儿引用、重复业务键和缺失文件统计。
- 任务、交互审计、知识库映射、chat 消息、租约、清理任务的保留要求。
- 下载缓存、OCR/MinerU 缓存、回调历史和报告产物的保留/清理要求。
- SQLite 备份、JSON 导出和恢复抽样验证。

已确认当前 SQLite 历史数据仅用于测试，可以清空且无需迁移。阶段 3 仍必须保留 Schema 映射、种子数据和切换验证，不能因无历史数据而跳过数据库一致性测试。

### 0F：安全基线

至少确认：

- 文件下载 URL 的协议、域名/IP 白名单、DNS 重绑定防护、重定向、大小和超时。
- Callback URL 的来源、允许网段、认证、TLS 和重定向。
- Debug 路由在反向代理/防火墙层的拒绝规则。
- 上传文件扩展名、MIME、恶意文件扫描和解压/路径穿越防护。
- 临时目录和对象存储 key 的任务隔离。
- 日志中密钥、Authorization、文件正文、Prompt 和回调正文的脱敏。
- MySQL/RabbitMQ/Redis/MinIO/AnythingLLM 使用独立最小权限账号。

“离线网络”不等于 URL 天然可信。目标实现应使用环境配置维护允许的协议、主机/IP 和端口，开发环境可单独允许已登记的 localhost/测试地址；每次重定向后重新校验目标。该策略不增加接口参数，但 D0-11 仍需补充实际服务器清单。
