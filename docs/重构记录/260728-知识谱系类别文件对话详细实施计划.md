## 1. 目标与非目标

### 1.1 必须实现的目标

1. 在既有 `/llm/chat` 中增加与 `fileNames` 互斥的 `architectureId` 范围选择模式，不创建第二套
   聊天路由、SSE Presenter、历史服务或供应商会话链。
2. architecture 模式首轮只读取该 ID 的直接文件，在受理时冻结有序文档身份，并创建唯一、
   不可变的 Active Scope Revision。
3. architecture 模式后续每轮仍要求前端携带同一规范化 ID，但后端只复用旧 Scope Head，不重新
   查询类别目录，不自动吸收后来新增、删除、重新解析或重新分类的文件。
4. 一个 `chatId` 首次成功受理后永久绑定范围模式；architecture 模式还永久绑定规范化 ID。
5. 保持 fileNames 模式的全部现有行为、错误、历史 `files`、SSE 事件和 Scope 状态机不变。
6. architecture 模式 history 的 user 消息只返回 JSON number `architectureId`，不返回 `files`；
   assistant 消息不返回二者。
7. 将请求选择、会话绑定、Scope、run input 和 user message 形成可审计、可恢复、失败关闭的
   SQLite 权威事实，为未来可靠队列和多实例 Repository 迁移保留清晰边界。

### 1.2 本次明确不做

1. 不新增 `/llm/architecture-chat` 等平行接口。
2. 不把父类别扩展为子孙类别集合，只做精确 ID 的直接文件查询。
3. 不提供主动刷新类别快照；需要刷新时由前端使用新 `chatId`。
4. 不复制或版本化文件正文；只冻结成员和供应商无关文档引用。
5. 不改变标题、终止、删除、SSE 断线和资源清理的公开合同。
6. 不新增租户、用户或权限体系；沿用当前单一可信业务域边界。
7. 不以 Workspace 当前绑定、远端目录或历史消息反推 architecture 范围。
8. 不在本阶段宣称 SQLite 多实例安全、可靠任务队列或生产高并发已经完成。

## 2. 已确认的业务合同

### 2.1 请求选择器

`params` 必须形成严格的二选一选择器：

```text
ChatScopeSelector
├── FilesSelector
│   └── file_names: tuple[str, ...]       # 保持现状，可为空
└── ArchitectureSelector
    └── architecture_id: int              # 已规范化，1..INT64_MAX
```

- `architectureId` 与 `fileNames` 同时出现时返回 HTTP 400；字段存在性而非 truthy 值决定冲突，
  所以 `architectureId + fileNames=[]` 也必须拒绝。
- architecture 模式每一轮都必须传入 ID。
- 公开 ID 规范化复用 `app.adapters.web.normalize_architecture_id`；Chat Domain 和 Application 只接收
  规范后的 `int`，不得依赖 Weaponry Domain。
- `1`、`"1"` 与 `"0001"` 绑定为同一 ID。

### 2.2 会话永久绑定

| 当前会话事实 | 本轮选择器 | 结果 |
| --- | --- | --- |
| 不存在 | architecture X，候选非空且有效 | 创建 architecture 绑定 X，冻结 Revision，受理 run |
| 不存在 | architecture X，类别为空/不存在 | HTTP 404，全部回滚 |
| 不存在 | architecture X，候选损坏/歧义 | HTTP 400，全部回滚 |
| architecture X | architecture X | 不查当前类别，复用原 Head，受理 run |
| architecture X | architecture Y | HTTP 409，不写任何新事实 |
| architecture X | fileNames | HTTP 409，不写任何新事实 |
| files | architecture X | HTTP 409，不写任何新事实 |
| files | fileNames | 完整保持当前状态机 |

同一新 `chatId` 的并发首轮只允许首个成功提交的请求决定模式和绑定 ID。模式绑定一经成功提交
不可更新；删除会话时随会话级联删除，不提供单独“解绑”命令。

### 2.3 快照与历史

1. 首轮 architecture Scope 按 `file_name` 稳定升序冻结直接文件。
2. 每个成员继续保存 `file_name`、`original_name`、`document_ref`、`external_location`。
3. architecture user message 不写 `chat_message_files`，只写规范化 ID；后续 history 不展开成员。
4. run input 必须保存该轮前端确实提交的 `requested_architecture_id`，不能只从 Session Binding
   推导，以保留请求审计事实。
5. Scope Revision 额外保存 `source_architecture_id`，从而区分“范围来源”与“每轮请求选择器”。
6. Worker 仍只凭 `run_id` 加载 Effective Scope，不按 ID 查询当前知识库。

## 4. 目标领域模型

### 4.1 选择器和值对象

建议新增或扩展以下不可变对象：

```text
ChatScopeSelector
├── mode: files | architecture
├── file_names: tuple[str, ...]
└── architecture_id: int | None

ChatSessionScopeBinding
├── chat_id
├── scope_mode: files | architecture
├── architecture_id: int | None
└── created_at

ChatArchitectureCandidates
├── architecture_id
├── resolution_outcome: resolved | not_found | invalid
├── documents: tuple[ChatDocumentCandidate, ...]
└── error_code: str
```

必须由构造器保证：

- files 选择器不携带 ID；architecture 选择器不携带 `file_names`；
- files Binding 的 ID 必须为空；architecture Binding 的 ID 必须是规范正整数；
- `resolved` 必须有至少一个文档；`not_found/invalid` 不携带部分成功文档；
- DTO 深冻结输入容器；严格 Schema 未知版本和字段失败关闭。

### 4.2 为什么候选错误必须延迟到事务裁决

事务外只读探测可能出现以下合法并发：

1. 请求 B 读取时尚未看到 Session Binding；
2. 请求 A 随后创建 architecture X 会话并冻结 Scope；
3. B 此时读取到当前类别为空、损坏或已发生分类调整；
4. B 进入 Chat 受理事务时，会话其实已经存在且应复用 A 的旧快照。

因此 Resolver 不能在所有 architecture 空目录场景下直接抛出 HTTP 404。它应形成有界候选结果，
交由 `BEGIN IMMEDIATE` 内判断：

- `session_created=true`：必须采用并校验候选；`not_found/invalid` 回滚并映射公开错误；
- `session_created=false` 且 Binding 为同一 architecture：忽略当前候选结果，只复用 Head；
- Binding 模式或 ID 不同：返回 409。

禁止为解决该竞态而在 Chat 写事务内访问知识库数据库或 AnythingLLM；两个数据库读取不能伪装成
跨库原子事务。

### 4.3 Scope 状态扩展

新增内部常量：

- Scope Source：`architecture_initial`
- Selection Mode：`architecture_initial`
- Selection Mode：`architecture_reuse`

`architecture_reuse` 不创建 Revision、不切换 Head；它只引用原 architecture Revision。architecture
会话只允许存在一份初始 Scope Revision，除非未来另行确认刷新合同。

## 5. SQLite Schema v5 设计

### 5.1 会话范围绑定表

建议新增：

```sql
CREATE TABLE chat_session_scope_bindings (
    chat_id TEXT PRIMARY KEY,
    scope_mode TEXT NOT NULL
        CHECK (scope_mode IN ('files', 'architecture')),
    architecture_id INTEGER,
    created_at TEXT NOT NULL,
    CHECK (
        (scope_mode = 'files' AND architecture_id IS NULL)
        OR
        (scope_mode = 'architecture'
         AND architecture_id BETWEEN 1 AND 9223372036854775807)
    ),
    FOREIGN KEY(chat_id) REFERENCES chat_sessions(chat_id) ON DELETE CASCADE
);
```

- 增加 `BEFORE UPDATE` 不可变触发器；
- 不提供 Repository 更新方法；
- Schema v4 既有 Session 迁移时全部回填为 `files`；
- Binding 缺失、重复或值不合法时运行时失败关闭，禁止从 Head 猜测并自动修复。

### 5.2 Scope Revision

将 `chat_scope_revisions` 扩展为：

- `source_mode` 允许 `automatic_initial`、`explicit`、`architecture_initial`；
- 新增 `source_architecture_id INTEGER NULL`；
- architecture source 必须携带合法 ID，其他 source 必须为空；
- architecture Revision 的 ID 必须与同 chat 的 immutable Binding 相同。

由于 v4 的 `source_mode` 是表级 CHECK，v5 必须按 SQLite 正式表重建流程迁移，不能只修改 Python
常量。迁移要作为一个事务重建 Revision/Member/Head 依赖集合、恢复索引和触发器，最后执行：

- `PRAGMA foreign_key_check`
- 行数、成员数、Head 引用数前后对账
- v4 既有 Revision 内容逐字段等价检查

### 5.3 Run Input 与 Message

为 `chat_run_inputs` 增加：

```sql
requested_architecture_id INTEGER NULL
```

为 `chat_messages` 增加：

```sql
architecture_id INTEGER NULL
```

约束与触发器要求：

1. `architecture_initial/architecture_reuse`：
   - `requested_files_json='[]'`
   - `requested_architecture_id` 合法且等于 Session Binding
   - `effective_scope_revision_id` 指向同 chat 的 architecture Revision
2. 其他正式 file selection mode：`requested_architecture_id IS NULL`。
3. architecture user message：`architecture_id` 等于 Binding，且不得存在 `chat_message_files`。
4. file user message：`architecture_id IS NULL`，继续允许 `files=[]`。
5. assistant message：`architecture_id IS NULL`，不得写消息文件。
6. 所有字段与 run/message 必须在同一受理事务写入；失败整体回滚。

### 5.4 Repository

新增 `ChatSessionScopeBindingRepository`，并在 `ChatPersistenceStore/ChatStore` 暴露只读/创建能力：

- `get(chat_id)`
- `create_in_transaction(...)`
- `require_for_chat_in_transaction(...)`

禁止公开 `update`。Scope Repository、Run Input Codec、Message Codec 必须严格读取 v5 字段，发现
未知 mode、错 ID、缺 Binding 或历史字段互斥失败时抛出明确内部异常并记录结构化错误。

## 6. 类别文档解析设计

### 6.1 知识目录查询

在 `DatabaseService` 增加按 ID 的只读方法，例如：

```text
list_document_records_by_architecture_id(architecture_id: int) -> list[dict]
```

要求：

- SQL 使用 `WHERE architecture_id = ?`，不在 Application 全表扫描；
- 只匹配直接文件，不展开树；
- `ORDER BY file_name ASC, id ASC`，结果稳定；
- 复用统一 metadata 严格解码；
- 不产生迁移、写入或远端副作用；
- 空列表表示“不存在或没有直接文件”，按已批准合同统一处理。

### 6.2 Resolver

扩展 `ChatDocumentResolver`：

```text
resolve_by_architecture_id(id) -> ChatArchitectureCandidates
```

它必须复用 `_resolve_record` 资格校验，并整体检查：

- 空文件名、原名或供应商无关引用；
- 同类别重复业务名；
- 重复 `document_ref`；
- 重复 `external_location`；
- 部分合法、部分损坏时整体 `invalid`，禁止静默跳过坏记录。

日志只记录规范化 ID、目录记录数、有效数、outcome 和错误代码，不记录文件名、URL 或正文。

## 7. 原子受理顺序

`ChatRunLockService.try_acquire_chat_run()` 的目标顺序：

1. `BEGIN IMMEDIATE`；
2. `INSERT OR IGNORE chat_sessions` 并取得 `session_created`；
3. 读取或创建 `chat_session_scope_bindings`：
   - 新 Session 根据选择器创建 Binding；
   - 既有 Session 先校验模式，再校验 architecture ID；
4. Binding 校验通过后，再处理过期 run 和检查活跃 run；
5. 读取 Scope Head 和 Revision；
6. 分支决策：
   - 新 architecture Session：要求 `resolved` 且非空、数量未超限，创建 Revision/Head；
   - 既有 architecture Session：要求 Head/Revision/Binding 三者一致，忽略当前目录候选；
   - file 模式：执行现有状态机，字节级行为不变；
7. 插入 `chat_runs`；
8. 写入 run input 的 requested selector、Effective Scope、selection mode；
9. 写入 pending user message：architecture ID 或 requested files 二选一；
10. 提交事务；
11. 事务提交后才允许 Dispatcher/同步执行器领取 run。

错误优先级：

- 公开参数校验始终先于任何持久化；
- 既有 Session 的模式/ID 冲突先于活跃流冲突；
- 同模式同 ID 时，活跃 run 返回现有 409；
- 新 Session 的候选空、损坏、超限全部回滚首次 Session 和 Binding。

## 8. 执行、历史与可观测性

### 8.1 执行

- `SynchronousChatRunExecutor` 只从 `ChatRunInput.files` 获得 Effective Scope；
- architecture ID 不传入 AnythingLLM 作为动态目录选择条件；
- Workspace 可以累计绑定历史文档，但模型调用只查询冻结成员；
- 受理后类别变更不重新解析；引用失效按既有 SSE error 失败收敛；
- 重启/恢复仍只接收 `run_id`，不依赖请求内存。

### 8.2 历史

`ChatHistoryService` 按持久化消息选择公开字段：

- file user：保持 `files`，不返回 `architectureId`；
- architecture user：返回 number `architectureId`，不返回 `files`；
- assistant：不返回二者；
- 标题生成只继续消费 role/content，不把 architecture ID 或成员写入 Prompt。

历史不得通过当前类别目录补齐 ID；若 architecture user message 缺 ID，应作为持久化损坏失败关闭，
不能回退成 `files=[]`。

### 8.3 日志与调试

新增结构化字段：

- `scope_mode`
- `requested_architecture_id`
- `bound_architecture_id`
- `architecture_candidate_outcome`
- `selection_mode`
- `session_created`
- `effective_file_count`
- `scope_revision_id`

禁止记录实际文件名、原名、文档 URL、正文、完整请求体或供应商响应。调试页如需展示模式，必须
作为内部诊断事实单独评审，不能借机增加 `/llm/chat*` 的公开字段。

## 13. 风险与停止条件

| 风险 | 防护与停止条件 |
| --- | --- |
| architecture 空目录竞态误判 | 候选 outcome 延迟到事务判断；无法实现则停止，不以事务外 session 猜测代替 |
| Schema v5 表重建丢数据 | v4 fixture 对账、foreign_key_check 未通过立即停止 |
| fileNames 行为被新模式污染 | file 黄金合同任一变化立即停止并回滚该阶段 |
| history 同时返回 files 和 ID | DB 触发器、Domain 和 Presenter 三层拒绝 |
| 类别后续变化动态扩大范围 | Worker 禁止按 architectureId 重查；测试发现重查立即阻断 |
| 跨库原子性误解 | 明确候选读取点与 Chat 提交点；不宣称知识目录和 Chat DB 是同一事务 |
| 真实文档引用失效 | SSE 失败关闭，不自动替换成员，不伪装成功 |
| 多实例并发 | 当前只接受 single_instance；非该模式不得宣称通过 |

任何需要新增其他前端参数、改变 SSE、修改 fileNames 模式、包含子类别、刷新旧快照或展开历史成员
的需求，都必须停止并重新确认接口文档。
