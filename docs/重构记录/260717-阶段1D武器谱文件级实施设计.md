### 0.1 2026-07-18 全面审查后冻结修订

阶段 1D-0～1D-2 全面审查后的七项口径已经确认并写入代码与后续波次门禁：

1. Selected Evidence 不做字符截断，也不设置单条、总量或单文档数量/字符配额；Candidate
   top-N 仍只是向检索供应商请求候选的批次大小，`max_table_rows=100` 只限制结构化答案行数。
2. 请求 TABLE 模板出现重复列名时维持既有“内部采用首次出现列、原始公开模板仍完整保留”
   行为；业务保证不会传入重复列，本阶段不新增接口错误或参数。
3. 宽泛“类型”列不再单独作为 TABLE 行身份。优先使用显式 row key 或名称、型号、编号、
   代号、标识等强身份；否则使用排除“类型”后的带列名复合身份，仅有弱信息时保持独立行。
4. 1D-2 当时的 Schema v1 曾冻结 provider/embedding/reranker、Query、分数与相关性信号、候选
   批次、去重、Extraction Prompt/模型/上下文、TABLE 合并/行数和辅助语境目录策略；该历史开发
   版本已在 1D-3B 被唯一 Schema v2 直接替换，不再存在运行期 Decoder。
5. 约 1500 层等极深 JSON 属于已确认不处理的极端输入，本阶段不增加递归深度防护。
6. `/llm/weaponry`、weaponry check-task/Progress、任务快照、遗留 Worker 和 Callback 共用
   ArchitectureId 纯规范化规则；合法字符串前导零不产生第二个业务键，输出身份统一为数值。
7. 成功结果必须按受理快照完整覆盖字段数量、顺序和定义；TABLE 每个已返回行必须完整覆盖
   冻结列及顺序；领域结果状态还必须与 execution/public terminal 状态一致，校验失败不能进入
   终态 CAS。业务空字段和空 TABLE 数据行仍按既有成功回调语义表达。

上述修订没有新增、删除或重命名任何公开请求、响应或回调参数。ArchitectureId 和 Evidence/
`rows` 语义已经同步接口文档；重复列及极深 JSON 是明确接受的内部边界，不升级为公开承诺。

### 0.2 2026-07-18 检索选择、Schema v2 与文档处理边界修订

本节是当前有效口径；1D-0/1D-0R 中关于固定绝对阈值、独立 reranker、完整 Candidate 级标注、
正式精度目标和“原始 MHTML 阻塞 1D-3B”的内容只保留为历史校准事实，不再作为当前退出门禁：

1. **不建设独立 reranker。** 删除生产策略中的 reranker 分支、指纹、阈值和必需信号；不得用
   另一次模型调用或 Cross-Encoder 作为 1D 上线前置。
2. **不设置绝对相关性阈值。** Candidate 只要通过冻结文档来源、分数或排名协议、正文质量和
   同文档精确去重门禁，就按稳定顺序进入 Selected Evidence；不再要求 anchor 命中，也不因
   分数低而拒绝，不为凑数量引入额外候选。
3. **保留缺失分数的 rank-only 路径。** 供应商声明本批提供分数时，每个分数必须满足冻结的
   类型、有限值、方向和范围协议；声明不提供分数时，必须提供稳定、正整数且批内无冲突的
   provider rank。混合分数模式、非法分数、缺失稳定 rank 或排序身份不完整均属于协议错误，
   不能把非法分数伪装成缺失，也不能静默转为 `0`。
4. **稳定排序不等于精度证明。** 有分数批次按规范分数、provider rank、文档顺序和 Candidate
   稳定身份排序；rank-only 批次按 provider rank、文档顺序和 Candidate 稳定身份排序。同一输入
   和同一 profile 必须得到同序 `rows`，但计划不宣称达到某个准确率、召回率或绝对相关性水平。
5. **保留非相关性正确性门禁。** 空白/过短正文、metadata 主导、参考文献型正文、来源越界、
   文档身份不明和同文档规范化精确重复仍被拒绝；不同文档相同正文仍分别保留。Selected
   Evidence 正文继续完整保留，不设置单条、总量或单文档数量/字符上限。
6. **新增内部输入 Schema v2。** v2 移除 reranker/anchor/绝对阈值字段，以精确键冻结
   `score_protocol=explicit-unit-score-or-stable-rank-v2`、
   `ranking_strategy=score-desc-or-rank-asc-stable-v2`、Candidate 批次、正文处理指纹和去重策略。
   公开 HTTP、Progress、Callback 参数和数据库表结构均不变化。
7. **Schema v2 直接取代 Schema v1。** 当前不存在需要读取的历史 weaponry execution、历史数据
   或旧 Worker，v1 也尚未进入生产，因此不建设 v1/v2 双读、兼容 Decoder、“先 Reader 后 Writer”
   或数据迁移流程。v2 前置波次直接删除 v1 Encoder/Decoder、版本常量、只服务 v1 的策略字段和
   测试夹具，所有新任务与 Worker 只接受 v2。该替换不改变公开接口或数据库表结构；内部影响仅
   是需要在同一波次更新代码和测试。删除前仍须以静态引用扫描、空活动 execution 检查和完整
   回归证明没有实际依赖，避免误删与其他业务同名但无关的 Schema 版本。
8. **production profile 改为运行策略清单。** 它用于冻结 provider/embedding/Query/正文清理/
   去重/排序/Extraction Context 指纹和失败语义，保证 Adapter 兼容、重试确定、审计和回滚；
   它不再代表“经高精度校准”的质量认证，也不要求 Candidate 级完整标注。
9. **质量资产采用放松口径。** 自建少量多文档黄金样例，至少覆盖相似 A/B 文档、字段存在/
   缺失、跨文档干扰、重复 Chunk、空白、metadata 主导和参考文献型正文，只验证来源、协议、
   排序、去重、上下文和重试确定性；不设置正式精度验收指标。
10. **文档处理迁入平级阶段 1H。** 1D 可在明确记录
    `legacy-normalized-artifact-v1` 来源、哈希和处理指纹后使用历史清洗文本实现 Adapter；新的
    原始文件处理、MHTML/MinerU/OCR/Office 转换及其从 `app/services/translator/` 的剥离由 1H
    独立完成。阶段 3 再把 Artifact Store 切到 MinIO。

接口文档已按批准权限同步 `rows` 的分数或排名语义，没有增删或重命名任何字段。

## 1. 目标与非目标

### 1.1 目标

1. 将 `weaponry_service.py` 中的领域规则、应用编排和外部 I/O 拆分为
   `weaponry/domain`、`application`、`ports`、`adapters` 四层。
2. 建立 `SubmitWeaponryTask` 和 `RunWeaponryTask(task_id)`；Worker 只凭内部 TaskId 从
   持久化 execution 快照恢复全部输入，不接收 Flask 请求对象、可变请求字典或路由线程参数。
3. 同一 `architectureId` 的活动任务使用数据库原子受理：最多一个请求成功受理，其他请求
   保持 HTTP 409 `{"error":"任务正在处理中"}`，不创建线程、不覆盖旧 execution。
4. 正常积压不设置业务数量上限。202 前必须提交持久化任务事实，内存仅保留常量空间唤醒；
   重型 AnythingLLM/模型执行继续通过共享许可限流并依次处理。
5. 所有 Progress、业务终态、回调状态和最新投影写入都携带 expected TaskId；旧 Worker、
   迟到模型结果或旧回调不得覆盖同一业务键的新执行。
6. 把字段、表格、来源映射、响应解析、行合并和回调映射变为无 Flask、数据库、网络、配置
   依赖的纯规则，并以当前黄金样例证明输出等价。
7. 把选中文档解析、目标检索、术语规则、模型问答、Translation、交互审计、Progress、
   Callback 和临时资源清理变为显式 Port。
8. 消除任务执行期间对来源类别永久 workspace 的临时删改；任务级临时 workspace/thread
   必须隔离、可追踪、可幂等清理并可由有界扫描恢复。
9. weaponry 的 `/llm/check-task` 内部兼容分支继续保留甲方规定的请求内同步回调恢复副作用，
   但迁入与正常 Worker 共用的 latest-wins、lease/fencing 和 Callback Guard。
10. 在完成 Guard、资源恢复、Dispatcher 和组合根验收后，才把公开路由切换为薄适配层并应用
    已批准的 202 空响应体。
11. 删除已经确认废弃的 `WEAPONRY_ANALYSE_MODE=1` 按 Chunk 分支；1D 只保留按文件聚合的
    单一提取语义，不再让环境变量改变回调来源结构。
12. 把术语规则辅助实现为可选辅助语境 Provider；关闭时不读取、上传、挂载、检索或修改任何
    术语资源，将来删除该 Provider 时不修改核心字段、表格、任务或回调代码。
13. 将“用于寻找证据的精炼 Retrieval Query”与“基于证据生成答案的 Extraction Prompt”建模为
    两类不可互换的领域对象；INPUT 不再把包含输出格式、示例和“未找到”规则的完整 Prompt
    直接用于向量召回，TABLE 保持并强化现有专用检索 Query 边界。
14. 每个 `analyseDataSource` 的模型上下文只能包含最终回调 `rows` 中的目标 Evidence 和可选
    辅助语境；禁止任何目标文档二次 RAG、共享父 Thread 历史回退以及未验证上下文的模型回答
    进入结果，确保 `rows` 确实是本次抽取实际提交给模型的全部目标 Chunk。
15. 在 Retrieval 候选与最终 Evidence 之间建立独立、可测试的 Evidence Selection：校验冻结
    来源、合法分数或稳定排名协议、正文质量并做同文档精确去重；不设置绝对相关性阈值，也
    不建设独立 reranker。所有通过门禁的 Selected Evidence 按稳定排名保留完整正文，不设置
    单条、总量或单文档行数/字符数配额；INPUT 8、TABLE 16 仅表示向供应商请求候选的批次大小。

### 1.2 非目标

- 不在 1D 部署 MySQL、RabbitMQ、Redis、MinIO、Celery、FastAPI 或 Docker Compose。
- 不实现跨实例消费、Broker ACK、Outbox、DLQ、Redis 跨实例 Progress 或生产级分布式租约；
  这些能力仍属于阶段 3～7。
- 不迁移或顺带重写 analysis、reassign、chat、file 业务。
- 除已批准删除模式 1、收紧非法请求、隔离术语辅助结构，以及本轮明确批准的“精炼检索 Query、
  单文档抽取上下文、严格来源校验和稳定 score-or-rank Evidence Selection”外，不重新设计模式 2 的字段
  含义、答案格式、排序或表格合并算法；检索质量变化必须通过专门黄金样例和联调样例验证，
  不能与无关调参混在一起。
- 不新增字段数量、请求字节数或积压数量限制。若以后需要拒绝超大请求，必须单独确认契约。
- 不把当前内部兼容的 weaponry check-task/Progress 能力升级为新增公开承诺。
- 不删除 `weaponry_service.py`、旧任务表或旧快照表；遗留删除证据统一留到 1G。
- 不把离线 50 线程控制面测试描述为 50 个 AnythingLLM/模型任务并行能力；真实容量验收仍在
  阶段 10。

## 2. 当前代码事实与结构风险

### 2.1 当前调用链

```text
POST /llm/weaponry
  → app/blueprints/llm.py::llm_weaponry
      → Web 层解析 filePathList、查 DatabaseService、冻结部分选中文档
      → LLMTaskService.create_weaponry_task(...)
      → LLMProgressHub.publish(...)
      → threading.Thread(daemon=True)
          → run_weaponry_task(整份 request_payload + 进程内 selected_documents)
              → 直接 load_anythingllm_config / new AnythingLLMClient
              → 查永久 workspace 或创建临时 workspace
              → 上传/复用术语规则并临时移除永久 workspace 中的术语文档
              → 创建父 Thread；每次字段查询再创建子 Thread
              → 向量检索、模型问答、翻译、INPUT/TABLE 组装
              → 按 architectureId 更新任务/Progress/结果
              → post_callback_payload
              → best-effort 恢复术语、删除 Thread/workspace
```

### 2.2 已核实的主要风险

| 当前事实 | 直接风险 | 1D 处理位置 |
| --- | --- | --- |
| `weaponry_service.py` 约 2,067 行并直接导入 Client、配置、数据库、任务、Progress、Translation 和 Callback | 业务规则无法独立测试或替换基础设施，任一修改都可能影响整条链路 | 1D-1～1D-4 |
| Flask 路由直接创建 daemon thread，并把请求字典和对象参数传入线程 | 请求量转化为等待线程；进程退出会丢执行；无法由队列凭 TaskId 恢复 | 1D-4～1D-6 |
| 旧写入大多只按 `weaponry + architectureId` | 新任务覆盖后，旧 Worker 仍可能写进度、终态或回调 | 1D-2、1D-4、1D-6 |
| `weaponry_task_document_snapshots` 以业务键为主维度，重跑会删除上一轮快照 | 旧 execution 无法重放自己的输入；与可靠队列不可变消息要求不一致 | 1D-2 |
| 非空 `filePathList` 已冻结文档；缺省/空数组仍在执行时读取当前类别 | 长时间排队后文档集合可能漂移；已确认改为受理时冻结 | 1D-0、1D-2 |
| 全类别任务会临时从永久 workspace 删除术语文档，结束后再恢复 | 并发任务、进程崩溃或恢复失败会改变其他业务可见的永久集合 | 1D-3、1D-6 |
| 关闭术语辅助时，准备阶段仍扫描/上传术语目录、确保共享 workspace，并可能删后恢复目标 workspace 中的术语文档 | “关闭”只跳过字段检索和 Prompt 注入，仍产生外部 I/O 与共享资源副作用 | 1D-0、1D-3、1D-5 |
| `fieldDescription` 同时进入目标检索和最终抽取 Prompt，但术语逻辑与核心检索混在同一 Service | 现有字段说明确实生效，却难以独立证明优先级，也难以无风险删除术语功能 | 1D-0、1D-1、1D-3 |
| INPUT 把包含回答格式、示例、“未找到”和多值规则的完整抽取 Prompt 直接作为向量检索 Query | 程序性文本稀释字段名与 `fieldDescription` 的语义，且使不同字段 Query 过度相似 | 1D-0、1D-1、1D-3 |
| INPUT/TABLE 当前分别以全 workspace 的全局 TopN=8/16 直接形成候选；缺失/非法 score 被 `_get_score` 静默折叠为 0，且单文件可能占满全局候选 | 无法区分合法 rank-only、非法分数和真实零分；排序与重试语义不可审计，其他文件也可能在分组前失去候选 | 1D-0～1D-4 |
| 目标 Chunk 已按来源文件分组后，模型问答仍以 `mode=chat` 对整个任务 workspace 进行第二次 RAG | B 调用可能再次召回 A；即便只召回 B 的其他 Chunk，也会使接口声明的“rows 是实际提交模型的全部目标 Chunk”失真 | 1D-0、1D-3、1D-4 |
| 字段子 Thread 创建失败或 Facade 返回 `None` 时回退到 execution 共享父 Thread | 前一个文件的答案进入历史后会污染后续文件；部分失败路径没有明确 warning | 1D-0、1D-3、1D-4 |
| weaponry 当前忽略模型回答的来源列表，并主要依赖 title/sourceDocument 等展示别名映射来源 | 越界、缺失或冲突来源仍可能被写入 `analyseDataSource.content`，同名别名也可能误归属 | 1D-0～1D-4 |
| 模式 1/2 在字段函数内按环境变量动态分支 | 同一持久任务重试可能改变算法和回调来源形状；模式 1 已确认废弃 | 1D-0、1D-1、1D-5 |
| workspace/thread 名主要使用毫秒时间戳 | 无稳定 execution 身份，崩溃后难以发现和幂等清理孤儿资源 | 1D-3、1D-6 |
| 字段子 Thread 仅在当前调用栈 best-effort 删除 | 进程崩溃后没有权威资源记录和补偿扫描 | 1D-3、1D-6 |
| 回调绕过 execution 级 Guard；check-task 仍走旧式直接重放 | 并发恢复可能重复发送，旧任务可能在新任务提交后继续回调 | 1D-6 |
| Translation 通过全局服务定位器取得 | 测试难以隔离，任务间缓存或有状态实现可能串扰 | 1D-3、1D-4 |
| 模块内多处直接读取 `os.getenv` 和模块级路径 | 一次 execution 重试可能因运行配置变化得到不同语义 | 1D-2、1D-3 |
| 向量检索失败通常折叠为空结果，模型空回答也继续字段级降级 | 这是当前兼容语义，迁移时容易被误改成整任务失败 | 1D-0、1D-1 |
| 业务交互没有 execution 级完整审计和幂等调用身份 | 无法解释某字段由哪次检索/Prompt/回答形成，也难以安全重放 | 1D-3、1D-4 |

| 成功/失败回调 | 参数集合、字段类型、字段顺序、状态和 msg 兼容当前黄金样例 |

### 3.2 202 的准确含义

1D 单实例兼容实现返回 202 时，只能承诺：

1. 不可变 execution、原始公开请求投影和内部输入快照已在一个 SQLite 事务中提交；
2. 同业务键的活动冲突和 Callback Guard 冻结已原子检查；
3. 初始 Progress 和 Dispatcher 唤醒已经尝试；即使唤醒瞬时失败，持久化扫描仍能发现任务；
4. 不承诺任务已经开始、模型已经完成、回调已经发送或进程崩溃后自动恢复 running；
5. 不承诺 50 个重型任务并行，只承诺积压不丢弃并按许可持续处理。

### 3.4 2026-07-17 已确认的七项来源与证据隔离技术口径

下列内容是已批准的内部正确性修复，不新增、删除或重命名任何 HTTP、Callback 或 Progress

- 发现当前真实联调回调与接口文档/黄金样例字段不一致；
- 需要新增、删除、重命名任何请求、响应、回调或 Progress 参数；

## 5. 内部领域模型与不可变输入

### 5.1 业务身份

- `task_type` 固定为 `weaponry`。
- `business_key` 是规范化后的 `architectureId` 文本，只用于内部任务和 Guard 索引。
- `public_architecture_id` 是 D02 规范化后的有符号 64 位正整数，用于 Progress 和 Callback。
- 每次主动提交生成新的 `TaskId/execution_id`；不得根据 architectureId 推导或复用 TaskId。

### 5.2 字段模板

字段对象必须保持调用方原始键、未知扩展键和列表顺序。不要为了“类型化”而丢弃未来可能
由甲方增加但当前后端不读取的字段。建议使用：

- 深冻结且严格 JSON 的原始字段模板；
- 只为当前算法读取的 `fieldName`、`fieldType`、`fieldDescription`、`tableFieldList` 提供
  受控访问器；
- 结果组装时在副本中写入 `analyseData`、`analyseDataSource` 或展开后的 `tableFieldList`；
- JSON 序列化必须拒绝 NaN/Infinity，不得在持久化后才发现无法编码。

#### 5.2.1 `fieldDescription` 的核心语义

`fieldDescription` 不是术语规则功能的替代开关，也不会因术语辅助关闭而失效。模式 2 当前
已经在两个关键位置使用它，1D 必须用黄金测试显式证明并保持：

1. INPUT：以 `fieldName + fieldDescription` 构造独立、精炼的目标证据 Retrieval Query；Query
   不含回答格式、示例、“未找到”或多值分隔等生成指令。召回 Chunk 后，二者再与当前文档的
   Evidence 一起进入按文件聚合的最终 Extraction Prompt。
2. TABLE：表级 `fieldDescription`、每一列的 `fieldName` 和列级 `fieldDescription` 同时进入目标
   检索 query；最终 JSON 行抽取 Prompt 再包含相同的表说明和全部列定义。
3. 字段说明为空时才只依赖字段名；非空原值必须保存在公开字段模板和回调中，不能被术语
   Provider 改写。
4. 可选辅助语境只能帮助理解别名、口径和单位，不能覆盖请求中的 `fieldDescription`，也不能
   成为 `analyseData` 或 `analyseDataSource` 的事实来源。

因此，“关闭术语辅助”的核心抽取链仍然完整使用 `fieldDescription`。本轮已经明确批准把 INPUT
完整抽取 Prompt 替换为精炼 Retrieval Query，但只删除与检索无关的程序性指令，不擅自调整描述
权重、改写描述或增加未经批准的同义词。Query 质量变化用独立黄金/联调样例验证，不与 Prompt
答案格式或表格合并规则调整混在同一提交中。

### 5.3 文档范围快照

内部 `WeaponryDocumentSnapshot` 至少保存：

| 字段 | 用途 |
| --- | --- |
| `sequence_no` | 严格保持请求或类别解析顺序 |
| `document_key` | execution 内稳定且唯一的文档身份；所有 Evidence、调用、来源校验和审计只引用它 |
| `file_name` | 回调 `fileName` 的哈希名 |
| `original_name` | 回调 `source`，只判空不改写原值 |
| `ingested_file_name` | AnythingLLM 来源别名映射，永不进入公开回调 |
| `source_architecture_id` | 内部来源类别审计 |
| `external_document_ref` | 供应商不透明文档位置；领域层不得拆解 |
| `anything_document_id` | 可选审计引用；不能代替稳定 external ref |

1D 冻结的是文档身份和引用，不在 202 受理路径复制完整文档字节。执行器不得按文件名或当前类别
重新选文；若冻结的 `external_document_ref`/供应商文档映射缺失、被替换或无法验证，必须按故障
矩阵失败或来源级降级，绝不能自动选择“当前同名文件”。持久字节快照、内容 SHA-256 与 MinIO
Artifact 所有权在后续基础设施阶段补齐；在此之前不得把 1D 描述为文档字节永久可重放。

快照必须直接编码进 `llm_task_executions.input_payload`。新链路不再依赖按业务键替换的
`weaponry_task_document_snapshots`；旧表只保留给遗留路径和回归，直到 1G 有删除证据。

### 5.4 输入 Schema v2

`WeaponryInputSnapshot` 建议包含：

```text
task_id
architecture_id / business_key
field_templates（深冻结、严格 JSON、保序）
document_scope_mode = explicit | category
  documents = tuple[WeaponryDocumentSnapshot, ...]
evidence_selection_policy:
  profile_id / provider_fingerprint / embedding_fingerprint
  document_processing_fingerprint
  query_version = field-semantic-v2
  score_semantics = higher-is-more-relevant-in-unit-interval
  score_protocol = explicit-unit-score-or-stable-rank-v2
  ranking_strategy = score-desc-or-rank-asc-stable-v2
  input_candidate_top_n / table_candidate_top_n
  dedup_strategy = normalized-exact-within-document-v1
  reject_reference_like
execution_policy:
  extraction_strategy = file_aggregate_v1（固定，不再由环境变量选择）
  extraction_prompt_version / extraction_model_fingerprint
  extraction_context_strategy = provided_evidence_model_v1 | evidence_only_context_v1
  table_merge_policy_version / max_table_rows = 100
auxiliary_guidance_policy:
  policy_id = none | terms_rules_v1
  catalog_fingerprint / top_n / max_context_chars（none 时为空）
accepted_at / trace_id
```

执行策略快照用于保证同一任务重试时不因环境变量变化改变算法。回调 URL、认证凭据和网络
超时仍从当前部署 Adapter 读取，不写入任务输入，避免保存敏感配置。

`candidate_top_n` 是供应商召回的有界批次，不是最终 `rows` 数量；它必须根据冻结文档数量和
供应商能力配置，避免当前全局 TopN 被单个文件占满。批次内所有通过来源、质量、分数或排名协议和
同文档精确去重门禁的候选均以完整正文进入 Selected Evidence，不再应用单条、总量或单文档
行数/字符配额。`max_table_rows=100` 仍只限制 TABLE 结构化答案的数据行，不是证据 Chunk 数量。

### 5.5 Evidence Candidate、Selection Policy 与 Selected Evidence

领域层至少区分以下三个不可互换的对象：

| 对象 | 必要信息 | 约束 |
| --- | --- | --- |
| `EvidenceCandidate` | `document_key`、Chunk 身份、正文、供应商 rank、可选原始/规范分数和 score/rank profile | 只表示已召回候选，不能直接进入 Prompt 或回调 `rows` |
| `EvidenceSelectionPolicy` | profile/供应商/embedding 指纹、分数/排名协议、稳定排序、正文质量、候选批次和去重策略 | 全部来自 execution 快照；运行时不得随环境漂移；不含 reranker、绝对阈值或 Evidence 数量/字符配额 |
| `EvidenceSelectionResult` | 有序完整 Selected Evidence、拒绝原因计数和去重事实 | Selected Evidence 才能逐项投影为 `rows` 并进入 Extraction Request |

`select_evidence(candidates, allowed_document_keys, policy)` 必须是无 I/O 的纯规则，按以下固定顺序
执行，顺序变化也视为策略版本变化：

1. 拒绝不在冻结文档集合、身份无法证明或 score/rank profile 不匹配的候选；
2. 先校验整批协议：score 模式要求分数类型、有限值、方向和范围全部合法；rank-only 模式要求
   分数明确缺失且 provider rank 为稳定、正整数、批内无冲突。拒绝混合模式、非法分数、缺失
   rank 或排序身份不完整的批次，不得静默转换为 `0`；
3. 拒绝空白/过短正文、metadata 主导块和参考文献型正文；这些门禁只判断正文可用性，不承担
   字段语义相关性评分；
4. 只在同一 `document_key` 内按规范化后的完整正文做精确去重，保留稳定优胜候选；不同文档
   即使正文相同也分别保留，避免丢失合法来源；
5. score 模式按规范分数降序、provider rank、文档顺序和 Chunk 稳定身份排序；rank-only 模式按
   provider rank、文档顺序和 Chunk 稳定身份排序；不应用绝对相关性阈值或 reranker；
6. 将全部通过门禁且去重后的完整正文作为 Selected Evidence；禁止对单条、总量或单文档内容
   再做字符截断、行数裁剪或按配额拒绝，公开 `rows` 与实际抽取上下文逐项、同序一致。

首版只实施“同文档规范化精确全文去重”。模糊去重、MMR 或 Cross-Encoder 重排会改变召回语义、
增加模型/基础设施成本，除非后续有独立语料、指标和明确收益证据，否则不得在 1D 顺带引入。
这里的“规范化”只允许把 `CRLF/CR` 统一为 `LF` 并去除正文首尾空白，与现有 Chunk 清理语义
保持一致；不得大小写折叠、Unicode 兼容归一化、删除标点或合并正文内部空白。优胜候选按当前
score/rank 模式的稳定排序键决定，因此相同输入在任何重试中都选择同一条记录。

production profile 不是精度证书，而是可审计的运行策略清单。它必须冻结 `profile_id +
provider_fingerprint + embedding_fingerprint + query_strategy + document_processing_profile +
score_or_rank_protocol + stable_sort_policy + chunk_quality_policy + dedup_strategy`。任何指纹、分数/
排名协议、Query、正文处理或排序变化均形成新 profile；旧 execution 始终使用自己的快照。少量
多文档黄金样例只证明来源隔离、协议合法、稳定排序、正文质量、去重和重试确定性，不声明正式
精度、召回率或“每条 Evidence 必然与字段语义相关”。

### 5.6 结果和公开投影

- `WeaponryResult` 保存成功/失败领域结果和稳定错误分类。
- 成功结果必须与输入快照逐项核对字段数量、顺序和完整字段定义；TABLE 每个非空结果行必须
  完整覆盖冻结列及顺序。空内容是合法业务结果，缺失字段/列是程序完整性错误。
- execution result 可以包含内部 Schema 版本、审计引用和资源摘要。
- `llm_tasks.result_payload` 只能保存既有公开 Callback payload，不能泄漏内部 task_id、
  workspace、thread、trace 或文档外部引用。
- 成功公开状态保持 `2`，失败保持 `3`；受理/运行阶段保持当前 `1` 语义。
- `WeaponryResult.status` 必须与 execution state/public status 使用同一终态组合，禁止
  “成功 payload + failed/3”或“失败 payload + succeeded/2”。
- 终态写必须在一个事务内更新 execution 和最新公开投影，并带 expected TaskId。

## 6. Port 与 Adapter 设计

### 6.1 Document Scope Port

`WeaponryDocumentScopePort` 负责把外部可见文件名或类别解析为供应商无关文档快照：

- 输入保留调用方顺序；大小写去重规则按当前行为冻结；
- 未找到显式文件返回稳定 not-found 分类，由 Web Presenter 映射既有 404；
- 同名多记录或多个文件指向同一外部文档返回 ambiguity，由 Presenter 映射既有 400；
- Repository 只读本地权威知识库映射，不调用 AnythingLLM；
- 任何外部文档引用都视为不透明文本，不根据路径格式推断业务原名。

### 6.2 Target Retrieval 与 Evidence Extraction Port

检索和生成必须使用两个不可互换的 Port/DTO，避免再次把完整 Prompt 传给向量检索：

1. `TargetEvidenceRetrievalPort.open_scope(task_id, document_scope, policy)`：建立 execution 独占
   检索范围；
2. `search_target(query: RetrievalQuery, allowed_document_keys, candidate_top_n)`：只接收精炼
   Query，返回类型化且绑定稳定 `document_key` 的 `EvidenceCandidate`；越界或无法归属的 Chunk
   不得伪装成合法候选，原始分数和规范分数必须可审计；
3. Application 调用纯领域 `select_evidence(...)`，只有 Selected Evidence 可以进入抽取；
4. `EvidenceExtractionPort.extract(request: EvidenceExtractionRequest)`：请求必须只包含一个
   `document_key`、最终逐项投影为回调 `rows` 的有序 Evidence、字段/表格 Specification、可选
   辅助语境及稳定调用身份；
5. 返回 `ExtractionAnswer`，包含清理文本、原始文本摘要、供应商来源轨迹和校验结果；Application
   不读取 workspace/thread slug 或供应商字典；
6. 两个 Port 都提供可审计 trace 和幂等 close/cleanup 结果，但资源生命周期由 Resource Port 统一
   持久化。

迁移期 AnythingLLM Retrieval/Extraction Adapter 可以内部使用旧原子 Client，但必须：

- 每个 execution 创建和关闭自己的 Client/Transport，不跨线程共享 Session；
- 使用 `task_id` 和固定步骤编号命名资源，不使用毫秒时间戳作为唯一身份；
- 对所有任务使用任务级只读文档集合，禁止删改来源类别永久 workspace；
- 外部资源创建成功后立即登记，登记失败时停止后续业务步骤并进入补偿；
- 外部创建返回结果未知时保留可对账事实，不能盲目再次创建同名资源。
- 目标检索得到 Evidence 后按 `document_key` 分组；来源归属必须依据任务写入的随机来源标记或
  精确供应商文档身份，禁止只凭 title、URL、`sourceDocument` 或展示文件名猜测；
- Retrieval Adapter 必须显式声明当前批次是 score 还是 rank-only：score 模式解释分数方向、
  范围和类型，并只按当前 `profile_id` 生成规范分数；rank-only 模式必须提供稳定正整数 rank
  和 Candidate 身份。NaN、Infinity、类型非法、混合模式或语义不匹配不得沿用旧
  `_get_score(...)=0` 的静默兼容；
- 召回 Candidate 与最终 Selected Evidence 分开审计。全局候选批次可有界扩大或使用供应商
  支持的按文档检索以避免单文件垄断，但不得绕过冻结文档范围；所有通过门禁的 Candidate
  必须以完整正文进入 Selected Evidence，不得在 Adapter 中重新引入行数或字符配额；
- 每个来源级抽取调用创建全新、无历史的 Thread/Conversation，不建立 execution 共享父 Thread；
  创建返回 `None`、异常或缺少 slug 一律视为失败，不得回退到任何已有会话；
- `provided_evidence_model_v1` 不得把 Extraction Prompt 发送到任何挂载任务/分类文档的
  workspace；可以使用直接模型端口，或使用从创建到删除都不绑定文档的 execution-owned 空
  workspace。即使供应商内部固定执行空向量搜索，也不得得到任何业务 Chunk 或非空来源；回答
  的唯一目标事实上下文就是 Request 中的 Evidence；
- 若当前模型供应商无法提供上述无文档检索推理，才允许固定选择 `evidence_only_context_v1`：
  临时上下文只写入本次有序 Evidence，并用 call/document/evidence digest 标记；供应商返回的
  任何来源都必须映射回该 Evidence 集合，额外或无法证明的上下文使回答作废；
- `ExtractionAnswer` 成功后投影的 `rows` 必须与实际发送的完整 Evidence 文本和顺序逐项
  一致；不得用 Retrieval 候选全集、供应商第二次召回结果或事后拼接文本替换；
- 禁止一次调用失败后在运行时降级到任务/分类 workspace 的 `chat`、`query` 或其他文档会话；
- 一个来源调用经有界重试仍失败或来源校验不通过时，只丢弃该次回答并沿用来源级空结果兼容
  语义；不得把其他来源的回答写入当前 `analyseDataSource`。

### 6.3 可插拔 Auxiliary Guidance Port

#### 6.3.1 当前启用/关闭差异

当前代码无论开关值为何，`_prepare_retrieval_context()` 都会先读取目标 workspace、发现
`term_rule_*.md`、必要时从本地目录上传、确保术语 workspace，并可能从目标 workspace 删除后
恢复术语文档。开关只控制字段阶段是否执行第二次术语向量检索和 Prompt 注入。因此现有
`false` 是“禁用术语内容参与回答”，不是“禁用术语功能及其外部副作用”。

#### 6.3.2 1D 目标边界

定义供应商无关的 `AuxiliaryGuidancePort`，输入只包含不可变 Field/Table Specification 和稳定
`call_id`，输出只包含有类型的辅助片段；核心 Application 不知道术语目录、文件名前缀、
workspace 或环境变量。

- `NoAuxiliaryGuidanceAdapter`：直接返回空元组，不进行网络、文件、workspace、embedding 或
  数据库操作；`WEAPONRY_TERMS_RULE_CONTEXT_ENABLED=false` 必须装配此实现。
- `AnythingLLMTermsRuleGuidanceAdapter`：独占术语目录发现、幂等上传/补齐、共享只读 workspace、
  术语检索、来源过滤、Top-N、字符截断和格式化；共享 workspace 不由单个任务删除，首次
  上传/补齐由独立幂等协调器完成。
- Prompt Domain 只接受通用 `AuxiliaryGuidance` 列表；不得出现 `terms_workspace_slug`、
  `term_rule_` 或环境变量名称。这样删除具体 Provider 后，核心 Prompt 签名和行为仍然成立。
- 目标文档始终进入任务 workspace，术语文档永不进入该 workspace；因此两种开关状态都不再
  对永久来源 workspace 执行删除/恢复。
- 开启状态下术语目录准备或检索失败，沿用当前兼容语义：记录结构化 warning/audit 并降级为空
  辅助语境，不让目标文档抽取整任务失败。
- 组合根只在启动时解析一次开关，并把选定的通用 policy、术语目录清单指纹、Top-N 和字符
  上限写入任务快照，Worker 不再按字段动态读取 `os.getenv`。Provider 无法满足快照版本时按
  当前兼容语义降级为空辅助语境并留下可审计原因，不偷偷改用另一版本。

#### 6.3.3 将来删除术语功能

删除前先停止 weaponry 新受理并排空 `auxiliary_guidance.policy_id=terms_rules_v1` 的活动任务；随后
把新任务固定装配为 `none`，删除 `terms_rule_guidance.py`、三项术语配置、术语专属测试和说明。
`RunWeaponryTask`、INPUT/TABLE Domain、Document Scope、Callback、Dispatcher 和公开接口均无需
修改。历史终态 payload 原样保留，不重新执行或迁移。既有共享术语 workspace 和已上传文档
属于外部存量资源，代码删除与数据清理必须分开：先生成清单和引用审计，再由运维明确批准
是否删除，应用升级不得自动清理共享资源。

### 6.4 Translation Port

- 输入文本和目标语言显式传入，返回翻译文本或稳定失败结果；
- 保持“翻译失败返回空字符串、不让整个字段或任务失败”的当前语义；
- 允许 execution 内按文本去重缓存，但缓存不得跨任务共享可变状态；
- 日志只记录字符数、错误类型和 task_id，不输出业务正文。

### 6.5 Interaction Audit Port

每次目标检索、术语检索和模型问答使用稳定逻辑调用身份；来源级调用必须包含文档顺序，避免
同一字段的多个文件发生审计键碰撞：

```text
weaponry:{task_id}:f{field_sequence}:d{document_sequence|scope}:{operation}[:i{item_sequence}]
attempt_no = 1..N
```

`item_sequence` 只用于同一来源内可能出现多次的 Translation 子项；例如 TABLE 的多个单元格。
它避免同一字段、同一文档的多次翻译共享审计 call_id。逻辑 call_id 仍不包含 attempt_no，重试
通过稳定 call_id 加递增 attempt_no 形成唯一 `attempt_key`。

外部调用前先以逻辑 call_id、attempt_no、Query/Prompt 摘要、允许的 `document_key` 和来源标记
预留 pending 审计事实；完成后再写回答摘要、实际来源、校验计数、外部结果和时间。崩溃遗留的
pending 不得伪装成功，也不得把同一 attempt 的幂等 reservation 当成新的外部调用许可。首次
预留、历史 pending 和历史 completed 必须显式分类；后两者只能由确定性恢复查回或隔离。
只有已经形成“明确失败且允许重试”的完整审计终态时，才可使用同一逻辑 call_id 和递增
attempt_no。审计必须绑定 expected
TaskId；若关键审计预留或完成提交失败，不得把该次模型结果提交为业务成功。正文保留策略和
脱敏继续遵循项目既有审计约束。

### 6.6 Callback Port

weaponry 定义自己的 Callback DTO 和 Port，但 SQLite 实现复用通用 Guard 表方法：

- 获取发送权前检查 latest execution；
- Guard lease 同时包含随机 token 和单调 fencing token；
- 网络调用前再次权威检查 latest；
- 只有 2xx 为成功；连接失败等“明确未发送”记 failed；读取响应失败、超时等不能证明未发送
  的情况记 `delivery_outcome_unknown`；
- Guard 完成 CAS 成功后才写非权威本地调试历史；
- 过期 sending 由有界维护扫描冻结为 unknown，不自动重发；
- check-task 显式恢复允许重试明确 failed，但 busy/unknown/already completed 不重复发送；
- 同一 architectureId 的新提交遇到 unknown 时返回既有 409，直到内部人工解除并审计。

### 6.7 Resource Port

`WeaponryResourceRecord` 以 execution_id 为主键，记录：

- 任务检索 workspace，以及所选策略需要的空推理 workspace/Evidence-only 抽取上下文；
- 每次来源级调用创建的无历史 Thread/Conversation；不记录或创建 execution 共享父 Thread；
- 临时上传文档、workspace 绑定、embedding/Pin 事件、Evidence Context 及
  `document_key → provider document/source marker` 映射；每项必须标记 owned/shared，禁止
  清理共享来源文档；
- 外部创建/绑定/删除事件、操作幂等键和结果分类；
- cleanup 状态、版本、lease、重试水位、下次恢复时间和最后错误；
- 不把共享术语 workspace 标记为任务所有资源。

清理顺序建议为来源 Thread → Evidence-only 抽取上下文 → 任务检索 workspace → 仅由本 execution
拥有的临时文档 Artifact。workspace 删除若能幂等覆盖其内部 Thread，仍需保留逐资源事件，
避免在供应商语义变化后错误宣称完成。shared 文档/术语 workspace 永不由任务清理。进程崩溃
窗口通过稳定资源名称和“按名称查找后登记/清理”的对账步骤补强。

## 7. Application 用例

### 7.1 SubmitWeaponryTask

1. 接收已经通过 Web 形状校验的 `WeaponrySubmission`，生成 trace_id。
2. 通过 Document Scope Port 解析并冻结文档范围；不发生 AnythingLLM 网络调用。
3. 固定 `extraction_strategy=file_aggregate_v1`，并把组合根当前选择的通用
   `auxiliary_guidance_policy` 写入输入快照。
4. 构造 `TaskSubmissionCommand`，由 weaponry Codec 在事务前验证输入可严格 JSON 往返。
5. `create_if_allowed` 在一个短事务中检查活动状态和 Callback Guard，创建 accepted execution、
   原始请求投影和不可变 input snapshot。
6. active/Guard 冲突由 Presenter 映射既有 409；基础设施失败不得返回 202。
7. 事务提交后发布初始 Progress；通知失败只记录日志，accepted 事实不回滚。
8. 调用 Dispatcher 的常量空间唤醒；唤醒失败记录错误并等待持久化轮询恢复。
9. 返回不含内部任务 ID 的应用结果，Presenter 输出 202 零字节。

禁止在受理事务中执行文档下载、AnythingLLM、Translation、Callback、线程创建或长时间审计。

### 7.2 RunWeaponryTask(task_id)

1. 按 TaskId 读取 execution，校验 task_type 和输入 Schema。
2. 条件领取 accepted → running；missing、terminal、already-running 和 stale 使用稳定结果返回。
3. 以 expected TaskId 写“准备知识库”进度；失权立即停止外部步骤。
4. 创建并登记资源 scope，再打开 Target Evidence Retrieval Scope。
5. 按输入字段原始顺序处理；TABLE 仍按整表计一个公开进度单位。
6. 根据输入快照选择 `NoAuxiliaryGuidance` 或术语 Provider；每个字段/表格先以稳定 call_id 获取
   可选辅助语境，关闭时该步骤是零 I/O 空结果。
7. 使用专用 Retrieval Query 执行目标检索，拒绝把 Extraction Prompt 作为 Query；每条 Evidence
   Candidate 必须先映射到冻结的 `document_key`，并携带可验证的 score/rank profile。
8. 使用 execution 快照中的 Evidence Selection Policy 做来源、分数或排名协议、正文质量校验、
   同文档精确去重和稳定排序。不设置绝对相关性阈值或 reranker；协议损坏时得到零 Evidence，
   禁止填满 TopN；通过门禁的
   Evidence 完整保留且不执行数量/字符配额；零 Evidence 时不调用 Extraction Port，按当前
   字段级空结果语义继续。
9. 对每个有 Selected Evidence 的文档构造只包含最终 `rows` 的 Extraction Request；创建无历史、无目标
   文档二次检索的调用上下文，执行模型问答并严格校验上下文轨迹。无论调用上下文创建失败、
   出现额外供应商来源还是 Evidence 不一致，都不得回退到父 Thread 或任何文档 workspace。
10. 每次目标检索、Evidence Selection、可选辅助检索和模型问答先预留稳定调用审计，完成后写回答/来源摘要；
   INPUT/TABLE 的解析、来源过滤、行合并和结果组装只调用纯 Domain 规则，请求中的
   `fieldDescription` 必须同时参与精炼目标召回和最终抽取 Prompt。
11. Translation 通过 Port 执行；失败保持空字符串兼容行为。
12. 构造成功结果，以 expected TaskId 条件提交终态。CAS 失权时结果为 stale，禁止 Progress 和回调。
13. 成功提交后发布终态 Progress，再通过 Callback Guard 尝试外发。
14. 无论业务成功、失败还是 stale，资源都进入幂等清理；清理 pending 不反向改写已经提交的
    业务结果，但必须留给恢复扫描。

### 7.3 失败路径

- 领域可识别失败：构造当前兼容的 status=3 回调和 msg，条件提交失败终态后再回调；
- 来源级 Thread/Conversation 创建失败：禁止回退共享会话；有界重试耗尽后只把当前来源记为
  无有效回答并继续其他来源，保持当前字段级降级/成功回调兼容语义；
- 模型返回额外来源、上下文缺失/冲突或 Evidence 不一致：整次回答作废并记录安全审计；有界重试后仍不通过时不得
  构造当前来源的 `analyseDataSource.content`；
- Candidate 来源、正文质量或同文档重复门禁未通过：记录稳定拒绝原因且不进入 `rows`；当前
  字段/来源没有 Selected Evidence 时不调用模型并保持既有空结果兼容语义；
- Candidate 批次的 score/rank 模式混合、分数非法、rank 缺失/冲突或 profile 不匹配：记录协议/
  配置降级审计并拒绝该批次；不得把非法分数当作缺失或转换为 `0`；若整批协议失效，按既有检索失败的
  字段级空结果/成功回调兼容语义收敛，同时保存稳定内部 error_code，不能静默产生低可信答案；
- 端口契约损坏、审计失败或未知异常：记录稳定内部 error_code，不把堆栈/URL/正文放入回调；
- 终态 CAS 失败：按 stale 处理，不调用旧 execution 的回调；
- 回调失败：不覆盖业务终态，只更新 Guard/callback 状态；
- 清理失败：保留 cleanup_pending/quarantined 事实，后续有界扫描恢复；
- accepted 输入损坏或领取前 Adapter 故障：持久化冷却时间，跳过该项继续扫描后续 FIFO，避免
  毒任务热循环；阶段 5 的 DLQ 上线前不得删除该任务。

### 7.4 同步回调恢复

`RecoverWeaponryCallbackSynchronously` 只做：

1. 按 architectureId 读取最新、终态且 callback=pending/failed 的 execution；
2. 使用显式 check-task reason 获取共享 Guard；
3. 调用与 Worker 完全相同的 delivery；
4. 使用同一 lease/fencing 完成 Guard；
5. 只有 2xx 且完成 CAS 成功才返回内部 `True`。

它不创建第二套 HTTP Client，不读取旧业务键后直接发送，也不改变当前 check-task HTTP 返回
结构和返回时点。阶段 4～6 的可靠队列会调用同一恢复用例作为后台兜底。

## 8. 持久化与一致性设计

### 8.1 复用通用任务事实

- `llm_task_executions`：追加式 execution、输入 Schema、状态、进度、结果、callback 状态；
- `llm_tasks`：现有 check-task/Progress 所需最新公开投影；
- `callback_delivery_guards`：按 weaponry + architectureId 串行化外发和新提交；
- `callback_guard_release_audits`：人工解除 unknown 的追加审计。

业务 Codec 负责 weaponry JSON；通用 Task Adapter 不导入 weaponry。

### 8.2 新增资源记录

新增 `weaponry_resource_records`，采用只增不删的 SQLite Schema，主键为 execution_id，至少
包含 state、version、record_payload、next_recovery_at、created_at、updated_at。外部 I/O
绝不能发生在持有 SQLite 写事务期间。

### 8.3 选中文档旧表

- 新模块不再向 `weaponry_task_document_snapshots` 写入或读取；
- 遗留路由尚未切换时继续使用旧表，避免中间波次破坏现有功能；
- 1D-6 切换后旧表保留，不迁移历史测试数据；
- 1G 只有在生产引用、测试引用和配置引用三类证据均清零后才讨论删除。

### 8.4 事务规则

1. 受理、终态、Guard 获取/完成、资源 CAS 各自使用短事务；
2. 所有外部 HTTP、模型、Translation 和文件操作位于事务外；
3. 外部副作用完成后若本地提交失败，状态必须进入可恢复/需人工核查，不能假装未发生；
4. 公开投影更新必须同时限制 business_type、business_key 和 expected execution_id；
5. SQLite 单实例只作为阶段 1D 兼容实现，阶段 3 迁入同步 SQLAlchemy/MySQL Repository。

## 9. 本地持久积压 Dispatcher

### 9.1 设计选择

1D-5 已把 Report Dispatcher 验证过的通用生命周期能力抽取到
`tasks/adapters/local_persistent_dispatcher.py`：

- 持久化 accepted FIFO 扫描；
- `threading.Event` 常量空间唤醒；
- 可中断共享执行许可；
- start/stop/close、readiness 和 fatal error；
- 领取前故障冷却；
- running 只读诊断；
- 跨进程单实例 Guard；
- 注入式有界维护任务。

Report 和 Weaponry 各自保留薄组合器及业务维护任务。若抽取必须改变 Report 行为，先完整运行
1C Dispatcher/资源/Callback 回归；无法证明等价时停止，不在 1D 内强行迁移 Report。禁止
简单复制 700 行 Report Dispatcher 形成第二套生命周期实现。

### 9.2 Weaponry 运行方式

- 一条 weaponry 执行 Worker 扫描 `task_type=weaponry`；
- 资源恢复和 Callback Guard sweep 使用独立维护任务，不被长模型调用阻塞；
- 与 report/analysis 共享 `UploadTaskLimiter`，当前执行并发由部署配置限制；
- 使用 `runtime/locks/weaponry-dispatcher.lock` 拒绝第二个本地实例同时领取；
- `accepted_batch_size` 是每页扫描大小，不是积压上限；
- 停机停止领取新任务，并有限等待当前函数；未退出的 running 不自动重置；
- 阶段 2 的 Attempt/heartbeat/lease 完成前，进程崩溃遗留 running 只报警和人工处置。

### 9.3 跨业务公平性边界

Report 和 Weaponry 暂时拥有独立 accepted 扫描器并共享重型许可，因此 1D 只保证每个业务
内部稳定扫描，不承诺跨业务严格全局 FIFO 或权重公平。阶段 2 冻结统一 Attempt/调度语义，
阶段 5 使用独立队列、路由和资源权重解决跨业务公平性。1D 不应为了提前解决该问题把多个
业务重新耦合进一个巨型 Worker。

## 10. 配置、日志与指标

### 10.1 配置

新增严格 `WeaponryInfrastructureConfig`，把当前模块级环境读取收口到组合根。建议内部配置：

- `DOCSENSE_WEAPONRY_RUNTIME_MODE=single_instance`；
- scan interval、accepted batch size、dispatch retry、resource sweep interval/limit；
- running sample limit、stop timeout、cleanup HTTP timeout/lease；
- 固定 `extraction_strategy=file_aggregate_v1`，不再提供可切换的
  `WEAPONRY_ANALYSE_MODE`；迁移期若发现显式值 `1`，启动时给出明确废弃错误，不能静默执行；
- `WEAPONRY_TERMS_RULE_CONTEXT_ENABLED`；只有值为 `true` 时才加载并校验
  `WEAPONRY_TERMS_WORKSPACE_NAME`、`WEAPONRY_TERMS_DIR`，值为 `false` 时不得访问术语目录或服务；
- `query_version=field-semantic-v2`、`score_protocol=explicit-unit-score-or-stable-rank-v2`
  和稳定排序策略固定写入任务快照；
- `extraction_context_strategy` 只允许 `provided_evidence_model_v1` 或
  `evidence_only_context_v1`，由部署能力验证后固定选择，运行中禁止自动降级为任务/分类
  workspace RAG 或共享父 Thread；
- 供应商 Candidate top-N、术语辅助语境字符数、表格 100 行和模型重试策略；不得重新加入
  Selected Evidence 的单条、总量或单文档数量/字符限制。

配置必须在应用启动时严格校验；非法值 fail-fast。任何 scan/batch/limit 都不得被解释为业务
积压上限。敏感 URL、Token 不写入任务快照或日志。

### 10.2 结构化日志字段

至少包含：

```text
task_id / architecture_id / trace_id
execution_state / public_status / expected_owner
field_sequence / document_sequence / document_key_hash / field_type / field_name_hash
retrieval_kind / query_digest / prompt_digest / extraction_context_strategy / evidence_selection_profile
candidate_count / selected_count / rejected_invalid_score_count / rejected_invalid_rank_count
rejected_source_count / rejected_body_quality_count / deduplicated_count
selected_chars_total / selected_chars_max / score_or_rank_mode / stable_sort_policy
auxiliary_policy / auxiliary_source_count / source_count / verified_source_count
missing_source_count / mismatched_source_count / prompt_chars / answer_chars
resource_type / resource_state / cleanup_outcome
callback_outcome / fencing_token / http_status
queue_accepted_count / running_count / oldest_age_seconds
```

禁止记录完整请求、Prompt、模型正文、文档 URL、Token、回调正文或用户文件内容。字段名如有
敏感性只记录长度或哈希。

### 10.3 指标

- 受理、409、持久化失败、Dispatcher 唤醒失败；
- accepted/running 数量与最老年龄；
- 字段、检索、模型、Translation 和任务总耗时；
- INPUT/TABLE 空命中、解析失败、完整 Evidence 字符规模和表格行数；
- Retrieval Candidate 数、来源拒绝、非法分数、非法/冲突 rank、profile 不匹配、正文质量拒绝、
  同文档精确去重、Selected Evidence 数和“零证据跳过模型”次数；
- 来源级会话创建失败、越界/缺失来源拒绝、隔离重试和被丢弃回答；
- Callback success/failed/unknown/stale/busy；
- cleanup pending/quarantined/recovered；
- Dispatcher readiness、fatal error、维护失败。

阶段 1D 先提供可测试快照和日志字段，生产指标导出与告警阈值在后续可观测性阶段落地。

## 13. 验收矩阵

### 13.1 契约

- 合法 INPUT、TABLE、显式选文、空选文；
- `architectureId` 整数/十进制整数字符串等价规范化，全部非法边界稳定 400；
- `status` 缺省、存在和不同值均不影响执行；字段/TABLE 非法形状不产生 500 或静默降级；
- 400/404/409 的状态、错误文本和无副作用；
- 202 响应体严格零字节；
- 成功/失败 Callback 字段、类型、顺序、空值和 msg；
- 仅存在模式 2 的按文件来源结构，模式 1 不可通过配置恢复；
- 术语关闭时 `fieldDescription` 仍同时影响精炼目标召回和最终抽取 Prompt；INPUT Query 不含
  输出格式、示例或“未找到”等生成规则；
- 术语开启时，误导性术语示例不得覆盖目标 Evidence；术语辅助不进入公开 rows，也不能单独
  形成非空 `content`；
- Candidate 经过冻结 profile 的来源、score/rank 协议、正文质量和同文档精确去重门禁后才可
  进入 rows；不设置绝对阈值或 reranker；协议损坏的批次不会触发模型，全部被拒绝时仍产生
  既有合法空结果；
- INPUT 8、TABLE 16 仅是供应商候选批次；Selected Evidence 不设单条、总量或单文档内容
  上限，`max_table_rows=100` 仅是 TABLE 结构化答案行上限；
- ArchitectureId 在主提交、check-task、Progress、Worker、回调和任务快照中使用同一规范值；
- check-task 同步副作用和当前 HTTP 返回边界分开验证。

### 13.2 并发与隔离

- 50 个同 architectureId 提交：1 accepted、49 conflict；
- 50 个不同 architectureId 提交：全部形成独立持久化输入，不创建 50 个路由线程；
- 50 个并发 Callback acquire/check-task：最多一个发送者；
- 新任务提交后旧 Worker 的 Progress、终态和回调全部 CAS 失权；
- 50 个任务的字段模板、文档、Translation、workspace、thread、审计和回调互不串扰；
- 同一任务 A/B 文档使用互斥证据时，B 的回答只能绑定 B Evidence；Thread 创建失败不调用父
  Thread，Evidence/rows 不一致或出现额外上下文时非空回答不得进入结果；
- 同一批 Candidate 在重试后产生完全一致的协议校验、同文档去重、稳定顺序和完整 rows；不同
  文档正文相同不被跨文档误删；单文件占满候选时不得导致其他文档复用其 Evidence；
- 共享 limiter 限制实际重型执行，等待任务仍留在数据库。

### 13.3 故障注入

| 故障点 | 期望 |
| --- | --- |
| 文档范围查询失败 | 不提交 accepted，不返回 202 |
| 受理事务失败 | 无半提交 execution/投影/快照 |
| 初始 Progress/dispatch 失败 | accepted 保留，扫描可恢复 |
| 任务检索 workspace 创建明确失败 | 失败终态 + 回调 + 已知资源清理 |
| 来源级 Thread/Conversation 创建失败或返回 `None` | 禁止父会话回退；有界重试后当前来源为空，其他来源继续并审计 |
| 外部创建结果未知 | 不盲目重复，进入对账/人工核查 |
| 向量检索失败/空命中 | 按当前字段级降级黄金样例，不误改整任务语义 |
| 合法 score 批次 | 不使用绝对阈值；按规范分数、rank、文档顺序和稳定 Candidate 身份排序，全部通过其余门禁的正文进入 rows |
| 供应商明确不提供分数 | 仅在 rank-only profile 下按稳定正整数 rank 选择；缺失/冲突/非正整数 rank 使整批协议失败 |
| NaN/Infinity/类型非法、score/rank 混合或 profile 不匹配 | 显式审计并拒绝整批，不把非法分数伪装成缺失或静默转 0；按既有字段级空结果/成功回调降级，并保存稳定内部错误分类 |
| 术语 Provider 准备/检索失败 | 结构化审计后降级为空辅助语境，目标抽取继续 |
| 术语开关关闭 | 不扫描目录、不创建/读取术语 workspace、不上传/挂载/检索术语文档 |
| 模型回答空/不可解析 | INPUT/TABLE 按各自当前规则降级并审计 |
| 模型收到额外/缺失 Evidence、混入其他文档上下文或返回无法归属的来源 | 整次非空回答作废；不得部分接受或写入当前来源 content |
| Translation 失败 | translate 为空，任务继续 |
| 审计提交失败 | 不提交成功业务终态 |
| 终态 CAS stale | 禁止 Progress 和 Callback，清理旧资源 |
| Callback 3xx/4xx/5xx | failed，不视为成功 |
| Callback 超时/读取失败 | unknown，冻结新提交 |
| 清理中断 | cleanup_pending，按检查点有界恢复 |
| Dispatcher 线程/许可归还失败 | readiness=false、fatal error、停止后续领取 |

### 13.4 静态与回归

- weaponry Domain/Ports/Application 架构规则零违规；
- 正式路由无 `threading.Thread`、旧 `run_weaponry_task`、Client 或数据库调用；
- 无模式 1 执行分支；核心 Domain/Application 不引用术语环境变量、目录、文件前缀或 workspace；
- INPUT Retrieval 不能接收 Extraction Prompt；没有共享父 Thread；Extraction 不得访问任务/分类
  文档 workspace，Evidence/rows 校验不可被 Adapter 配置关闭；
- Candidate 不能绕过纯 `select_evidence` 进入 Extraction/rows；生产 Adapter 不存在非法分数转 0、
  把非法分数伪装为缺失、无稳定 rank 的隐式排序或运行时改变 profile 分支；
- 现有 889 项安全回归基线不得出现新增失败；新增测试数量以执行记录为准，不在计划中预报；
- `compileall`、关键 `py_compile`、`git diff --check` 通过；
- 不运行 `run.py`，不将真实外部服务可用性作为离线关闭条件。

## 14. 灰度、回滚与生产边界

1. 1D-1～1D-5 只新增并离线装配，不改变公开 weaponry 路由。
2. 1D-6 切换时新旧执行只能二选一，禁止同一请求双写、双执行或双 Callback。
3. 新链路内部不提供“出错后调用旧父 Thread/旧宽范围 RAG”的细粒度回退开关；回滚只能在停止
   新受理并处置活动 execution 后整体切换路由，避免一次任务混用新旧来源语义。
4. 回滚前先停止 weaponry 新受理，列出 accepted/running/Guard unknown/cleanup pending；排空或
   明确处置后才能切回旧路径。
5. 新 execution 的输入位于 `llm_task_executions`，旧 Worker 无法可靠执行它；存在新 accepted
   时禁止直接回滚旧 Worker。
6. SQLite 变更只增不删；回滚应用绑定不破坏表和审计现场。
7. 无法安全排空的 running 只保留现场并人工处置，不自动改回 accepted。
8. 即使 1D 关闭，仍不等于生产上线：MySQL、Outbox、RabbitMQ、后台可靠回调、多实例、Redis
   通知、FastAPI 和真实容量均在后续阶段。

## 17. 当前全面复盘结论与后置边界

本轮从契约、依赖方向、任务身份、文档范围、检索/生成边界、会话隔离、来源证明、审计键、
资源所有权、回调、Dispatcher、回滚和后续可靠队列逐项复核后，1D-0～1D-7 的依赖顺序保持
成立：先冻结契约和串扰回归，再迁移纯规则与不可变输入，随后实现严格 Port/Adapter 和
Application，最后才组装 Dispatcher、Guard、资源恢复并切换路由。没有发现需要新增或删除公开参数的
事项。1D-0 已在此前批准的 D03 范围内把逐项 400/404/409 错误文本补入接口文档；参数集合、
错误体结构和回调字段均未改变。

仍有五项必须如实保留的实施/生产边界：

1. 当前模型供应商能否提供无文档二次检索的推理调用，是实际环境启用前必须验证的能力事实，不是领域
   契约。先验证 `provided_evidence_model_v1`；不可用才验证只包含本次 rows 的
   `evidence_only_context_v1`，两者均失败时按 3.5 停止并报告，禁止不安全兜底。
2. 1D 的 execution 快照冻结文档集合、顺序和引用，能够阻止执行时重新选中同名文件，但尚不
   提供 MinIO 级文档字节长期保留；跨实例可靠重放所需内容 Artifact 和 SHA-256 在阶段 3 补齐。
3. 来源标记和 Evidence/rows 一致性能证明模型没有接收其他业务文档上下文，但不能数学证明
   生成文本中的每个词都被 Evidence 语义蕴含；需要通过矛盾证据、误导性术语样例和真实模型
   质量回归持续验证，不能把“来源校验通过”误写成“绝无模型幻觉”。
4. 离线 Fake/Transport 能证明 50 个控制面任务、调用身份和上下文不串扰，但真实模型召回质量、
   AnythingLLM 版本能力及 50+ 在途/长连接/短请求容量仍须在首次完整集成环境和阶段 10 验收。
5. 1D-0R 的分数漂移、单文档语料和历史清洗副本结论仍是重要风险证据，但不再用于推导绝对
   阈值或阻止 Adapter 开工。Schema v2 的 production profile 只批准“合法 score 或稳定 rank 的
   确定性运行策略”；供应商、embedding、Query、正文处理或排序协议变化时必须生成新 profile，
   不能让旧 execution 读取新默认值。
6. SQLite 单实例阶段的 Audit reserve 三态解决的是同一外部 attempt 的重放歧义，不等价于
   多实例 execution 所有权。阶段 2～3 仍必须建立 execution lease、heartbeat、fencing 和领取结果
   未知对账，RabbitMQ redelivery 不能仅依赖 Audit 表判断 Worker 生死。

因此，当前没有未决的公开接口问题，也不再存在“必须先证明高精度”的 production profile 门禁。
1D-3B 的 Schema v2/生产 Adapter、1D-5 的 Dispatcher/严格配置/离线组合根、1D-6 的
Callback Guard/资源恢复/生产装配/公开路由，以及 1D-7 的永久门禁和离线关闭均已完成。后续阶段
可以继续开发；在 AnythingLLM 服务可用且四类指纹明确的受控环境，仍须补齐真实供应商协议、
来源和 Extraction Context attestation，机器校验通过前不得将当前版本标记为 production ready。
原始文件处理、忠实 MHTML 重建和 Translator 解耦由独立阶段 1H 承担，不得重新塞回 1D Adapter。
公开 `rows` 语义已在获批范围内同步，参数集合保持不变。
