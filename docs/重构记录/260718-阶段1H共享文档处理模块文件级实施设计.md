## 1. 目标与非目标

### 1.1 目标

1. 建立独立 `app/modules/document_processing`，统一拥有格式识别、MHTML、MinerU、OCR、
   PDF/DOCX/PPTX/XLSX/TXT/Markdown 预处理及处理谱系。
2. 让 Translation 只负责语言转换和翻译结果渲染，不再拥有原始文件识别、转换、OCR、
   MinerU 进程、临时目录或中间 Artifact 生命周期。
3. 使用不可变 Request/Result/Profile/Artifact/Lineage DTO；调用方只通过 Port 获取处理结果，
   不依赖供应商路径、打开的文件句柄或进程级单例。
4. 每个任务使用独立目录、稳定步骤身份和幂等 Artifact key；50 个在途任务不得共享可变路径、
   进度回调、Converter 实例或中间文件。
5. 记录原始/规范化 Artifact 的 SHA-256、MIME、处理 profile、父子关系和处理工具指纹，使 1D
   的 `legacy-normalized-artifact-v1` 和未来原始 MHTML 处理都可审计。
6. 保留本地 Artifact Adapter 作为阶段 1～2 兼容实现；阶段 3 只替换为 MinIO Adapter，不重写
   Application 或业务模块。
7. 通过兼容 Facade 小步迁移现有调用方，最后用架构门禁阻止新增代码从
   `app/services/translator/` 导入文档转换能力。

### 1.2 非目标

- 不在 1H 部署 MySQL、MinIO、RabbitMQ、Redis、Celery、FastAPI 或 Docker Compose。
- 不改变文件上传/解析、报告、武器谱、文件对话或翻译接口的参数、状态码、回调字段和时点。
- 不在 1H 承诺 OCR/MinerU 的识别准确率或 50 个重型转换同时执行；重型并发继续限流排队。
- 不把所有文件统一转换成一种格式；不同业务由冻结 profile 选择合适产物类型。
- 不自动删除历史目录、现有 workspace、文档、模型文件或 MinerU 缓存。
- 不把 Translation 专属的双语排版、术语翻译和语言模型 Prompt 放入文档处理模块。

### 2.2 Legacy Office 结构结论

Legacy Office 当前结构**部分符合预计设计，可复用但不能原样扩展为整个 1H**：

1. 可直接复用：LibreOffice 发现/版本策略、OLE2 和 OOXML 安全校验、私有用户 Profile、最小进程
   环境、超时与进程树回收、并发许可、日志脱敏、离线交付脚本及其故障测试。
2. 需要适配后复用：`LegacyOfficePreparer`、`LegacyOfficeConfig` 和现有 Container 装配；兼容期
   保持现有导出，内部改由通用处理 Adapter 调用。
3. 不应上升为通用合同：携带真实 `Path` 的 `LegacyOfficePreparationResult`、内嵌清理回调的
   `_CleanupLease`、调用方自行复制转换结果，以及用单个大类同时拥有发布和资源生命周期。
4. 不重复建设：`scripts/legacy_office/` 的安装、锁文件、离线包和平台 Smoke 与 1H 模块分层无关；
   除非供应商能力本身变化，本阶段只运行回归，不改写这些交付资产。

因此，本阶段采取“**保留已验证内核，外移所有权，建立通用编排**”的重构策略，不重新实现
LibreOffice 转换算法，也不把 Report 的业务 Artifact 类型粗暴搬成全局共享类型。

```text

              │                           ▲
              │                           │
```

“Artifact 解耦”不要求在阶段 1H 立即新建一个无边界的全局 `artifacts` 大模块。Artifact 的领域
身份、谱系和存储 Port 先由共享 `document_processing` 模块拥有；业务模块只能持有不透明引用，
具体本地路径由 Artifact Adapter 解析。Translation 是独立消费者，只接收已经准备好的 Artifact，
不参与源格式判断和转换。阶段 3 若多个模块确实需要完全相同的对象存储实现，可再把纯存储 Adapter
下沉为共享基础设施，不能提前把 Report、Analysis 的业务类别揉成一个通用枚举。

## 4. 内部契约

### 4.0 Artifact 的准确含义

本计划中的 Artifact 是“某次任务中可被稳定引用、校验、追溯和管理生命周期的文件或文本产物”，
不是前端参数，也不是泛指临时文件，更不是模型工具中的同名展示概念。它由两部分组成：

1. **Artifact 内容**：本地文件或未来 MinIO Object 中的不可变字节，例如原始 `.doc`、转换后的
   `.docx`、MHTML 提取文本、OCR/MinerU Markdown、翻译后的单语/双语 HTML。
2. **ArtifactRef 与元数据**：Application 可持有的不透明 ID，以及 kind、MIME、size、SHA-256、
   task/step 所有权、profile、processor fingerprint 和父 Artifact 引用。引用不包含绝对路径、
   bucket、供应商目录或打开的句柄。

只有经过校验并原子发布的内容才是 Artifact。LibreOffice/MinerU 临时目录、`.part` 文件、浏览器
Profile、解压目录和进程日志只是 execution-owned scratch；AnythingLLM Workspace/Document 是
外部资源，继续通过 Resource Port 管理，也不冒充本地 Artifact。

典型谱系如下：

```text
A0 source.doc
  └─[legacy-office-26.2-profile-v1]─► A1 normalized.docx
       └─[mineru-markdown-vN]────────► A2 prepared.md
            ├─[translation-render-vN]► A3 bilingual.html
            └─[translation-render-vN]► A4 monolingual.html
```

这样做的直接效果是：业务只说明“需要 Markdown/文本/PDF”，DocumentProcessing 决定如何生成；
Translation 只读取 A2，不知道 A2 来自 DOC、MHTML、OCR 还是直通；本地文件存储切换到 MinIO 时，
业务 Application 和 Translation Application 都不需要改写。

### 4.1 不可变 DTO

`DocumentProcessingRequest` 至少包含：

```text
task_id / step_id / source_artifact_ref
source_sha256 / declared_media_type / detected_media_type
target_representation = original | pdf | markdown | text | html
processing_profile_id / trace_id
```

`DocumentProcessingResult` 至少包含：

```text
result_artifact_ref / size / sha256 / media_type
processing_profile_id / processor_fingerprint
parent_artifact_ref / lineage_events
warnings / outcome = succeeded | skipped | failed | outcome_unknown
```

所有集合使用不可变结构；不得在任务之间共享可变字典、Converter、Session、临时目录或进度
Callback。日志只记录 task_id、步骤、文件类型、大小、哈希摘要前缀、耗时和错误分类，不记录正文。

DTO 还必须满足：

- `ArtifactRef` 不提供 `Path` 属性；只有 Adapter 在受控物化租约内取得真实路径。
- `Result` 不内嵌 cleanup callback、锁、Session 或可变 Lease；清理意图和结果通过 Resource/Record
  Port 持久化。
- Artifact 逻辑键至少由 task/step、source SHA-256、profile ID、target representation 和 ordinal
  共同确定；同键重试必须查询并校验既有结果，不能另建随机业务副本。
- `succeeded` 只有在内容发布、哈希复核和 lineage 事实均完成后成立；`outcome_unknown` 不得静默
  当作失败重跑不可逆的外部步骤。

### 4.2 处理 profile

profile 是可重试和可审计的运行清单，不是文档质量评分，至少冻结：

- MIME/扩展名冲突处理规则；
- MHTML MIME 解码、主内容清理和降级策略版本；
- MinerU/OCR 引擎、模型/语言/解析模式和供应商指纹；
- 目标产物类型、编码、换行和空文件规则；
- 允许的明确失败降级路径；
- 超时、重试次数、临时资源和 Artifact 命名策略。

同一 task/step 重试必须读取 execution 中的 profile，不能重新读取变化后的环境默认值。profile
变化生成新版本，旧 execution 不迁移。

### 4.3 Artifact 与 lineage

- 原始 Artifact 永不被规范化结果覆盖；每个派生产物保存父引用、SHA-256、size 和 MIME。
- `legacy-normalized-artifact-v1` 明确表示“历史处理文本清洗副本”；必须保存可获得的来源引用、
  清洗器指纹和哈希，且不得标记为 `original` 或 `mhtml-main-content-v1`。
- 本地阶段使用 `{task_id}/{step_id}/{artifact_kind}/...` 任务级命名空间和原子发布；阶段 3 用相同
  逻辑 key 映射 MinIO。
- 处理中间文件属于 execution-owned scratch；共享模型、共享 MinerU 服务和既有业务文档属于
  shared，任务清理器不得删除。
- 外部转换“返回结果未知”时保留资源事实并进入对账，不盲目重新提交或猜测性删除。

### 1H-4：MinerU、OCR 与通用格式 Adapter

**目标：** 让 PDF/现代 Office/TXT/MD 的准备过程完全脱离 Translation。

   size、MIME 和 Artifact 发布校验。
4. 重型转换使用共享 FIFO 许可或当前等价的有界许可；50 个 accepted/in-flight 任务保留独立事实，
   只限制实际重型 I/O，不创建无界线程或进程内业务队列。
5. 外部提交前写资源意图，提交后写供应商身份；响应未知时进入 outcome unknown，只允许显式对账，
   不盲目重复提交或猜测性删除。

**修改范围：** 新增 `adapters/{mineru,builtin_ocr,passthrough}.py`；迁移
`app/services/translator/MinerUConverter.py`、`MarkdownHandler.py` 中的处理部分和
`app/services/utils/ocr_preprocessor.py`；调整 OCR/MinerU 配置装配和对应测试。

**测试与验收：** 服务不可用、排队超时、处理中断、空/多个 Markdown、解压路径逃逸、Artifact
发布失败、cleanup 重试、许可公平性与释放；50 个在途任务具有不同 input/scratch/result/lineage，
实际 MinerU/OCR 并发不超过配置值，且没有共享可变 Converter、Session 或 Progress Callback。

**达成效果：** DocumentProcessing 成为所有格式准备的唯一所有者；Translation 不再是使用 OCR、

**实施结果（2026-07-29）：** MinerU 与内置 OCR 唯一实现已迁入 Adapter，旧

### 1H-6：业务调用方逐一切换

**目标：** 只保留一条生产文件处理链，不进行长期双写。

**切换顺序与门禁：**

6. 每切换一个调用方，组合根只选择新旧之一；完成黄金/故障/资源回归后再切下一个，不允许 shadow

**修改范围：** `app/modules/report/{ports,adapters,application}`、
`app/modules/analysis/{domain,ports,adapters,application,composition.py}`、`app/container.py`、必要的

**测试与验收：** 每个业务分别运行 Port/Fake、Application、生产 Adapter、Dispatcher/恢复、契约
黄金和 Callback 测试；额外断言公开 JSON、状态码、空体、Progress 与回调逐字节/结构等价。若该

只清理明确归属的 scratch、失败候选和 `.part`，未来由带引用/保留期/审计事实的独立 GC 处理。
`docs/接口文档/` 未修改，MHTML 继续固定使用 `--no-sandbox`。至此 1H-0～1H-7 代码与离线关闭
验收完成，但不代表真实 MinerU/OCR/浏览器/LibreOffice、MinIO、可靠队列、多实例或生产容量验收。

### 1H-R：关闭后全面审查修复

2026-07-29 全面审查发现的降级漂移、富文本损失、scratch 所有权、终态恢复和长运行风险，
按 R1～R6 顺序修复；每个波次通过门禁后才进入下一波次。

1. **R1 降级语义**：扫描 PDF 保留 `MinerU -> 内置 OCR -> 原 PDF`（Report 为
   `内置 OCR -> 原 PDF`）。原 PDF 只作为 RAG 输入，不冒充 Markdown/Text；全文翻译没有文本
   Artifact 时按既有可降级失败投影空结果。`outcome_unknown` 绝不跨处理器降级。
2. **R2 结构与图片**：Translation Renderer 按 prepared representation 解析安全 Markdown，
   保留标题、列表、表格、链接和图片；单元失败保留原文，不向正文写异常类型。MinerU 相对图片
   在大小、类型和路径边界校验后内联为 data URI，使 scratch 删除后 Artifact 仍自包含。
3. **R3 结果集与所有权**：真实 MinerU Converter 向 Processor 返回完整结果目录，由 Processor
   执行“恰好一个 Markdown”校验。MHTML job 使用独占创建，任何既有目录（含合法旧标记）均不
   接管、不删除并进入待对账；签名检查只读取固定 1024 字节。
4. **R4 对账与安全 Profile**：新增内部 `ReconcileProcessingRecord`，陈旧 `running` 只能先
   隔离为 `outcome_unknown`，随后显式确认失败或以已验证 Artifact 恢复成功；MinerU 记录供应商
   task identity 与明确终态。Profile 只持久化 `local/remote` 和脱敏 endpoint fingerprint，
   URL、用户信息、query 密钥只保留在运行时 Adapter。
5. **R5 单实例长运行安全**：本地 Store 的按 Artifact 锁采用引用计数并在零使用者时回收；
   `open_reader` 在同一读租约中校验并交付同一个句柄，删除等待读租约。宿主源文件只读取一次，
   header/hash/发布统一来自受控快照。FIFO 等待者有硬上限且取消会出队；Ollama 生成使用有界
   connect/read timeout；LibreOffice 超时后只有确认进程树停止才记确定失败，否则为 unknown。
6. **Artifact Catalog**：source 与派生产物都登记到无“一步一个”限制的 Catalog，允许相同
   step 的多个 ordinal；旧 result/lineage 表继续作为单主产物兼容投影。1H 仍不启用自动 GC。

本轮没有修改公开路由、参数、状态码、响应、Callback、Progress、SSE 或 WebSocket 合同，因此
`docs/接口文档/` 不变，MHTML 继续固定使用 `--no-sandbox`。

仍有两项明确后续边界：Analysis/Report 接受任务时尚未冻结全部 OCR/MinerU/Translation
运行参数，需要阶段 2 升级内部 Task Input Schema 并由 Worker 执行指纹匹配；Tesseract、
PyMuPDF、MinerU、Markdown Renderer 等完整运行时供应链指纹也必须随该快照统一冻结。阶段 1H
当前只保证步骤首次领取时的 Profile 一致性与 MinerU endpoint 脱敏，不把它描述为跨重启的完整
执行快照。

最终安全全仓动态发现 2,145 项，沿用既有清单精确排除 13 项环境/平台测试，执行 2,132 项，
成功 2,129 项、失败 0、错误 0、跳过 3；`compileall`、架构门禁和 `git diff --check` 同时通过。

## 6. 与 1D、1G 和后续基础设施的关系

### 6.1 与 1D

- 1D-3B 不再等待原始 MHTML 忠实重建，可使用明确标记的
  `legacy-normalized-artifact-v1` 实施 Retrieval Adapter。
- 1D production profile 必须记录 document processing profile/Artifact provenance；处理指纹变化
  时生成新 profile，不重写旧 execution。
- 1D 仍必须完成来源身份、score/rank 协议、正文质量、Evidence/rows 和无二次 RAG 门禁；1H
  不替代这些业务正确性要求。
- 新的生产文件入库流程完成 1H 后必须改用独立 DocumentProcessing Application；不得继续让
  Translator 拥有转换生命周期。

### 6.2 与 1G

1H 可以与 1D/1E/1F 的后续波次并行设计和按调用点迁移，但 1G 的最终旧路径删除必须等待
1H-7 的三类引用证据。阶段编号表达独立工作流，不表示可以绕过依赖强行按字母顺序关闭。

### 6.3 与阶段 2～5

- 阶段 1 当前决策：Processing Record 与既有任务事实共用物理 `llm_tasks.sqlite3`，但模块独立
  持有表、Repository 和事务；不导入遗留 `TaskService`，不对遗留任务表建立外键。SQLite 门禁只
  证明单实例兼容能力，不据此宣称多实例安全。
- 阶段 2：把 `document_processing_steps` 的执行事实纳入 Attempt/Step/Checkpoint、
  lease/fencing 和统一本地执行器；阶段 1 的幂等步骤键、Artifact/Lineage 语义保持稳定。
- 阶段 3：把模块自有表映射到共享 MySQL 的同步 SQLAlchemy Repository/UoW，并实现 MinIO
  ArtifactStore Adapter；Artifact 内容进入 MinIO，数据库继续保存引用、所有权和删除资格，
  MinIO 不是任务状态真相源。同步建立 `retention_class`、可空删除资格、删除状态/尝试/审计；
  未确认具体保留期前不得启用自动 TTL 或 Artifact GC。
- 阶段 4：需要异步派发的文档处理步骤，其任务/步骤事实与 Outbox 派发意图必须通过共享 UoW
  在同一事务提交；禁止“先发消息、后写事实”。
- 阶段 5：MinerU/OCR/摄取使用独立队列和资源许可；积压无业务数量上限，Worker 持续排空。

## 8. 回滚与完成边界

1. 每次只切换一个调用点，旧 Facade 暂时保留；同一请求只能由新旧实现之一拥有处理权。
2. 新增 Schema/Artifact 类型只增不删；回滚组合根不删除已生成 Artifact 和 lineage。
3. 回滚不得让新 execution 读取旧环境默认值；不能解码目标 profile 时明确失败，不静默降级。
4. 1H 完成不等于 MinIO、可靠队列、多实例或生产容量完成；这些仍属于阶段 2～5、10。
5. 只有 Translator 不再拥有文件转换实现、全部调用点迁移、架构门禁和扩大回归通过后，才能
   宣称“文件处理已从 Translator 独立”。
6. 1H 完成也不授权即时删除有效 source/prepared Artifact。未来 GC 只有在数据库证明任务终态、
   无租约/重试/Outbox/回调恢复/其他引用、保留期已到且已取得 fenced 删除权时才能执行；对象删除
   与引用/lineage 状态必须可审计、可恢复。

## 10. 建议提交边界、依赖与停止条件

### 10.1 建议提交边界

每个波次至少形成一个可独立回滚的提交；1H-3、1H-4、1H-6 按 Processor 或业务调用方继续拆分，
不要把“骨架、所有供应商迁移、生产切换、旧文件删除”压成一个提交。推荐顺序为：

```text
1H-0 基线
  → 1H-1 Artifact/Port/Application
    → 1H-2 Legacy Office 纳管
      → 1H-3 MHTML
        → 1H-4 MinerU/OCR/通用格式
          → 1H-5 Translation
            → 1H-6 Utils → Report → Analysis → Translation 调用方切换
              → 1H-7 引用清零与关闭验收
```

### 10.2 必须立即停止并确认

出现以下任一情况，不得自行扩大范围：

1. 需要新增、删除、重命名 HTTP/Callback/Progress/SSE/WebSocket 字段，或改变状态码、空响应体、
   回调时点和公开错误文本。
2. 旧行为只能通过修改接口文档才能解释，或接口文档与当前生产代码存在新的冲突。
3. 需要把真实文档正文、绝对路径、供应商任务 ID、Artifact 内部 ID 或 lineage 写入公开响应/日志。
4. 需要修改已冻结的 Legacy Office 平台范围、LibreOffice 版本系列、XLS/XLSX 单 Sheet 规则或
   多 Sheet 失败语义。
5. 发现同一请求必须让新旧处理器同时执行才能上线，或回滚会重复不可逆外部提交。
6. 需要依赖尚未落地的 MySQL、MinIO、RabbitMQ、分布式锁或跨实例 fencing 才能保证当前正确性。
7. 真实 MinerU/OCR/浏览器/LibreOffice、AnythingLLM 或模型服务验证需要启动后台服务或访问生产数据。

### 10.3 最终可观察效果

- Analysis/Report/Translation 只声明目标表示和处理 profile，不知道具体转换供应商。
- 所有已发布中间/最终文件均有不透明 ArtifactRef、内容摘要和父子谱系；scratch 与外部资源边界清楚。
- Translation 的吞吐不再被 MinerU 共享目录迫使全局串行，文档处理容量可以独立配置和限流。
- Legacy Office 安全能力完整保留，并成为众多 Processor Adapter 中的一个，而不是新的中心化大类。
- 阶段 3 切换 MinIO、阶段 5 切换独立队列时，业务 Application、公开接口和 Translation 规则无需重写。
