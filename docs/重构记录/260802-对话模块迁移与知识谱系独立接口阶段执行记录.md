## 6. 阶段 5：共享运行、原子来源历史与双策略

**状态：已完成。**

### 6.1 File/Weaponry 应用策略

- 新增纯 Application `ChatUseCasePolicy`：File 等待合法供应商终态但抑制来源，历史继续投影用户
  `files`；Weaponry 暴露来源快照，用户历史只保留基础三字段，assistant 始终增加 `chunks`；未知
  identity kind 失败关闭；
- 持久化 Run 恢复时通过内部 `conversation_id` 反查不可变 Identity Binding，执行 DTO 不依赖
  Web `businessType`，两类接口继续共用同一 Conversation Factory、Run Executor、History、Title、
  Abort、Delete 和 Cleanup 用例；
- 工作区/主线程继续只用随机内部 Conversation ID 命名，标题临时线程使用随机 attempt ID，不拼接
  `userId`、`architectureId` 或 AnythingLLM 用户身份。

### 6.2 来源提交与输出时序

- Weaponry Run 把唯一 Finalization 交给 `SourceMapper`，生成内部 `source_snapshot`；Query 无上下文
  拒答生成一个空快照；供应商流没有合法终态时整轮失败，不能把迭代结束当作成功；
- Recorder 缓存内部来源快照，收到 `done` 后把 user/assistant、全部 Chunk、成功事件和 Run 终态在
  一个事务中提交；事务成功后才依次向 Presenter 交付 `source_snapshot`、`done`；
- 因此客户端在 `sourceChunks` 后、`done` 前断开时，History 已有完整事实；提交前断开、error 或 abort
  不会留下 assistant/Chunk。Chunk 正文及顺序与 SSE/History 完全一致，空来源两处均为 `[]`；

### 11.6 后续恢复边界

远端清理成功与本地删除终态不能组成跨系统原子事务。若进程恰在两者之间终止，会话可能停留在
`deleting`；当前冻结合同规定该状态再次 delete 返回 HTTP 409，因此本阶段没有擅自改变公开重试
语义。后续可靠任务阶段必须提供持久化 Reconciler/Finalizer，以清理成功事实、关闭租约和
`deleting` 状态为严格前置条件幂等收敛本地终态。该边界不否定本阶段正常路径证据，但明确阻止把
当前 SQLite/Inline 实现描述为崩溃自动恢复或多实例可靠删除。
