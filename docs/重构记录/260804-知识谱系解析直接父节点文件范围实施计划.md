## 2. 当前事实与问题结论

### 2.1 当前 Weaponry 文件范围

当前 `/llm/weaponry` 有两种受理范围：

1. `filePathList` 非空时是 `explicit` 范围。服务端按文件名在全部本地文档记录中唯一定位，允许文档
   来自其他类别，并在受理时冻结文件名、来源类别、外部文档位置和实际入库文件名。
2. `filePathList` 缺省或为空数组时是 `category` 范围。当前实现只选择
   `documents.architecture_id == params.architectureId` 的直接文档，不读取类别树。

这里的 `params.architectureId` 已确认是永久知识库的实际存储类别 ID。现有行为以及本专项的父级扩展
都不调用 `resolve_storage_architecture_id()` 做二次换算；如果调用方传入 Analysis Callback 中另一个
明细分类 ID，服务端只会把该 ID 当作独立存储类别精确查询。

两种范围都会写入 Weaponry execution 的不可变 `document_scope`。Worker、重试和恢复只消费该快照，
不会重新查询类别或文档目录。这一原则必须保留。

### 2.2 当前本地知识库没有父节点关系

`app/services/core/database.py` 当前维护：

- `workspaces(architecture_id, workspace_slug)`；
- `documents(file_name, original_name, ingested_file_name, architecture_id, anything_doc_id, doc_path,
  metadata_json)`。

其中 `documents.architecture_id` 只说明文档直接属于哪个永久知识类别；`workspaces` 只说明类别与
AnythingLLM Workspace 的一对一映射。两张表都没有 `parent_id`、`parent_architecture_id`、`path` 或
可等价表示父子关系的字段。因此，**当前不能只查询知识库数据库就可靠回答某个类别的直接父节点**。

Reassign 的旧、新类别 ID、文档 metadata 和 Workspace 名称也不能替代类别目录：它们分别是操作事实、
文档属性或外部资源身份，不是完整、当前且唯一的父子关系来源。

### 2.3 Analysis 确实保存了 `parentId` 和 `path`，但只是任务快照

`/llm/analysis` 的每个 `params[]` 会传入 `architectureList`。节点公开字段包括：

- `id`；
- `parentId`；
- `path`；
- `pathName`；
- `name`、`remark` 及调用方扩展字段。

受理链会构造 `AnalysisSubmissionSnapshot`，把原始 `raw_params` 和应用默认值后的
`effective_ranges` 深冻结；`AnalysisTaskInputCodec` 随后将它们保存到
`llm_task_executions.input_payload`。所以：

- `architectureList[].parentId/path/pathName` 当前会随 Analysis execution 输入快照保存在本地任务库；
- 文件下载用的 `params[].filePath` 也会同时保存在 `raw_params` 和独立 `file_path` 字段；
- 这些记录按 execution 保存，是可重放的历史输入，不是面向 Weaponry 查询的规范化类别目录；
- Weaponry 当前完全不读取 Analysis execution JSON；
- 历史任务可能来自不同时间、不同有限候选树或不同 Schema，直接扫描“大 JSON + 猜最新值”既低效，
  也无法稳定处理冲突、重分类和多实例并发。

接口文档还明确规定 `pathName` 是不透明文本，不能根据 `/` 推断层级。`path` 当前也只作为调用方提供并
随 execution 保存的审计文本；现有校验不会证明它与 `parentId` 拓扑一致，因此不能通过拆字符串来替代
明确的 `parentId`。本专项只以通过现有 `ArchitectureTreeIndex` 校验后的 `parentId` 为父关系来源。

### 2.4 结论

当前状态可以概括为：

- **没有**可被 Weaponry 直接查询的本地父节点目录；
- **有**包含 `parentId/path` 的 Analysis 历史执行快照；
- 但历史快照不能直接充当运行时类别目录，必须在 Analysis 受理边界增加规范化、可索引、可审计的
  父关系投影，再由 Weaponry 通过 Port 只读消费。

## 3. 目标行为

建议新增环境变量：

```dotenv
DOCSENSE_WEAPONRY_INCLUDE_DIRECT_PARENT_DOCUMENTS=false
```

只接受项目现有严格布尔值集合；非法值在应用装配阶段失败，禁止运行中按请求重新读取环境变量。

### 3.1 文件范围矩阵

本节中的“目标类别”均为请求 `architectureId` 精确对应的 `documents.architecture_id`；“直接父类别”
均为授权 Analysis 调用方通过已验证 `parentId` 发布的一级父类别。不得使用 Callback 明细分类、
`path/pathName` 或运行时模型结果重新解释这两个 ID。

| 开关 | `filePathList` | 目标类别状态 | 受理时冻结的文件范围 |
| --- | --- | --- | --- |
| `false` | 缺省或 `[]` | 任意 | 仅目标类别直接文件，完全保持当前行为 |
| `true` | 非空 | 任意 | 仅调用方显式选择的文件；不自动扩展 |
| `true` | 缺省或 `[]` | 已知根节点 | 仅目标类别直接文件 |
| `true` | 缺省或 `[]` | 已知直接父节点 | 目标类别直接文件 + 直接父类别文件 |
| `true` | 缺省或 `[]` | 关系缺失、冲突或损坏 | 受理前失败关闭，不创建 execution |

正式语义如下：

1. 只包含**直接父节点一级**，不递归祖父节点，不包含兄弟节点、子节点或其他祖先。
2. 目标类别文件排在父类别文件之前；每一类别内部继续按规范化文件名、原文件名和外部位置稳定排序。
3. 目标类别没有文件但父类别有文件时，允许只冻结父类别文件。
4. 父类别没有文件时，仍正常冻结目标类别文件，不把“父类别为空”当作目录损坏。
5. 目录中明确登记为根节点与“目录没有该节点”必须区分：根节点安全退化为本类别，未知节点失败关闭。
6. 目标和父类别之间出现大小写不敏感重复文件名、重复规范化外部文档位置或其他来源身份冲突时，
   禁止静默去重或随机保留，按本地权威记录不一致失败关闭。
7. 受理完成后，即使环境变量、父关系或文档目录发生变化，已受理 execution 仍使用原快照。
8. 任务级临时 Workspace 继续只绑定快照中的外部文档引用，不修改目标或父类别的永久 Workspace。
9. Callback 中 `source`、`fileName`、`rows` 等字段继续按每个来源文档的现有谱系生成，不增加“来自父级”
   等公开字段。

### 3.2 需要在阶段 0 确认的公开失败语义

推荐把“开关已启用但父关系目录缺失、冲突或损坏”视为服务端配置/数据完整性问题，而不是调用方
`architectureId` 参数错误：

- 内部抛出独立的目录完整性异常；
- 不映射为现有 HTTP 400 文档范围错误，避免把服务端缺失伪装成调用方错误；
- 公开 HTTP 状态和既有通用错误体必须在阶段 0 与负责人确认并写入权威接口文档后再冻结。

如果负责人不批准任何公开错误语义变化，则实现必须沿用当时已批准的通用服务端失败分支，不能自行
增加新的状态码或错误字段。

### 3.3 已确认口径与阶段 0 剩余决策

2026-08-09 已确认：

1. 新能力只作用于 `/llm/weaponry` 缺省或空 `filePathList`；非空显式范围以及 Analysis、
   Weaponry Chat 和其他接口均不扩展。
2. 请求 `architectureId` 是永久知识库实际存储类别 ID，并与 `documents.architecture_id` 精确匹配；
   本专项不隐式换算 Analysis Callback 明细分类 ID。
3. 正式 Analysis 调用方有权发布类别关系；只信任通过既有校验的显式 `parentId`，禁止解析
   `path/pathName` 猜测父级。

以下内容仍是阶段 0 阻塞项，未确认前不得进入对应代码实施：

1. `architectureList` 缺省、`null` 或空数组时产生的服务端兼容默认树，是否允许发布业务父关系。
2. 同批或跨批出现同节点不同 `parentId` 时，Analysis 批次是否继续受理、目录如何进入冲突态，以及
   冲突是否只能人工解除；当前接口没有 taxonomy 业务版本，不能预设“后到请求必然更新”。
3. 目录未知、冲突、损坏时最终使用的公开 HTTP 状态和既有错误体；接口文档未获明确授权前不得修改。
4. 开关从 false 切换为 true 前的目录覆盖率、允许的回填数据源、可启用阈值和只读诊断输出。
5. `relation_revision` 是整棵树修订还是单节点修订、同批去重后的来源 execution 选择，以及是否需要
   追加式 relation event 表才能满足完整审计。

## 4. 架构与数据设计

### 4.1 新增规范化 Architecture Catalog

建议建立独立的内部 `architecture_catalog` 边界，负责“Analysis 发布父关系，Weaponry 只读查询”。
它不依赖 Flask、AnythingLLM、Callback 或 Weaponry 提取模型。

核心领域对象建议包括：

- `ArchitectureParentRelation`：`architecture_id`、明确根节点或直接 `parent_architecture_id`；
- `ArchitectureRelationRevision`：来源 execution、受理时间、批次与树指纹组成的稳定修订身份；
- `ArchitectureParentLookup`：`known_parent`、`known_root`、`unknown`、`conflict` 四态结果；
- `ArchitectureRelationPublication`：一次 Analysis 受理中已验证、去重后的父关系集合。

建议在 `llm_tasks.sqlite3` 中增加内部控制面表：

```text
architecture_parent_relations
  architecture_id              INTEGER PRIMARY KEY
  parent_architecture_id       INTEGER NULL
  relation_state               TEXT NOT NULL
  source_execution_id          TEXT NOT NULL
  source_batch_id              TEXT NOT NULL
  source_batch_sequence        INTEGER NOT NULL
  source_accepted_at           TEXT NOT NULL
  source_tree_fingerprint      TEXT NOT NULL
  relation_revision            TEXT NOT NULL
  updated_at                   TEXT NOT NULL
```

约束要求：

- `architecture_id` 和非空 `parent_architecture_id` 必须是合法正整数且不能相等；
- `relation_state` 只能为 `known_parent`、`known_root` 或 `conflict`；
- `known_parent` 必须有父 ID，`known_root`/`conflict` 必须没有父 ID；
- `source_execution_id`、`relation_revision` 唯一标识来源，禁止只用本地当前时间猜测先后；
- 为 `parent_architecture_id` 和 `relation_state` 建立必要索引，但 Weaponry 的主查询必须走
  `architecture_id` 主键；
- 表缺失、重复、非法状态、父子自环或读取结果类型错误都按损坏处理。

选择任务库而不是 `knowledge.sqlite3` 的原因是：父关系来自 Analysis 请求输入，是控制面受理事实；把
关系投影和 Analysis execution 放进同一个 SQLite `BEGIN IMMEDIATE`，可以保证“任务已受理但父关系
未落库”与“父关系已变但任务受理回滚”都不会发生。`documents` 仍由知识库数据库拥有，不能把完整
领域树塞入每一条文档 metadata。

### 4.2 Analysis 发布规则

1. 只接受正式 Analysis 授权调用方已经通过 Parser、领域树和完整批次预校验的输入；继续由
   `build_architecture_tree_index()` 完成 ID、`parentId`、深度、环和资源上限校验。
2. 从规范树节点生成 `(id, parent_id)`，其中 `parentId` 是唯一父关系权威；不解析
   `path`/`pathName`，不复制 `name`、`remark` 或未知扩展字段到父关系表。
3. 缺省、`null` 或空 `architectureList` 所触发的服务端默认树是否具备发布资格，必须先完成 3.3 的
   阶段 0 决策；实现不得仅因为默认树出现在 `effective_ranges` 中就自动写入业务目录。
4. 新增独立的拓扑指纹，只覆盖排序后的规范 `(id, parent_id)`，避免名称、备注或调用方扩展字段变化造成无意义的
   父关系版本漂移。
5. 同一批次中完全相同的树先按拓扑指纹去重，避免最多 32 个文件重复写入相同的 10,000 个节点。
6. 同一批次中同一个 ID 出现不同父关系时，至少必须让该节点目录失败关闭并记录有限冲突事实；
   Analysis 批次是否继续受理、冲突能否自动解除及修订顺序，按 3.3 的阶段 0 决策实现，不能默认采用
   “服务器最后接收者获胜”。
7. 父关系写入必须和 Analysis 批次 execution、公开投影及 Guard 检查处于同一写事务；批次拒绝或
   任一步失败时全部回滚。
8. 只发布已成功通过 Parser、领域树和完整批次预校验且符合阶段 0 来源资格的数据。不能从失败 JSON、Callback 结果、模型
   分类输出、文档 Workspace 名称或历史 `path` 字符串反推父关系。

这是一份“最近已受理的合法关系投影”，不是独立的上游主数据系统。现有接口没有 taxonomy 版本和
删除事件，因此本阶段不能证明节点删除；如果未来需要严格同步节点新增、移动、删除，应引入独立的
版本化类别目录接口或事件源，不能继续依赖文件解析请求顺带同步。

### 4.3 Weaponry 父关系读取 Port

新增只读 `ArchitectureParentLookupPort`，按目标 `architectureId` 返回：

- 关系状态；
- 直接父 ID（若有）；
- 不透明 `relation_revision`；
- 来源树指纹的有限摘要，用于日志和诊断，不进入公开响应。

SQLite Adapter 每次受理读取数据库，不使用进程内永久缓存。这样未来多实例迁移到共享数据库时，
Application 和 Domain 无需更改；当前阶段仍只能声明 SQLite 单实例能力。

当开关开启且 `filePathList` 为空时，范围解析使用以下有界步骤：

1. 读取目标节点关系快照 R1；
2. 根据 R1 形成 `(target_id,)` 或 `(target_id, parent_id)`；
3. 在知识库数据库的一次只读事务中按这些 ID 查询文档；
4. 再次读取关系快照 R2；
5. R1 与 R2 修订相同才冻结范围；若发生变化，最多进行有界重试，连续漂移则失败关闭。

该“双读修订”用于关闭任务库与知识库分属两个 SQLite 文件时的关系切换竞态。未来迁移到共享数据库
后，应把父关系和文档读取收口到同一数据库一致性快照，而不是把双读永久当作分布式事务方案。

### 4.4 文档查询与稳定顺序

当前 `DatabaseServiceWeaponryDocumentScopeAdapter` 会先读取全部 `documents` 再在 Python 中过滤。
本专项应同时收口为索引查询：

- 新增 `list_document_records_by_architecture_ids()`，只允许 1～2 个已校验 ID；
- SQL 使用 `WHERE architecture_id IN (...)`，依赖现有 `(architecture_id, file_name)` 唯一索引；
- 为显式文件范围补充 `documents(file_name)` 索引和按文件名集合查询，取消显式范围的全表扫描；
- 返回记录先按目标类别、父类别分组，再在组内稳定排序；
- 继续验证空文件名、重复文件名、外部文档身份和 `ingested_file_name`；
- 不增加任意文档数或字符截断。容量问题必须通过基准、分页/流式设计或后续正式配额解决，不能静默
  丢弃靠后的父类别文件。

### 4.5 Weaponry execution 快照升级

建议把内部 `WEAPONRY_INPUT_SCHEMA_VERSION` 从 v2 升级到 v3，在 `document_scope` 中增加：

- `resolution_policy`：`explicit_v1`、`category_direct_v1` 或 `category_direct_parent_v1`；
- `resolved_architecture_ids`：类别范围实际使用的有序 ID，目标在前、父节点在后；
- `catalog_relation_revision`：父关系修订；显式范围或关闭开关时为空。

现有每个 `WeaponryDocumentSnapshot.source_architecture_id` 继续保留。v3 Codec 必须严格拒绝未知字段、
非法顺序和关系修订不一致；同时保留 v2 解码器：

- 历史 v2 `category` execution 一律解释为 `category_direct_v1`；
- 历史 v2 `explicit` execution 一律解释为 `explicit_v1`；
- 历史已受理任务即使部署后开关为 true，也不得在重试时追加父类别文件。

发布 v3 前必须停止并隔离旧 Worker。新代码兼容读取 v2，不代表旧代码能够安全读取 v3。

### 4.6 环境配置、装配和日志

`WeaponryInfrastructureConfig` 新增布尔字段 `include_direct_parent_documents`，由
`load_weaponry_infrastructure_config()` 使用现有 `_strict_bool()` 一次读取。要求：

- 默认 `false`；
- 非法值启动失败；
- Application、Adapter 和 Worker 中禁止直接调用 `os.getenv()`；
- 组合根把固定布尔值和 `ArchitectureParentLookupPort` 注入文档范围 Adapter；
- 开关为 false 时不查询父关系目录，保证关闭路径没有额外数据库 I/O；
- 开关为 true 时启动门禁必须验证父关系表与 Schema，并执行阶段 0 已确认的覆盖率和冲突门禁；
  “任意存在一条可读取关系”不得作为可启用证明。目标 ID 是否存在仍在每次请求受理时严格检查。

建议日志：

- 启动：开关值、目录是否就绪、关系/冲突数量；
- 受理：目标 architectureId、是否命中父节点、父 ID、关系修订摘要、目标/父类别文档数量、总数；
- 冲突：目标 ID、关系状态、修订摘要和错误类型；
- 禁止记录完整 `architectureList`、`path/pathName`、文件正文、URL、API Key、外部响应或文档内容。

- false + 空范围：只含目标类别，结果与当前黄金基线一致。

- true + 子节点：精确包含目标和直接父类别，不包含祖父、兄弟或子类别。

- 目标在父关系查询两次之间被移动：重试后形成单一修订；持续漂移失败关闭。
- 缺失、conflict、非法父 ID、自环和损坏行均零 execution 副作用。
- 跨目标/父类别的重复文件名、重复规范化外部位置失败关闭。
- 稳定顺序始终为目标类别在前、父类别在后、组内确定排序。
- Analysis 的文件解析/分类结果、Weaponry Chat 会话范围及其他公开接口均不受此开关影响。

## 8. 数据迁移、发布和回滚

### 8.1 加法迁移

- 新父关系表与索引采用 `CREATE TABLE/INDEX IF NOT EXISTS`，不改写 `documents`、`workspaces` 或旧
  execution payload。
- 初始化后执行 `integrity_check`、Schema 列/约束检查和冲突统计。
- 不从 `documents.architecture_id`、Workspace 名称或 `path` 字符串猜父级。

### 8.2 历史回填

只读诊断脚本可按受理顺序读取可解码的 Analysis V1～V4 execution，只从阶段 0 确认具备发布资格的
来源提取已验证 `parentId`，生成拟写入关系和冲突报告。不得因为默认树存在于 `effective_ranges` 就
自动视为可回填来源。脚本默认只读，输出只包含数量、ID、修订摘要和错误类型，不打印完整请求、URL、
文件名或树文本。

允许写入的回填必须满足：

1. 明确维护窗口、目标任务库和备份位置；
2. `--apply` 显式授权；
3. 与在线 Worker 隔离；
4. 使用与运行时代码相同的领域校验和修订比较；
5. 完成后再次只读验证；
6. 没有可验证快照时停止，要求先以开关 false 接受新的合法 Analysis 请求，禁止猜测。

### 8.3 发布顺序

1. 停旧实例并确认无旧 Worker。
2. 备份 SQLite。
3. 部署支持 v2/v3 和父关系表的新代码，开关保持 false。
4. 初始化/回填并完成只读门禁。
5. 验证 false 路径等价。
6. 取得负责人确认后设置 true 并重启。
7. 先执行小范围协议验收，再逐步开放真实流量。

### 8.4 回滚

- 首选回滚是把开关恢复 false 并重启；新受理任务立即恢复只取本类别。
- 已受理 v3 任务继续使用冻结的父级文档，不因回滚开关改变。若业务要求立即停止这些任务，必须走
  单独的任务处置流程，不能原地改写 execution 快照。
- 父关系表保留为审计事实，不在回滚时删除；删除会破坏诊断和后续恢复依据。
- 如需回退到不认识 v3 的旧代码，必须先证明不存在 v3 accepted/running/recovery 任务，否则禁止启动
  旧 Worker。

## 9. 完成定义

全部完成必须同时满足：

1. ENV 开关默认 false、严格解析、启动时冻结。
2. 开关仅影响 `/llm/weaponry` 缺省或空 `filePathList`；非空显式范围以及 Analysis、Weaponry Chat
   和其他接口不受影响。
3. `architectureId` 与永久知识库 `documents.architecture_id` 精确匹配，不隐式换算 Callback 明细分类。
4. false 路径与当前本类别范围行为和公共合同等价。
5. true + 空范围精确冻结目标类别和直接父类别，不扩大到其他节点。
6. 非空 `filePathList` 完全不受自动父级扩展影响。
7. 父关系来自授权 Analysis 调用方已验证 `parentId` 的规范化、原子、可审计投影，不解析 `path`，
   不扫描不符合来源资格的历史 JSON 猜测。
8. 未知、冲突、损坏和连续漂移失败关闭，且失败请求不创建 execution。
9. 新 v3 execution 冻结范围策略、关系修订、类别顺序和全部文档身份；历史 v2 语义不变。
10. 范围查询使用索引，不加载整个文档目录，不共享可变任务状态或 HTTP Session。
11. AnythingLLM 永久父/子 Workspace 不被临时修改，任务资源仍按现有持久清理流程收敛。
12. 请求、响应、Callback、Progress、Header 和事件字段集合零变化；权威文档已在明确授权后同步。
13. 中文注释说明为什么 `parentId` 是权威、为什么不解析 `path`、为什么任务必须冻结范围；新增日志完整
     脱敏。
14. 定向、并发、安全全仓、静态门禁和真实协议验收按各自证据边界通过。

## 10. 达成效果与剩余边界

完成后，部署方可以只通过 ENV 开关选择：

- 保持当前“仅目标类别文件”；或
- 对空 `filePathList` 自动使用“请求存储类别 + 其直接父类别文件”。

前端不需要增加字段，Worker 不需要动态查询父节点，重试不会因目录变化漂移；父关系有规范化本地事实、
来源修订和失败关闭边界，后续迁移到共享数据库时可替换 SQLite Adapter。

本专项仍不实现：

- 祖先递归、兄弟/子树范围或调用方按请求选择层数；
- 类别主数据的独立版本、删除事件和跨系统双向同步；
- 可靠消息队列、事务 Outbox、共享数据库、多实例租约/fencing；
- 动态热切换、生产容量保证或 exactly-once。

这些能力必须在后续阶段以显式版本化目录、共享数据库事务和可靠队列设计实现，不能用进程内缓存、
历史任务扫描或“最后一次字符串 path”冒充。
