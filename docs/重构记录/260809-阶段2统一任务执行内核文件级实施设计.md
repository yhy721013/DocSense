## 1. 结论与阶段目标

### 1.1 阶段 2 真正要解决的问题

阶段 1 已经完成业务模块拆分、薄路由、按 `TaskId` 恢复输入的 Worker-ready 入口和本地持久任务扫描。阶段 2 不应重复做模块拆分，也不应提前接入 MySQL、RabbitMQ、Redis 或 MinIO。它必须补齐下列仍然缺失的执行控制事实：

1. 一条业务 Task 可以经历多次受控执行 Attempt，但任一时刻只有一份有效执行权；
2. 执行权具有 owner、lease token、到期时间、heartbeat 和单调 fencing token；
3. 进度、步骤、产物引用和终态写入都必须携带当前 Attempt 的执行权，旧 Worker 不能只凭 `TaskId` 继续写；
4. 外部副作用前后必须保存 Step/Checkpoint；进程失联后只能依据持久事实分类恢复，禁止通用 `running -> accepted`；
5. 本地执行器只保存常量或有界唤醒/在途对象，全部积压和恢复事实仍在 SQLite；
6. Analysis、Report、Weaponry 使用同一任务执行内核，但业务结果、Callback、资源清理和公开状态仍由各自模块拥有；
7. 为阶段 3 的共享数据库 Repository 和阶段 5 的 Worker 适配器冻结稳定端口，使后续基础设施替换不再修改业务流程；
8. 把阶段 2 实际触达的 Task、Progress、Report、Analysis、Weaponry 持久化与运行配置从
   `app/services` 过渡层迁回明确所有者，禁止在新 Store 外再包一层巨型 `LLMTaskService`；
9. 迁移稳定共享领域规则和窄基础设施工具，同时保留顶层 Web Adapter 边界，避免把“整理目录”
   误做成跨模块重写。
10. 使用新 Task Control SQLite 空库和数据库级身份取代原地改旧 Schema；用共享事务基础设施 + 窄
    UoW 保持受理、Step intent/业务资源和终态原子性；
11. 冻结三业务 Executor 拓扑、分层公平容量、Clock/owner/租约不等式、Step/Recovery Registry 和
    `recovery_required` 新受理/解锁规则，使实现不再依赖临场判断。

### 1.2 本阶段完成后的准确能力

完成后可以声明：

- Analysis、Report、Weaponry 在 SQLite 单实例模式下拥有统一 Task/Attempt/Step/Event、租约、心跳、fencing、检查点和保守 Reaper 语义；
- Worker 崩溃后，只有被证明可安全重试的任务才会重新进入可领取状态；未知结果会隔离，不会盲重放；
- 两个独立 SQLite 连接模拟并发执行者时，旧 Attempt 的条件写会被拒绝；
- 50 条及以上持久化在途任务可以在固定并发下持续排空，内存中不保存与积压数等长的任务队列；
- 一个 Executor 内核按三业务实例化，业务内顺序和跨业务公平边界明确；真实重型总并发初始仍为 1；
- Task Control 使用严格身份校验的新 v2 空库；窄 UoW、UTC Clock、启动世代 owner 和 Step Registry
  均有可复用契约测试；
- 阶段 2 已改造事实只有一个权威 Store/写入者；Report、Analysis、Weaponry 生产路径不再依赖
  `LLMTaskService`，Tasks Progress 不再依赖 `app.services.core.progress*`；
- 当前 HTTP/Callback/Progress/Chat 合同不变。

完成后仍然**不能**声明：

- 已有可靠消息队列、事务 Outbox 或跨进程消息投递；
- 已支持共享数据库、多应用实例或跨主机 fencing；
- Web 进程退出后任务必然由其他进程继续执行；
- 已具备 MinIO 共享产物、生产容量或真实供应商验收；本系统也不把阶段 2 结果表述为
  exactly-once，后续目标始终是至少一次投递、条件写、幂等副作用和未知结果隔离；
- Chat 已经异步 Worker 化。

### 1.3 非目标

- 不运行或修改 `run.py` 的启动流程来完成验收；
- 不迁移历史 SQLite 业务数据；旧库只读预检并保留，阶段 2 在独立新路径初始化空 v2 库；
- 不在阶段 2 建立 Outbox、RabbitMQ/Celery、Redis、MinIO 或 SQLAlchemy；
- 不新增通用任务取消接口。当前异步 Analysis/Report/Weaponry 没有已批准的公开取消合同，Chat 中断继续属于 `ChatRun`；
- 不把 Callback Delivery、模型调用审计、资源清理或 Reassign Step Attempt 强行合并成 Task Attempt；
- 不把 ChatRun、ReassignmentOperation 或 DocumentProcessing Step 复制成第二份统一 Task 事实；
- 不在阶段 2 宣称 URL、文件名或文档身份已经等同于不可变文件字节。共享内容 Artifact 属于阶段 3；
- 不整体搬迁 `app/adapters/web`、Presenter 或 Flask/FastAPI 目录；它们属于目标 Web 边界，阶段 8
  再做框架组织收口；
- 不在阶段 2 物理搬迁 `app/services/core/database.py` 及其 Knowledge 权威表。阶段 2 只冻结
  Knowledge Port、表所有权和禁止新增直接依赖，阶段 3A 随 MySQL Repository 一次迁移。

## 2. 最新代码基线与差距

### 2.1 已有的可靠基础

| 范围 | 当前事实 | 阶段 2 应复用的价值 |
| --- | --- | --- |
| `app/modules/tasks/domain/models.py` | 已有 `TaskId`、业务键、执行输入快照和 Progress 快照 | `TaskId == execution_id` 已可作为统一 Task 身份 |
| `app/modules/tasks/ports/task_commands.py` | 已有原子受理、领取、latest、进度和终态条件写 | 业务调用形态已经接近 Worker 所需边界 |
| `app/modules/tasks/adapters/local_persistent_dispatcher.py` | SQLite 扫描、常量空间 Event 唤醒、停机、诊断和维护线程 | 无需重造内存队列；应在此基础上增加固定 Worker 数和执行租约监督 |
| `llm_task_executions` | 追加 execution、不可变输入、全局调度序号、批次序号、状态和结果 | 阶段 2 SQLite 物理 Task 主表，不另建第二份 `tasks` 双写表 |
| `llm_tasks` | 按业务键保存公开 latest 投影 | 继续作为兼容投影，不作为执行权真相 |
| Analysis/Report/Weaponry | `RunXxxTask(task_id)`、严格 Codec、资源/Callback 审计 | 可逐业务接入统一执行权，不需要重拆业务用例 |
| Callback Guard | 已有发送权、fencing、unknown 冻结和显式恢复审计 | 保持独立副作用状态机；不能冒充整任务 Attempt |
| Reassign | 已有 Operation/Step/Event、lease/fencing、checkpoint、恢复接管 | 可复用设计经验，但不复制为通用 Task |
| DocumentProcessing | 已有 Step、External Operation、Artifact、`outcome_unknown` 和对账 | 继续作为父 Task 的领域步骤/子流程，不另建 Task |
| Chat | 已有 ChatRun、输入、事件、心跳、内联 Dispatcher 和能力声明 | 阶段 9 接队列时映射统一执行权；阶段 2 不制造双事实 |

### 2.2 当前整任务执行权仍然缺失

1. `TaskCommandPort.claim(task_id)` 只把 `accepted` 改为 `running`，没有 attempt、lease、heartbeat 或 fencing；
2. 进度和终态只校验 expected TaskId/latest，无法阻止“同一 Task 的旧执行者”覆盖新 Attempt；
3. 本地 Dispatcher 对孤儿 `running` 只告警，明确禁止自动重置，当前没有 Reaper；
4. `LegacyTaskCommandAdapter` 仍依赖 7000 行以上的具体 `LLMTaskService`；Codec 协议和编码 DTO 甚至定义在 Adapter 文件中，业务 Codec 反向导入 `tasks.adapters`；
5. Analysis 的请求内顺序目前依靠单 Worker 和 `dispatch_sequence` 自然实现。只要增加 Worker 数，后续文件就可能在前一文件终态前被领取；
6. Report v1 输入只冻结 URL 和业务文本，没有冻结 DocumentProcessing、RAG Provider、Prompt/Sanitizer 等执行配置；
7. Analysis v4 已冻结分类和文档处理策略，但 Translation Profile 仍在执行时从环境和当前运行组件构造；
8. Weaponry v2 的策略指纹较完整，但其文档仍是身份/引用快照，不是 execution-owned 内容字节；
9. 当前任务状态把 `accepted/running/terminal` 放在一张执行行中，尚未区分 Task 状态、Attempt 状态和 Step 结果；
10. 当前任务更新没有同事务追加的内部事件账本，Progress Hub 只适合单实例低延迟通知，不是恢复真相；
11. `app/services/llm_service/task_service.py` 同时拥有 Task、Callback Control、Report/Analysis 资源、
    Weaponry 快照、Recall 与模型交互审计等多类 SQL，已经无法用单一“任务服务”描述；
12. Tasks Progress 规则、进程内 Hub 与 Adapter 分散在 `app/services/core` 和 `app/modules/tasks`，
    容易形成双通知中心；
13. `app/services/core/config.py` 混合 Chat、Report、Analysis 和共享基础设施配置；阶段 2 若继续
    向其中追加 Worker/lease/Reaper 配置，会扩大过渡核心；
14. `app/domain/knowledge_workspace.py` 是稳定纯规则但顶层目录仅承载这一职责；`callback_client.py`、
    `file_downloader.py`、`word_extractor.py` 仍以通用工具名承载明确业务/基础设施职责。
15. 当前三个 Dispatcher 与一个共享 limiter 的关系没有形成长期拓扑；简单增加 Worker 可能产生跨业务饥饿；
16. 拆分多 Store 后尚无显式 UoW/Connection 所有权，容易破坏 Admission、Step intent 与资源事实原子性；
17. 旧 `execution_state CHECK` 不接受 `recovery_required`，不能通过普通 `ADD COLUMN` 修复；
18. 业务 Step 尚无可执行 Registry，通用 `outcome_unknown` 不能告诉 Recovery Policy 应探测、补偿还是重试；
19. 持久时间、FakeClock、进程启动世代 owner 和完整租约不等式未统一，可能误判活 Worker 失联；
20. `recovery_required` 的同键新受理、清理 unknown 和 Callback unknown 尚未逐业务分离，存在隐藏扩大 409 的风险。

## 3. 对旧阶段 2 及后续设计的修订

### 3.1 旧设计中正确且保留的方向

- 数据库是任务真相源，Event 只是可丢唤醒；
- 消息和 Worker 只传内部 ID，不传 request、Session、文件句柄或大对象；
- 至少一次投递必须由幂等消费、条件写、lease/fencing 和检查点承接；
- 业务终态、Callback Delivery 和资源清理相互独立；
- 先统一业务内核，再迁移数据库、Outbox、队列、FastAPI 和 Chat Worker；
- 未知所有权或未知外部结果保守隔离；
- 阶段 2 只提供 SQLite 单实例证据，不冒充生产和多实例能力。

### 3.2 旧设计的不足及本次修改

| 旧问题 | 风险 | 本次修订 |
| --- | --- | --- |
| 把 `accepted -> queued -> leased -> running -> outcome_unknown` 画成一条 Task 状态机 | 混淆持久受理、消息派发、执行权和步骤结果；公开状态无法安全映射 | 拆为 Task、Attempt、Step 三套状态机；`leased` 属于 Attempt，`outcome_unknown` 首先属于 Step/Delivery |
| “Reaper 只回收过期且非终态任务” | 可能重复外部写、重复模型调用或误删资源 | Reaper 必须先读 Step/Checkpoint 和业务恢复策略；过期只是候选条件，不是重试许可 |
| 阶段 2 直接新建 `tasks/task_inputs` | 与现有 `llm_task_executions` 形成双 Task 真相和长双写 | SQLite 阶段复用现有 execution 行作为 Task；只新增 Attempt/Step/Event 与 Recovery Case/Operation/Observation/Decision 表；阶段 3 再在空 MySQL 中规范命名 |
| 所有“attempt”统一入 `task_attempts` | 模型重试、Callback 发送、Step 重试和 Worker 所有权语义不同 | `task_attempts` 只表示整任务执行权；Step、模型、Callback 各自保存领域 Attempt，并通过 task/attempt/step 关联 |
| 要求所有输入已经完整不可变 | 当前 URL 和文档引用可能在重启间变化 | 区分“决策快照”“源身份快照”“内容 Artifact”；阶段 2 冻结前两者并记录运行时内容摘要，阶段 3 才冻结共享内容字节 |
| 阶段 2 让 Chat 直接复用统一 Task 表 | ChatRun 与 Task 双写，消息/中断/流终态可能不一致 | 阶段 2 只冻结映射；ChatRun 继续唯一权威，阶段 9 需要队列派发时再由 Task 引用 ChatRun |
| 阶段 2 再“统一 Dispatcher” | 当前通用内核已经存在，重复重写风险高 | 复用一个 Executor 实现并按 Report/Weaponry/Analysis 分别实例化，建立公平共享容量，把重型执行与维护调度分离；不重造队列 |
| 拆 Store 但不定义事务协调 | Store 各自提交会产生 Task 有了但 Guard/Event/资源 intent 缺失的半状态 | 建立共享 SQLite Transaction Manager + 窄用例 UoW；Store 绑定同一连接且不得自行提交 |
| 在旧 SQLite 原地追加字段 | 旧 CHECK 不能接受新状态，Schema 世代和旧代码兼容性不可判断 | 使用独立 v2 空库、数据库级身份和旧库只读预检；不迁移历史行、不隐式修表 |
| 只定义通用副作用类别 | 无法从业务 Step unknown 推导安全恢复动作 | 每业务建立版本化 Step/Recovery Registry，并把 `effect_kind` 与 `replay_policy` 正交建模 |
| 各处直接读取系统时间/复用线程名 owner | 时钟回拨可能误收割，进程重启后的 `worker-0` 身份碰撞 | 注入 Clock/FakeClock、统一 UTC、owner 含启动世代并冻结租约不等式；异常 fail closed |
| 把所有 unknown 当失败或都阻塞新任务 | 可能改变公开状态/409，或让清理故障阻塞正常业务 | 核心 unknown 保持活动投影并复用现有冲突；终态 cleanup 独立；Callback unknown 沿用 Guard；不同键不全局阻塞 |
| 未处理 Analysis 增加并发后的顺序 | 后续文件可能提前执行，改变公开可观察语义 | 增加持久化 runnable 资格：同批次只有最小未终态 sequence 可领取 |
| `task_events` 同时描述公开回放和内部审计 | 容易把内部字段泄露给 SSE，或误走事件溯源 | 阶段 2 事件只做内部追加审计；Task 行仍是当前状态真相，阶段 7 再设计公开通知投影 |
| 阶段 5 再“实现” lease/fencing/Reaper | 同一语义会在本地和 Celery 重写两次 | 阶段 2 完成语义和 SQLite实现；阶段 3/5 只替换存储/运行适配器并做跨实例故障验证 |
| 阶段 3 同时把 MySQL 与 MinIO 作为一个不可分割门禁 | 两项基础设施迁移互相阻塞，故障定位困难 | 阶段 3 分成 3A 共享数据库和 3B 共享 Artifact，两套门禁独立；外部 Worker 切换必须同时满足二者 |
| 只在 `LLMTaskService` 外增加新 Port/Store | SQL 和事务所有权仍留在巨型旧服务，形成“新名字调用旧实现” | 新 Store 直接拥有 SQL；只允许旧调用入口短期单向委托新 Store，调用方清零后物理删除旧入口 |
| 把所有结构整理延期到阶段 3 | 阶段 2 会继续扩大 `services` 债务，阶段 3 同时承担目录和数据库双重迁移 | 阶段 2 随业务波次迁走已触达职责；Knowledge DatabaseService/Index/RAG Lease 只冻结边界，阶段 3A 再迁移 |
| 继续向 `core/config.py` 增加任务配置 | 配置来源、校验和模块所有权继续混杂 | Tasks、Report、Analysis 配置归入各自 `adapters/runtime_config.py`；Weaponry 在其迁移波次规范命名；未改造模块按后续阶段迁移 |
| 把 Callback 本地 JSON 当作发送真相或全部删除 | 前者可能错误驱动重试，后者会破坏现有 Debug 诊断 | 将其定义为 best-effort 诊断副本并迁入显式 Observability Adapter；Callback Guard/Delivery 表仍是权威事实 |

## 4. 冻结的内部设计决议

### D2-01：Task 身份

- 阶段 2 中 `TaskId` 继续等于现有 `llm_task_executions.execution_id`；
- `business_type + business_key` 只定位公开 latest 投影和并发规则，不作为 Task 主键；
- 同一业务键的新执行拥有新 TaskId，旧 Task 可被标记为 `stale`，但其资源、审计和未知结果仍按旧 TaskId 保留；
- 内部 ID 不进入任何现有公开响应。

### D2-02：Task 状态机

```text
accepted ──claim──> running ───────────────> succeeded
    │                  ├───────────────────> failed
    │                  ├───────────────────> recovery_required
    │                  └──superseded───────> stale
    └──superseded──────────────────────────> stale

recovery_required ──retry_authorized─────> accepted
recovery_required ──reconciled_result────> succeeded / failed
recovery_required ──superseded───────────> stale
```

- `accepted` 同时表达“已持久受理、等待领取或处于持久退避”，阶段 2 不增加无消息系统支撑的 `queued`；
- `recovery_required` 是内部运维隔离态，不自动重试；它没有新的公开状态值；
- `recovery_required` 不能直接进入 `running`，也不能恢复旧 Attempt。只有持久化 Recovery
  Decision 证明无副作用、已幂等对账或补偿完成后，Task 才能先回到 `accepted`，再由普通 claim
  创建更大 attempt/fencing 的新执行权；
- `succeeded/failed/stale` 对普通执行路径不可逆；仅显式恢复用例可从 `recovery_required` 收敛；
- 不加入通用 `cancelled`。Chat 的 abort 继续使用 ChatRun 状态机。

`recovery_required` 的公开投影不采用统一新值。必须先区分“核心业务结果未知”“终态后的清理未知”
和“Callback 投递未知”，三者不能共用一个模糊的失败状态：

| 进入原因 | 公开投影规则 |
| --- | --- |
| 核心业务 Step 结果未知，无法确认本次业务是否已经成功或失败 | Task 进入 `recovery_required`；保留最后一次已提交的既有“活动中”公开 status/progress/message，不伪造失败或成功 |
| 核心业务已经形成可信失败结果 | 使用该业务既有失败 Presenter；仅当仍有核心结果未知时 Task 才保持 `recovery_required` |
| 业务终态已可信提交，只剩临时资源清理/删除未知 | Task 保持既有成功/失败终态；清理进入独立 pending/quarantine，不回滚 Task，不伪造 `recovery_required` |
| 业务终态已可信提交，只剩 Callback 投递未知 | Task 保持终态；继续由独立 Callback Guard/Delivery 表和现有 `/llm/check-task` 合同处理 |
| 对账确认成功或失败 | 通过该业务现有成功/失败 Presenter 条件提交 |
| Task 已被同业务键新 Task 取代 | 旧 Task 标记 stale，不再更新 latest 公开投影 |

因此阶段 2 不需要修改接口文档。核心业务结果未知时仍投影为该业务既有“活动任务”，同业务键
新提交复用现有活动冲突规则；Callback unknown 继续复用既有 Guard 冲突规则。终态后的独立清理
unknown 在资源身份和 fencing 隔离成立时不得阻塞新受理；不同业务键不得被一个恢复现场全局阻塞。
如果某个业务无法在既有活动状态/错误结构内表达上述规则，必须停止编码并先确认接口文档，不能
通过“内部状态机调整”新增 HTTP 状态码、扩大 409 含义或改动公开字段。

### D2-03：Attempt 状态机和执行权

```text
leased ──start──> running ───────────────> succeeded
   │                 ├───────────────────> failed
   │                 └──lease expired────> expired
   └──lease expired──────────────────────> expired

expired ──reaper classification─────────> abandoned
```

`TaskExecutionAuthority` 至少包含：

- `task_id`；
- `attempt_no`；
- `owner_id`；
- 随机 `lease_token`；
- 单调 `fencing_token`；
- `lease_expires_at`。

`owner_id` 只用于诊断和追踪，不是执行权本身；其稳定结构、持久化时间和租约不等式见 D2-17。
claim 输入必须携带不可变 `TaskOwnerIdentity(instance_start_id, process_id, executor_name,
worker_slot)`；规范 `owner_id` 只能由该对象派生。SQLite 同时保存组合文本和四个拆分字段，Store
不得解析调用方提供的任意 owner 字符串，也不得把 owner 任一字段提升为 Authority。

领取在一个 `BEGIN IMMEDIATE` 短事务中完成：确认 Task 可领取、创建下一 Attempt、递增 fencing、切换 Task 当前 Attempt 并追加事件。心跳、进度、Step、产物引用和终态都必须按完整 Authority 条件写；仅校验 TaskId 不足以写入。

### D2-04：Step、Step Attempt 与副作用分类

`task_steps` 保存每个稳定 `step_key` 的当前投影，`task_step_attempts` 追加保存每次步骤执行。原先单个
`effect_class` 同时混合“动作发生在哪里”和“能否重放”两个维度，无法准确表达“外部写但可探测”
与“本地写但所有权未知”。阶段 2 改为两个正交字段：

| `effect_kind` | 含义 |
| --- | --- |
| `pure` | 纯计算，不写本地或外部状态 |
| `local_write` | 写任务目录、本地 Artifact 或本地业务事实 |
| `external_read` | 只读下载、查询、检索或探测；仍需考虑来源内容漂移 |
| `external_write` | 创建、绑定、上传、模型生成、Callback 等可能改变外部状态的动作 |

| `replay_policy` | 过期/响应丢失后的默认处理 |
| --- | --- |
| `safe` | 由冻结输入可确定性重算，或确认尚未越过任何副作用边界 |
| `idempotent_after_probe` | 必须先按稳定幂等键/外部引用探测，证明复用或重放安全后才允许继续 |
| `reconcile_only` | 普通 Worker 不得重放，只允许 Recovery Coordinator 对账、补偿或从检查点收敛 |
| `never_auto` | 即使超时也不自动重放；证据不足时长期隔离并等待专项决策 |

每个业务 Step 还必须登记稳定 `step_key`、定义版本、幂等键推导、Intent/Checkpoint Schema、结果
引用、探测/补偿方式和 `retry_from_step` 规则；完整目录见 D2-19。不得只凭 `effect_kind` 推导恢复。

Step 状态：

```text
pending -> running -> succeeded
                  ├-> failed
                  ├-> outcome_unknown -> recovery_required / succeeded / failed
                  ├-> skipped
                  └-> compensated
```

每个外部写步骤必须先保存 `intent_recorded` 检查点，再执行网络 I/O，返回后保存 `effect_confirmed` 或
`outcome_unknown`。`TaskStepCompletionCommand` 必须显式携带 `SUCCEED/FAIL/MARK_OUTCOME_UNKNOWN`
转换，禁止用 checkpoint 是否存在猜结果；`SKIP` 使用独立命令，`COMPENSATE` 只允许 Recovery
Authority 路径。unknown 完成必须在同一事务撤销当前 Attempt、把 Task 隔离为
`recovery_required`、创建新 generation Case 并追加 Event。数据库事务内禁止网络调用。

### D2-05：Attempt 命名空间

- `task_attempts`：整任务 Worker 执行权；
- `task_step_attempts`：一个业务步骤的多次执行；
- `llm_interaction_attempts`：RAG/模型调用审计；
- `callback_delivery_attempt*`：Callback HTTP 投递；
- Reassign 自有 Step Attempt：同步 Saga 写入；
- DocumentProcessing 自有 External Operation：转换器/浏览器/MinerU 调用。

这些记录可以互相引用 `task_id/attempt_no/step_key`，但不能因名称相似而合表或共享状态枚举。

### D2-06：Event 不是事件溯源

- `task_events` 与对应状态变更在同一事务追加；追加失败必须回滚状态变更；
- 每个 Task 的 `sequence_no` 严格递增且唯一；
- Task/Attempt/Step 行是当前状态权威，启动时不通过重放全部事件重建状态；
- 事件只保存稳定事件类型、身份、原因码和有上限的脱敏元数据；不保存密钥、完整请求、文件正文、模型正文、Callback 正文或公开响应对象；
- 阶段 7 的跨实例 Progress 可以读取当前 Task 投影并把事件作为唤醒/诊断依据，但不能原样公开内部事件。

### D2-07：Reaper 是分类器，不是重置器

Reaper 只扫描“Task 为 `running` 且当前 Attempt 租约已过期”的候选。对每个候选调用业务 `TaskRecoveryPolicyPort`，结果只能是：

| 分类 | 动作 |
| --- | --- |
| `retry_safe` | 旧 Attempt 标为 `expired/abandoned`，Task 回到 `accepted` 并设置有限退避；下一次 claim 创建新 Attempt |
| `finalize_from_checkpoint` | 依据已验证检查点条件提交既有结果，不重新调用外部系统 |
| `reconcile_required` | Task 进入 `recovery_required`，等待业务对账或人工处理 |
| `mark_stale` | latest 已变化，旧 Task/Attempt 收敛为 stale/abandoned |
| `defer` | 证据暂不足但仍可能自动探测，记录原因和下次检查时间；不延长旧执行权 |

`retry_safe` 使用专属 `TaskTransition.RETRY_SAFE` 表达证据充分的 `running -> accepted`；只有
`classify_candidate_if_current` 在 source Attempt/fencing CAS 成功时可调用，并必须同时把旧 Attempt
收敛为 abandoned、设置有限退避和追加 Event。它不开放普通 Worker 或脚本的通用 running reset。

过期本身永远不等于 `retry_safe`。Callback `delivery_outcome_unknown`、Weaponry 未确认 Workspace 所有权、DocumentProcessing `outcome_unknown`、Reassign 未确认远端成员关系等都不能被通用 Reaper 自动重放。

`outcome_unknown` 与 `recovery_required` 不合并为一个状态：前者描述某一次 Step/Callback Delivery
“请求可能已产生外部效果，但结果无法确认”的领域结果；后者描述整个 Task/Operation 已被通用
调度器隔离、必须先对账或人工决定的控制状态。二者可能同时出现，例如 Step 保存
`outcome_unknown`，Task 因此进入 `recovery_required`。保留两层事实才能区分“未知发生在哪个
副作用”与“整个任务现在是否允许重新调度”，也避免对外增加统一新状态值。

### D2-07A：`recovery_required` 的恢复执行协议

`recovery_required` 不是“等待普通 Worker 重试”，而是从 Executor runnable 集合中隔离出来的
控制态。恢复必须经过独立的 Recovery Case，不能由 SQL、脚本或人工把 `execution_state` 直接改成
`accepted/running`。旧 Attempt、旧 Step Attempt 和原始 `outcome_unknown` 事实保持追加式历史，
只有进入一个全新的独立恢复现场并创建 Recovery Case 时才递增 `recovery_generation`；同一 Case
内的领取、Observation、`keep_quarantined`、关闭 Decision 和 `retry_authorized` 都不得再次递增。
真正重新执行时由普通 claim 递增 `attempt_no` 和 Task fencing，不能借恢复代次表达执行代次。

Recovery Case 自身采用 `open -> observing -> awaiting_evidence -> resolved/superseded`。`open` 和
`awaiting_evidence` 可直接领取；`observing` 只有在数据库租约不晚于新请求 `claimed_at` 时才能由
一条 CAS 直接接管并递增 Recovery fencing，未过期 owner 不得被抢占。已经提交的 Operation Intent
和 Observation 均不回滚；
`resolved/superseded` 不可重新打开，如后续发现新的独立恢复现场，必须递增 recovery generation
并创建新 Case。

#### 恢复流程

过期候选的五类 Policy 结论统一通过
`TaskRecoveryClassificationCommand(candidate, classification, policy_version, classified_at,
case_id, next_action_at)` 提交，Store 只提供 `classify_candidate_if_current` 一条 source
Attempt/fencing CAS 入口：`reconcile_required/finalize_from_checkpoint` 必须预先给出稳定 Case ID，
`retry_safe/defer` 必须给出晚于分类时间的下一动作时间，`mark_stale` 不携带二者。旧的
`create_case_if_current` 不能继续存在，因为它无法完整表达非 Case 分类，也会诱导调用方把所有
过期现场都错误等同于建 Case。分类后的精确状态动作仍必须遵守既有 Task/Attempt 状态机和下述
Recovery Decision 协议，不能仅凭方法名推导 `running -> accepted`。

1. **建立 Recovery Case**：Reaper 在同一短事务中复核 Task、过期 Attempt、Step/Checkpoint、
   latest 和行版本，把旧 Attempt 收敛为 `expired/abandoned`，将 Task 置为 `recovery_required`，
   创建/复用该 generation 唯一的 Recovery Case 并追加隔离事件。
2. **取得恢复权**：自动协调器或审计化内部运维命令通过 CAS 取得 Recovery Case 的短租约和独立
   fencing。Task Attempt fencing 与 Recovery fencing 不混用；同一个 Case 同时只有一个恢复 owner。
   事务外探测/补偿期间必须通过 `heartbeat_case` 携带完整 Recovery Authority 条件续约；成功返回
   新到期时间后旧 Authority 立即失效。一旦 heartbeat 失权，停止后续可停止动作，Observation/
   Decision 条件写必须被旧 Recovery fencing 拒绝。
3. **收集证据**：先用 `begin_operation` 在事务中登记带稳定 operation ID/幂等键的
   probe/compensation intent，再在事务外执行有界、优先只读的远端探测；随后携带当前 Recovery
   fencing 追加引用该 operation 的唯一 Observation，并在同一短事务把 Operation 收敛为
   `observation_recorded`。接管 owner 可对账旧 fencing 已提交但未收敛的 Intent，不能换 ID 绕过
   幂等键。不得在数据库事务内访问 AnythingLLM、模型、MinIO 或 Callback 接收方，也不得用
   “查不到”直接推断“从未执行”。
4. **形成 Decision**：业务 `TaskRecoveryPolicyPort` 只使用冻结输入/Profile、Step 历史、外部引用、
   Observation 和明确的幂等/补偿证据作出下表决策。Decision 必须保存稳定 ID、expected Task
   row version/source Attempt/source fencing、policy version、证据摘要、操作者/自动来源和原因码。
5. **原子收敛**：Control Store 用 Task CAS + Recovery fencing 在同一短事务提交 Decision、Task
   状态、保持不变的 recovery generation、重试检查点和 Event。`keep_quarantined` 可写下一观察时间；
   `retry_authorized` 必须携带 `TaskRecoveryStepResolution`，按 source Step Attempt/row version 和
   operation/observation/evidence digest 复核，只把当前 `outcome_unknown` Step 投影转回 `pending`，
   旧 Step Attempt 保持不可变；
   `finalize_from_checkpoint` 必须携带内部 Terminal Projection，并复核来源 Step Attempt、checkpoint
   code/digest 后原子更新既有 latest `public_status/message/result_ref`，Store 禁止按业务类型猜值。
   阶段 2 提交后只发送本地可丢唤醒；阶段 4 后，
   允许重试的 Decision 与 Recovery Dispatch Outbox 在同一 MySQL UoW 提交。

| Decision | 必要证据 | Task 动作 | 是否重新执行业务 |
| --- | --- | --- | --- |
| `keep_quarantined` | 证据不足、远端不可查或所有权仍未知 | Case 转为 `awaiting_evidence`，Task 保持 `recovery_required`，记录下次探测时间或等待人工补证；这是非关闭 Decision，可在取得新证据后再次评估 | 否 |
| `retry_authorized` | 确认请求未发送/未生效；或补偿完成且复核通过；证据必须引用已收敛 Operation/Observation | `recovery_required -> accepted`，保持当前 recovery generation，以 Step Resolution 把精确 unknown 当前投影转回 `pending`，旧 Step Attempt 不变 | 是；由普通 Executor 之后创建新 Task Attempt 和新 Step Attempt |
| `finalize_from_checkpoint` | 外部结果和本地结果引用已确认完整、输入/Profile 一致 | 条件提交既有成功/失败结果，不再调用外部系统 | 否 |
| `mark_stale` | 同业务键 latest 已被新 Task 合法取代，且旧现场已按策略隔离 | Task/旧 Attempt 收敛为 stale/abandoned | 否 |

`retry_authorized` 后也不能直接调用 `RunXxxTask`：Task 先回到 `accepted`，由正常 Executor/Consumer
执行 claim，创建新 Attempt、递增 Task fencing，然后依据 `retry_from_step/checkpoint` 跳过已经
验证成功且仍有效的步骤，只为允许重试的步骤创建新 Step Attempt。新 Attempt 必须继续使用原 Task
冻结的输入、内容摘要和 Execution Profile；任一输入/Artifact/Profile 漂移都重新进入隔离，不能
读取当前环境默认值继续执行。公开 Progress 保留最后一次可信投影，恢复执行不得先倒退公开进度，
只有新检查点超过既有可信进度后才向前更新。

四类序号必须始终分别表达一个含义：

| 序号 | 递增时点 |
| --- | --- |
| `attempt_no` | 普通 Executor/Consumer 每次合法取得新的业务执行权 |
| Task `fencing_token` | 每次新的 Task 执行 Authority 成立 |
| `recovery_generation` | 每次进入全新的独立恢复现场并创建 Recovery Case |
| Recovery fencing | 同一个 Recovery Case 被新的恢复 owner 合法领取 |

这里恢复的是“同一个 Task 的新 Attempt”，不是创建新 Task。调用方再次提交既有业务接口只是
普通新受理，不是 Recovery Decision；如果现有公开合同允许该请求并使 latest 指向新 Task，旧
Recovery Case 只能按 `mark_stale` 收敛并继续隔离/清理其未知资源，绝不能再次恢复执行、重新成为
latest 或覆盖新 Task 投影。阶段 2 不自行增加新的 409，但各业务已有活动任务、Callback Guard、
资源所有权和幂等门禁仍必须在受理事务中完整执行。

人工处理也不提供通用“接受重复风险并强制重跑”按钮。默认只能提交证据和请求业务恢复策略重新
判定；若未来某个外部步骤确需人工授权 at-least-once 重放，必须为该步骤单独立项，冻结幂等键、
重复副作用和补偿协议，并取得负责人确认，不能复用 `/llm/check-task` 或通用 Recovery Decision。

### D2-08：Callback 与业务终态保持正交

- 业务 Task 成功/失败不等待远端清理，也不因 Callback unknown 回滚；
- `/llm/check-task` 永久保留请求内同步恢复，继续与正常 Worker/未来后台 Worker 竞争同一 Callback Guard；
- 该接口只按现有合同查询业务键并授权 file/report/weaponry 的 Callback Delivery 恢复，包括
  Callback `outcome_unknown` 的 at-least-once 补发；它不是通用业务 Task/Step 恢复或重跑接口。
  业务执行 `outcome_unknown`/`recovery_required` 必须走内部对账、恢复策略或审计化运维命令，
  不得复用 check-task 偷渡新的公开副作用语义。
- Callback Guard/Delivery 继续使用独立状态机；由于新任务受理必须与 Guard 冲突判断处于同一
  SQLite 事务，其底层持久化原语与 Task Control Store 共用连接/事务，业务 Callback Application
  仍拥有“何时发送、如何分类和如何恢复”的语义；
- 阶段 2 只增加关联 Task Attempt/Step 上下文，不改变已有 Guard、显式 unknown 恢复和人工解除语义；
- Callback Delivery Attempt 不计入 Task Attempt 编号。

### D2-09：Analysis 批量采用“子 Task + 持久可运行资格”

- 每个文件继续是一条独立 Task，保留共同 `batch_id` 和连续 `batch_sequence`；
- Admission 冻结输入必须显式携带 `TaskBatchRef(batch_id, sequence)`；file Task 缺少批次或非 file
  Task 携带批次均失败关闭。`admit_many` 只接受同一 batch ID、从 1 开始连续且与输入次序一致的
  Analysis 列表，禁止 Store 从 payload 推断、补号或重排；
- 不新建没有公开业务价值的父 Task；`AnalysisBatchOrderCoordinator` 继续验证受理回显，不保存队列；
- SQLite runnable 查询只返回：本 Task 为 accepted、已到退避时间、latest 未变化，且同 batch 中不存在更小 sequence 的非终态/`recovery_required` Task；
- 同一批次前序 `failed` 仍按当前既有语义允许后序继续；前序 `recovery_required` 阻止后序，直到显式收敛；阶段 2 不允许未经逐 Task 证据判定的“整批隐式 supersede”；
- 不同批次在 Analysis Executor 内按 `dispatch_sequence` 公平扫描；跨业务不承诺严格全局 FIFO，真实重型执行受共享公平 limiter 约束且必须无饥饿。

### D2-10：输入快照分层

| 层次 | 阶段 2 责任 | 例子 |
| --- | --- | --- |
| 决策快照 | 必须在 accepted 事务前冻结并版本化 | 解析规则、OCR/MinerU/Translation Profile、Prompt/模型/检索策略指纹 |
| 源身份快照 | 必须冻结请求时选择结果 | URL、fileName、document key、architecture id、AnythingLLM document id |
| 内容 Artifact | 阶段 2 在首次读取后记录 size/SHA-256/本地引用；跨实例不可变存储延期到阶段 3B | 下载文件、模板、报告、中间 Markdown、Weaponry 文档内容 |

具体版本处理：

- Report 新写内部 Input v2，兼容读取 v1；v2 增加文档处理、RAG Provider、Prompt/Sanitizer 及输出策略指纹；
- Analysis 新写内部 Input v5，兼容读取 v1～v4；v5 增加 Translation Profile 和当前仍在运行时解析的执行策略；
- Weaponry 继续写当前 v2，不因统一任务内核无意义升版。`260804-知识谱系解析直接父节点文件范围实施计划.md` 若获批实施，由该专项独占 Weaponry v3；
- 通用 Task 控制 Schema 与业务 Input Schema 分开版本化，避免“任务租约升级”消耗业务 Codec 版本号。

D2-18 采用新空库，因此历史 Codec 的“兼容读取”用于契约测试、离线诊断和明确输入样本，不表示把
旧 Task 行迁入 v2 后继续执行。禁止用当前环境默认值为旧 Profile 补字段后恢复运行。

Execution Profile 必须使用确定性 Canonical JSON：UTF-8 编码；对象键按 Unicode 码点排序；数组
保持业务顺序；集合先规范化再稳定排序；禁止 `NaN/Infinity`；需要精确比较的数值使用规范十进制
字符串；时间统一使用带 `Z` 的 UTC；秘密、Token、完整 URL 查询串和本机绝对路径不得进入 Profile，
只保存经过规则化的标识或脱敏 fingerprint。Fingerprint 统一为
`SHA-256(schema_name + "\n" + schema_version + "\n" + canonical_json_bytes)`。每个 Input 版本必须
冻结字段名、类型、是否可空、默认值、排序规则和 Capability 比较规则；不得因 Python 字典顺序、
集合迭代顺序或当前环境默认值产生不同身份。

Worker 在第一笔外部 I/O 前必须用运行时 Capability 与冻结 Profile 做精确兼容校验；不匹配时按
现有业务失败 Presenter 收敛或进入内部恢复隔离，禁止读取新环境默认值继续执行。Fingerprint 只证明
配置身份可追踪，不证明模型质量或生产 attestation。若同一 Task 已记录源内容 SHA-256，后续重新读取
得到不同内容，必须进入 `recovery_required`，不能把变化后的字节当成原任务继续运行。

### D2-11：Chat、Reassign、DocumentProcessing 的关系

- ChatRun 继续拥有会话互斥、pending/committed 消息、流事件、中断和终态；当前 SQLite Chat lease 能力仍明确声明没有 fencing；
- 阶段 2 只建立语义对照和 Repository 契约测试，不向 Chat 写第二条 Task。阶段 9 创建可靠派发时，Task 只引用 `chat_run_id` 并承载可调度执行权；消息和流终态仍由 ChatRun 原子提交；
- ReassignmentOperation 是同步 Saga，不进入本地异步 Task 扫描。其已验证的 lease/fencing/checkpoint 作为通用任务实现参考；
- DocumentProcessing Step/ExternalOperation 是父业务 Task 的步骤证据。父 Task 只保存关联 step key 和处理记录引用，不复制处理表；
- Translation 是共享能力步骤，不独立创建 Task Attempt。

### D2-12：本地执行与维护分离

- 采用“**统一 Executor 内核、按业务分别实例化**”的拓扑：共享一个 `LocalTaskExecutor` 实现和
  Task Control 协议，但在组合根中分别创建 `ReportExecutor`、`WeaponryExecutor`、`AnalysisExecutor`；
  每个实例只扫描自身 `task_type`，注入自己的 Runner、Recovery Policy、worker slots、退避/毒任务
  冷却、readiness 名称和未来队列路由；不得复制 claim/heartbeat/fencing/停机内核；
- `LocalMaintenanceScheduler` 负责 Callback Guard sweep、资源恢复、Task Reaper 等周期任务；
- 两者都把 Event 当作合并唤醒，启动和周期扫描才是恢复保障；
- 每个业务实例内只保存不超过本业务 `worker_count` 的在途 TaskId 和一个合并唤醒；所有实例均不
  保存 accepted 全量 ID；毒任务的 `next_dispatch_at/reason_code` 持久化，不能靠内存跳过；
- 各业务内部按自身 `dispatch_sequence`/批次资格保持 FIFO；跨业务不承诺严格全局 FIFO，由共享
  公平容量仲裁器按业务轮转/配额保证无饥饿，不能由最快扫描器长期抢占唯一许可；
- 容量分层：业务 worker slot 只限制本业务线程；AnythingLLM ingestion、模型调用、文档处理和
  Callback 分别使用明确 limiter，不能用一个含义模糊的总许可覆盖全部 I/O；阶段 2 初始配置仍让
  真实重型业务总并发为 1，其他容量只通过 Fake 验证，不据此宣称供应商并发能力；
- 现有三个 `local_dispatcher.py` 只保留业务装配、唤醒和指标映射，不再拥有独立调度算法；阶段 5
  可一一映射为 Report/Weaponry/Analysis 独立队列与 Consumer，而不修改 Task Runtime；
- 共享容量许可等待、业务 worker 和 heartbeat 必须可中断；某一业务 readiness 失败不得让其他业务
  错误领取该类型任务，但共享 Control DB/时钟异常必须使所有新 claim fail closed。

  内部回调 `LLMTaskService`。迁移期只允许旧 Facade/旧调用方单向委托新 Store；同一操作不得双写；
- `LLMTaskService` 在阶段 2 关闭时不得继续混合 Task、Callback、业务资源和审计写入。若阶段 3
  确有需后置的 Knowledge Index/RAG Lease 能力，必须先拆成职责明确的过渡 Store；不得继续用

- `app/domain/knowledge_workspace.py` 迁入 `app/shared/domain/knowledge_workspace.py`。该规则无 I/O、
  被多个模块稳定复用，属于小型共享领域内核；迁移后删除空的 `app/domain`；
- `app/adapters/web` 是目标协议边界而非遗留目录。阶段 2 不整体搬迁，只允许随 Admission 用例

- `DatabaseService` 的 Knowledge 表和操作只在阶段 2 冻结 Port/所有权并禁止新增直接依赖，物理

每个迁移单元必须按“纯路径移动与导入调整 -> 定向/合同测试 -> 新位置语义改造 -> 删除兼容路径”
执行。禁止在同一不可审查补丁中同时搬文件、改类名、改 SQL、改状态机和删除回滚点。

### D2-15：Callback 本地历史是诊断副本

`/debug/api/callback`、`/debug/callback` 和人工比对使用，因此阶段 2 不删除该能力。其语义必须冻结为：

- best-effort、追加写、文件名防覆盖的本地诊断副本；写入失败记录脱敏日志，但不改变 Callback
  发送、Guard 或业务终态；
- 不能作为 Callback 是否成功、是否允许重试、latest-wins、Task Recovery 或恢复证据的权威来源；
  权威事实仍是 Callback Guard/Delivery/Attempt 表；
- Writer 从 `app/services/utils/callback_client.py` 迁入明确的 Observability Infrastructure Adapter，
  Debug Reader 继续保持只读 Port/Adapter，并由组合根注入同一历史目录；
- 当前无正式生产调用方的 `post_callback_payload` 经生产、脚本、测试和动态引用门禁后删除；各业务
  Callback HTTP Adapter 继续拥有发送语义，不建立新的通用 HTTP Facade；
- 文件可能含业务载荷，日志不得输出正文；部署继续限制 `/debug/*`。自动 TTL/清理在保留期决策

### D2-16：SQLite 事务采用“共享基础设施 + 窄用例 UoW”

拆分 `LLMTaskService` 不能以牺牲原子性为代价。阶段 2 不保留巨型 Service，也不建立一个包含所有
模块方法的巨型 UoW，而是分为两层：

1. `SQLiteConnectionFactory/SQLiteTransactionManager` 只负责连接创建、`BEGIN IMMEDIATE`、
   commit/rollback、busy/locked 分类、Schema 身份校验和关闭；它不理解 Task、Report 或 Callback；
2. `TaskAdmissionUnitOfWork`、`ReportExecutionUnitOfWork`、`WeaponryExecutionUnitOfWork`、
   `AnalysisExecutionUnitOfWork`、`TaskRecoveryUnitOfWork` 等窄 UoW 只暴露一个用例所需 Store，
   由 Application 明确决定事务边界。

冻结规则如下：

- 同一 UoW 内所有 Store 绑定同一个 SQLite Connection；Store 禁止自行 commit/rollback/close；
- 写命令必须进入显式 UoW；只读 Query Store 可以使用独立短连接，但不得把读出的旧版本当作写权限；
- Application 必须显式 `commit()`；正常退出但未 commit、异常退出或取消一律 rollback；
- 阶段 2 禁止嵌套 UoW 和业务层 SAVEPOINT，避免部分提交语义；确需嵌套必须先独立评审；
- SQLite Connection 不跨线程共享；每个 UoW 在创建线程内完成，连接工厂按调用创建/归还；
- 网络、模型、文件转换、对象删除、阻塞许可等待不得发生在 UoW 内；
- busy/locked 统一映射为可观测的基础设施错误，由上层按操作类别决定有限退避；Store 不得隐藏重试，
  事务管理器不得自动重放包含未知调用方逻辑的事务；
- 一个迁移单元只能有一个事务所有者；旧 Facade 可以单向调用新 UoW，但新 Store/UoW 禁止回调旧 Service。

必须保持原子的用例组至少包括：

| UoW | 同一事务内的事实 |
| --- | --- |
| Admission | 活动 Task/Callback Guard 冲突检查、输入 execution、latest 投影、accepted Event；Analysis 批量全部成功或全部回滚 |
| Claim | runnable/latest/批次资格复核、Attempt、Task fencing/current attempt/running、claimed Event |
| Begin external step | Authority、Task Step intent、Step Attempt、业务 Resource/ExternalOperation intent、Event |
| Complete step | Authority、显式 Step 转换、Step 结果/Checkpoint/外部引用、业务 Resource/Audit 事实、Event；unknown 同事务撤销 Attempt 并建立 Recovery Case |
| Business terminal | Authority、Task/Attempt 终态、latest 公开投影、结果引用、Event，以及已有合同所需的 Callback eligibility/Guard 事实；Callback HTTP 在事务外 |
| Recovery | 过期复核/Case 建立，或 Recovery claim/heartbeat/Observation/Decision、下一观察时间、Terminal Projection 来源 CAS 及对应 Task/latest/Event 条件写 |

### D2-17：持久化时钟、租约不等式与 Worker 身份

- 新增 `ClockPort.now_utc()`；所有持久化时间统一写为 UTC RFC3339 微秒格式并带 `Z`，禁止 naive
  datetime、本地时区字符串和不同模块自行格式化；Repository 负责严格解析和拒绝非法时间；
- 测试注入 `FakeClock` 推进时间，不以真实 `sleep` 证明租约正确性；进程内等待/超时预算可以使用
  monotonic clock，但 monotonic 值绝不持久化、绝不与其他进程比较；
- 阶段 2 单机 wall clock 若相对 monotonic 发生超过允许抖动的回拨/跃迁，系统必须暂停新 claim 和
  Reaper、把 readiness 标记为 degraded、禁止 Worker 开始新的外部副作用并记录 CRITICAL 脱敏日志；
  不能在时间异常时猜测租约已过期；阶段 3 改用数据库权威时间；
- 每次进程启动生成 `instance_start_id` UUID。诊断 `owner_id` 结构固定为
  `instance_start_id/pid/executor_name/worker_slot`；PID 只供诊断。真正写保护仍由
  `task_id + attempt_no + lease_token + fencing_token + lease_expires_at` 完成；
- `lease_token` 使用高熵随机值且不记录日志；同名 `worker-0` 在进程重启后因为
  `instance_start_id` 不同，不能被误认为旧 owner 复活。

初始建议值为 heartbeat 5 秒、SQLite busy budget 2 秒、最大时钟/调度抖动 3 秒、Task/Recovery lease 30 秒、
Reaper scan 5 秒、stop grace 10 秒；这些只是单实例保守默认值，不是生产容量结论。配置必须满足：

```text
task_lease_duration >= 3 * heartbeat_interval + 2 * sqlite_busy_budget + max_clock_jitter
recovery_lease_duration >= 3 * heartbeat_interval + 2 * sqlite_busy_budget + max_clock_jitter
reaper_scan_interval <= lease_duration
stop_grace >= heartbeat_interval + sqlite_busy_budget
```

任何非法组合在启动后台线程前失败；运行日志记录数值和配置 fingerprint，不记录秘密。

### D2-18：阶段 2 使用全新的 Task Control SQLite 路径

阶段 2 不重建旧表、不原地修改旧 `execution_state CHECK`，也不自动迁移历史行。新增内部配置
`DOCSENSE_TASK_CONTROL_DB_PATH`，默认
`${DOCSENSE_RUNTIME_DIR}/db/task-control-v2.sqlite3`。新库承载 Task Control、Callback Control 以及
阶段 2 为满足同事务要求而迁入的 Report/Analysis/Weaponry 控制/资源/审计表；Knowledge、Chat、
DocumentProcessing 等明确未迁移的权威表继续保持各自边界。

启动/切换顺序必须固定为：

1. 装载并校验 Runtime Config，解析旧/新数据库绝对路径，确认二者不同；
2. 在构造任何旧 `LLMTaskService`、Store、Application 或后台线程前取得进程级 Schema/启动锁；
3. 以只读 URI 打开旧库预检；若存在 accepted/running、Callback sending/outcome_unknown、待保留的
   recovery/cleanup/资源所有权未知事实，停止切换并输出脱敏诊断，禁止自动复制、重置或伪造检查点；
4. 新路径不存在时只允许创建空 v2 Schema；存在时必须严格验证数据库身份、Schema generation、
   根 fingerprint、组件注册/fingerprint、外键、索引和完整性；
5. 构造 Connection Factory/UoW/Store/Application；最后才启动三个业务 Executor 与 Maintenance Scheduler。

数据库级身份至少包括 `PRAGMA application_id`、`PRAGMA user_version` 和
`task_control_schema_metadata`，后者保存 `schema_name`、`schema_generation=2`、兼容范围、Schema
fingerprint、DB instance UUID 和创建时间。每行 `control_schema_version` 不能替代数据库级身份。
`schema_fingerprint` 只覆盖阶段 2-2 不可被业务组件修改的根 Manifest；根同时建立
`task_control_schema_components`。后续 Report/Weaponry/Analysis Schema 各自以稳定组件名、版本和
canonical fingerprint 登记，实际对象必须精确等于“根 + 全部已登记且当前代码认识的组件”并集。
组件不得给根表补列或改约束；未知组件、未登记对象、对象重叠或组件 fingerprint 不匹配均失败关闭。
完整算法以 `阶段2资产/260812-阶段2-2根Schema与组件Manifest设计.md` 为实施权威。
新代码遇到旧/未知/更高 generation、缺少 metadata 但已有业务表、fingerprint 不匹配时一律拒绝；
不得用宽松的 `CREATE TABLE IF NOT EXISTS` 静默修补。旧应用不读取新环境键；部署必须保证旧/新版本
不同时消费同一个 Task Control DB。

`.sqlite3`、`-wal`、`-shm` 是一个文件集。应用不得自动删除、移动或只归档其中一个；旧库只读
预检后原样保留，需归档时必须在所有相关进程停止后通过显式维护步骤完成。只有确认 v2 中不存在
accepted/running/recovery、Callback/cleanup unknown、未对账外部副作用和必须保留的新任务事实时，
才允许回切旧版本；否则只能停止领取、保留 v2 文件集并前向修复。

### D2-19：业务 Step/Recovery Registry 是编码前门禁

Report、Weaponry、Analysis 分别在模块内建立版本化 Registry；建议文件为
`domain/execution_steps.py`、`domain/recovery_policy.py`、`domain/execution_profile.py`。每条定义至少冻结：

- `step_key`、`definition_version`、`effect_kind`、`replay_policy`；
- 幂等键推导、Intent/Checkpoint/ExternalRef Schema；
- 成功结果引用、只读探测、受控补偿、超时映射和 `retry_from_step` 规则；
- 依赖的 Input/Profile 字段、允许跨 Attempt 复用的检查点和禁止自动重放的条件。

2-0 必须先对当前生产调用链做代码审计，再将下面候选拆成最终 Registry；名称可以在审计中细化，
但不得在业务切换时由实现者临时猜测：

| 业务 | 至少审计并冻结的候选 Step |
| --- | --- |
| Report | `source.download`、`document.prepare`、`template.download`、`template.extract`、`rag.session.open`、`rag.document.upload`、`rag.generate`、`interaction_audit.commit`、`report.render`、`artifact.publish`、`terminal.commit` |
| Weaponry | `document_scope.load`、`rag.workspace.create`、`rag.document.bind`、`retrieval.execute`、`evidence.select`、`field_model.execute:{field_key}`、`interaction_audit.commit`、`result.map`、`terminal.commit` |
| Analysis | `source.download`、`document.prepare`、`recall.reserve`、`rag.session.open`、`rag.document.upload`、`classification.execute`、`identity.reselect`、`extraction.execute`、`recall.finalize`、`interaction_audit.commit`、`knowledge.workspace.ensure`、`knowledge.document.bind`、`translation.execute`、`terminal.commit` |

每个最终 Step 必须有 Recovery Decision 矩阵，明确何种证据得到 `retry_safe`、
`finalize_from_checkpoint`、`reconcile_required`、`defer` 或 `mark_stale`。`TaskRecoveryPolicyPort` 是纯
决策函数，不直接访问网络或数据库；Recovery Coordinator 先持久化 probe/compensation intent，
Adapter 在事务外执行探测，再保存 Observation，最后由 Policy 基于冻结事实决策。

### D2-20：`recovery_required` 期间的新受理与解锁矩阵

统一原则是“核心结果未知保留活动投影并阻止同键；终态后的清理独立；Callback unknown 沿用现有
Guard；不同键不受牵连”。逐业务冻结如下：

| 业务 | 同键新提交 | 资源隔离和解锁条件 |
| --- | --- | --- |
| Report | 核心 RAG/生成/产物结果未知时，Task 保持现有活动投影，新提交走既有活动任务 409；终态后仅清理未知不得阻塞 | Artifact/临时 RAG 资源必须带 TaskId、Attempt/fencing 和稳定外部引用；确认结果、完成补偿或证明未生效后才由 Recovery Decision 解锁 |
| Weaponry | Workspace 创建/绑定等核心所有权未知时，保持 processing 投影并复用既有活动冲突；不得仅凭同名 Workspace 复用或删除 | 临时 Workspace/Thread 必须 Task-scoped；稳定远端 ID + Task owner + fencing 才能证明归属；永久 Knowledge Workspace 绝不进入任务清理 |
| Analysis | 同批较小 sequence 的 `recovery_required` 阻止后序；同 fileName 新批次提交复用既有活动冲突；完全无关 fileName/批次不阻塞 | 不允许整批隐式 supersede；只有逐 Task 对账成功、可证明 stale 或安全补偿后才收敛；永久 Knowledge 写入必须带可对账身份/fencing |
| Callback unknown | 继续按现有 Callback Guard 拒绝/恢复 | 仅现有 `/llm/check-task` 或既有内部恢复路径有权补发；不触发业务 Step 重跑 |

旧 Task 只有在“尚未越过外部副作用边界”“旧现场已完成对账/补偿”“资源完全 Task-scoped 且不会
污染新任务”或 Recovery Policy 已有证据作出 `mark_stale` 时才可被 supersede。即使变为 stale，
Recovery Case、Observation 和未知资源事实仍保留，旧 owner 不能写 latest 或清理新任务资源。

解锁只能来自持久化证据、Observation、补偿结果和 Recovery Decision；禁止以超时自动解锁、人工
直接改 SQL、`/llm/check-task` 偷渡业务重跑，或把内部 `recovery_required` 投影成公开 failed 后又
额外返回 409。任何无法遵守现有公开状态/409 合同的例外必须先单独确认接口文档。

## 5. SQLite 逻辑 Schema 与事务边界

### 5.1 物理表策略

阶段 2 不新增第二张 `tasks` 主表。下表全部使用 D2-18 的新 `task-control-v2.sqlite3` 空库初始化；
旧库不原地改表、不复制历史行：

| 表 | 阶段 2 定位 |
| --- | --- |
| `task_control_schema_metadata` | 新库唯一数据库级身份：Schema generation/fingerprint、兼容范围、DB instance UUID 和创建时间 |
| `task_control_schema_components` | 已安装业务组件的名称、版本、根 generation、canonical fingerprint 和安装时间；不保存任意 DDL |
| `llm_task_executions` | SQLite Task 当前事实；扩展控制版本、当前 Attempt、行版本和恢复原因 |
| `llm_tasks` | 现有公开 latest 投影；与 Task 状态/结果在同一事务更新 |
| `task_attempts` | 新增；整任务执行权、lease、heartbeat、fencing 和 Attempt 结果 |
| `task_steps` | 新增；稳定 step key 的当前检查点投影 |
| `task_step_attempts` | 新增；每次步骤执行的追加历史 |
| `task_recovery_cases` | 新增；每个 recovery generation 的当前隔离、恢复租约/fencing 和 Decision 投影 |
| `task_recovery_operations` | 新增；事务外探测/补偿前提交的 Intent、稳定幂等键和收敛状态 |
| `task_recovery_observations` | 新增；远端探测、补偿和本地一致性检查的追加证据 |
| `task_recovery_decisions` | 新增；自动/人工恢复结论、expected Authority、证据摘要和审计身份 |
| `task_events` | 新增；Task 内部追加审计 |
| 现有 Callback Guard/Delivery 表 | 保持独立状态机；底层事务原语归入 Task Control Store，以便受理与 Guard 冲突同事务；业务发送/恢复语义仍归各垂直模块 |
| 现有 Resource/Audit/DocumentProcessing 表 | 保留各自所有权，不合并；通过 task/attempt/step 身份关联 |

阶段 3 使用空 MySQL Schema 时再采用规范逻辑表名 `tasks/task_inputs/...`。Repository Port 必须隐藏 SQLite 兼容表名，使业务代码不因改名再次修改。

### 5.2 `llm_task_executions` 阶段 2 增量字段

- `control_schema_version INTEGER NOT NULL`：统一任务控制模型版本；
- `current_attempt_no INTEGER NOT NULL DEFAULT 0`；
- `row_version INTEGER NOT NULL DEFAULT 0`：当前行 CAS 版本；
- `recovery_generation INTEGER NOT NULL DEFAULT 0`：仅在进入新的独立恢复现场并创建 Recovery Case 时单调递增；Case 领取或关闭时保持不变；
- `current_recovery_case_id TEXT NULL`：仅在 `recovery_required` 时引用当前 Case；
- `recovery_reason_code TEXT NOT NULL DEFAULT ''`；
- `next_recovery_at TEXT NULL`；
- `retry_from_step_key TEXT NULL`：仅由 `retry_authorized` Decision 写入，不允许普通 Worker 修改；
- `execution_state` 允许 `recovery_required`，其余既有状态保留；
- 继续保留 `input_schema_version/input_payload/batch_id/batch_sequence/dispatch_sequence/next_dispatch_at`。

旧 SQLite 数据无需业务迁移。实施前按 D2-18 对旧文件集执行只读预检；不满足条件时停止，满足后
在新路径初始化空 v2 库，旧文件集原样保留。禁止把旧 Task/Guard/资源行复制进新库，禁止为未知
运行中旧行伪造 Attempt、Checkpoint 或 Recovery Decision。

### 5.3 新表关键约束

#### `task_attempts`

- 主键：`(task_id, attempt_no)`；
- `fencing_token` 对同 Task 单调递增且唯一；
- `lease_token` 全局高熵随机，不写日志；
- 状态、owner、claimed/started/heartbeat/expires/completed 时间完整；
- owner 字段至少拆出 `instance_start_id/executor_name/worker_slot`，PID 只作诊断；所有时间符合 D2-17；
- `error_code/error_summary/recovery_reason_code` 有确定长度上限；
- 当前 Attempt 通过 Task 行的 `current_attempt_no` 引用；
- 索引覆盖 `(state, lease_expires_at)` 和 `(owner_id, state)`。

#### `task_steps`

- 主键：`(task_id, step_key)`；
- 保存 `definition_version/effect_kind/replay_policy/state/checkpoint_code/current_step_attempt_no/idempotency_key/external_ref/row_version`；
- 外部引用和错误摘要有长度上限；
- 不保存模型正文、文件正文或完整公开响应。

#### `task_step_attempts`

- 主键：`(task_id, step_key, step_attempt_no)`；
- 保存对应 `task_attempt_no/fencing_token/intent_at/result_at/outcome/error_code`；
- 一个 Step Attempt 只允许单终态，身份由 `(task_id, step_key, step_attempt_no)` 冻结；同一稳定
  幂等键允许在经过 Recovery 授权的新 Step Attempt 中继续使用。只有完整 Authority、Step 定义、
  row version、幂等键和 intent 时间都与当前 running Attempt 一致的命令重放才返回
  `duplicate_step_intent`；冲突不得伪装成幂等成功，也不得覆盖历史。

#### `task_recovery_cases/operations/observations/decisions`

- `task_recovery_cases` 对 `(task_id, recovery_generation)` 唯一，保存 source attempt/fencing、状态、
  原因、policy version、recovery owner/token/lease expiry/单调 fencing、下次探测时间和当前 Decision；
- `task_recovery_operations` 在事务外 I/O 前保存 operation ID、case/generation/fencing、
  `probe|compensation`、step、稳定幂等键、intent digest/外部引用、状态和 intent/result 时间；
- `task_recovery_observations` 追加保存 case/operation/observation ID、step key、观测结论、外部引用
  摘要、recovery fencing、来源与时间；Observation 与 Operation 收敛必须在同一短事务完成，不保存
  供应商响应正文、凭据或文件内容；
- `task_recovery_decisions` 追加保存稳定 decision ID、expected Task row version、source attempt/fencing、
  recovery generation/fencing、decision、retry checkpoint、evidence digest、actor marker、reason code、
  policy version、时间，以及重试时精确的 Step Resolution；同一 generation 可以追加多次非关闭
  `keep_quarantined` 评估，但只能有一个
  `retry_authorized/finalize_from_checkpoint/mark_stale` 关闭 Decision；
- Recovery lease token 不写日志；actor marker 必须脱敏且可审计。旧 fencing、旧 row version、旧
  generation 或证据摘要不匹配时 Decision CAS 为零并 fail closed。

#### `task_events`

- 主键使用内部 event id，唯一约束 `(task_id, sequence_no)`；
- 保存 `event_type/attempt_no/step_key/reason_code/metadata_json/trace_id/created_at`；
- `metadata_json` 设置字节上限和允许键集合；
- 索引覆盖 `(task_id, sequence_no)` 和运维需要的 `(event_type, created_at)`。

### 5.4 原子事务矩阵

下列操作全部通过 D2-16 的窄 UoW 完成，Store 不得自行提交：

| 操作 | 同一事务内必须完成 | 事务外动作 |
| --- | --- | --- |
| 单项/Analysis 批量受理 | Callback/活动冲突判断、Task 输入、latest 投影、accepted 事件 | 提交后仅发送可丢唤醒 |
| claim | runnable/latest 复核、创建 Attempt、递增 fencing、Task running/current attempt、claimed 事件 | 启动 heartbeat supervisor，调用业务用例 |
| start | Authority/lease 未过期复核、Attempt running、started 事件 | 创建任务目录或执行第一步 |
| heartbeat | Authority 条件续期、heartbeat 事件按采样策略记录 | 无 |
| begin step | Authority、Step intent、Step Attempt、对应业务 Resource/ExternalOperation intent、事件 | 外部 I/O |
| complete step | Authority、Step 结果/检查点/外部引用、对应业务 Resource/Audit 事实、事件 | 后续业务步骤 |
| progress | Authority、Task/latest 公开投影、内部事件 | 提交后发布进程内 Progress |
| business terminal | Authority、Task/Attempt 终态、latest 公开投影、结果引用、事件和既有合同所需 Callback eligibility/Guard 事实 | Callback HTTP/清理按既有独立状态机执行 |
| Reaper classify | 过期复核、旧 Attempt 收敛、Task recovery/accepted/stale、Recovery Case、事件 | 可选业务探测必须在短事务外执行 |
| recovery claim | Case/generation/状态复核、recovery lease/fencing、事件 | 执行只读探测或受控补偿 |
| recovery observation | Recovery fencing 复核、追加 Observation、事件 | 重新调用业务 Recovery Policy |
| recovery decision | Task row version/current Case/source Attempt/Recovery fencing 复核、追加 Decision、Task 状态/保持当前 recovery generation/retry checkpoint、事件 | 阶段 2 本地 wake；阶段 4 后发布同事务 Outbox |

所有网络、模型、文件转换和对象删除均在数据库事务外执行。任何外部动作前后的数据库写分别形成可判断的检查点。

## 6. 目标调用链

```text
现有 Web Adapter
  -> SubmitAnalysis/SubmitReport/SubmitWeaponry
  -> TaskAdmissionPort
  -> TaskAdmissionUnitOfWork
       -> SQLiteTaskControlStore（Task + latest 投影）
       -> SQLiteCallbackControlStore（Guard 冲突）
  -> commit
  -> 对应业务 LocalTaskExecutor.wake_up()（可丢提示）

ReportExecutor / WeaponryExecutor / AnalysisExecutor
  -> 共享 LocalTaskExecutor 内核
  -> 对应 task_type 的 TaskRunnableQueryPort.scan()
  -> 共享公平容量仲裁器
  -> 对应 RunXxxTask.execute(task_id)
  -> TaskExecutionRuntime.run(task_id, business_workflow)
       -> claim + TaskExecutionAuthority
       -> ThreadedLeaseHeartbeatSupervisor
       -> business_workflow(TaskExecutionContext)
            -> begin/complete Step
            -> 条件 Progress
            -> 业务 Port 外部 I/O
            -> 条件终态
       -> 停止 heartbeat

LocalMaintenanceScheduler
  -> RecoverExpiredTaskAttempts
  -> TaskRecoveryPolicyPort（按业务分类）
  -> SQLiteTaskControlStore 条件收敛

RecoveryCoordinator / 受审计内部命令
  -> claim Recovery Case + recovery fencing
  -> record probe intent
  -> 事务外只读探测/受控补偿
  -> append Observation
  -> TaskRecoveryPolicyPort 再判定
  -> commit Decision
       -> keep recovery_required
       -> accepted + retry checkpoint + local wake
       -> succeeded/failed from checkpoint
       -> stale
```

`TaskExecutionRuntime` 是应用服务，不知道 Report/Analysis/Weaponry 字段；业务 Workflow 不导入 SQLite、threading 或 Dispatcher。线程只存在于本地 Adapter，阶段 5 可由 Celery Worker 的运行监督 Adapter 替换。
三个业务 Executor 是同一实现的独立实例，不是三套调度算法；它们分别映射未来的业务队列，
同时复用相同 Task Runtime、Authority、UoW、Clock 和状态机。

## 9. 故障与恢复矩阵

| 故障点 | 持久事实 | 自动动作 | 禁止动作 |
| --- | --- | --- | --- |
| accepted 后、claim 前崩溃 | Task accepted | 周期扫描重新发现 | 不需要新 Task |
| claim 后、start 前崩溃 | Attempt leased，无 Step | lease 到期后可判定 retry_safe | 旧 owner 恢复后写入 |
| start 后、任何 Step intent 前崩溃 | Attempt running，无副作用检查点 | 业务策略确认后重试 | 仅凭超时重置 |
| 本地任务目录创建后崩溃 | `local_write + idempotent_after_probe`，且路径为 task-owned | 复核归属、清理后重试 | 删除共享/未知目录 |
| 外部 intent 已记、确认未发出 | definitely_not_sent | 有限重试/新 Step Attempt | 覆盖旧 Attempt 历史 |
| 请求可能已发、响应丢失 | outcome_unknown | recovery_required/探测 | 自动再次请求 |
| 外部结果已确认、终态前崩溃 | effect_confirmed + result ref | 从检查点继续/提交终态 | 再次执行外部调用 |
| recovery_required 证据不足 | open Recovery Case | keep_quarantined/追加 Observation | 人工直接改 accepted/running |
| 探测确认未生效或补偿已验证 | 生效 Recovery Decision + retry checkpoint | Task 回 accepted，普通 claim 创建新 Attempt | 复用旧 Attempt/旧 fencing 或直接调用 Runner |
| 探测确认既有结果完整 | effect_confirmed + result ref + Decision | finalize_from_checkpoint | 为“保险”再次调用外部系统 |
| Recovery Coordinator 在探测后崩溃 | probe intent/可能缺少 Observation | 新 recovery owner 先按幂等/只读规则复核 | 假定探测未执行并盲重放补偿 |
| heartbeat 失败 | Authority 失效 | 当前 Worker 设置失权，停止后续可停止步骤 | 继续 Progress/终态/新副作用 |
| 新 Task supersede 旧 Task | 已证明未越过副作用边界/已对账补偿/资源完全隔离，且 latest 指向新 Task | Recovery Decision 逐 Task 标记 stale；资源事实继续隔离 | 整批隐式 stale、旧 Task 写公开投影或清理新任务资源 |
| 核心业务结果 unknown 时同键重提 | Task recovery_required + 既有活动投影 | 复用现有活动冲突；Recovery Coordinator 继续对账 | 投影 failed 后新增 409、创建第二个争用同资源的 Task |
| 业务终态后仅 cleanup unknown | Task terminal + cleanup pending/quarantine | 资源身份/fencing 成立时允许既有新受理规则继续 | 回滚 Task 或用 cleanup 阻塞同键新任务 |
| Callback HTTP unknown | Callback Guard unknown | 既有 check-task 显式恢复/人工审计 | Task Reaper 自动补发 |
| cleanup 失败 | 独立 cleanup pending/quarantine | 维护 Scheduler 有界重试 | 回滚业务终态或等待 DELETE |
| Reaper 自身崩溃 | 事务内无半状态 | 下次周期继续 | 内存标志作为完成证据 |

## 10. 测试与验收

### 10.1 领域与端口测试

- Task/Attempt/Step 的每条合法和非法转换；
- terminal 不可由普通执行路径复活；
- Authority 字段必须成组、token 不泄露、时间带时区；
- Recovery 默认 fail closed；
- Recovery Case/Observation/Decision 的合法转换、单 generation 唯一关闭 Decision、可重复的
  非关闭 `keep_quarantined` 评估、证据摘要和 `retry_authorized` 前置条件；
- recovery generation 只在新 Case 建立时递增；`retry_authorized`、Case re-claim 和关闭 Decision
  保持 generation 不变，分别由 attempt/fencing 表达新执行/新恢复 owner；
- `recovery_required` 不能直接进入 running；新执行必须由 accepted claim 创建更大 Attempt/fencing；
- Codec 未知版本/字段失败关闭，历史版本显式读取；
- Event metadata 大小、允许键和敏感字段门禁。

### 10.2 SQLite Repository 并发与事务测试

使用临时 SQLite 和至少两个独立连接/Store 实例：

1. 同业务键并发受理只有既有规则允许的一个结果；
2. 同 Task 并发 claim 只有一个有效 Authority；
3. fencing 严格单调，lease token 不复用；
4. 旧 Authority 的 heartbeat/progress/step/terminal 全部被条件拒绝；
5. 状态与 latest 投影任一侧写失败时整事务回滚；
6. 事件追加失败时状态不提交；
7. sequence 唯一、有序；
8. terminal、Step completion、Reaper 重复调用幂等；
9. 同一 Recovery Case 并发 claim/Decision 只有一个 fencing owner，旧 generation/row version/
   source Attempt/Recovery fencing 的写入均为零；
10. `retry_authorized` 与 Task accepted/保持不变的 recovery generation/retry checkpoint/Event 原子
    提交；任一侧失败全部回滚，旧 Step Attempt 历史不被覆盖；
11. `integrity_check`、`foreign_key_check` 和索引查询计划符合预期；
12. SQLite busy/locked 明确分类，不被伪装成业务成功；
13. Admission/Begin Step/Complete Step/Terminal/Recovery 的跨 Store 原子组共用同一连接，任一 Store
    失败整组 rollback；Store 自行 commit、嵌套 UoW 和跨线程 Connection 被测试拒绝；
14. 新旧数据库路径相同、旧库仍有活动/unknown、metadata/fingerprint 不匹配、未知/更高 Schema
    generation 均在构造业务 Store 前失败；应用不自动删除/移动 `.sqlite3/-wal/-shm`；
15. FakeClock 前进/回拨、UTC 格式、owner 启动世代和租约不等式通过；测试不依赖真实 sleep。

### 10.3 本地 Executor 验收

- 50 个 Fake 重任务同时持久化在途，在三业务 worker slots 和共享重型容量下全部最终收敛；这证明
  持久在途与本地调度隔离，不等于 50 个重任务并行执行；
- 500 个 accepted 积压时，内存 TaskId/Future/线程数量不随积压等长增长；在途对象不超过 Worker 数和固定维护项；
- 重复 100 次 wake/dispatch 不产生重复有效 Attempt；
- Worker 异常只影响当前 Task，其他 Task 继续排空；
- stop 后不再 claim；等待许可和 heartbeat 可有界停止；
- 失权 Worker 无法提交 Progress、Step、Artifact 引用或终态；
- 启动扫描与周期扫描能恢复丢失唤醒。
- Report/Weaponry/Analysis 三个实例只扫描自身 task type，复用同一 Executor 内核；共享容量在混合
  积压下按业务无饥饿，跨业务完成顺序不被误写成严格全局 FIFO；
- 某一业务 Runner/readiness 失败不导致其他业务领取错误类型任务；Control DB/Clock 异常则所有新
  claim fail closed。

## 11. 日志、指标与安全要求

### 11.1 日志字段

内部结构化日志统一包含必要的：

- `task_type`、`task_id`、`business_key`（必要时摘要）、`attempt_no`、`fencing_token`；
- `step_key`、`event_type`、`recovery_classification`、`reason_code`；
- `recovery_case_id`、`recovery_generation`、`decision_id`、`policy_version` 和脱敏 actor marker；
- `trace_id`、`instance_start_id`、`executor_name`、`worker_slot`、脱敏 `owner_id`、队列年龄、lease 剩余时间；
- `clock_anomaly_reason`、配置 fingerprint、Schema generation/DB instance 的脱敏短标识。

禁止记录 lease token、密钥、完整 URL 查询参数、文件正文、Prompt/模型正文、Callback 正文和未脱敏异常对象。高频 heartbeat 成功只记指标或 DEBUG 采样；失权、过期、unknown、quarantine 使用 WARNING/ERROR 并带稳定原因码。

### 11.2 指标

- 各 task type 的 accepted/running/recovery_required/terminal 数；
- 最老 accepted、最老 running、lease 即将到期和过期数；
- claim 成功/竞争失败、heartbeat 成功/失权/异常；
- stale Authority 条件写拒绝数；
- Step outcome_unknown、恢复分类和 Reaper 处理数；
- open/观察中/长期未决 Recovery Case 数、最老 Case 年龄、Observation/Decision 数、
  keep_quarantined/retry_authorized/finalize/stale 分类数和恢复 CAS 拒绝数；
- 各业务 Executor active/idle Worker、按 limiter 分类的等待、跨业务公平/饥饿水位、stop 超时；
- 时钟异常、readiness fail-closed、Schema/旧库预检拒绝、UoW rollback 和非法嵌套次数；
- Event 追加失败和 SQLite busy 次数；
- Callback/cleanup 指标继续独立统计，不混入 Task 成功率。

## 12. 发布、回滚与数据处理

### 12.1 每波切换规则

- 同一业务类型同一时刻只有一条 Task 写路径和一个 Executor；
- 每个目录迁移先单独提交/审查“等价移动 + 导入/组合根调整”，门禁通过后才修改 SQL/状态机；
- 新旧 Adapter 可以在代码中短期并存，但不得双写、双 claim 或双扫同一 control schema version；
- 每切一个业务先执行其全部合同、故障和 Container 测试，再切下一个；
- 兼容入口只能由旧路径单向调用新 Store，禁止新 Store 回调旧 Service；当前波次调用清零后立即
  物理删除，不把通用转发 Facade 留到阶段末；
- Callback 历史迁移只切换 Writer 所有权，不删除既有 JSON；真实数据保留期和清理另行决策。

### 12.2 SQLite 数据

- 开工前在任何旧 Store 构造之前只读预检旧库；有活动 Task、Callback/资源 unknown 或需保留事实时
  停止并确认，不自动清库、不删除侧车文件；
- 阶段 2 使用 `DOCSENSE_TASK_CONTROL_DB_PATH` 指向全新空 v2 库；不原地修改旧 CHECK、不迁移历史
  行、不为旧 running 行伪造 Attempt/Checkpoint；
- 新库严格校验 application ID、user version、metadata generation/fingerprint/DB instance；旧、未知、
  更高或损坏 Schema fail closed，不以 `CREATE TABLE IF NOT EXISTS` 修复；
- 旧库及其 `-wal/-shm` 原样保留。显式归档必须在所有进程停止后处理整个文件集；
- 回滚到不认识 control schema v2 的代码前，必须证明没有 v2 accepted/running/recovery、Callback/
  cleanup unknown、未对账副作用或需保留新 Task；否则停止执行并前向修复。

### 12.3 代码回滚

- 在尚未产生任何需保留 v2 Task/副作用且 D2-18 回滚预检通过时，可回切上一业务 Adapter；不得让
  旧/新代码并行消费同一个 Task Control DB；
- 一旦 v2 Task 已产生外部副作用或 recovery_required 现场，不允许简单回切旧代码继续消费；先停止 Executor、保留数据库和任务目录，再使用新版本诊断/收敛；
- 回滚不改变接口文档和公开合同。

## 13. 修订后的阶段 3～11 路线

### 阶段 3A：共享 MySQL 与 Alembic

- 分成 3A-1 MySQL/Alembic/UoW 基线、3A-2 模块 Repository 逐一切换、3A-3 唯一写路径与
  备份恢复演练；以阶段 2 Repository 契约实现同步 SQLAlchemy Adapter；
- 将 lease/fencing/Reaper 语义移植到数据库权威时间、事务隔离和跨连接条件写；
- 空库切换，不长期双写；
- MySQL 通过只证明共享持久化，不证明消息可靠。

### 阶段 3B：共享 Artifact/MinIO

- 分成 3B-1 Artifact Catalog/状态机、3B-2 staged upload/MinIO Adapter、3B-3 对账/孤儿对象/
  保守 GC；冻结输入、scratch、中间结果和最终产物的对象 key、size、系统 SHA-256、所有权和
  retention class；
- MinIO Adapter 与 MySQL Artifact Catalog 分别验收；MinIO ETag 不作为通用 SHA-256；
- 队列 Worker 切换前，所有跨进程需要的内容必须摆脱单机路径；
- 未确认保留期前不启用 TTL/自动 GC。

### 阶段 4：事务 Outbox

- 初次执行、Reaper 允许的新 Attempt 恢复、Callback 后台恢复使用三类独立命令；对应业务事实
  与 Outbox 同 MySQL UoW，并冻结 command ID、dispatch generation 和 schema version；
- Relay 负责 publisher confirm、重复发布和积压；
- 阶段 2 的本地 Event 账本不是 Outbox，不能直接充当消息表。

### 阶段 5：RabbitMQ/Celery

- Celery Task 只传内部 ID并调用同一 `RunXxxTask`；
- 复用阶段 2 已冻结的 Attempt/Authority/Checkpoint/Reaper，不再设计第二套状态机；
- Broker 重投递/Celery retry 不等于新 Task Attempt；Consumer 先以 MySQL Authority/CAS 决策，
  unknown 隔离而不热重试；
- 验证 MySQL 多实例 claim、heartbeat、fencing、late ACK、重复消息、Worker kill 和 DLQ；
- 只有共享 Artifact 已完成的业务才能进入外部 Worker。

### 阶段 6：逐业务可靠切换

建议顺序修改为：Callback 后台兜底（保留 check-task 同步入口） -> Cleanup/补偿 -> Report -> Analysis -> Weaponry。Report 作为阶段 2 试点最先验证队列；Analysis 随后验证批次顺序；Weaponry 最后验证复杂外部资源和供应商 attestation。Chat 留在阶段 9。跨实例切换使用 MySQL 中版本化的 `local_only -> shadow_publish -> queue_active -> local_drain -> local_removed` 策略；每个 Task 冻结派发代次，回滚不改变已入队任务的执行所有者。

### 阶段 7～11

- 阶段 7：MySQL 当前事实 + Redis 可丢通知，迁移既有“订阅—快照”屏障和有界合并语义，完成跨实例 Progress；
- 阶段 8：迁移 FastAPI Web Adapter，不重写同步业务/Repository；阶段 9 前 Chat 路由保持单一受理所有者，Web lifespan 不启动本地业务 Dispatcher；
- 阶段 9：ChatRun 受理与 Outbox 同事务，Task 引用 ChatRun；SSE 断线持久化停止意图，内部账本不提供公开回放，成功/中断按条件写竞争；
- 阶段 10：分别冻结短请求、长连接、在途任务和重型 Worker 并发口径，完成稳态、故障和容量验收；
- 阶段 11：使用 expand/contract 与 N/N-1 Schema/消息兼容完成生产灰度、备份恢复、监控 Runbook 和旧路径物理下线；系统不承诺 exactly-once。

## 14. 阶段 2 完成定义

1. Analysis、Report、Weaponry 都通过同一 Task Execution 内核运行；

6. Report/Analysis 执行 Profile 已按 Canonical JSON 版本化；Weaponry v2 不被通用改造误升版；三类
   业务 Step/Recovery Registry 均已冻结并覆盖实际运行步骤；

   业务生产路径不再依赖它，新 Store 不反向调用旧 Service；剩余阶段 3 能力已拆成明确过渡 Store，
