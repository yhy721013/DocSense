## 2. 已确认的业务决策

### 2.1 请求与活动范围

1. 前端本轮传入非空 `fileNames` 时：
   - 本轮实际执行范围精确等于该非空列表；
   - 该列表成为会话新的“当前活动范围”；
   - 更新对首次或后续任意轮次都生效。
2. 前端本轮传入空 `fileNames=[]` 时：
   - 若会话从未出现过非空 `fileNames`，使用首次创建会话时冻结的全量已解析文件快照；
   - 若会话已经出现过非空 `fileNames`，继续使用最后一次非空列表对应的活动范围；
   - 空数组本身不创建新的活动范围版本。
3. 后续知识库新增文件不自动进入活动范围。
4. 非空请求更新活动范围时采用“整体替换”，不是与上一次范围取并集。

### 2.2 Workspace 绑定

1. AnythingLLM Workspace 仍采用累计绑定模型。
2. 更新活动范围不会主动从 Workspace 解绑旧文档。
3. Workspace 中存在某文档，不代表该文档属于当前活动范围。
4. 模型调用必须显式传入当前活动范围的文档引用，不能再用 Workspace 全部绑定文档替代
   活动范围。

### 2.3 数量限制

1. 首次空数组自动展开后的活动范围继续受 `DOCSENSE_CHAT_MAX_FILES` 限制。
2. 任意非空请求继续受同一限制。
3. 超限继续返回现有 HTTP 400 和既有单字段错误体：

```json
{"error": "fileNames超过文件对话数量上限"}
```

4. 禁止绕过上限、静默截断或分批形成部分活动范围。

### 2.4 历史与开发数据

1. `/llm/chat/history` 中用户消息的 `files` 只反映该轮前端显式传入的 `fileNames`：
   - 前端传空数组时，历史返回 `files: []`；
   - 前端传非空数组时，历史只返回该非空数组对应的文件原名。
2. 后端自动选择或继承的活动范围不得展开到历史 `files`。
3. 当前开发环境数据无保留要求。
4. 发布切换时允许停服并清理 Chat SQLite 数据库，不对旧消息猜测回填 requested/effective
   语义。

## 3. 精确状态机

### 3.1 术语

| 术语 | 定义 |
| --- | --- |
| Requested Scope | 前端本轮显式传入的规范化 `fileNames`；允许为空 |
| Active Scope | 会话当前持久化的默认活动文件范围 |
| Effective Scope | 本轮实际交给绑定与模型查询链的不可变范围 |
| Workspace Bindings | AnythingLLM Workspace 和本地 binding heads 中累计存在的文件集合 |
| Scope Revision | 一次不可变的活动范围版本及其有序成员 |
| Scope Head | 当前会话指向的最新活动范围版本 |

### 3.2 状态转换

| 会话状态 | 本轮请求 | 本轮 Effective Scope | 是否创建新 Scope Revision | 新 Scope Head |
| --- | --- | --- | --- | --- |
| 会话不存在 | `[]` | 受理时刻全量已解析文件快照 | 是，`automatic_initial` | 新建的首次全量版本 |
| 会话不存在 | 非空 | 本轮 Requested Scope | 是，`explicit` | 本轮显式版本 |
| 当前为 `automatic_initial` | `[]` | 当前 Scope Head | 否 | 不变 |
| 当前为 `automatic_initial` | 非空 | 本轮 Requested Scope | 是，`explicit` | 本轮显式版本 |
| 当前为 `explicit` | `[]` | 当前 Scope Head | 否 | 不变 |
| 当前为 `explicit` | 非空 | 本轮 Requested Scope | 是，`explicit` | 新的本轮显式版本 |

### 3.3 冻结细则

1. 首次空数组且知识库为空时，仍创建成员数为 0 的 `automatic_initial` Scope Revision。
   后续即使知识库新增文件，空数组仍保持空范围，直到前端首次传入非空列表。
2. 只有成功进入受理事务并最终提交的请求才允许更新 Scope Head。
3. 参数错误、超限、目录冲突、活动 run 冲突或事务故障都不得修改 Scope Head。
4. 非空请求一旦原子受理，其显式范围立即成为新的 Scope Head；即使后续模型调用失败，
   下一轮空数组也继续使用这份最后受理的非空范围。
5. Scope Revision 保存受理时刻的 `file_name`、`original_name`、`document_ref` 和
   `external_location`，后续知识库记录替换不得改写旧 Revision。
6. 同一业务文件的新版本只有在后续非空请求再次明确选中时，才会进入新的 Scope Revision。
7. 已有 session 若缺失 Scope Head、Head 指向错误 chat 或成员解码失败，必须失败关闭并记录
   结构化错误；禁止通过重新扫描知识库或读取 Workspace bindings 静默重建范围。

## 4. 目标数据模型

### 4.1 运行输入

将当前单一文件概念拆分为：

```text
ChatRunInput
├── requested_files       # 前端本轮显式传入；历史展示来源
├── effective_scope_id    # 本轮实际范围的不可变 Revision
└── effective_files       # Repository 通过 Revision 成员读取的执行快照
```

其中：

- `requested_files` 只需要业务文件名和原始文件名；
- `effective_files` 必须包含供应商无关的完整文档身份；
- 执行器、任务队列和恢复流程只根据 `run_id` 重新加载两类事实；
- 禁止从当前知识库、当前 Workspace 或请求内存重新推断已受理范围。

### 4.2 SQLite Schema v4

通过 `ensure_chat_schema()` 增加编号为 4 的正式迁移：

```sql
CREATE TABLE chat_scope_revisions (
    scope_revision_id TEXT PRIMARY KEY,
    chat_id TEXT NOT NULL,
    source_mode TEXT NOT NULL
        CHECK (source_mode IN ('automatic_initial', 'explicit')),
    source_run_id TEXT NOT NULL,
    created_at TEXT NOT NULL,
    FOREIGN KEY(chat_id) REFERENCES chat_sessions(chat_id) ON DELETE CASCADE
);

CREATE TABLE chat_scope_members (
    scope_revision_id TEXT NOT NULL,
    ordinal INTEGER NOT NULL CHECK (ordinal >= 0),
    file_name TEXT NOT NULL,
    original_name TEXT NOT NULL,
    document_ref TEXT NOT NULL,
    external_location TEXT NOT NULL,
    PRIMARY KEY(scope_revision_id, ordinal),
    UNIQUE(scope_revision_id, file_name),
    FOREIGN KEY(scope_revision_id)
        REFERENCES chat_scope_revisions(scope_revision_id) ON DELETE CASCADE
);

CREATE TABLE chat_scope_heads (
    chat_id TEXT PRIMARY KEY,
    scope_revision_id TEXT NOT NULL UNIQUE,
    updated_at TEXT NOT NULL,
    FOREIGN KEY(chat_id) REFERENCES chat_sessions(chat_id) ON DELETE CASCADE,
    FOREIGN KEY(scope_revision_id)
        REFERENCES chat_scope_revisions(scope_revision_id)
);
```

同时为 `chat_run_inputs` 增加：

```sql
requested_files_json TEXT NOT NULL DEFAULT '[]'
effective_scope_revision_id TEXT
selection_mode TEXT
```

约束要求：

1. `effective_scope_revision_id` 必须属于该 run 对应的同一 `chat_id`；
2. 插入 Revision 时通过事务内查询或触发器确认 `source_run_id` 属于同一 `chat_id`，但不把
   Revision 生命周期外键级联到 run；未来清理历史 run 时不得删除仍被 Head 或其他 run input
   引用的活动范围；
3. `selection_mode` 只允许：
   - `automatic_initial`
   - `explicit`
   - `active_scope_reuse`
4. Scope Revision 和成员创建后不可更新；
5. 只有 `chat_scope_heads` 可以在受理事务内切换；
6. Scope 成员保持请求或全量目录冻结顺序；
7. 不把全量成员 JSON 重复复制到每一轮 run input，避免大量文件导致 SQLite 重复膨胀；
8. `ChatRunInputRepository` 通过 `effective_scope_revision_id` 加载不可变成员，向 Application
   返回完整 effective 文件 DTO。

### 4.3 数据清理策略

本次不设计业务数据回填。实施切换时：

1. 先停止应用及所有可能访问 Chat SQLite 的本地进程；
2. 解析并打印实际 `DOCSENSE_CHAT_DB` 或默认 Chat 数据库绝对路径；
3. 只清理明确确认的 Chat SQLite 主文件及同目录同基名 WAL/SHM；
4. 禁止删除整个 `DOCSENSE_RUNTIME_DIR`；
5. 启动后由 Schema v1～v4 在空库上顺序初始化；
6. 记录清理时间、目标路径和不可恢复说明。

开发数据无保留要求不代表可以跳过路径校验或在服务运行中直接删除数据库。

## 5. 原子受理设计

### 5.1 事务前候选准备

`SynchronousChatRunExecutor` 只执行只读候选准备：

1. 非空请求：
   - 只解析前端显式文件；
   - 不读取全量目录；
   - 形成 Requested Candidate 和 Explicit Scope Candidate。
2. 空请求：
   - 不在事务外根据 `sessions.get()` 推断最终范围；
   - 可以准备首次全量候选，但最终是否采用必须由事务内 session/head 事实决定；
   - 为避免已有会话每轮扫描全库，可先做只读 Scope Head 探测；
   - 即使探测与并发请求交错，事务内仍必须重新读取并决定。

### 5.2 `BEGIN IMMEDIATE` 内的唯一决策

受理事务必须按以下顺序执行：

1. 插入或读取 `chat_sessions`，取得 `session_created`；
2. 处理过期 run 并检查活动 run；
3. 读取当前 Scope Head；
4. 根据“session 是否首次创建、请求是否非空、Head 是否存在”选择状态机分支；
5. 对首次空请求验证全量候选；
6. 对非空请求验证显式候选；
7. 校验 Effective Scope 数量上限；
8. 插入 `chat_runs`；
9. 必要时插入不可变 Scope Revision 和成员；
10. 必要时切换 Scope Head；
11. 写入 `chat_run_inputs`：
    - requested 文件；
    - effective Scope Revision；
    - selection mode；
12. 写入 pending user 消息：
    - 正文保持既有行为；
    - `chat_message_files` 只写 requested 文件；
13. 提交事务。

任何异常必须整体回滚 session、run、scope revision、scope head、run input 和 pending message。
事务中禁止调用 AnythingLLM、模型、文件系统或其他外部服务。

### 5.3 并发要求

1. 同一 `chatId` 的 50 个首次空请求仍只能有一个 accepted；
2. 同一 `chatId` 的并发非空请求只能有一个更新 Scope Head；
3. 失败的竞争者不得创建孤立 Scope Revision；
4. 不同 `chatId` 的 requested/effective/head 不得串写；
5. 当前证据仍限定为 SQLite 单实例；
6. 未来迁移 PostgreSQL/可靠队列时，Scope Repository 与受理 Unit of Work 必须保持同一
   原子边界，不能由 Worker 在执行期补写 Head。

## 6. 执行与 Workspace 设计

### 6.1 执行输入

执行器只按 `run_id` 加载：

- Requested Scope：用于消息附件与审计；
- Effective Scope Revision：用于绑定、模型查询和恢复。

不得在执行期重新读取知识库全量目录，也不得直接把 Workspace current bindings 当作
Effective Scope。

### 6.2 文档绑定

1. 对 Effective Scope 中尚未绑定或版本不一致的成员执行既有：
   - resource lease；
   - `attach_documents()`；
   - binding revision；
   - current head 更新。
2. 已绑定但不属于当前 Effective Scope 的旧文档：
   - 继续保留在 Workspace；
   - 不进入本轮 `stream_message(document_refs=...)`；
   - 不删除、不解绑、不关闭其资源租约。
3. `stream_message()` 的 `document_refs` 顺序必须与 Scope Revision 成员顺序一致。
4. Scope 中的远端引用缺失、绑定失败或供应商结果未知时，沿用现有失败关闭和资源恢复规则，
   不扩大到 Workspace 全部文档作为兜底。

### 6.3 示例

```text
Workspace Bindings = [A, B, C]
Current Active Scope = [A]
前端本轮 fileNames = []

Requested Scope = []
Effective Scope = [A]
模型查询文档 = [A]
历史 files = []
```

下一轮前端传入 `[B, C]`：

```text
Workspace Bindings = [A, B, C]
Requested Scope = [B, C]
New Active Scope = [B, C]
Effective Scope = [B, C]
模型查询文档 = [B, C]
历史 files = [B, C]
```

再下一轮传空数组：

```text
Workspace Bindings = [A, B, C]
Requested Scope = []
Active Scope 保持 [B, C]
Effective Scope = [B, C]
模型查询文档 = [B, C]
历史 files = []
```

## 7. 历史、标题、调试与日志

### 7.1 `/llm/chat/history`

响应结构保持：

```json
{
  "role": "user",
  "content": "问题",
  "timestamp": 1777364120677,
  "files": []
}
```

语义调整为：

- `files` 只表示该轮前端显式请求文件；
- 空数组请求始终返回 `files: []`；
- 自动初始范围和继承活动范围都不展开到历史；
- assistant 消息仍不包含 `files`；
- 历史继续以本地 committed message 为权威。

### 7.2 标题生成

标题生成当前只消费历史中的 `role` 和 `content`，继续保持该边界。不得因为新增 Requested/
Effective DTO 把大量文件列表带入标题 Prompt。

### 7.3 调试页

调试数据必须分区展示：

1. Active Scope：当前 Scope Head 的文件数量；
2. Workspace Bindings：累计绑定文件数量；
3. 历史消息：只展示每轮 Requested Scope。

页面不得把 Workspace Bindings 标记为“当前模型范围”，也不得通过历史空数组推断会话没有
活动文件。

### 7.4 日志

日志只记录：

- `requested_file_count`
- `effective_file_count`
- `active_scope_member_count`
- `workspace_binding_count`
- `selection_mode`
- `scope_revision_id`
- `chat_id`
- `run_id`

禁止记录文件名、原始文件名、文档正文、远端文档 URL 或完整供应商响应。

Blueprint 或 AnythingLLM Gateway。

## 9. 分阶段实施计划

### 阶段 0：契约与状态机黄金基线

1. 冻结当前 HTTP/SSE/Header/chatId 字节级合同；
2. 为 Requested/Active/Effective/Bindings 建立真值表资产；
3. 新增目标 history 黄金样例，但在生产代码切换前不得修改当前接口文档为已实现；
4. 冻结空知识库、上限、失败首轮和并发决策；
5. 记录当前 Chat、安全全仓基线。

关闭门禁：目标测试可以先作为独立纯规则资产存在，但不得提交会让当前生产路由永久失败的
占位测试。

### 阶段 1：Domain DTO 与 Scope 纯规则

1. 新增不可变 Scope Revision/Member/Selection DTO；
2. 明确状态转换纯函数；
3. 升级内部候选 Schema，未知字段和版本失败关闭；
4. 测试顺序、重复文件、空范围、深冻结和序列化往返。

关闭门禁：Domain 不导入 Flask、SQLite、DatabaseService 或 AnythingLLM。

### 阶段 2：SQLite Schema v4 与 Repository

1. 增加 Scope 三表和 run input 字段；
2. 实现 Scope Revision 追加、成员批量插入、Head 读取/切换；
3. 实现同 chat、run、scope 的完整性门禁；
4. 实现 run input requested/effective Codec；
5. 增加旧开发库清理前置检查和空库重建验证。

关闭门禁：Repository 测试覆盖事务回滚、不可变性、坏 JSON、错 chat 外键和 50 个不同会话
隔离。

### 阶段 3：受理事务原子状态机

1. 在 Coordinator 的 `BEGIN IMMEDIATE` 内接入 Scope Head；
2. 首次空请求创建 `automatic_initial` Revision；
3. 非空请求创建并切换 `explicit` Revision；
4. 后续空请求复用 Head；
5. requested message files 与 effective scope 同事务写入；
6. 上限、活动 run、候选错误和故障注入全量回滚。

关闭门禁：同一 `chatId` 50 并发只允许一个 accepted 和一个确定 Head；失败请求不留下 Scope
或消息半成品。

### 阶段 4：执行、绑定与恢复

1. Worker 只按 `run_id` 加载 Requested/Effective；
2. effective 成员复用既有 lease、attach、binding 和 stream 链；
3. Workspace 累计绑定不再决定空数组范围；
4. 受理后目录变化不改变执行范围；
5. 执行失败后下一轮空数组仍使用最后 accepted 的显式范围；
6. 断连、abort、错误和重复执行保持既有收敛语义。

关闭门禁：重启式离线恢复仅凭 SQLite 事实得到相同 requested/history 和 effective/model 范围。

### 阶段 5：历史、日志与调试一致性

1. history 用户 `files` 只投影 requested；
2. 大量 effective 文件不扩大 history；
3. 调试页分开 Active Scope 与 Workspace Bindings；
4. 日志分开 requested/effective/active/binding 计数；
5. 继续禁止内部 scope/run/lease ID 进入公开 JSON 或 SSE。

关闭门禁：接口结构黄金样例不变，文件取值语义符合本文。

### 阶段 6：开发库停服清理与全面离线回归

1. 输出将要清理的 Chat DB、WAL、SHM 精确绝对路径；
2. 确认服务停止后执行开发数据清理；
3. 空库初始化 Schema v1～v4；
4. 运行 Chat 全量发现、契约/网关/容器/架构矩阵；

6. 报告发现、排除、执行、失败、错误、跳过、expected failure 和 unexpected success。

关闭门禁：不得启动 `run.py`，不得连接真实后台服务，不得把 SQLite 单实例离线结果描述为
生产就绪。

### 阶段 7：接口文档同步与关闭验收

## 10. 验收矩阵

| 场景 | 预期 Active/Effective | 预期 history `files` |
| --- | --- | --- |
| 新会话空数组，知识库为空 | 空 Revision；后续不自动吸收 | `[]` |
| 新会话空数组，知识库有 A/B | Active=A/B，Effective=A/B | `[]` |
| 上述会话再次空数组 | Active 不变，Effective=A/B | `[]` |
| 知识库后来新增 C，再传空数组 | 仍为 A/B | `[]` |
| 新会话首轮显式 A | Active=A，Effective=A | `[A]` |
| Active=A 时显式 B/C | Active 替换为 B/C，Effective=B/C | `[B,C]` |
| Active=B/C 时再次空数组 | Effective=B/C | `[]` |
| Workspace=A/B/C，Active=B | Effective=B，禁止查询 A/C | `[]` |
| 显式范围超限 | HTTP 400，Head 不变 | 不产生新历史 |
| 首次全量超限 | HTTP 400，无 session/scope/run/message | 不产生历史 |
| 非空请求执行失败 | Head 已更新为该 accepted 范围 | 按既有失败消息提交规则展示 requested |
| 同 chat 50 并发 | 1 accepted，其余 409；唯一 Head | 只出现 accepted 运行历史 |
| 不同 chat 50 并发 | Scope、Workspace、历史完全隔离 | 各自 requested |
| SSE 黄金合同 | 事件、字段、Header、状态码零变化 | 不适用 |

还必须验证：

- 同名、重复远端身份、坏目录记录整体拒绝；
- Scope 成员顺序稳定；
- requested/effective JSON 严格解码；
- 全量 Scope 只存一份，后续空轮次只引用 Revision；
- Scope Head 与 binding head 不互相替代；
- 1,000 个 effective 文件时 history 用户 `files` 仍为 `[]`；
- 调试页不把累计 Workspace 文档误报为当前 Active Scope；
- 日志不包含文件身份或正文。

## 11. 接口文档影响

本需求必须修改 `docs/接口文档/文件对话.md`，但只在生产代码完成切换时同步修改。

需要修改的语义：

1. `POST /llm/chat`：
   - 首次空数组建立首次全量活动快照；
   - 后续空数组沿用当前活动范围；
   - 非空数组整体替换当前活动范围。
2. `GET /llm/chat/history`：
   - 用户消息 `files` 只表示该轮前端显式传入文件；
   - 后端自动或继承的 Effective Scope 不在历史中展开。

保持不变：

- 请求体字段和类型；
- `fileNames` 必填数组要求；
- `files` 字段名称、数组结构和元素 `{ "name": String }`；
- HTTP 状态码；
- SSE 事件名、数据结构和 Header；
- `chatId` 类型。

## 12. 发布与回滚

### 12.1 发布

1. 完成代码、定向测试和安全回归；
2. 停止应用；
3. 校验 Chat DB 绝对路径；
4. 清理无保留要求的开发 Chat DB/WAL/SHM；
5. 启动时初始化 Schema v1～v4；
6. 执行离线/本地最小冒烟：
   - 首次空；
   - 显式非空；
   - 再次空；
   - history；
7. 确认 Active Scope 与 Workspace Bindings 分离；
8. 再开放调用。

### 12.2 回滚

由于新旧代码对“空数组”的默认范围含义不同，推荐回滚方式为：

1. 停止应用；
2. 回滚代码与接口文档；
3. 校验 Chat DB 精确路径；
4. 清理开发 Chat DB/WAL/SHM；
5. 使用旧代码重建空库；
6. 不尝试把新 Scope Head 自动折叠回 Workspace current bindings。

禁止：

- 运行中直接删除数据库；
- 只回滚 Blueprint 或 History Presenter；
- 删除 AnythingLLM Workspace 文档来模拟活动范围收缩；
- 保留新数据库却宣称已恢复旧空数组语义。

## 13. 风险与边界

1. 本计划解决历史响应膨胀和活动范围歧义，不消除首次全量绑定本身的容量成本。
2. `DOCSENSE_CHAT_MAX_FILES` 仍是必要保护；未来大量文件场景若需要突破上限，应另立分页、
   检索路由或分层召回方案，不能在本计划中隐式放开。
3. Workspace 继续累计旧绑定，长期资源治理和主动解绑需要独立的安全设计。
4. 当前 SQLite 仍是单实例事实存储，不是可靠任务队列或多实例协调器。
5. 未验证真实 AnythingLLM、模型、Embedding、长连接容量和供应商限流。
6. 当前计划不增加租户、用户、分类或权限范围；全量目录仍是当前实例级范围。
7. Scope Revision 引用的远端文档若被外部人工删除，执行应失败关闭并保留恢复证据，不得扩大
   到 Workspace 其他文件。

## 14. 完成定义

只有同时满足以下条件，才能关闭本计划：

- Requested、Active、Effective 和 Workspace Bindings 四类概念在代码中具有独立模型；
- 首次空数组只冻结一次全量目录；
- 新增知识库文件不被后续空数组自动吸收；
- 任意非空请求整体替换 Active Scope；
- 后续空数组保持最后一次非空范围；
- Workspace 累计绑定不会扩大本轮模型范围；
- history 只展示前端本轮显式文件；
- 全量 Scope 不在每轮 run input 中重复存储；
- Scope Head、run input 和 pending message 在同一事务内提交；
- 超限、冲突和故障不留下部分 Scope 事实；
- 50 同会话/不同会话离线并发矩阵通过；
- HTTP、JSON、SSE、Header、状态码和 `chatId` 契约零结构变化；
- 开发 Chat 数据按停服、精确路径方式清理并重建；
- README、接口文档、重构记录和更新记录与最终代码一致；
- 验证报告明确限定为 SQLite 单实例离线证据，不宣称多实例或生产就绪。
