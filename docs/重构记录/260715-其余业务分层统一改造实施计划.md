## 3. 目录结构方案比较与正式决策

### 3.1 可选方案

| 方案 | 优点 | 主要风险 | 结论 |
| --- | --- | --- | --- |
| 传统技术分层：controllers/services/repositories/models | 简单直观、迁移成本较低 | 一个业务散落多个全局目录，容易继续形成巨型 Service | 不采用为目标结构 |
| 全局 Clean Architecture：domain/application/ports/infrastructure | 依赖方向清晰、测试方便 | 业务增多后全局 domain/application 容易成为新的大杂烩 | 只吸收依赖规则，不采用纯全局目录 |
| 纯按业务聚合：chat/report/weaponry | 业务高内聚、修改范围清晰 | 各模块可能重复连接池、队列、日志和外部 Client | 作为基础，但必须增加统一分层与平台边界 |
| 垂直切片：submit/query/execute | 单个用例交付快、适合命令查询 | 领域规则和基础设施若无约束容易重复 | 作为模块 application 内部组织方式 |
| 插件化 | 动态扩展能力强 | 生命周期、兼容协议和插件治理成本过高 | 当前不采用 |
| 微服务 | 部署和故障隔离强 | 分布式事务、网络契约、部署和运维成本过早放大 | 当前不采用；保留未来按模块拆分可能 |
| **模块化单体 + 业务聚合 + 模块内分层 + Ports/Adapters** | 同时获得高内聚、低耦合、渐进迁移和未来可拆分性 | 需要架构测试持续约束模块边界 | **正式采用** |

### 3.2 正式架构决策

本项目采用以下组合：

1. 以**模块化单体（Modular Monolith）**作为部署和代码组织基础。
2. 以 analysis、report、weaponry、reassign、chat、tasks 作为业务模块。
3. 每个模块内部使用 domain、application、ports、adapters 分层。
4. application 内按 command/query/execute 等垂直用例切片。
5. AnythingLLM、数据库、消息队列、Redis、存储、翻译和文档处理通过 Port/Adapter 隔离。
6. Web、Celery Worker 和调度器都是入站适配器，不拥有业务规则。
7. 当前保持单体部署；只有模块边界、数据所有权和运维能力成熟后才评估拆微服务。

### 3.3 为什么不能直接复制 chat 目录

chat 已经证明业务聚合方式可行，但目标结构不能机械复制其当前 SQLite、locking 和 persistence 细节：

- chat 的领域状态机和应用用例可以作为参考。
- chat 当前单实例 SQLite、内联 Dispatcher 和轮询通知只是过渡适配器，不是所有模块的基础设施模板。
- 每个模块拥有自己的 Repository 协议和数据映射；数据库 Engine、Session、迁移、消息连接等平台能力统一管理。
- 不要求立即把现有 `services/chat/` 物理移动到新目录；先建立依赖边界，再在测试保护下渐进整理。

### 4.2 放置规则

- 只服务一个业务的规则、DTO、Port 和 Repository 映射放入该业务模块。
- 数据库连接池、消息连接、日志初始化和对象存储客户端等技术底座放入 infrastructure。
- AnythingLLM 原始 HTTP、路径、字段和错误只允许出现在 `integrations/anythingllm`。
- `shared` 只能保存经过至少两个业务验证且语义完全一致的稳定能力，禁止成为新的 `utils`。
- 模块之间不能直接导入对方 adapters 或数据表实现；通过应用接口、只读查询契约或领域事件协作。
- Web Presenter 属于入站协议边界；业务模块不得返回 Flask Response、FastAPI Response 或 SSE 文本。
- Celery task 只反序列化内部 ID、调用应用服务并分类异常，不复制业务流程。

## 5. 模块与共享端口边界

### 5.1 tasks 模块

tasks 是跨业务共享的稳定领域，而不是 Celery 包装层。建议包含：

- `TaskCommandService`：创建任务、保存不可变输入、请求取消、推进受控状态。
- `TaskReadService`：按现有业务键读取兼容任务投影，不产生副作用。
- `RequestCallbackRecoveryService`：组合 Task Read 与可靠恢复命令登记，保留 `/llm/check-task` 的查询校验及显式补偿触发语义；不在 Web 请求内执行外部回调。
- `TaskRepository`、`TaskInputRepository`、`TaskEventRepository`。
- `TaskDispatcher`：只接受内部任务 ID 和任务类型。
- `TaskStatusPresenter`：按 file/report/weaponry 的既有公开值分别映射。
- Interaction Audit 与 Callback Delivery 采用独立 Repository/Service，不继续堆入一个 God Service。

### 5.2 进度能力

进度拆分为三个方向：

- `ProgressPublisher`：业务执行器发布内部进度事件。
- `ProgressQuery`：查询数据库中的最新快照。
- `ProgressSubscriber`：WebSocket/SSE 获得跨实例唤醒。

当前 `LLMProgressHub` 仅实现单实例版本。后续 MySQL 保存事实，Redis 只发通知。

### 5.3 回调能力

- 业务模块只构造领域结果，Callback Presenter 负责保持现有回调载荷。
- `CallbackDeliveryPort` 负责发送，不允许业务模块直接调用 `requests.post`。
- 回调 task ID、attempt、触发来源、投递阶段、内部 outcome、结果摘要和下次重试时间持久化。
- 接收方幂等和结果查询能力无法确认：仅明确未送达错误允许有限自动重试；发送后超时/中断标记 `delivery_outcome_unknown`，非 2xx 进入人工/死信处理，二者均不由 Worker 自动重试。
- `/llm/check-task` 继续作为显式补发入口，但请求只在 MySQL 事务内创建或复用活动 recovery request，并同步写 Outbox；每次真正外发由 callback Worker 独立审计，且不得触发后台递归重试。
- 不建设阶段 1 兼容同步恢复适配器、有界同步并行或批次总超时方案。阶段 1 只冻结 Command Port/DTO/Presenter 和 Fake 契约；阶段 4～6 完成 Outbox + RabbitMQ + callback Worker 后直接切换生产路由。

### 5.4 文件、预处理和产物

- `SourceFilePort`：从现有 URL 或路径取得任务输入。
- `DocumentPreprocessorPort`：OCR、MinerU、MHTML 和 Word 文本提取。
- `ArtifactStorePort`：报告和中间产物的提交、查询与清理。
- 所有方法使用任务作用域路径/对象引用，不返回打开的句柄或进程私有临时对象。

### 5.5 Translation 与 RAG

- `TranslationPort` 接受显式请求和任务级 Progress Reporter，不使用全局可变回调。
- 已完成的 `DocumentRagPort`、`KnowledgeIndexPort`、`ChatConversationPort` 和 AnythingLLM Gateway 继续复用。
- report 和 weaponry 如需要不同语义，应定义业务拥有的 Port，不把供应商响应 DTO 直接传入领域层。

### 5.6 禁止的伪抽象

不得新增以下类型的通用入口：

- `GenericLLMService.run(payload)`。
- 接受任意 `dict` 并按 `businessType` 分支的应用服务。
- 同时承担任务、审计、回调、进度和队列的超级 Repository。
- 所有模块共同依赖的 `shared/utils.py`。
- 为“少写几个类”而让领域层直接导入 AnythingLLM、SQLAlchemy、Celery 或 Web 框架。

| Debug | Debug Query Services | 无生产任务 | HTML/JSON Debug Presenter |

异步业务统一使用以下边界：

```text
Flask/FastAPI Adapter
  → SubmitXxxTask
      → 持久化任务和输入快照
      → TaskDispatcher.dispatch(task_id)
  → 按现有接口立即返回

Local Executor/Celery Adapter
  → RunXxxTask(task_id)
      → 重新读取输入和执行权
      → 调用领域规则与外部 Port
      → 持久化进度、结果、产物和回调事实
```

`/llm/reassign` 不采用上述异步返回方式。它必须在当前请求内完成同步 Saga，并按既有接口返回。

## 8. 单个用例的标准迁移步骤

每个路由或后台用例必须按以下顺序执行：

1. **冻结契约**：记录请求、响应、状态码、回调和日志中的必要业务语义。
2. **建立 DTO**：把 Web `dict` 转换为框架无关、不可变或受校验的 Command/Query DTO。
3. **提取纯规则**：先移动无 I/O 的领域规则并补单元测试。
4. **定义 Port**：由业务模块表达需要什么能力，不由基础设施反向决定接口。
5. **实现兼容 Adapter**：包装当前 SQLite、Hub、Client 或工具，避免同时重写所有技术实现。
6. **建立应用用例**：显式声明事务边界、任务状态和补偿策略。
7. **切换组合根**：只切换当前路由，不影响其他业务；check-task 在阶段 1 只完成命令
   边界，不执行本步骤，必须等待阶段 6 可靠链路后一次性切换。
8. **差异验证**：新旧实现使用相同输入和 Fake，比较公开输出和副作用。
9. **稳定后清理**：确认无调用方后删除旧编排；不保留长期双写。

若任一步发现除 2026-07-15 已确认定向调整之外还必须修改公开参数或接口文档，立即停止，不得通过兼容猜测继续实现。
