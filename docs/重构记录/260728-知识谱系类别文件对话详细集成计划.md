## 1. 集成目标

1. 把 architecture 范围选择安全接入现有单一 Chat 垂直链，不复制接口、Executor、History、
   Workspace 或资源清理实现。
2. 将 Schema v5、会话永久绑定、候选解析、原子受理、执行恢复和历史投影作为一个完整发布单元
   合入 `main`，禁止半套代码进入可部署主线。
3. 保持 fileNames 模式、SSE、标题、中断、删除、AnythingLLM Gateway 和其他 LLM 业务零回归。
4. 给未来开发提供可重复的 Git、迁移、测试、前后端联调、发布、回滚和停止条件。
5. 集成证据严格区分：离线单实例通过、真实供应商联调、生产多实例/容量验证。

## 2. 集成原则

### 2.1 一个功能分支、一个最终切换点

- 从最新 `main` 创建单一功能分支；不在多个长期分支分别修改 Blueprint、Schema 和 History。
- 可以按里程碑提交，但只有全部门禁通过后才能合入 `main`。
- 不使用 cherry-pick 拼装部分 Schema/Route/Presenter 提交。
- 若功能分支已经共享，使用 `main` 合并进入功能分支处理漂移；不强制改写共享历史。

### 2.2 后端先于前端启用

发布顺序必须是：

1. 后端代码、Schema 和接口测试完整上线；
2. 后端最小冒烟确认 architecture 请求和历史可用；
3. 前端再开始发送 `architectureId`；
4. 前端不能先上线，否则旧后端会按 fileNames 模式拒绝请求。

### 2.3 不使用在线双跑

architecture 模式没有旧实现，禁止同时保留“路由临时展开 fileNames”和“新 Scope Binding”两条
生产链。唯一权威链必须是 Parser → Candidate → Coordinator → Scope/Run Input → Executor → History。

## 8. I3：Schema v5 与 Coordinator 集成

### 8.1 数据库迁移演练

至少准备三类临时 SQLite：

1. 空库：依次执行 v1→v5；
2. v4 file 会话库：包含 automatic/explicit/reuse、历史、run input、Scope/Head；
3. 故障库：错 Head、坏成员、缺 run input、非法 JSON，用于确认迁移或运行时失败关闭。

对 v4 fixture 迁移前后记录：

- 各表行数；
- 每个 chat 的 Revision/Member/Head；
- run input requested/effective；
- committed message 和 files；
- `PRAGMA foreign_key_check`；
- migration version 集合。

迁移后既有 Session 全部必须绑定 `files`，history 和模型范围等价。

### 8.2 Coordinator 集成

按以下顺序审查 SQL：Binding → mode/ID → active run → Head/Revision → run → input → message。

故障注入应覆盖每个 INSERT/UPDATE 前后；任意抛错后重新打开数据库，确认没有：

- 只有 Session 没有 Binding；
- 只有 Binding 没有 Head；
- 孤立 Revision/Member；
- run input 与 Binding ID 不一致；
- architecture message 同时携带 files；
- 失败竞争者留下 pending message。

## 12. I7：发布与前后端集成演练

### 12.1 数据策略二选一

**开发环境默认：停服清理 Chat 数据**

3. 经确认后只清理精确文件，不删除整个 runtime 目录；

**需要保留数据：执行 v4→v5 迁移**

4. 任一不一致立即停止，不启动服务；
5. 保留可恢复的完整备份，禁止只备份主文件而遗漏未 checkpoint 的 WAL。

### 12.2 最小冒烟

不执行真实模型时可用 Fake/测试应用验证：

1. 新 architecture chat 首轮冻结 A/B；
2. 类别新增 C 后第二轮仍为 A/B；
3. history user 返回 ID、无 files；
4. 不同 ID 和 file 模式冲突返回 409；
5. 旧 fileNames chat 完整成功；

真实联调环境在获得授权后再验证 AnythingLLM 文档引用、SSE 长连接和前端展示；不得在自动离线

### 12.3 前端上线顺序

1. 后端健康、Schema 和冒烟通过；
2. 前端 architecture 页面开始创建独立 chatId；
3. 每轮只传同一 architectureId，不传 fileNames；
4. 历史按 user `architectureId` 展示类别上下文；
5. 监控 400/404/409、SSE error 和范围计数异常；
6. 出现模式冲突激增时先停止前端新入口，不在线改库解绑会话。

## 14. 回滚计划

### 14.1 Merge 前

- 直接修复或丢弃未共享的功能分支提交；
- 不改动 `main`；
- 不使用破坏性命令覆盖当前工作区文档。

### 14.2 已合入但前端未启用

- 回滚完整功能 Merge commit，而不是只回滚 Blueprint；
- 停服处理 Schema；
- 如果保留 v5 DB，旧代码兼容性未经证明，优先恢复备份或按开发策略清理重建；
- 权威接口文档恢复“待实现”状态。

### 14.3 前端已启用并产生 architecture 会话

1. 先关闭前端 architecture 入口，阻止新请求；
2. 停止后端；
3. 保存故障诊断和 v5 数据备份；
4. 回滚完整后端功能；
5. 恢复发布前 v4 备份，或在明确无保留要求时清理 Chat DB；
6. 旧代码重建后验证 fileNames chat；
7. 不尝试把 architecture 会话自动转换成 fileNames 或展开成员回填历史。

禁止只删除 Session Binding、只改 `scope_mode`、只删除 `architecture_id` 或保留 v5 数据后声称已经
恢复旧合同。

## 15. 停止条件

出现以下任一情况必须停止集成：

1. 需要新增或改变已批准文档之外的公开字段、状态码、SSE 或错误文本；
2. fileNames 黄金合同发生非预期变化；
3. v4→v5 对账或 foreign_key_check 不通过；
4. architecture 后续轮次重新读取当前类别或扩大模型范围；
5. 同一 chat 可以形成两个 mode/ID Binding；
6. history user 同时出现 `files` 和 `architectureId`；
7. 并发失败者留下 Session/Scope/Run/Message 半成品；
8. 主线存在无法判定归属的重叠修改；
9. 测试要求运行真实 `run.py` 或未经授权的外部服务；
10. 试图以 SQLite 单实例结果替代多实例/可靠队列证明。

## 16. 集成完成定义与达成效果

只有满足以下全部条件，集成才算完成：

- `main` 包含完整 architecture Chat 垂直链和 Schema v5；
- 新旧前端组合矩阵有明确上线顺序；
- architecture 首轮冻结直接文件，后续每轮同 ID 复用旧快照；
- chatId 模式/ID 永久绑定且并发唯一；
- history user 字段按模式互斥；
