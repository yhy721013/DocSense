# 知识谱系类别文件对话接口文档

> **合同状态（2026-07-28）：已批准，已在当前开发分支实现并通过离线关闭验收。**  本文只描述前端使用
> `architectureId` 发起知识谱系类别文件对话的公开合同，不描述 `fileNames` 模式。
> 路由、持久化、历史展示和合同测试已经完成；真实供应商、发布环境和多实例能力仍须按集成计划
> 独立验收，不得把当前结果表述为生产就绪。

## 1. 合同范围与核心规则

本模式复用既有 `/llm/chat` 和 `/llm/chat/history` 接口，不创建第二套聊天接口。复用范围包括
SSE 事件、模型执行、并发控制、会话历史和错误响应的单字段 `error` 结构。

知识谱系类别文件对话遵循以下完整规则：

1. `architectureId` 与 `fileNames` 是互斥的范围选择参数。本模式每次请求都必须传入
   `architectureId`，并且不得同时传入 `fileNames`。
2. 服务端使用事务内的会话创建事实判断是否为新对话，调用方不能声明或推测
   `isNewChat`。
3. 某个 `chatId` 首次成功受理 architecture 模式请求时，永久绑定规范化后的
   `architectureId` 和 architecture 范围模式。
4. 首次受理时，服务端只选择本地知识目录中类别 ID 精确等于该 ID 的直接文件，不包含
   任何子类别文件，并把实际文件身份和稳定顺序冻结为不可变 Active Scope。
5. 已有对话的后续请求仍必须携带相同 `architectureId`，但服务端只复用首次冻结的
   Active Scope，不重新查询类别文件。因此后来新增、删除、重新解析或重新分类的文件不会
   动态改变该会话的实际对话文件。
6. 再次传入与绑定值等价的规范化 ID，例如首次传 `1`、后续传 `"0001"`，视为同一个
   `architectureId`；不会刷新快照。
7. 同一 `chatId` 不允许切换到其他 `architectureId`，也不允许切换为其他文件范围模式。
   反向地，已经属于其他范围模式的 `chatId` 也不能切换到 architecture 模式。
8. 首次受理时类别不存在或没有任何可用于对话的直接文件，整个请求以 HTTP 404 拒绝，
   不创建会话、范围、运行、消息、文件绑定或远端资源。
9. 首次冻结的有效文件数量继续受 `DOCSENSE_CHAT_MAX_FILES` 限制。超限时整体拒绝，
   不截取前若干文件，并复用既有错误文本 `fileNames超过文件对话数量上限`。
10. 快照冻结的是文件成员及其文档引用，而不是复制一份永久不变的文件内容。远端绑定时，
    每个冻结的 `external_location` 必须在供应商回执中唯一出现一次；缺失或重复都通过既有
    SSE `error` 事件失败收敛，且不得写入部分本地 Binding。唯一匹配的回执可以提供供应商
    规范化后的 `document_ref`，后续模型调用和本地 Binding 使用该规范引用，但不得把文件
    替换为另一个远端位置或类别中的其他成员。

## 2. 发送对话消息接口

**接口路径：** `/llm/chat`

**请求方法：** `POST`

**响应方式：** SSE（Server-Sent Events）流式输出

**成功响应 Content-Type：** `text/event-stream`

### 2.1 请求参数

| 参数 | 类型 | 说明 | 必填 |
|------|------|------|------|
| businessType | String | 业务类型标识，固定值为 `"chat"` | 是 |
| params | Object | 对话参数对象 | 是 |

### 2.2 params 结构

| 字段 | 类型 | 说明 | 必填 | 示例值 |
|------|------|------|------|--------|
| chatId | Integer | 调用方生成的正整数对话唯一标识；同一 ID 首次受理后永久绑定范围模式和 `architectureId` | 是 | `10001` |
| architectureId | Integer / 十进制整数字符串 | JavaScript 安全正整数范围内的知识谱系类别 ID；每轮都必须传入与会话绑定值相同的 ID | 是 | `1768464916588441` / `"1768464916588441"` |
| message | String | 用户发送的问题；服务端去除首尾空白后不能为空 | 是 | `"请总结该类别下全部文件的核心观点"` |

本模式的 `params` **不得出现 `fileNames`**。`architectureId` 与 `fileNames` 同时出现时，
即使 `fileNames=[]`，也必须拒绝整个请求，不能按任一字段优先处理。

### 2.3 chatId 规则

- `chatId` 必须是 JSON number 类型的正整数。
- 字符串、布尔值、浮点数、`0` 和负数均返回 HTTP 400：
  `{"error":"chatId必须为正整数"}`。
- SSE 和历史请求中的 `chatId` 继续遵循既有正整数合同；内部 run、Scope Revision、租约和
  围栏令牌不会对前端公开。

### 2.4 architectureId 规则

`architectureId` 在 Chat 接口中采用适合 JSON number 与浏览器精确表示的独立上界；
知识谱系解析、分类节点变更等其他业务的 64 位 ID 合同不受此处影响：

- 接受 `1..9007199254740991` 范围内的 JSON 正整数；
- 接受只包含 ASCII 数字的十进制字符串；
- 字符串允许前导零，并按整数值规范化；
- 拒绝布尔值、零、负数、浮点数、指数形式、正负号字符串、空白字符串、包含非 ASCII 数字
  的字符串、对象、数组和超出上限的值；
- 无论请求传入整数还是字符串，历史响应中的 `architectureId` 始终为 JSON number。

### 2.5 首次请求示例

```json
{
  "businessType": "chat",
  "params": {
    "chatId": 10001,
    "architectureId": "1768464916588441",
    "message": "请总结该类别下全部文件的核心观点"
  }
}
```

首次成功受理时，服务端必须：

1. 规范化 `architectureId`；
2. 确认 `chatId` 尚未绑定其他范围模式；
3. 按规范化 ID 读取该类别的直接文件；
4. 对全部候选执行完整的文档身份、远端引用和数量上限校验；
5. 以稳定顺序冻结不可变 Active Scope；
6. 原子保存会话模式、绑定 ID、Scope Head、运行输入和待处理用户消息；
7. 仅在上述受理事实成功提交后调用模型。

### 2.6 已有对话的后续请求示例

```json
{
  "businessType": "chat",
  "params": {
    "chatId": 10001,
    "architectureId": 1768464916588441,
    "message": "请继续比较这些文件中的技术指标"
  }
}
```

后续请求仍必须携带同一 `architectureId`。服务端只校验该 ID 与会话绑定值一致，并读取已经
持久化的 Active Scope；不得因为类别当前文件集合发生变化而重新生成、追加、删减或替换快照。

如果多个请求并发争用同一新 `chatId`，服务端先为其中一个请求保留短期准入权，不提前创建
session、Scope、run 或消息；保留期间的其他同 `chatId` 请求稳定返回 409。持有者若在正式
受理前失败或全局流容量已满，准入权会释放或到期回收，后续请求可以重试。只有完成正式受理
事务的请求才能建立会话绑定，不能形成两个范围版本或两个并发模型调用。同一 `chatId` 冲突
在全局流容量 429 之前判定，因此两个条件同时成立时优先返回 409。

### 2.7 SSE 事件

architecture 模式不增加或修改任何 SSE 事件和字段：

| event | data 内容 | 说明 |
|-------|-----------|------|
| `chatInfo` | `{"chatId":10001,"isNewChat":true/false}` | 首个事件；`isNewChat` 由服务端受理事实决定 |
| `textChunk` | `{"content":"..."}` | 大模型回答文本片段，可能多次推送 |
| `done` | `{"chatId":10001}` | 流式输出完成 |
| `aborted` | `{"chatId":10001}` | 调用 `/llm/chat/abort` 后，本轮以不完整回答语义结束 |
| `error` | `{"error":"..."}` | SSE 建立后的执行错误；推送后关闭连接 |

示例：

```text
event: chatInfo
data: {"chatId":10001,"isNewChat":true}

event: textChunk
data: {"content":"根据该类别冻结的文件范围，"}

event: textChunk
data: {"content":"核心观点包括……"}

event: done
data: {"chatId":10001}
```

`done`、`aborted`、`error` 均为终结事件。`aborted` 只表示中断已经由执行流观察并完成状态
收敛，本轮回答不完整，不等同于业务成功；其请求方式和延迟边界继续以
[文件对话新增接口](文件对话新增接口.md#2-中断流式对话接口) 为准。

### 2.8 建立 SSE 前的错误响应

所有错误继续使用单字段 JSON 结构：`{"error":"..."}`。

| 场景 | HTTP 状态码 | error 文本 |
|------|-------------|------------|
| `businessType` 不是 `"chat"` | 400 | `businessType必须为chat` |
| `params` 缺失或不是对象 | 400 | `params不能为空` |
| `chatId` 不是 JSON 正整数 | 400 | `chatId必须为正整数` |
| `architectureId` 已出现但为空或为 `null` | 400 | `architectureId不能为空` |
| `architectureId` 类型、格式或范围非法 | 400 | `architectureId必须为1到9007199254740991之间的正整数` |
| 同时出现 `architectureId` 和 `fileNames` | 400 | `architectureId与fileNames不能同时传入` |
| `message` 缺失、不是字符串或去除首尾空白后为空 | 400 | `message不能为空` |
| `message` 超过既有长度上限 | 400 | `message超过文件对话长度上限` |
| 首次受理时类别不存在或没有可用于对话的直接文件 | 404 | `architectureId对应类别不存在或没有可用于对话的文件` |
| 类别文件包含损坏、歧义或重复远端身份，无法形成唯一快照 | 400 | `architectureId对应类别文件无法形成有效对话范围` |
| 首次冻结的有效文件超过数量上限 | 400 | `fileNames超过文件对话数量上限` |
| `chatId` 已绑定其他范围模式 | 409 | `当前对话的范围模式不匹配` |
| `chatId` 已绑定其他 `architectureId` | 409 | `当前对话已绑定其他architectureId` |
| 同一 `chatId` 已有活跃流 | 409 | `当前对话已有进行中的流式响应` |
| 进程内流容量已满 | 429 | `文件对话并发流已达上限，请稍后重试` |

首次类别范围校验失败时，不得创建 session、Scope Revision、Scope Head、run、消息、文件绑定或
远端资源。已有会话的 ID 或模式校验失败时，不得修改既有 Active Scope。

### 2.9 SSE 建立后的错误与客户端断开

SSE 建立后的模型、文档引用或供应商错误通过 `error` 事件返回：

```text
event: error
data: {"error":"大模型服务响应异常"}
```

客户端主动关闭 SSE 连接时，继续遵循既有文件对话规则：

- 若 run 尚未被领取，不调用模型，待提交用户消息不进入历史；
- 若 run 已开始执行，服务端终止本轮并标记失败，保留已提交的用户消息，不保存不完整的
  assistant 片段；
- 接口不提供断线续传、SSE 回放或调用方断开后的后台继续生成。

## 3. 获取对话历史接口

**接口路径：** `/llm/chat/history`

**请求方法：** `GET`

**功能说明：** 根据 `chatId` 返回 architecture 模式对话的历史消息，按时间正序排列。

### 3.1 请求参数

| 参数 | 类型 | 传递方式 | 说明 | 必填 |
|------|------|----------|------|------|
| chatId | Integer | Query 参数 | 正整数对话唯一标识；URL 中使用无符号、无前导零的十进制文本 | 是 |

请求示例：

```http
GET /llm/chat/history?chatId=10001
```

### 3.2 成功响应

响应体为 JSON 数组。architecture 模式下：

- `role="user"` 的消息必须包含规范化后的 JSON number 类型 `architectureId`，不得包含
  `files`；
- `role="assistant"` 的消息既不包含 `architectureId`，也不包含 `files`；
- 同一会话全部 user 消息的 `architectureId` 必须相同；
- 历史只返回会话绑定的 ID，不展开冻结的实际文件成员；
- 响应不得公开 Scope Revision、文档引用、外部位置、run ID、租约或围栏令牌。

### 3.3 数组元素结构

| 字段 | 类型 | 说明 |
|------|------|------|
| role | String | 消息角色：`"user"` 或 `"assistant"` |
| content | String | 消息内容 |
| timestamp | Number \| null | 消息时间戳，单位为毫秒 |
| architectureId | Integer | 仅当 `role="user"` 时存在；为该会话绑定的 JavaScript 安全整数类别 ID |

### 3.4 响应示例

#### 成功响应（HTTP 200）

```json
[
  {
    "role": "user",
    "content": "请总结该类别下全部文件的核心观点",
    "timestamp": 1777364120677,
    "architectureId": 1768464916588441
  },
  {
    "role": "assistant",
    "content": "根据该类别首次受理时冻结的文件范围，核心观点包括……",
    "timestamp": 1777364120678
  },
  {
    "role": "user",
    "content": "请继续比较这些文件中的技术指标",
    "timestamp": 1777364180123,
    "architectureId": 1768464916588441
  }
]
```

#### chatId 无效（HTTP 400）

```json
{
  "error": "chatId必须为正整数"
}
```

#### 对话不存在（HTTP 200）

```json
[]
```

历史接口只负责读取已经提交的消息，不重新查询 `architectureId` 当前类别文件，也不根据当前
类别状态刷新或修复 Active Scope。

## 4. 前端调用要求

1. 为 architecture 模式生成独立 `chatId`，不得复用其他文件范围模式的会话 ID。
2. 首次和后续每轮请求都传入同一个 `architectureId`；前端不需要保存或回传实际文件列表。
3. 不得在 architecture 模式请求中发送 `fileNames`，包括空数组。
4. 前端不能通过重新发送 `architectureId` 请求刷新类别文件；如未来需要主动刷新，必须使用新的
   `chatId` 开启新对话，或另行确认新的公开合同。
5. 前端展示历史时，以 user 消息中的 `architectureId` 识别类别上下文，不依赖 `files` 字段。
